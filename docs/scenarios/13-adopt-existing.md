# 13. 今あるプロダクト・会社に後から入れる(守りだけを持ち込む)

> 入口は [README.md](README.md)。人は [companies.md](companies.md)。判定の印: ✅ 回る / 🟡 人の手か外の道具で回る / ❌ 穴([gaps.md](gaps.md))。
> キットは「ここから作る」雛形として作ってある。この台本は反対に、**もう動いているプロダクトと会社に、守り(ハーネス・危険度・権限の表の型・数字)だけを持ち込めるか**を通す。外から来た人の目の点検([09-adoption.md](09-adoption.md) の 9-5)で「一部だけ入れる道が無い」と分かった所を、1歩ずつ確かめる。
> 2026-10-27 に、キットの main の `.claude/`(設定とフック)・`.github/`(ラベル・PR テンプレート・ワークフロー)・`scripts/setup/`・`scripts/metrics/`・`docs/authz/`・`infra/terraform/` を読んで判定した(実際に別のリポジトリへ入れてはいない)。「📚 世の中では」は、公開の事故報告・登壇・記事から一般化した学び(出どころは書かない)。

## 登場する会社(この台本だけ)

[companies.md](companies.md) の A 社・B 社はキットから作った会社なので、この台本では「後から入れる」側を2つ足す(架空。この台本の中だけ)。

| 会社 | 中身 |
|---|---|
| **予約の会社**(12人) | 飲食店向けの予約の SaaS。Next.js+Supabase(Postgres・認証・RLS)で2年動いている。デプロイは外のホスティング。CI は lint とテストだけ。Claude Code を使い始めたが、守りは無い。テックリード1人・エンジニア4人 |
| **中堅企業**(300人。その中の新規事業の部署) | 既存のリポジトリと既存の CI(社内の型)。ISMS を取得済みで、変更管理の規程がある。AWS のアカウントは情シスが払い出し、組織の側で CloudTrail・GuardDuty・Security Hub を一括で管理している |

## 📌 いまの結論(2026-10-27)

- **持ち込める部品はある**。フック(`.claude/hooks/`)は Node の標準だけで書かれ、外のパッケージに頼らない。危険度のラベル・PR テンプレート・権限の表の書き方・点検の台帳の考え方は、そのまま読める。`pnpm setup:github` は一覧に無いラベルを消さない。
- **ただ、どれもキットの作りに結びついている**。守るパスはキットのフォルダ(`apps/api/src/auth/**` など)・作業を終える前の確かめは pnpm と turbo と Biome・権限の表の確かめは Hono の OpenAPI・数字の本番のデプロイは GitHub の Environment `prod`。中身を自分のリポジトリに合わせる手引きが無い(G-51)。
- **一番危ないのは GitHub の設定を一括で当てるとき**。`pnpm setup:github --apply` は、今ある必須のチェックを外してキットのチェックの名前に置き換え、ルールセットの例外(Bypass list)も外す。既存の CI の名前と違えば、全部の PR が止まる(試しで差分は出る)。
- **会社の決まりとの重なり**(ISMS の規程・情シスの AWS)は、9-5 の判定のまま(G-52・G-53)。数字は、既存のリポジトリで流すとデプロイが 0 件に見える(G-54)。
- 足した穴は G-75・G-76([gaps.md](gaps.md) の「👥 人・更新・後から入れる」)。G-51〜G-54 は判定だけ。いちばん先は **G-75(既存の設定を置き換える)**。

## 13-1 何を持ち込むかを決める(予約の会社・12人)

- 🧑‍💻 予約の会社のテックリード: 「AI に任せても事故を起こさない」の部分だけ欲しい。アプリ(Hono・TanStack・AWS)は要らない。
- 判定: ❌ **持ち込む部品の一覧と順番が無い**(G-51)。
  - 🟡 部品のカタログ(`docs/kit/catalog.yaml`)は、キットから作った人が「消す」ための一覧で、「この部品だけ持ち出す」ための依存(何を一緒に持ってくるか)は書いていない。
  - 🟡 考え方は自己完結して読める([../concepts/line.md](../concepts/line.md)・[../concepts/people-and-ai.md](../concepts/people-and-ai.md))。持ち込む物を自分で選ぶ材料にはなる。

## 13-2 手元の守り(フック)を入れる(予約の会社・12人)

- 🧑‍💻 予約の会社のテックリード: `.claude/settings.json` と `.claude/hooks/` を写した。
- 判定: ❌ **動くが、そのままでは毎回止まる**(穴 G-76)。
  - ✅ フックは Node の標準だけで書かれている(`guard-bash.mjs`・`guard-edit.mjs`・`record-outbound.mjs` の import は `node:` だけ)。確認を飛ばすモードの禁止(`disableBypassPermissionsMode`)・`aws` や強制 push やマージの禁止(`deny`)は、どのリポジトリでも効く。
  - ❌ 作業を終える前の確かめ(`verify.mjs`)は `pnpm turbo run typecheck test --affected` と `origin/main` を前提にする。npm と ESLint のリポジトリでは毎回失敗し、「2回続けて落ちた。人に渡して止まる」に入る。書いた後の整形(`format.mjs`)は `pnpm exec biome` を前提にする。
  - ❌ 守るパスの一覧(`protected-paths.json`)はキットのフォルダ名のまま。予約の会社の大事な所(`supabase/migrations/**`・RLS のポリシー・`middleware.ts`・認証の処理・`.github/**`)を、自分で選び直す型が無い。`pnpm guards`(`scripts/check-guards.mjs`)も `labeler.yml`・`CODEOWNERS`・ルートの `CLAUDE.md` の場所と書き方を前提にする。
  - ❌ ルートの `CLAUDE.md` の「してはいけない」は、キットの作り(`c.var.tx`・`RootDb`・テナントはセッションから)に合わせた言葉。Supabase なら「サービスロールの鍵をクライアントで使う」「RLS を切った表を作る」のように言い換えが要るが、その型が無い。
- 📚 世の中では: AI の守りを既存のリポジトリに入れるとき、最初につまずくのは「守りが誤って止める」こと。止めすぎると、人は守りを外す。**最初は記録だけ(止めない)で1〜2週回し、誤って止める所を直してから止める**、の順が効く。

## 13-3 GitHub の設定をそろえる(予約の会社・12人)

- 🧑‍💻 予約の会社のテックリード: `.github/setup.yml` と `labels.yml` を写し、`pnpm setup:github` を流した。
- 判定: ❌ **試しで気づけるが、「足すだけ」で当てる道が無い**(穴 G-75)。
  - ✅ 既定は試し(差分だけ)で、書くのは `--apply` のときだけ。AI は試しまで(打つのは人)。一覧に無いラベルは消さない(`scripts/setup/areas-basic.mjs` の「消さない」)。
  - ❌ ルールセットは、扱う規則の中身を `setup.yml` の形に置き換える。今ある必須のチェックのうち一覧に無い物は「外す」、キットのチェックの名前(「結合(Postgres・RLS・2社・権限の表 ②)」など)は「足す」(`scripts/setup/areas-ruleset.mjs` の `checksDiffs`)。予約の会社の CI にその名前のジョブは無いので、当てると全部の PR が「待っている」で止まる。例外(Bypass list)も外す。
  - ❌ 「ラベルと Environments だけ」「ルールセットは触らない」のように、範囲を選んで当てる道が無い。`required_checks` を自分の CI の名前に直せば `pnpm setup:check` はジョブの名前を確かめるが、それもキットのワークフローの置き場を前提にする。

## 13-4 危険度のラベルと PR テンプレートを入れる(予約の会社・12人)

- 🧑‍💻 予約の会社のテックリード: 変えたパスで `risk:high` などを付ける `labeler.yml` と、PR テンプレートを写した。
- 判定: 🟡 **型はそのまま使える。中身は書き直す**(G-51)。
  - ✅ ラベルを付けるのはパスで、AI の自己申告に頼らない(`labeler.yml` の冒頭)。PR テンプレートの欄(危険度・テスト結果・人に判断してほしい所・🚪 外へ出した物)は、どのプロダクトでも使える。
  - 🟡 `labeler.yml` の `risk:high` のパスはキットのフォルダ。13-2 の守るパスと同じ物を3か所(守るパス・ラベル・`CODEOWNERS`)にそろえる手間がある。
  - 🟡 PR の本文の「取り組み」と「作業の種類」が必須のチェック(`pr-work.yml`)。賭け(`docs/product/bets/`)を使わない会社では、「保守」「基盤」などで埋めるか、チェックを外す。外してよいかの案内は無い。

## 13-5 権限の表と RLS の型を持ち帰る(予約の会社・12人)

- 🧑‍💻 予約の会社のテックリード: Supabase の RLS は書いているが、「誰が何をできるか」の一覧が無い。キットの権限の表(`docs/authz/matrix.yaml`)の形が欲しい。
- 判定: 🟡 **表の書き方は持ち帰れる。確かめ方は作り直し**(G-51)。
  - ✅ 表の考え方(誰が・どの API を・叩いたら・どうなるべきか。変更は危険度「高」)は、スタックに関係なく使える。
  - 🟡 表を確かめる2つのテストは、キットの作りに結びつく: ① 全部の API が表にあるか(`authz-coverage.test.ts`)は Hono の OpenAPI から API の一覧を作る。Next.js のルートには OpenAPI が無い。② 表の全行を各ロール・他社・未ログインで叩く(`authz-matrix.int.test.ts`)は、キットの結合テストの土台(Postgres を立てる・2社の種)で動く。
  - 🟡 RLS の型(`tenant_id` と RLS を必ず付ける・2社のテスト)は `.claude/skills/db-migration` と結合テストにある。Supabase の RLS(`auth.uid()` とクレーム)に言い換える手引きは無い。

## 13-6 数字を流す(予約の会社・12人)

- 🧑‍💻 予約の会社のテックリード: 「AI を入れて速くなったか」を代表に見せたい。`scripts/metrics/` を写して `pnpm metrics` を流した。
- 判定: 🟡 **流れるが、一部が 0 に見える**(G-54)。
  - ✅ 読むのは `gh` で GitHub だけ(マージした PR・ラベル・本番のデプロイ・振り返りのファイル)。名前と本文は出さない([../guides/metrics.md](../guides/metrics.md))。
  - 🟡 本番のデプロイは GitHub の Environment `prod` のデプロイを数える(`scripts/metrics/collect.mjs`)。外のホスティングが別の名前で記録していれば 0 件になり、DORA の4つのうちデプロイの頻度と変更の失敗率が出ない。AI が手伝った PR はラベル `ai:assisted`(`ai-label.yml`)で数えるので、入れる前の PR には付いていない。導入前の基準を取る道は G-54。

## 13-7 ISMS を取得済みの会社に入れる(中堅企業)

- 🛡 中堅企業の情報セキュリティの事務局: 「新しい部署が AI で開発する。規程とどう合わせるか」。
- 判定: 🟡 9-5 の判定のまま(G-53)。キットの認証の準備(`docs/compliance/controls.yaml` → 適用宣言書・規程のひな形・毎月の証跡)は「これから取る会社」向けで、既存の範囲に足す対応表が無い。PR の危険度と承認・監査ログ・管理操作の記録は、変更管理の証跡として使える形ではある(どの管理策に当たるかは `controls.yaml` に番号がある)。

## 13-8 情シスが AWS を払い出す会社に入れる(中堅企業)

- 🏢 中堅企業の情シス: 「アカウントはこちらで払い出す。CloudTrail・GuardDuty・Security Hub は組織で一括。勝手に作らないで」。
- 判定: 🟡 9-5 の判定のまま(G-52)。`infra/terraform/envs/prod/main.tf` は `modules/security-baseline` と `modules/audit-trail` を無条件に使い、外すスイッチが無い。守りだけを持ち込むなら AWS の部品は要らないので、この台本の予約の会社(外のホスティング)では当たらない。

## 13-9 既存の CI の横に、キットの検査を並べる(中堅企業)

- 🧑‍💻 中堅企業のエンジニア: 社内の型の CI はそのまま。秘密の検査・コードの検査・依存の検査だけを足したい。
- 判定: 🟡 **検査ごとのジョブは写せる。手引きが無い**(G-51)。
  - ✅ `ci.yml` の秘密情報(gitleaks)・コードの検査(Semgrep)・依存と設定(Trivy)・ワークフローの検査(actionlint・zizmor)は、それぞれ独立したジョブで、Action は SHA で固定してある。
  - 🟡 自社ルールの Semgrep(`.semgrep/`)は、キットの作り(要配慮の表をフォルダの外から読まない など)に合わせた物が多い。どれが一般に使えるかの印は無い。
  - 🟡 写したジョブの名前を必須のチェックにするのは、13-3 の `setup:github` を使わずに手で(か、範囲を選べるようになってから)。

## 📚 世の中では(後から入れる)

- 既存の組織に開発の仕組みを入れるとき、成功するのは「**1つずつ・止めない形から**」。最初は記録と見える化だけ(ラベル・数字・守りの警告)、誤りが減ってから止める(必須のチェック・守るパスの確認)。全部を1日で当てると、止まった PR の数で反発が起き、外される。
- 会社の側にすでにある決まり(変更管理・アカウントの払い出し・監査)とは、置き換えるのではなく**対応表で重ねる**。キットの物が会社の決まりのどの行の証跡になるかを1枚にすると、審査と情シスの両方が通りやすい。

## 演習の仕方

- 捨てるリポジトリ(Next.js の雛形など)に `.claude/` だけを写し、Claude Code で小さな変更を3つ頼む。フックが誤って止めた所・止めなかった所を書き出す(13-2)。
- 同じリポジトリで `pnpm setup:github` を試しだけ流し、「外す」の行を数える(`--apply` は打たない。13-3)。
