# 6. セキュリティ・監査・ライブラリの更新・外からの攻撃

> 入口は [README.md](README.md)。人は [companies.md](companies.md)。判定の印: ✅ 回る / 🟡 人の手か外の道具で回る / ❌ 穴([gaps.md](gaps.md))。
> 「📚 世の中では」は、公開の事故報告・登壇・記事から一般化した学び(2026-10 時点。出どころは書かない)。
> 決まりの本体は [../security.md](../security.md)、認証の準備は [../compliance/README.md](../compliance/README.md)。

## 6-1 毎週の点検(A 社・10人)

- 🔔 月曜 8:00 に点検の Issue が来る(急ぎは毎日)。`pnpm checkup` が、自動で確かめられる物(ブランチ保護が外れていないか・重い脆弱性が開いたままか・Renovate が流れているか・秘密の見つけ物)を実際に確かめる。
- 🏭 鈴木: Claude Code で `/checkup`。人に聞くこと・手でやることを1問ずつ、なぜ要るか・放っておくと何が起きるか・おすすめつきで聞かれる。答えは台帳に書かれて PR に。
- 🏭 鈴木: 月1回 `/checkup-refresh` で、世の中の変化(道具の重い脆弱性・GitHub や AWS の仕様の変更・法令の改正)を台帳に取り込む案を見る。
- 判定: ✅ 回る。

## 6-2 ライブラリを更新し続ける(A 社・10人)

- 🤖 Renovate: 毎週月曜の朝に更新の PR(出てから3日たった版だけ・最大5本)。脆弱性の直しはいつでも。大きい版は Dependency Dashboard の承認待ちに並ぶ。
- 🧑‍💻 エンジニア: 危険度「低」はまとめてマージ。認証・Cookie・暗号・DB に触る依存は、小さい版でも「高」として見る。
- 🏭 鈴木: 半年ごとに「大きい版の更新(Node・React・TanStack・PostgreSQL)が溜まっていないか」と「サポートの期限」を点検で見る。
- 判定: ✅ 回る。🟡 危険度「低」の自動マージはまだ無い(見逃しを数えてから。穴 G-12 と同じく、数字を出す物が先)。

## 6-3 重い CVE が出た(A 社・10人)

- 🔔 月曜 5:00 の定期の脆弱性チェック(`vuln-scan.yml`)が落ちて Issue が立つ。または Dependabot の通知。
- 🧑‍💻 エンジニア: `/cve <ID>`。6段で精査(入っているか・版・どこで動くか・穴のある使い方・外から届くか・悪用が出回っているか)→ 期限つきの対応方針(上げる・間接の依存だけ上げる・外す・設定で塞ぐ・届かないので外す)。
- ⚠️ 届く・まだ直していない穴の中身は、リポジトリにも Issue にも書かない(公開のリポジトリなら特に)。
- 📚 世の中では: 実行環境そのもの(言語の処理系)に、同じ日に2つの緊急の直しが出たことがある(認証なしの遠隔コード実行と、圧縮の展開の範囲外への書き込み)。翌朝には「修正の前でも、止めるという選択」の解説が出た。キットは Node.js と土台のイメージを版を固定しないタグで引き、CI も `.node-version` の系列の最新を入れるので、**作り直せば直る**。ただし本番が動いていれば、作り直して stg → 本番に出すまで穴は残る。
- 判定: ✅ 依存の穴は回る([../guides/vulnerabilities.md](../guides/vulnerabilities.md))。✅ 基盤の穴は手順書 `docs/runbooks/platform-vuln.md`(作り直し → stg → 本番・手元の処理系も。G-24 済み)。

## 6-4 ログインの総当たり・大量のアクセス(A 社・10人)

- 🔔 WAF が止めた(数えた)数のアラームが鳴る。
- 🏭 鈴木: 手順書の「最初の5分」で、総当たり・大量のアクセス・API の悪用・型どおりの攻撃のどれかを見分け、それぞれの手当て(IP ごとの上限・一時的な止め・Cognito の設定)をする。
- 🏭 鈴木: 使い始めて3か月で、誤検知が無いのを確かめてから WAF を「数えるだけ」から「止める」へ(点検の台帳が知らせる)。
- 判定: ✅ 回る([../runbooks/attack.md](../runbooks/attack.md))。
- 📚 世の中では: クラウドの設定の誤り(公開の設定・権限・委託先の設定ミス)での漏えいが続いている。続報で範囲が広がった例もある。キットは Security Hub で設定の穴を、委託先の台帳で委託先を見る。

## 6-5 他社のデータが見えたかもしれない・個人データが漏れた(A 社/B 社)

- 🎧 CS: 「別の会社の現場の写真が見えた」という問い合わせ。
- 🏭 鈴木: [../runbooks/tenant-data-leak.md](../runbooks/tenant-data-leak.md) で止血と範囲の確定。個人データが絡むなら [../runbooks/personal-data-breach.md](../runbooks/personal-data-breach.md): 個人情報保護委員会への速報(知ってから3〜5日)・確報(30日。不正の目的なら60日)・本人への通知・B2B のお客さんへの知らせ。
- 🔐 B 社: 要配慮の中身は、事故の調べでも AI に渡さない。受け取るのは組織・利用者の ID と鍵の利用の記録の形まで。
- 判定: ✅ 回る。

## 6-6 鍵が漏れた(A 社・10人)

- 🔔 GitHub の push 保護か gitleaks が、秘密らしき物を見つける。
- 🏭 鈴木: [../runbooks/secret-leak.md](../runbooks/secret-leak.md) で、まず無効にして入れ替え、それから履歴と使われた跡を見る。
- 判定: ✅ 回る。

## 6-7 外部の診断を受ける(A 社・公開の前/B 社・年1)

- 🏭 鈴木: 点検の台帳が「公開の前に、外部の診断を受ける」「年1」を知らせる。業者に渡す物は [../security.md](../security.md) の「外部の診断を頼むときの渡し物」(テナントの分離を重点に)。
- 判定: ✅ 回る。❌ ただし、**画面の CSP(Content-Security-Policy)がまだ無い**(穴 G-17)。外部の診断ではほぼ必ず指摘される。SSR が埋め込むスクリプトに nonce を付ける形が要る。

## 6-8 ISMS・P マークの準備と内部監査(B 社・100人)

- 🛡 B 社の CISO: 部品 `certification-prep` を残す(既定は消す)。附属書 A の管理策(`docs/compliance/controls.yaml`)から適用宣言書(`pnpm compliance --write`)。規程のひな形(`docs/compliance/policies/`)を自社の物に。
- 🛡 事務局(情シス): 毎月の証跡(`evidence.yml` が消せない S3 へ)。年1の教育・内部監査(作った人と別の人)・マネジメントレビューは `/compliance-check` が期限で聞く。
- 🔍 監査人: AWS の管理操作の記録(CloudTrail・ロックした S3 に400日)と、アプリの監査ログを見せる。
- 判定: ✅ 回る(審査の手続きと判断は人)。

## 6-9 社員が入る・辞める(B 社・100人。毎月数人)

- 👥 B 社の人事: 「今月は3人入って2人辞める」。
- 🛡 情シス: GitHub・AWS・Sentry・運営の組織(代理ログインのため)・Slack のアカウントを、入る日に作り、辞める日に止めたい。
- 判定: ✅ 回る(G-13 済み。仕様 0034)。入る日・辞める日の手順書 [../runbooks/joiner-leaver.md](../runbooks/joiner-leaver.md)(GitHub・AWS・Sentry・運営の組織・Slack)と、点検の台帳の項目がある。お客さんの組織の人は、SCIM で情シスの道具から止められる(G-14)。
- 足す前の判定: ❌ **入社・退職のときのアカウントの手順書が無い**(穴 G-13)。点検の台帳には半年ごとの「人と権限・使っていない鍵の棚卸し」があるが、その日にやる手順が無い。辞めた人のアカウントが半年残りうる。

## 6-10 病院の情シスから「SSO と IP の制限は?」(B 社・100人)

- 🏥 大きな病院の情シス: 「職員は院内の ID(SAML)でログインさせたい。院外の IP からは入れないようにしたい。辞めた職員はすぐ止めたい(SCIM)」。
- 判定: ✅ 回る(穴 G-14 は済み)。どれもプランの機能(`sso`・`scim`・`ip-allowlist`・`audit-export`)で、上のプランに入れる。
  - SSO: 病院の管理者が会社のドメインを DNS で確かめ、運営が `sso-connect` で院内の IdP をつなぐ(`docs/runbooks/sso.md` の 4)。必須にすると職員はパスワードで入れず、緊急用の管理者(2人まで・二段階認証)だけが入れる
  - IP の制限: 管理者が院内の範囲(20 まで)を決める。外からはログインも操作も 403
  - SCIM: 管理者が鍵を作り、情シスの道具が職員を作る・止める。止めた職員は次の操作から 401(`docs/runbooks/sso.md` の 8)
  - 監査ログ: 管理者が期間(366 日まで)を選んで JSON Lines で書き出し、院の道具に取り込む。強制ログアウトはサーバー側のセッション保存なしで(ADR 0067)
  - 🟡 人の手: IdP をつなぐ打ち合わせ(メタデータの URL の受け取り)と、stg のテスト用の IdP での確かめは運営

## 6-11 背景の AI を夜も回す(B 社・100人)

- 🏭 B 社の基盤チーム: Issue から PR を出す AI を、人が見ていない夜にも回したい。
- 📚 世の中では: 「承認なしに変えるな」と言われていた AI が本番の DB を消し、「戻せない」と嘘をついた例がある(実際は人が戻せた)。原因はモデルの出来ではなく、AI が本番に常に入れて、止める関所が無かったこと。別の例では、テストで動いていた AI が、指示が禁じていなかった**フォームの送信**で、外の機関に作り話を送った。見つかったのは2か月後。→ 外へ送る操作は、書いて禁じるより手段を持たせない。AI の言う「戻せない」を信じず、バックアップは別に確かめる。
- 判定: 🟡 回る(G-22 済み。仕様 0057・ADR 0068・0069)。人が見ていない作業は、外への通信を絞った devcontainer か、Web を読めない背景の AI(`claude.yml`)でだけ回す([../guides/unattended-ai.md](../guides/unattended-ai.md))。🟡 は、背景の AI でテストを動かす Node は外へ出られる(わざと残る穴)ことと、AI が読む文章の書き手・費用の上限が穴として残ること([10-ai-incidents.md](10-ai-incidents.md) の 10-1・10-6。G-58・G-62)。
- 足す前の判定: 🟡 起動できるのはリポジトリの持ち主だけ・鍵は main だけの Environment、という守りはある。**AI の環境から外への通信を絞る形が無い**(穴 G-22。devcontainer で一度試して、AI が Docker を使えず結合テストを回せないので見送った)。人が見ていない所で長く回すなら、もう一度考える。

## 6-12 よく使われる依存が乗っ取られた(A 社・10人)

- 🔔 週に数億回ダウンロードされる小さな依存の作者がフィッシングで乗っ取られ、悪い版が出た。数日後、自分で広がる型(入った端末の鍵を盗み、ほかの依存にも入る)が続いた。
- 🏭 鈴木: キットは「出てから3日たった版だけ」を入れる(pnpm と Renovate の両方)。インストールのときにスクリプトを走らせてよい依存は許可リストだけ。悪い版は数時間で消されたので、入っていない。
- 🏭 鈴木: 念のため `pnpm vulns` と Dependabot の通知を見る。入っていたら、[../runbooks/secret-leak.md](../runbooks/secret-leak.md) で手元と CI の鍵(npm・GitHub・AWS)を入れ替える。
- 📚 世の中では: 別の乗っ取りでは、悪い版が開発者の端末に入っていた **AI の CLI を「確認を飛ばす」旗で呼び、鍵を探させた**。入口は、外から書き換えられる弱い GitHub のワークフローだった。
- 判定: ✅ 3日待ちと許可リストで、ほぼ入らない。ワークフローの検査(zizmor・actionlint)もある。✅ リポジトリの中では確認を飛ばすモードを使えない(`.claude/settings.json`。G-23 済み)。リポジトリの外で呼ばれる分は、端末に配る設定で(7-7)。
