# 想定の会社と人(ペルソナ)

> 入口は [README.md](README.md)。場面の台本は、この2社の人が動く形で書く。会社も人も架空。
> 規模は **2人 → 10人(A 社)** と **100人(B 社)**。1,000人はこのキットの守備範囲の外(下の「1,000人では」)。

## A 社: 現場の写真と日報(工務店・リフォーム会社向け)

| 項目 | 中身 |
|---|---|
| 作る物 | 現場の写真・日報・工程を、職人と事務所で共有する B2B の SaaS(月額・1社あたり 数千〜数万円) |
| お客さん | 社員 5〜50人の工務店・リフォーム会社。IT の担当者はいない。現場ではスマホで使う |
| 扱うデータ | 施主の名前と住所(個人情報)・現場の写真(人や表札が写りうる)。要配慮個人情報は扱わない |
| 段階 | 2人で始めて PMF を探す(①)→ 10人で伸ばす(②) |

### 立ち上げ(2人)

| 人 | 役割 | このキットでの持ち場 |
|---|---|---|
| 👩‍💼 代表(佐藤) | 経営・営業・PdM を兼ねる | `/kickoff`・`/bet`・話を聞く・規約と契約・本番の承認 |
| 🧑‍💻 テックリード(鈴木) | ラインの持ち主・ただ1人のエンジニア | `pnpm setup:github`・`/tailor`・AWS・レビュー・手順書 |

### 10人になったとき

| 人 | 役割 | このキットでの持ち場 |
|---|---|---|
| 👩‍💼 代表(佐藤) | 経営・大口の営業 | 賭けの優先順位・値決め・本番の障害の宣言 |
| 📝 PdM 兼 CS の長(田中) | 仕様の在庫・ロードマップ・問い合わせの振り分け | `/new-feature`・`/bet`・仕様の承認 |
| 🏭 テックリード 兼 EM(鈴木) | ライン・危険度・週の振り返り・採用 | 危険度「高」のレビュー・`/checkup`・当番の表 |
| 🧑‍💻 エンジニア ×3(高橋・伊藤・渡辺) | 領域の持ち主(写真・日報・組織と課金) | 危険度「中」のレビュー・AI が詰まった所 |
| 🎨 デザイナー(山本) | 画面とデザインシステム | `packages/ui`・VRT の差分を見る |
| 🤝 営業(中村) | 新しいお客さんを取る・申込書 | 申し込み → 開通の受け渡し・ロードマップを見て答える |
| 🎧 CS(小林) | 導入の手伝い・問い合わせ・解約 | 代理ログイン・`/report-bug`・解約の書き出し |
| 🗂 管理(加藤) | 経理・総務・法務の窓口・情シスを兼ねる | 費用のページ・`/ledger`・委託先の台帳・入退社のアカウント |
| (外)顧問の弁護士・税理士 | 規約・契約・会計の当てはめ | キットは文面を持たない。問いの一覧を渡す |

## B 社: Web 問診と予約(診療所・病院向け)

| 項目 | 中身 |
|---|---|
| 作る物 | 患者が来院前にスマホで問診に答え、予約する。医師が画面で見る(B2B の SaaS) |
| お客さん | 診療所 数千院・大きな病院 数十院(病院は情シスがいて、監査とセキュリティの質問票が来る) |
| 扱うデータ | **要配慮個人情報**(病歴・症状)。患者の名前・連絡先。医療の業界のガイドラインがかかる |
| 段階 | PMF の後・規模拡大の手前(③の入口)。ISMS を取得済み、P マークも求められる |

| 部門 | 人数 | このキットでの持ち場 |
|---|---|---|
| 経営(CEO・CTO・CFO・COO・CISO) | 5 | 賭けの束と予算・リスクの受け入れ・マネジメントレビュー |
| プロダクト(PdM) | 6 | 領域ごとの賭け・仕様・ロードマップ |
| エンジニア(EM 5・4つの領域のチーム・基盤・SRE とセキュリティ) | 35 | ライン・CODEOWNERS・当番・脆弱性・領域の DB |
| デザイン | 4 | デザインシステム・VRT |
| QA | 3 | E2E のシナリオ・人が見る所の一覧 |
| 営業(内勤・外回り・大きな病院の担当) | 18 | 申込書・セキュリティの質問票・ロードマップの約束 |
| CS(導入・サポート・継続の担当) | 15 | 代理ログイン・問い合わせ・障害の連絡・解約 |
| マーケ | 5 | 公開のサイト(キットの外)・事前登録 |
| コーポレート(経理3・法務2・人事3・情シス1) | 9 | 費用・`/ledger`・契約・入退社・ISMS の事務局 |
| **合計** | **100** | |

- 比率の確かめ: エンジニア系(エンジニア・デザイン・QA)42%・営業と CS 33%。世の中の目安(年の売上10億円・30〜60人で、エンジニア3〜4割・営業と CS 3〜4割)とおおむね合う。

## 1,000人では

- 開発のラインそのもの(危険度・権限の表・テナント分離・検査)は、1,000人でも形は同じ。ただし、**キットの部品の外**が主役になる: 社員の ID の基盤(SSO・SCIM)、会社ごとの専用の環境、自前のファクトリー(第3層)、データ基盤、法務とセキュリティの専門の部門。
- このキットは「100人までを1つのリポジトリと1つの AWS の形で回す」までを狙う。1,000人に近づいたら、[../concepts/stages.md](../concepts/stages.md) の 3(M → L → XL)の段階表を入口に、領域ごとにリポジトリと AWS アカウントを分ける設計をやり直す。
