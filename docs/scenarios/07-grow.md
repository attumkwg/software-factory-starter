# 7. 規模を上げる(2人 → 10人 → 100人)

> 入口は [README.md](README.md)。人は [companies.md](companies.md)。判定の印: ✅ 回る / 🟡 人の手か外の道具で回る / ❌ 穴([gaps.md](gaps.md))。
> 「📚 世の中では」は、公開の事故報告・登壇・記事から一般化した学び(2026-10 時点。出どころは書かない)。
> 考え方の本体は [../concepts/stages.md](../concepts/stages.md)・[../concepts/people-and-ai.md](../concepts/people-and-ai.md)。

## 7-1 2人 → 10人: 人が増えたらすぐ変える所(A 社)

| 何を | どう変える | どこで |
|---|---|---|
| main の承認 | 0 → 1。CODEOWNERS の承認を必須に | `.github/setup.yml` を直して `pnpm setup:github --apply` |
| 危険度「高」 | 2人で見る(チームを作り、CODEOWNERS の「高」の行に並べる) | `.github/CODEOWNERS` |
| prod の承認 | 自分の承認を止め、2人以上に | `.github/setup.yml`(Environments) |
| 管理者 | GitHub・AWS の管理者を2人に | 点検の台帳の「管理者を2人にする」 |
| 領域の持ち主 | 写真・日報・組織と課金に1人ずつ | CODEOWNERS・`docs/domain/` |

- 判定: ✅ 回る。値はファイルにあり、流し直すだけ。アカウントを作る・止める手順は G-13 で足した([../runbooks/joiner-leaver.md](../runbooks/joiner-leaver.md))。🟡 採用した人が初日に読む順番は G-49。
- 足す前の判定: ✅ 回る。値はファイルにあり、流し直すだけ。🟡 採用した人が初日に読む順番は、この README と [../getting-started.md](../getting-started.md) で足りるが、**アカウントを作る手順が無い**(穴 G-13)。

## 7-2 10人: 週の振り返りで AI に任せる範囲を広げる(A 社)

- 🏭 鈴木: 毎週30分「ラインの振り返り」。AI が同じ失敗をした所 → ルール・テスト・lint・スキルのどれに変えるか。
- 🏭 鈴木: 2か月ぶんの数字で、危険度「低」を人なしで自動マージにするか・本番の承認を自動にするかを決める([../concepts/people-and-ai.md](../concepts/people-and-ai.md) の 5)。
- 判定: ✅ 回る(G-12 済み)。`pnpm metrics` が AI の PR の割合・人の介在率・変更の失敗率を週ごとに出す。
- 足す前の判定: 🟡 決め方はあるが、**決めるための数字(AI の PR の割合・人の介在率・変更の失敗率)を自動で出す物が無い**(穴 G-12)。

## 7-3 10人 → 100人: チームを領域で分ける(B 社)

- 🏭 B 社の CTO: 4つの領域のチーム(問診・予約・医療機関の管理・課金)+基盤+SRE とセキュリティ。
- 🏭 EM: 領域ごとに CODEOWNERS とフォルダ(`apps/api/src/domains/<領域>/`)を持つ。AI には「この領域だけ」の文脈を渡す(領域ごとの CLAUDE.md・`docs/db/`)。1タスク1領域。
- 📚 世の中では: 年の売上が10億円・30〜60人の SaaS で、エンジニアが3〜4割、営業と CS が3〜4割、が目安とされる。売上が10億円を超えてからの壁は「大企業へ売る」「複数のプロダクト」「組織の力」の3つ、という振り返りもある。
- 判定: ✅ 回る(G-16 済み。仕様 0050)。領域ごとの CLAUDE.md の型 `docs/domain/_template-CLAUDE.md` があり、領域を足すとき `add-domain` のスキルが型から作る(触ってよい所・先に読む物・流すテスト)。
- 足す前の判定: 🟡 フォルダとスキーマの分け方・他の領域の表を読まない決まりはある。**領域ごとの CLAUDE.md の型が無い**(穴 G-16)。

## 7-4 100人: PR が詰まる(B 社)

- 🏭 B 社の基盤チーム: AI の PR が週300件。スカッシュ+「最新に追いついてから」で、1本ずつ追いつかせては CI を回し直す、が直列に並ぶ。
- 判定: ✅ 回る(G-15 済み。仕様 0051)。組織に移して、マージキューを使う手順は [../runbooks/move-to-org.md](../runbooks/move-to-org.md)(移す前に洗う物: URL・Renovate・Environments・ルールセット)。移すかどうかは人。
- 足す前の判定: 🟡 待ちの内訳とこつは [../guides/ci-speed.md](../guides/ci-speed.md) にある。**マージキューは個人のリポジトリで使えず、組織に移す手順が無い**(穴 G-15。URL・Renovate・Environments・ルールセットへの影響を洗ってから)。

## 7-5 100人: DB と費用の形を見直す(B 社)

- 🏭 SRE: 表が数百・DB の CPU が常に60%を超えた。読み取りのレプリカ・キャッシュ(キーに必ずテナント ID)・重い処理をキューへ・検索を外へ([../concepts/stages.md](../concepts/stages.md) の 3)。
- 💴 CFO: 100人の規模では、インフラ+AI は人件費の約2割。AI の利用額も予算と人ごとの上限で見る。
- 判定: 🟡 足す順番と決まりはある。キュー(SQS とワーカー)・トレース(OpenTelemetry)・負荷試験は、まだ型が無い(すでに「PMF の後でよいもの」に入っている)。1社あたりの原価は G-10 で出るようになった(推定の幅。[../guides/cost-dashboard.md](../guides/cost-dashboard.md) の 7)ので、大きな病院を別の DB に分ける判断の根拠はある。

## 7-6 100人: 自前のファクトリー(第3層)(B 社)

- 🏭 B 社の基盤チーム: Issue から PR までを、自社の仕組みで夜通し回したい(週1,000件を超えたら)。
- 判定: 🟡 キットはまだ作らない(PR が週に数十件を超えてから。[../concepts/line.md](../concepts/line.md) の 4)。100人の手前で要るのは、むしろ 7-2 の数字と、6-11 の外への通信の絞り(G-16・G-22 で足した)。

## 7-7 社員の手元の Claude Code の設定を配る(B 社・100人)

- 🛡 B 社の CISO: エンジニア35人に加えて、営業・CS・管理部門も Claude Code を使い始めた。手元の設定がばらばらで、誰かが「確認を飛ばすモード」で動かしているかもしれない。
- 📚 世の中では: 守りの設定(確認を飛ばすモードの禁止・インラインの bash や外への通信は確認・環境変数のファイルを読ませない・sudo の禁止・フォルダの外とネットワークを絞る・会社の方針を最初に読ませる)を、**端末の管理の仕組みで全社に配る**。エンジニアには上書きできる設定、エンジニア以外には最も安全な設定、と分けて配った会社がある。
- 判定: 🟡 リポジトリの中では確認を飛ばすモードを使えない。全社に配る設定は、`docs/guides/local-guards.md` の「手元の設定を全社に配る」(中身の例・エンジニアとそれ以外で分ける)。配るのは情シス(G-23 済み)。
