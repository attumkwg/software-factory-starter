# 11. 人がいなくなる(テックリードの不在・退職・キーパーソン・キットの作者)

> 入口は [README.md](README.md)。人は [companies.md](companies.md)。判定の印: ✅ 回る / 🟡 人の手か外の道具で回る / ❌ 穴([gaps.md](gaps.md))。
> 小さな会社では、ラインの持ち主が1人しかいない。この台本は、**その1人がいない日に、詳しくない人が回せるか**を通す。手順書の入口は [../runbooks/incident.md](../runbooks/incident.md)、人の出入りは [../runbooks/joiner-leaver.md](../runbooks/joiner-leaver.md)、点検は [../checkup/README.md](../checkup/README.md)。
> 2026-10-27 に、キットの main の設定(`.github/setup.yml`・`CODEOWNERS`)・点検の台帳とスクリプト・手順書・ワークフローを読んで判定した(実際に人を休ませて回してはいない)。「📚 世の中では」は、公開の事故報告・登壇・記事から一般化した学び(出どころは書かない)。

## 📌 いまの結論(2026-10-27)

- **知らせは止まらない**。毎週の点検の Issue・Renovate の PR・脆弱性の Issue・アラームは、鈴木がいなくても届き、`/cve` が関係あるかと期限まで決める。辞めた日の止め方(`joiner-leaver.md` の 3)も、届く範囲の広い物から順に書いてある。
- **止まるのは「本番に出す・戻す」と「答える」**。① 本番の承認は `pnpm setup:github --apply` を打った人(`@me`)1人だけで、鈴木がいないと直しも出せない。② 戻す手順は `aws` のコマンドで、代表には打てず、AI には打たせない。③ 点検に答えられるのは台帳の担当者1人で、代わりを立てる道が無い。
- **1人の間の備えが、約束だけで中身が無い**。点検の `acct-two-admins` は「1人しかいない」と答えると「引き継ぎの置き場を手順書に残す」と言うが、その手順書が無い。引き継ぎの練習(`handover`)は使い始めて1年後にしか出ない。
- **キットの作者がいなくなっても、作ったプロダクトは動き続ける**(MIT・実行時にキットに頼らない・資料は自己完結)。止まるのは直しが届くことで、これは G-41・G-42。
- 足した穴は G-64〜G-69([gaps.md](gaps.md) の「👥 人・更新・後から入れる」)。いちばん先は **G-64(本番の承認が1人)と G-67(引き継ぎの置き場)**。

## 11-1 鈴木が1か月いない。毎週の点検が来た(A 社・2人)

- 👩‍💼 代表(佐藤): 鈴木が家の事情で1か月休む。月曜の朝、GitHub のアプリに「点検 2026-W45」の Issue が来た。担当者は鈴木になっている。佐藤は Claude Code で `/checkup` と打った。
- 判定: ❌ **知らせは来るが、代わりに答えられない**(穴 G-66)。
  - ✅ 毎週の Issue は `checkup.yml` が作り、急ぎ(守りが外れた・重い穴・漏れ)は毎日見る。自動で確かめる項目(`w-guards`・`w-protection`・`w-vuln`・`w-renovate` など)は、誰も答えなくても毎週確かめ直す。
  - ❌ 答えを台帳に書けるのは `owners.responder`(担当者)だけ(`scripts/checkup/answer.mjs` の `whoMayAnswer`)。Issue も担当者に assign される(`scripts/checkup/notify-gh.mjs`)。代わりの人にするには `docs/checkup/todo.yaml` の `owners` を手で直す PR が要る。`pnpm checkup:adopt --by` は担当者を替えられるが、**引退していない項目を全部「まだ」に戻す**(使い始めるとき用)ので、途中の交代には使えない。
  - 🟡 相談先(`owners.advisor`)はあるが、「分からない」を受けるだけで、担当者の代わりではない。
- 📚 世の中では: 点検や当番は「担当の人」ではなく「担当の役」に結ぶ。休みは前から分かることが多いので、**期限つきの代わり**(この日からこの日まで)を先に置いておくと、戻った日に元に戻すのを忘れない。

## 11-2 Renovate の PR と、重い CVE の Issue がたまる(A 社・2人)

- 👩‍💼 代表(佐藤): 2週目。Renovate の PR が5本開き、うち2本は GitHub Actions と Docker のイメージの更新で「risk:high」が付いている。水曜には `vuln-scan.yml` が「重い穴」の Issue を立てた。
- 判定: 🟡 **AI が精査までやり、判断の材料はそろう。押す人が詳しくない**(穴 G-68)。
  - ✅ `/cve` が6段で精査し、届くか・期限(緊急は当日〜72時間・高は7日)・直し方を決める。人が決めるのは「期限を延ばすか」「本番をすぐ出し直すか」の2つだけ([../guides/vulnerabilities.md](../guides/vulnerabilities.md) の 6)。点検の `w-renovate` が「7日より長く止まっている PR」を毎週知らせる。
  - ✅ Renovate は開く数を5本に絞り(`prConcurrentLimit: 5`)、大きい版は人がチェックを入れたときだけ PR にする(`dependencyDashboardApproval`)。
  - 🟡 1人の間は承認 0(`required_approvals: 0`・`high_risk_approvals: 0`)なので、佐藤は CI が緑なら押せる。ただ「risk:high の更新を、詳しくない人が押してよいか」「押さずに待つなら、何日まで待ってよいか」は、どこにも書いていない。
  - ❌ 詳しくない人が1か月回すための1枚(何を押してよい・何は待つ・何は外の人を呼ぶ)が無い。外の顧問エンジニアに相談先を頼んでおく、という選択肢も書いていない。
- 📚 世の中では: 依存の更新は「ためない」が一番の守り。ただ、詳しくない人が代わりに押すときは「小さい更新・本番で動かない依存・CI が緑」だけを押し、ほかは待つ、のように**押してよい範囲を先に決めて**おくと、事故と放置の両方を避けられる。

## 11-3 夜に障害。いるのは代表だけ(A 社・2人)

- 👩‍💼 代表(佐藤): 22時、Slack の `#alerts-prod` に `api-target-5xx` が鳴った。昼に出した変更から後らしい。鈴木には連絡がつかない。
- 判定: ❌ **宣言と知らせはできるが、止血ができない**(穴 G-64・G-65)。
  - ✅ アラームは手順書の見出しに結んである([../runbooks/alarms.md](../runbooks/alarms.md))。宣言・役割・お客さんへの知らせの型は [../runbooks/incident.md](../runbooks/incident.md) の 1・2・4。AI に一次調査(直前のデプロイの差分・ID と集計を貼ったログ)を任せてよい。
  - ✅ デプロイの途中なら、5xx のアラームで ECS が自動で前の版に戻す([../runbooks/deploy-rollback.md](../runbooks/deploy-rollback.md) の 1.1)。
  - ❌ デプロイが終わった後に戻す手順(1.2)は `aws ecs update-service` を人が打つ。佐藤は AWS の prod の役割を持っていない(`joiner-leaver.md` の 1 は「prod は当番か要るときだけ」)し、コマンドも分からない。AI には `aws` を打たせない(`.claude/settings.json` の deny)。
  - ❌ 代わりに「直前の PR を戻す PR」を AI に作らせて main に入れることはできる。ただ本番に出す `deploy.yml` は Environment `prod` の承認が要り、承認する人は `@me`(`pnpm setup:github --apply` を打った人。たいてい鈴木)だけ(`.github/setup.yml` の `environments`)。機能フラグで止める道([../runbooks/feature-flags.md](../runbooks/feature-flags.md))も、同じ承認で止まる。
  - ❔ GitHub の管理者が Environments の承認を飛ばせるか(管理者の例外)は、キットの設定(`scripts/setup/areas-environments.mjs`)が扱っておらず、手引きにも無い。
- 📚 世の中では: 小さなチームの障害で長引くのは「直せる人に連絡がつかない」。**戻すことだけは、誰でも押せる1つのボタン**(前の版を出し直す・機能を止める)にし、押す権限を2人目に渡しておく。直すのは翌朝でよい。

## 11-4 急ぎの CVE の直しを、本番に出したい(A 社・2人)

- 👩‍💼 代表(佐藤): `/cve` が「緊急(当日〜72時間)」と決め、Renovate の PR も緑になった。マージはできたが、`deploy.yml` を流すと「承認待ち」で止まった。
- 判定: ❌ 11-3 と同じ。**本番の承認が1人に固定**(穴 G-64)。`setup.yml` の注記は「人が増えたら2人以上」で、2人目が「詳しくない代表」でもよいか、1人の間の緊急の出し方は書いていない。点検の `acct-two-admins` は GitHub と AWS の管理者を聞くが、本番の承認者は聞かない。

## 11-5 鈴木が辞める(A 社・3人目のエンジニアが入る前)

- 👩‍💼 代表(佐藤): 鈴木が3か月後に辞めると決まった。次のエンジニアはまだ決まっていない。
- 判定: 🟡 **止め方は回る。何を引き継ぐかの一覧が無い**(穴 G-67・G-68)。
  - ✅ 辞める日の手順([../runbooks/joiner-leaver.md](../runbooks/joiner-leaver.md) の 3): 本番に届く物は辞めると決まった日に外す・AWS → GitHub → 運営の組織 → ほかの道具 → メールの順・見られた秘密を替える(点検の `key-rotation`)・残りの管理者が1人になっていないか・**点検の担当者だったら次の人に替える**。点検の `people-changes` が毎月聞き、`access-review` が四半期に漏れを見つける。
  - ✅ 「辞めた人しか分からない設定がある → 止める前に引き継ぐ(`handover`)。止めるのは遅らせない」(同じ手順書の 5)。
  - ❌ `handover`(担当者がいなくても回るか)は `phase: 1y` で、使い始めて1年たつまで点検に出ない。2人の会社では、1年より前に人が抜けることがふつうにある。
  - ❌ 「どこに何のアカウントがあり、誰が鍵を持つか」の一覧の型が無い: AWS の root のメールと二段階認証の機器・ドメインの業者・GitHub の組織の持ち主・Claude と Sentry の請求・Apple や Google の開発者アカウント・Slack の Webhook の持ち主。点検の `acct-two-admins` は「今は1人しかいない」を選ぶと「1人で回す間の備え(引き継ぎの置き場)を手順書に残します」と言うが、**その手順書がキットに無い**。
- 📚 世の中では: 1人のエンジニアが抜けた会社で一番困るのは、コードより「ドメインの更新の通知が辞めた人のメールに届いていた」「root の二段階認証が辞めた人のスマホに入っていた」のような、**アカウントの持ち主**。中身(パスワード)ではなく、**どこにあり・誰が持ち・どう取り戻すか**を、公開しない場所に1枚で残す。

## 11-6 B 社で、基盤の EM が抜ける(B 社・100人)

- 🏭 基盤チームの EM: 基盤の EM が急に辞めた。CODEOWNERS の `infra/` の行・本番の承認者・点検の担当・当番の予備が、その人の名前だった。
- 判定: 🟡 **止め方と当番は回る。個人名が残った所を探す道具が無い**(穴 G-69)。
  - ✅ 当番は3人から・交代は週ごと・表はリポジトリの外([../guides/on-call.md](../guides/on-call.md) の 1)。障害の指揮は当番の一次がとる。
  - ✅ GitHub の組織から外せば、チーム・CODEOWNERS・Environments の承認者からも外れる。承認者に名前で入っていたら `.github/setup.yml` を直す PR(`joiner-leaver.md` の 3 の 2)。
  - 🟡 `CODEOWNERS` の冒頭は「チームができたら個人をチームに置き換える」と書くが、置き換えたかを確かめる物は無い。`pnpm setup:check` と点検の `w-protection` は、承認者・CODEOWNERS が個人1人だけの行を見ない。辞めた人の名前だけが残った行は、気づくまで「見る人がいない」まま。
  - 🟡 設計の全体像は「人の頭に残す」(ADR を人がレビューする。[../concepts/running.md](../concepts/running.md) の 7)。ADR と手順書があるので、知識はリポジトリに残りやすい。
- 📚 世の中では: 100人の規模では、人が抜けること自体は毎月起きる。困るのは「その人しか持っていない役」が設定の中に散らばっていること。**役はチームに結び、個人1人だけの役を機械で一覧にする**(棚卸しで探すのではなく、毎週出す)。

## 11-7 キットの作者がいなくなる(A 社・B 社)

- 🏭 B 社の CTO: 「このキットの作者が更新をやめたら、うちはどうなる?」と聞かれた。
- 判定: 🟡 **作ったプロダクトは動き続ける。直しが届かなくなる**(G-41・G-42 で扱う。新しい番号は振らない)。
  - ✅ ライセンスは MIT(ルートの `LICENSE`)。作ったリポジトリは自分の物で、続けて直してよい。
  - ✅ 実行時にキットに頼る所が無い: パッケージとして読み込む物は無く、資料はキットの外を指さない(`pnpm self-contained`)。`pnpm setup:github` がキットの最後のコミットの日を読む(`scripts/setup/plan.mjs` の `kitDates`)が、読めなければ飛ばすだけ。点検の台帳の調べる所(`refresh_sources`)は公開の外のサイトで、キットではない。
  - ✅ キットの作者の名前が残る所(`CODEOWNERS` の `@attumkwg`・`template_repository`・設計書の「承認(@attumkwg …)」)は、作った人が自分の物に替える手順がある(`pnpm checkup:adopt`・`pnpm decisions --adopt`・点検の `launch-decisions`)。
  - ❌ 誰がいつまで直すか・作者が止めたらどう知らせるかの約束が無い(G-41)。キットの直しを取り込む道も無い(G-42。[12-kit-updates.md](12-kit-updates.md))。
- 📚 世の中では: 雛形から作ったプロダクトは、作った日から雛形と別の物になる。作者が止めても困らないのは、**実行時に雛形に頼らない**作りだから。反対に、守りの直しを雛形から受け取るつもりなら、止まったときの受け取り先(フォークを誰が持つか)を決めておく。

## 演習の仕方

- Claude Code で「`docs/scenarios/11-people-leave.md` の 11-3 を、私が代表の役で演じて。テックリードには連絡がつかない前提で、いまのキットで本番を戻すまでの手順を1歩ずつ出して」のように頼む。どこで止まったか(権限・承認・コマンド)を書き出す。
- 年に1回の `handover` を待たずに、テックリードが休む前の週に、代表だけで `/checkup` と手順書を1つ通す(点検の `handover` の手順と同じ)。
