# 16. 海外の最初のお客さん(英語の画面・時間帯・通貨・GDPR・置き場所・移転)

> 入口は [README.md](README.md)。人は [companies.md](companies.md)。判定の印: ✅ 回る / 🟡 人の手か外の道具で回る / ❌ 穴([gaps.md](gaps.md))。
> キットは「日本の会社が日本のお客さんに売る」を前提に作ってある(画面は日本語・時間帯の既定は東京・データの置き場所は東京・法令の洗い出しは日本の法令)。この台本は、**最初の海外のお客さん**が来た場面を通す。
> 2026-10-27 に、キットの main の画面と API のコード・お金と時刻の部品・Terraform・取り決めと SLA の型・法令の手引きを読んで判定した(英語の画面は作っていない)。「📚 世の中では」は、公開の事例・登壇・記事から一般化した学び(出どころは書かない)。法令の名前は「専門家に確かめる先の候補」で、当たると言い切らない。

## 📌 いまの結論(2026-10-27)

- **時間帯とお金の持ち方は、最初から海外に耐える**。組織ごとの時間帯(IANA の名前・夏時間も正しい)・瞬間は UTC・日付だけは日付で持つ・金額は通貨つきの最小単位の整数(円・ドル・ユーロ)。ここは作り直さなくてよい([../adr/0005-money-and-time.md](../adr/0005-money-and-time.md))。
- **言葉は作り直しになる**(穴 G-89)。画面の文字は部品の中に日本語で直に書いてある(`apps/web/src` の画面のうち日本語の文を持つ物が34ファイル)・表示の形は `ja-JP` で固定・`<html lang="ja">`・招待や法令の知らせのメールも日本語。言葉を切り替える仕組みが無い。
- **法令の洗い出しが日本の法令だけ**(G-90)。GDPR のような国外の法令に当たるかの問いの一覧・取り決めの型(処理者としての条項・移転の仕組み)・事故の報告の期限の違いが無い。1人分の開示と削除の手順([../runbooks/person-data.md](../runbooks/person-data.md))は、国外の本人の求めにもそのまま使える見込み。
- **データの置き場所は東京だけで、契約の型では「変えない」**(G-91)。Terraform のリージョンは変数なので別の環境を国ごとに立てる道は理屈ではあるが、手引きが無く、組織ごとに置き場所を選ぶ形は無い。
- 円以外の請求は、キットが金額を持たない作りなので会計ソフトの側(🟡)。見積と申込書の型に通貨と税の欄が無い(G-92)。
- いちばん先は **G-90(法令の問いの一覧)**。契約できるかがここで決まり、言葉(G-89)と置き場所(G-91)を作るかはその後に決まる。

## 16-1 「英語の画面はある?」(A 社・10人)

- 🤝 営業(中村): 日系の建設会社の欧州の現地法人から問い合わせ。「現場の職人は現地の人。画面とメールを英語にできるか」。
- 🎨 デザイナー(山本)・🧑‍💻 エンジニア(伊藤): どこを直せばよいか見積もりたい。
- 判定: ❌ **言葉を切り替える仕組みが無い**(穴 G-89)。
  - ❌ 画面の文字は部品に直に書いてある(言葉の表が無い)。日付の表示は `apps/web/src/format.ts` が `ja-JP` で固定。`apps/web/src/routes/__root.tsx` は `lang="ja"`・OGP は `ja_JP`(`apps/web/src/head.ts`)。
  - ❌ API が作る文も日本語: 招待のメール(`apps/api/src/domains/organizations/invitations.ts`)・法令の知らせ(`apps/api/src/domains/legal/notifications.ts`)・エラーの文。組織か人ごとに言葉を持つ列が無い。
  - ❔ 公開の LP(`apps/site`)・規約・プライバシーポリシー・ヘルプの記事も日本語だけ。訳を誰が持つか・訳した版をどちらが正にするかは決める。
  - ✅ 色・余白・部品は `packages/ui` にまとまっていて、言葉が長くなったときの崩れは VRT で見られる(`pnpm vrt`)。
- 📚 世の中では: 後から言葉を足すと、文字を表に移す作業より「日付・数・名前の順番・文の長さ」で崩れる所の方が多い。最初の1か国のときに表に移す仕組みだけ入れ、訳は使われる画面から順に、が多い。

## 16-2 時間帯(A 社・欧州のお客さん)

- 👷 現地の職人: 「日報の『今日』が、こちらの朝9時に切り替わる」。
- 判定: ✅ 回る(作るときに決めれば)。
  - ✅ 組織ごとの時間帯(`organizations.tenants.time_zone`・IANA の名前)。開通のコマンドの申し込みに `timeZone`(既定 `Asia/Tokyo`。`apps/api/src/onboarding/create-tenant.ts`)。「今日」と1日の区切りは `packages/shared/src/time.ts` の `toLocalDate` などで組織の時間帯から。夏時間の国でも名前で持つので正しく動く。端末の時間帯を使う書き方は Semgrep が止める。
  - 🟡 作った後に組織の時間帯を変える運営のコマンドや画面は見当たらない(DB を直すことになる)。1つの組織の中で、人ごとに時間帯を分ける形も無い(欧州と日本の両方に人がいる組織)。
  - 🟡 表示の形は `ja-JP` のまま(G-89)。

## 16-3 ユーロで請求したい(A 社・管理)

- 🗂 管理(加藤): 「月額をユーロで。現地の付加価値税の扱いは?」
- 判定: 🟡 **持ち方はあるが、請求はキットの外**(穴 G-92)。
  - ✅ 金額は通貨つき(`packages/shared/src/money.ts` の `CURRENCY_DIGITS` に `JPY`・`USD`・`EUR`)。通貨が違う金額は足せない(`CurrencyMismatchError`)。
  - ✅ プランと価格表は金額を持たない(`packages/shared/src/plans.ts`)。請求は外の会計ソフトで手で([04-money.md](04-money.md))。
  - ❌ 見積([../legal/quote.md](../legal/quote.md))と申込書([../legal/order-form.md](../legal/order-form.md))の型に、通貨・為替の決め方・税の扱いの欄が無い。費用のページと賭けごとの損益は円で並べる前提。
  - ❔ 国外の会社との取引の消費税・相手の国の付加価値税・源泉の扱いは専門家に確かめる(税理士)。

## 16-4 「GDPR に対応している?」(A 社・欧州のお客さんの情シス)

- 🛡 現地法人の担当: 「我々は EU の会社。GDPR の処理者としての契約(DPA)と、移転の仕組みを出して。漏えいは何時間で知らせる?」
- 判定: ❌ **国外の法令の問いの一覧と型が無い**(穴 G-90)。
  - ✅ 取り決めの型([../legal/data-processing.md](../legal/data-processing.md))に、預かる項目・目的・安全管理・事故の連絡・再委託・消し方の欄があり、中身はキットの作りから埋まる。列ごとの分類表と個人データの台帳([../db/personal-data.md](../db/personal-data.md))がある。1人分の開示と削除の手順がある。
  - ❌ 法令の洗い出し([../product/_legal-template.md](../product/_legal-template.md)・[../guides/legal-documents.md](../guides/legal-documents.md))は日本の法令だけ。事故の手順書([../runbooks/personal-data-breach.md](../runbooks/personal-data-breach.md))の期限も日本の法令の形(速報はおおむね3〜5日・確報は30日)。短い期限を求められたときに守れるか(当番は営業時間だけ。[../guides/on-call.md](../guides/on-call.md))を決めていない。
  - ❌ 取り決めの型は「日本のお客さんから見て委託先」の形。EU の法令の言葉(管理者・処理者・移転の仕組み)との対応・再委託先の一覧を求められたときの出し方(委託先の台帳から作れる見込み)が書いていない。
  - ❔ 専門家に確かめる先の候補: GDPR(域外の会社に当たるか・EU の代理人が要るか・処理者の条項・処理の記録・漏えいの報告の期限)・日本と EU の間の移転の扱い(十分性の認定が当たるか)・現地の国の法令。
- 📚 世の中では: 最初の海外のお客さんは、法令そのものより「相手の会社の型の DPA にそのまま署名できるか」で止まる。相手の型を、自社の作り(置き場所・委託先・事故の連絡の時間)と突き合わせて、守れない所を先に返す。日本の取り決めと同じ3つの分け(変えない・仕組みを変える・契約だけ)が使える。

## 16-5 「データは EU に置いて」(A 社・欧州のお客さん)

- 🛡 現地法人の担当: 「写真と日報は EU の中に置いてほしい。無理なら、日本に置く理由と守り方を書いて」。
- 判定: ❌ **置き場所は東京だけ**(穴 G-91)。
  - ✅ 置き場所は東京と書いてあり、契約の型では「変えない」に入っている([../legal/README.md](../legal/README.md) の 2・3・[../legal/data-processing.md](../legal/data-processing.md) の 7)。**守れない約束をしない**ための形としては正しい。
  - ✅ Terraform のリージョンは変数(`infra/terraform/envs/prod/variables.tf` の `region`)。環境ごとに別のリージョンへ立てることは理屈ではできる。
  - ❌ 別の国の環境を立てる手引きが無い(stg と prod のほかに、国ごとの prod を持つか・CI とデプロイと監視と当番を2つ回すか・費用)。組織ごとに置き場所を選ぶ形(1つの API が2つの DB を持つ)は無い。
  - ❌ 東京の外に出る物の一覧はあるが(外形監視のアラーム・証明書は米国。ID と集計は米国の委託先)、EU の求めの形(国ごとの一覧・置き場所を選べる物)で並べていない。Sentry は EU の置き場も選べる(委託先の台帳)。
  - ❔ 置き場所を国ごとに持つかは事業判断(1社のためなら断る・上位のプランにする)。
- 📚 世の中では: 最初の1社のために国ごとの環境を立てて、運用が2倍になって後悔した例がある。多くは「日本に置く理由と守り方を書いた紙」で通すか、断る。国ごとに置くのは、その国で何十社と売ると決めてから。

## 16-6 日本の利用者のデータを、国外へ移す同意(A 社・日本の職人)

- 👷 日本の工務店の職人: 欧州の現地法人の人と同じ組織で日報を見る。日本の利用者のデータが、国外の人に見られる。
- 判定: 🟡 **国外の委託先の扱いは「専門家に確かめる」まで**(G-90 に含める)。
  - ✅ 米国の委託先(GitHub・Sentry・Slack・Anthropic)に渡すのは ID と集計までで、国は台帳に書いてある。外国にある第三者への提供に当たるかは、設計書 0017 の U-1 で「導入時に決める」([../compliance/ai-data.md](../compliance/ai-data.md) の 3)。
  - ❌ 「お客さんの組織の中の、国外にいる人が見る」場合と「お客さんの国外の会社に書き出す」場合の扱いを分けて書いていない。プライバシーポリシーと取り決めのどちらに書くかも決めていない。
  - ❔ 専門家に確かめる先の候補: 個人情報保護法(外国にある第三者への提供・本人への情報提供)。

## 16-7 時差のある問い合わせと障害の連絡(A 社・CS)

- 🎧 CS(小林): 欧州の朝(日本の夕方)から問い合わせが来る。夜中の障害は誰が知らせるか。
- 判定: 🟡 **SLA と当番は営業時間で約束する形があり、それで断れる**。SLA の連絡の時間は「営業時間の中で数える」が既定([../legal/sla.md](../legal/sla.md) の 6)。夜中も約束するなら当番を置くのが先([../guides/on-call.md](../guides/on-call.md))。知らせの文の時刻は日本時間([../runbooks/incident.md](../runbooks/incident.md) の 4)なので、海外のお客さんには相手の時間帯も添える決まりを足す(G-89 に含める)。
