# 18. 携わる人ごとの評価と、通しのシミュレーションの完成度

> 入口は [README.md](README.md)。人は [companies.md](companies.md)。
> 2026-10-27 に、このキットに携わる人を **23人の立場**で並べ、それぞれの「ふだんの仕事」をキットの文書・スキル・コマンド・手順書・画面でたどって、**刺さるか・使いやすいか・分かりやすいか**を 1〜5 で付けた(4人は [09-adoption.md](09-adoption.md) の「キットを選ぶ人」)。あわせて、台本 00〜17 が**どこまで実際に動かして確かめたか**を数えた。
> どれも読んで付けた点数(手を動かして確かめたのは 9-2 の install とテストだけ)。見つけた穴は G-100〜G-121([gaps.md](gaps.md) の「🧑‍🤝‍🧑 携わる人と、通しの完成度」)。

## 📌 いまの結論(2026-10-27)

- **刺さる(平均 3.7)**: 考え方・1問ずつ聞く対話のスキル・CI とフックで機械に守らせる作りは、23人のほぼ全員に効いた。指すパスは実物と合っていた。
- **使いやすい(平均 2.3)が一番低い**。理由は1つにまとまる: **エンジニアでない人の入口が無い**。代表・PdM・デザイナー・営業・CS・管理・CFO の仕事が、Claude Code と clone・`gh`・PR のマージ・`aws s3 cp`・ECS で打つ運営のコマンドの上にしか無い。運営の画面も無い。
- **10人の形にすると、承認と持ち場が1人(テックリード)に集まる**(CODEOWNERS の `*`・本番の承認者 `@me`・点検の担当1人)。文書の「危険度『低』は人なし」は実装されていなかった(2026-10-28 に文書を設定に合わせた。承認の数は全部の PR に同じ)。
- **外に出す一式と、書いてある事実の確かさが弱い**: 稟議の束は「埋める所 0件」と出しながら「未確認」が残る・事故の第1報の期限が文書で2通りだった(2026-10-28 にそろえた)。ISMS の本体(リスクアセスメント)と医療の安全管理ガイドラインの対応が無い。
- **通しのシミュレーションは、台本は約8割の段にあるが、実際に動かして確かめたのは約5%(作る前の段だけ)**。題材のアプリと想定の会社(写真・問診)が合っていないことも、現場の人の評価を下げた。

## 18-1 作る人(代表・PdM・テックリード・新人・デザイナー)

- 判定: 🟡 **エンジニアの2人(鈴木・渡辺)だけが通しで回せる**。`/kickoff`・`/bet` の問い(なぜ自分たちか・買う人と使う人と決める人・撤退の線・意思で進む)は代表と PdM にそのまま効く。
- ❌ 代表・PdM・デザイナーには、Claude Code を手元で動かす・`gh` でログインする・PR を見てマージする所までの手引きが無い(G-100)。費用のページは AWS のコンソールか `aws s3 presign` でしか見られない(G-102)。
- ❌ 10人の設定にすると、`docs/product/`・`docs/specs/` を持つ CODEOWNERS の行が無いので、PdM の仕様の PR も鈴木の承認待ち。本番の承認者の既定は `@me`(鈴木)。「危険度『低』は人なし」は文書だけで、承認数を1にすると全部の PR に1人要る(G-104)。
- ❌ デザイナー: `/new-feature` と仕様のひな形に、画面と流れ・見本を渡す欄が無い。VRT の基準の撮り直しに Docker か git が要る(G-106)。
- 🟡 新人: 入社した人の1日目の手引き(clone・起動はどちらか・読む順・最初の Issue)が無い。getting-started は創業者の道(G-107)。

## 18-2 売る・回す人(営業・CS・管理)

- 判定: 🟡 **毎回エンジニアを待つ**。運営の操作は約20あり、全部 ECS で打つコマンド(`create-tenant`・`plan`・`delete-tenant`・`person-data`・`feature-flag` など)。読むだけの運営の画面も、依頼を受けるフォームも無い(G-101)。
- ❌ CS: **お客さんの管理者が、辞めた人を外す・無効にする・ロールを変える画面が無い**。外した人は契約の人数にも数え続けられる(G-103)。
- ❌ 管理: 費用・時給・売上の入力が `aws s3 cp`・台帳は YAML と PR。入社・退職の手順書の表に管理・経理の列が無い(G-100・G-102)。
- 🟡 営業: `pnpm sales:pack` の「埋める所」が `<…>`・`YYYY` などしか拾わず、「未確認」「使う人が決めること」を残したまま「0件」と出る。キットの既定と本番で確かめた値を分けていない。Markdown しか出ない(G-108)。

## 18-3 守る・数える人(CISO・SRE・CFO)

- 判定: 🟡 漏えいの手順書・質問票の「本番で確かめた物だけ『はい』」・アラームごとの手順書・機能ごとの損益は、どれも良い。
- ❌ CISO: 病院の質問票の軸になる **医療の情報の安全管理ガイドラインとの対応表が無い**(G-111)。点検の担当者は台帳全体で1人(G-105)。
- 🟡 SRE: B 社の段階で、テナントごとの流量の上限・トレース・キュー・負荷試験が「PMF の後」のまま(G-121)。
- ❌ CFO: 入力も閲覧も AWS の上。月の締め(請求書との突き合わせ・実際のレート・長く残す)・部門と勘定科目の予算・ARR と NRR が無い(G-102・G-117)。

## 18-4 外から関わる人(DD・情シス・審査員・弁護士・現場)

- 判定: 🟡 守りの材料はそろっているが、**外に出す形**(束・図・一覧)と**事実の確かさ**が弱い。
- ✅ `docs/security.md` の古い記述(SSO が「未」)を質問票のスキルが最初に読み、下書きが「いいえ」になっていた(2026-10-27 に直した)。同じ種類の古さは `pnpm gaps` が CI で見る(済んだ穴を「穴」と書いた文書)。事故の第1報の期限は「取り決めの期限(既定3日)が先、法の目安は3〜5日」にそろえた(G-109。2026-10-28)。
- ❌ 審査員: 附属書 A の SoA と証跡は強いが、**リスクアセスメント・リスク対応計画(本文の 6.1)と、本文の 4〜10 の型が無い**。SoA に承認の欄が無い。適用なのに点検も証跡も無い管理策が27件(G-110)。
- 🟡 DD: 依存のライセンスの一覧・AI が書いたコードの管理の説明・構成図が無い(G-108・G-53・台本 15)。
- 🟡 弁護士: 「専門家に聞くこと」がファイルごとに散らばる(G-108)。
- ❌ 現場: 題材のアプリに日報・問診が無い(G-57)。写真・ファイルの保存の部品は API まである(G-45 済み。画面は付け先と一緒に作る)。押す所の大きさの決まりが 24px で、手袋や屋外を考えた決まりが無い。**題材のアプリの「消す」が確認なしで即実行**で、キット自身の画面の決まり(戻せない操作は確認)に反している(G-112)。

## 18-5 道具として入ってくる人(AI・貢献者・学ぶ人)

- 判定: 🟡 守りは CI とフックで機械的に強制され、指すパスは実物と合っていた。
- 🟡 AI: セッションの始めに必ず載る指示が約1.45万字(ルートの `CLAUDE.md` 約9,700字のうち、決まりは4分の1。G-49 で場所ごとに分けた後の量。量の話は G-49 に束ねた)。`add-domain` の「人に聞く」と「人に聞くのは4つだけ」が矛盾。画面を足すスキルが無い。仕様の無い依頼の入口が無い(G-113)。
- 🟡 貢献者: `CONTRIBUTING.md` が無い。Issue と PR のテンプレートはプロダクト向けだけ(G-114)。
- 🟡 学ぶ人: 学ぶ道(読む順)と、手を動かす練習の課題が無い。台本に作業の記録(足す前の判定・G 番号)が混ざり、物語として読みにくい(G-115・G-116)。

## 18-6 通しのシミュレーションの完成度

> **数は 2026-10-27 の点検の時点**。今の穴の数は `pnpm gaps`(穴の一覧の頭の表)。
> 台本の場面(`## n-m`)を 133 数え、「🟢 実際に動かした」「🧪 読んで判定し、判定の元の部品に CI のテストがある」「🔵 読んで判定しただけ」に分けた。段は「導入 → 何を作るか → 確かめる → 言葉・LP → 仕様と実装 → PR とマージ → stg と本番 → 開通と運用 → 障害 → 規模 → 売る → 終わり」と、横に走る「セキュリティ・お金・法務・人・AI(作る側・製品)・キットの保守」。

| 物差し | 値 | 数え方 |
|---|---|---|
| 台本がある割合 | 約 83% | 36の確かめる項目で(ある+一部×0.5)÷36 |
| 実際に動かして確かめた割合(🟢) | 約 4.5%(6/133) | 00 の ✅ 実行と、9-2 の install・テスト |
| 部品のテストまで含めた割合(🟢+🧪) | 約 38%(51/133) | 判定の元の部品が CI の結合テストか E2E で試されている |
| 場面の判定 | ✅ 76・🟡 29・❌ 28 | 台本に書いた今の判定 |
| 本物でしか確かめられない場面 | 約 20 | AWS・本物の Cognito と IdP・メールの到達・請求・リージョン |

- **通しで実際に回ったのは 00 の週0〜5(計画 → 話の記録 → 賭け → 試作)だけ**。その成果物は残っておらず、その後に変わった `/kickoff`・`/bet`・`/positioning`・`/brand` では通していない。
- **鎖が切れている所**: 試作 → 言葉・LP / 賭け → 仕様 → 実装 → PR(A 社のプロダクトのコードはまだ無い)/ マージ → stg → 本番(AWS を使わない)/ 本番 → 開通 → 利用 → 請求(1本につないだテストが無い)/ 障害 → 振り返り(14場面すべて読んだだけ)。
- ⚪ **台本が無い**: 初めて AWS に stg と本番を立てる・プレビュー環境を使う・最初の請求と入金・1社分の誤削除を戻す・QA の役。
- **AWS なしで上げられる範囲**(G-119): 捨てるリポジトリで 00 を今のスキルでやり直して成果物を残す・題材を1機能(日報)だけ差し替えて PR まで・docker compose を本番の代わりにして「事前登録 → 開通 → 招待 → 利用 → 書き出し → 解約」を1本の E2E に・障害と AI の事故の演習・Terraform を `terraform test` の偽の提供者で確かめる。🟢 を約5%から3〜4割へ上げられる見込み。
- 2026-10-28: 「事前登録 → 開通 → 招待 → 利用と写真 → プラン → 書き出し → 解約」を1本の E2E にした(`apps/web/e2e/journey.spec.ts`。CI の E2E で毎回回る)。「本番 → 開通 → 利用 → 請求」の鎖のうち、請求(外の会計ソフト)の手前までがつながった。人を外す(G-103)と1人分の削除(G-06 の残り)は「未」の印で報告に出る。
- **本物でしか確かめられない物**(G-120): 初めての apply と ECS のデプロイ・自動で戻る動き・本物の Cognito と IdP・メールの到達・アラームから Slack・Vault Lock と Object Lock・リージョンの障害・請求と入金。キットを使う側で stg を立てたときに確かめる一覧にする。
