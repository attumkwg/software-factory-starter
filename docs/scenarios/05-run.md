# 5. 運用(営業 → 開通 → CS → 障害 → 解約)

> 入口は [README.md](README.md)。人は [companies.md](companies.md)。判定の印: ✅ 回る / 🟡 人の手か外の道具で回る / ❌ 穴([gaps.md](gaps.md))。
> 手順書の入口は [../runbooks/incident.md](../runbooks/incident.md)。
> 「📚 世の中では」は、公開の事故報告・登壇・記事から一般化した学び(2026-10 時点。出どころは書かない)。

## 5-1 申し込みを受けて、組織を開通する(A 社・10人)

- 🤝 営業(中村): 工務店から申込書が届く。プラン・人数・始まりの日・最初の管理者のメールアドレスを CS に渡す。
- 🎧 CS(小林): 「組織を作って、管理者に招待のメールを送る」をしたい。
- 判定: ❌ **組織を作る運営のコマンドが無い**(穴 G-01)。いまは本番の DB に SQL で `organizations.tenants` と `organizations.users` に行を足す(運営の組織の作り方と同じ。[../runbooks/support-access.md](../runbooks/support-access.md) の 1)。解約には `delete-tenant`(試し → 名前の確認 → 実行)があるのに、始めの側に同じ形の物が無い。CS が本番の DB を触ることになり、監査ログにも残らない。
- 📚 世の中では: 営業・CS の分業は「受け渡し」で揉める。渡してよい条件を先に決めておく(申込書の項目・最初の管理者・プラン)と、受け渡しが速い。

## 5-2 お客さんの管理者が人を足す(A 社・10人)

- 👷 工務店の管理者: 「新しく入った職人を足したい」。
- 判定: ❌ **招待の画面が無い**(穴 G-02。部品のカタログの `invitations` が「未」)。いまは運営が SQL で users に行を足す([../runbooks/cognito-login.md](../runbooks/cognito-login.md))。お客さんが10社を超えると、CS の手が回らない。招待はリンクの期限と1回きり(`docs/security.md` の T-8)が決まりとしてある。

## 5-3 導入を手伝う(A 社・10人)

- 🎧 CS(小林): 「画面を一緒に見ながら設定したい」。お客さんの管理者が「設定」から期限つきで許可 → 番号を CS に伝える → CS は見るだけ・最長1時間でその組織の画面を開く。入った・見た・出たは、お客さんの監査ログに残る。
- 判定: ✅ 回る([../runbooks/support-access.md](../runbooks/support-access.md))。

## 5-4 問い合わせを受ける(A 社・10人/B 社)

- 🎧 CS: メールと電話で問い合わせが来る。不具合なら「問い合わせ番号」(画面のエラーに出る request ID)を聞いて `/report-bug`。
- 🎧 B 社の CS(15人): 1日100件。ヘルプデスクの道具(外の SaaS)を使い、よくある質問はヘルプの記事に。
- 📚 世の中では: 始めてしばらくは開発の人が兼任で回る(週5〜10件)。2〜3人の体制では1人休むと回らない・答えの質がばらつく。導入が数百社を超えた頃に、ヘルプの記事に検索を足したら、ヘルプを見る人が3倍になった例もある。
- 判定: 🟡 `/report-bug` と問い合わせ番号はある。**問い合わせの受け口(外の道具)をどう選び、どこまで AI に渡してよいか**が決まっていない(穴 G-11)。外の道具は委託先の台帳に1件、問い合わせの本文は個人データなので AI に渡すのは ID と集計まで(`docs/security.md` の AI-6)。

## 5-5 夜中にアラームが鳴る(A 社・10人)

- 🔔 23:40 に `#alerts-prod` へ「API の 5xx が増えている」。
- 🏭 鈴木: 誰が見るのか・何分以内に・朝まで待ってよいアラームはどれか。
- 📚 世の中では: 当番は一次対応・予備・上げる先の**3人から**。週ごとに回すなら4〜5人。夜に鳴らすのは「お客さんに影響がある」か「約束の水準を割った」ときだけで、急がない物は朝にまとめる。当番の間は普段の開発をせず、改善の作業だけにする。深夜が続かないよう、週ごとから日ごとの交代に変えた会社もある。24時間365日を自前だけで回すのは無理なので、呼び出しの道具を入れる。
- 判定: 🟡 アラームと Slack への知らせ・手順書([../runbooks/alarms.md](../runbooks/alarms.md))はある。**当番の決まり(順番・連絡の段・夜と休日・待ってよい物)が無い**(穴 G-08)。SLA を約束したら(2-3)必ず要る。点検の台帳の「知らせの先と、障害のときの連絡先を決める」は、連絡先までで当番の形は持たない。

## 5-6 障害を宣言して、お客さんに知らせる(A 社・10人)

- 🏭 鈴木: 手順書の型で、重さ(S1〜)を決めて宣言 → 指揮を1人決める → 原因が分からなくても先に止血(戻す・止める)。
- 🎧 CS: 手順書の「お客さんへの知らせ(型)」でメールを送る。終わったら、S1・S2 は5営業日以内に振り返り(`docs/incidents/`)。
- 📚 世の中では: 障害は「直す」より「伝える」で信頼を失う。ある会社は、エンジニアの持ち回りでうまくやれているつもりだったが、CS から「最近の障害対応はうまくいっていない」と言われた。手順書はあっても読み合わされず、「誰に何をどこまで伝えるか」が人によってばらばらだった。指揮役の専任化・連絡の型・Slack の使い方を3か月で直した。根本の原因と再発防止は24〜48時間以内に示す、が目安とされる。
- 判定: ✅ 回る。🟡 **稼働状況のページ(ステータスページ)が無い**(穴 G-09)。お客さんが「いま落ちているのか」を自分で見られる所が無く、問い合わせが CS に集まる。

## 5-7 解約する(A 社・10人)

- 👷 工務店の管理者: 「設定」から自社のデータを JSON で書き出す(秘密・他社の物は入らない・監査ログに残る。1社が大きくても1ページずつ流して返す)。
- 🎧 CS: 契約の終わりを確かめてから、運営が `delete-tenant`(既定は試し → `--execute --confirm-name`)。消した後に残る物と期間(バックアップは最長1年)は手順書のとおりお客さんに伝える。
- 判定: ✅ 回る([../runbooks/offboarding.md](../runbooks/offboarding.md))。

## 5-8 利用者1人から「私のデータを見せて・消して」(A 社/B 社)

- 👤 工務店を辞めた職人(または B 社の患者): 「自分のデータを開示してほしい」「消してほしい」。
- 判定: ❌ **1人分の開示・削除の手順が無い**(穴 G-06。部品のカタログの `person-deletion` が「未」)。組織を丸ごと消す仕組みはあるが、1人分は無い。誰が答えるか(お客さんの会社か、運営か)も、契約の形(2-4)で変わる。まずは手順書と運営のコマンドの「試し」までで足りる。

## 5-9 二段階認証のスマホを無くした(A 社・10人)

- 👷 職人: 「スマホを替えたらログインできない」。
- 🎧 CS: 手順書で本人を確かめてから、運営が二段階認証を外す([../runbooks/mfa-reset.md](../runbooks/mfa-reset.md))。
- 判定: ✅ 回る。

## 5-10 1人の医師が2つの病院で使う(B 社・100人)

- 🩺 医師: 「午前は A クリニック、午後は B 病院。アカウントを2つ持ちたくない」。
- 判定: ❌ **1人が複数の組織に入る形が無い**(穴 G-21)。いまは「1人 = 1組織」(ADR 0001)。テナントを決めるのはセッションからだけ、という決まりを崩さずに、組織を選び直す形が要る。

## 5-11 約束した稼働率を割った(A 社・10人)

- 🔔 月の稼働率が、SLA の 99.9% を割った(DB の入れ替えで40分止まった)。
- 🤝 営業(中村): 大口のお客さんから「SLA の返金は?」。
- 📚 世の中では: 補償を「自動で当てる」か「個別に話し合う」かは、測り方が先。**何を測るか(外から開けるか)・どの範囲か・原因の区分(自社か、外のサービスか、お客さんの側か)・どこから補償か・誰が事実を確定し、誰が例外を認めるか**を決めてから SLA を出す。
- 判定: 🟡 測る側の材料(外形監視・障害の重さと時系列の振り返り)はある。**補償の段と例外を決める人を書いた SLA の型が無い**(穴 G-04)。
