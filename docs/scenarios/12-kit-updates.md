# 12. キットの更新を取り込む(重い穴の直し・新しい守り・台帳)

> 入口は [README.md](README.md)。人は [companies.md](companies.md)。判定の印: ✅ 回る / 🟡 人の手か外の道具で回る / ❌ 穴([gaps.md](gaps.md))。
> キットから作ったリポジトリは、作った日からキットと別の物になる。この台本は、**作って3か月後にキットの側で大事な直しが入ったとき、使う側がどう知り、どう受け取るか**を通す。上流を取り込む道そのもの(G-42)と保守の約束(G-41)は済んだので、ここでは今の判定と、まだ足りない細かい物を書く。
> 2026-10-27 に、キットの main の `README.md`・`scripts/setup/`・点検の台帳とスクリプト・`pnpm adr`・キットの最近の PR(危険度「高」の承認の人数を足した PR)を読んで判定した(実際に別のリポジトリへ取り込んではいない)。「📚 世の中では」は、公開の事故報告・登壇・記事から一般化した学び(出どころは書かない)。

## 📌 いまの結論(2026-10-28。G-41・G-42 が済んだ後の姿)

- **依存の穴は、キットを待たずに届く**。作ったリポジトリでも Renovate・Dependabot・毎週の `vuln-scan.yml`・CI の Trivy が自分で動くので、ライブラリの重い CVE はキットの直しと関係なく知らせが来て、`/cve` で精査できる。
- **キット自身の直し(守り・関所・手順書)は、月1回の点検で知る**(G-41・G-42 済み)。キットは版と `CHANGELOG.md`(版ごとの「取り込むときにすること」)・`SECURITY.md` を持ち、取り込んだ版を `docs/kit/upstream.yaml` に残し、点検の `kit-upstream` が新しい版を知らせ、取り込み方は `docs/kit/upgrade.md` の3つから選ぶ。まだ無いのは、**守りの直しだけを毎週見る道**(G-71)と、**取り込むべき直しの印**(G-70)。
- **受け取るときにも詰まる所がある**: 仕様・設計書・ADR の番号のぶつかりは、使う側の番号を別の範囲から振って消した(G-116 済み)。残りは、点検の台帳の新しい項目を、自分の答えの記録を壊さずに足す道が無い・取り込んだ設定(必須のチェックなど)を GitHub に反映したかを、毎週の点検が見ていない。
- 足した穴は G-70〜G-74([gaps.md](gaps.md) の「👥 人・更新・後から入れる」)。どれも「🎯」の段の「使える前に」(G-72 は G-116 に束ねた)。

## 12-1 キットが更新されたことを、どう知るか(A 社・10人)

- 🏭 テックリード 兼 EM(鈴木): キットから作って3か月。キットの側で何が変わったかを気にしたことは無い。
- 判定: 🟡 **月1回の点検で知る**(G-41・G-42 済み)。守りの直しだけを毎週見る道は無い(穴 G-71)。
  - ✅ README と getting-started は、作るときに `git remote rename origin kit` でキットを残すように書く(後でキットの直しを見られる)。
  - ✅ キットは版の付け方([../kit/maintenance.md](../kit/maintenance.md) の 4)と `CHANGELOG.md` を持つ。取り込んだ版は `docs/kit/upstream.yaml`。点検の `kit-upstream` が月1回、新しい版があれば知らせ、`pnpm setup:github` の最後の「人がやること」にも同じ文が出る(最初のタグを打つまでは日付で)。キットのリポジトリを Watch → Releases にすればメールでも届く。
  - ❌ 月1回の点検は全部の変更をまとめて見る。守りの直しだけを毎週見る項目が無く、`/checkup-refresh` の調べる所(`refresh_sources`)にもキット自身が入っていない(穴 G-71)。
- 足す前の判定: ❌ **知る道が、作り始めるときの1回だけ**(G-41・穴 G-71)。
  - ✅ `pnpm setup:github`(試し)は、作った後にキットが更新されていれば「取り込みたい直しが無いか、キットのコミットの一覧を見る」を「人がやること」に出す(`scripts/setup/next-steps.mjs` の `kitFreshness`)。ただし**作り始めるときだけ**の知らせで、`--apply` の後は出ない。
  - ❌ キットに版のタグ・CHANGELOG・リリースが無い(G-41)。GitHub の「Watch → Releases」で受け取れない。
  - ❌ 点検の台帳に、キットの更新を見る項目が無い。月1回の `/checkup-refresh` の調べる所(`docs/checkup/todo.yaml` の `refresh_sources`)は GitHub・AWS・Claude Code・法令などで、**キット自身が入っていない**。
- 📚 世の中では: 雛形から作る道具は、「作った後の更新」を知らせる仕組みを持つ物と持たない物に分かれる。持たない物は、作って半年で利用者のほとんどが更新を追わなくなる。知らせは「全部の変更」ではなく「**取り込むべき直しだけ**」にしないと読まれない。

## 12-2 キットが使っているライブラリに、重い CVE が出た(A 社・10人)

- 🏭 テックリード(鈴木): キットが使う Web の部品のライブラリに、外から届く重い穴が出た。キットの側では、作者が版を上げる PR を入れた。
- 判定: ✅ **キットを待たずに、自分のリポジトリで回る**。
  - Renovate が自分のリポジトリに版を上げる PR を出す(`renovate.json` の `vulnerabilityAlerts` は待ち日数なし)。Dependabot の通知も自分のリポジトリに来る(`.github/setup.yml` の `security.dependabot_alerts`)。
  - 毎週の `vuln-scan.yml` が自分のリポジトリでも回り、落ちたら Issue を立てる → `/cve` が精査して期限を決める([../guides/vulnerabilities.md](../guides/vulnerabilities.md))。点検の `w-vuln` が開いている通知を毎週見る。
  - キットの側の PR は、取り込まなくてよい(同じ直しが自分の Renovate から来る)。

## 12-3 キット自身のコードに穴があった(A 社・10人)

- 🏭 テックリード(鈴木): キットの作者が「Bash のフックが、ある書き方の書き換えを見逃していた」「認可の関所が、ある条件で別の組織の行を返していた」を直した。どちらもライブラリではなく、キットが書いたコード。
- 判定: 🟡 **Watch していれば届く。していなければ月1回の点検まで届かない**(G-41 済み・穴 G-70・G-71)。
  - ✅ キットに穴の報告先と知らせ方がある(`SECURITY.md`。非公開の報告で受け、直したら勧告と `CHANGELOG.md` の「セキュリティ」に書く)。キットのリポジトリを Watch → Security alerts にしていれば届く。
  - ❌ ライブラリではないので、Renovate・Dependabot・Trivy は拾わない。テンプレートから作ったリポジトリに、キットの勧告の通知は来ない(穴 G-71)。
  - ❌ キットの PR に「使う側が取り込むべきか」の印が無い。守りの直しと、想定の場面の文書の直しが、同じ一覧に並ぶ(穴 G-70)。
- 足す前の判定: ❌ **使う側に届く道が無い**(穴 G-70・G-71)。
  - ❌ キットに穴の報告先と知らせ方の約束(SECURITY.md)が無い(G-41。外から知らせる道 `private_vulnerability_reporting` は公開のリポジトリで有効)。
- 📚 世の中では: コピーして使う形の部品(雛形・コピーして貼るライブラリ)は、穴が出ても利用者の依存の一覧に載らないので、機械では見つけられない。配る側は、**守りの直しだけを別の道で知らせ**(勧告・決まったラベル・メールの一覧)、利用者は点検で「配る側の守りの直し」を毎週見る。

## 12-4 キットに新しい守り(危険度「高」の承認の人数)が入った(B 社・100人)

- 🏭 基盤チーム: キットに「危険度『高』の PR だけ、決めた人数の承認がそろうまで止める」必須のチェックが入った(仕様 0059)。B 社も CODEOWNERS では2人目を強制できていないので、取り込みたい。
- 判定: 🟡 **取り込む手引きはある**(G-42 済み。[../kit/upgrade.md](../kit/upgrade.md) の3つの取り込み方から選ぶ)。番号のぶつかりは、キットが 0001〜4999・使う側が `pnpm checkup:adopt` で決めた範囲(既定 5000 から)で振るので起きない(G-116 済み・仕様 0091。`pnpm adr` が範囲の重なりと外れを CI で落とす)。取り込んだ後の確かめは、点検の `w-protection` が毎週 `.github/setup.yml` と GitHub のずれを見る(G-74 済み・2026-10-29)。守りの本体と説明の区別(穴 G-70)が残る。
- 足す前の判定: ❌ **取り込む手引きが無く、取り込んだ後の確かめも無い**(G-42・穴 G-72・G-74)。
  - ❌ キットの PR は1つで19ファイル: ワークフロー・数えるスクリプトとテスト・`.github/setup.yml`・`CODEOWNERS`・`protected-paths.json`・`labeler.yml`・`package.json`・README・手引き・仕様と設計書、それに想定の場面の文書(`docs/scenarios/`)。B 社は `CODEOWNERS`・`setup.yml`・README を自分の物に直しているので、そのまま当てるとぶつかる。どのファイルが「守りの本体」でどれが「キットの説明」かの区別が無い(G-70)。
  - ❌ キットの仕様と設計書は 0059。B 社は3か月の間に自分の仕様を 0059 まで書いていた。**同じフォルダで番号が重なると `pnpm adr` が CI で落ちる**(`scripts/adr-lib.mjs`)。どちらを振り直すか・使う側の番号をどこから始めるかの決まりが無い(穴 G-72)。
  - 🟡 取り込んだ後に要る人の作業は、キットの決まりどおり: `.github/**` は「高」なので人の承認・マージの後に人が `pnpm setup:github --apply`(必須のチェックに足す)・人が増えていれば `high_risk_approvals` を 2 に。`pnpm setup:check` は、`required_checks` の名前がジョブに無いと落ちる。
  - ✅ (2026-10-29・G-74)`--apply` を忘れたら、毎週の点検 `w-protection` が「必須になっていないチェック: …」で不合格にする(`scripts/checkup/checks/setup-drift.mjs`)。キット自身でも流した最初の回で、必須になっていないチェックが2つ見つかった。
  - (足す前)❌ ただ、`--apply` を忘れても気づけない。点検の `w-protection` は「必須のチェックが1つ以上あるか」を見るだけで(`scripts/checkup/checks/github-protection.mjs`)、`.github/setup.yml` と GitHub の今の設定のずれは見ない(穴 G-74)。新しいチェックは毎回流れるが、必須ではないので赤でもマージできる。
- 📚 世の中では: 設定をコードに置く(あるべき形をファイルに書く)仕組みは、**ファイルと本物のずれを定期で見る**までそろって初めて効く。ファイルを直してマージしただけで「入った」と思うのが、一番よくある抜け。

## 12-5 キットの点検の台帳に、新しい項目が足された(A 社・10人)

- 🏭 テックリード(鈴木): キットの台帳(`docs/checkup/todo.yaml`)に、新しい点検の項目が3つ足され、1つが引退した。A 社の台帳は `pnpm checkup:adopt` で自分の物にしてから、3か月ぶんの答えの記録(`history`)がある。
- 判定: ❌ **id で足すだけの道が無い**(穴 G-73)。
  - ✅ 台帳の決まりは「id は変えない・消さずに `retired`・`history` は足すだけ」(台帳の冒頭)。項目ごとに id があるので、機械で足し合わせられる形ではある。
  - ❌ キットの台帳を git でそのまま取り込むと、`owners`・`started_on`・`status`・`history` がぶつかる。`pnpm checkup:adopt` は自分の物にするときの1回用で、流し直すと全部の項目を「まだ」に戻す。新しい項目だけを足し、引退を写し、自分の答えは触らない道具が無い。
  - 🟡 `/checkup-refresh` は世の中の変化から項目を足す・直す道で、キットの台帳から写す道ではない。

## 12-6 3か月で大きく離れた(B 社・100人)

- 🏭 B 社の CTO: キットから作って3か月で、B 社のリポジトリには300の PR が入った。`/tailor` で部品をいくつか消し、ルートの `CLAUDE.md` も直した。キットの側でも80の PR が入った。
- 判定: 🟡 **取り込みの道はある**(G-42 済み)。まるごと merge・差分を要る場所だけ・直しだけ cherry-pick の3つから選ぶ([../kit/upgrade.md](../kit/upgrade.md))。消した部品に触れた直しは、使う側の記録(`docs/product/tailoring.md`)を見て飛ばす。
  - ⚠️ 残る所: 部品の単位で取り込む道具は無い(手引きの手順で)。キットの記録と使う側の記録が同じフォルダに混ざる(番号の範囲は分けた: G-116 済み。置き場を `docs/kit/` の下へ分けるのは、使う人の声が出てから)。
- 足す前の判定: ❌ **上流の取り込みの道が無い**(G-42。別のセッションで作っている)。
  - ❌ キットは1つのリポジトリ・squash で入る。消した部品に触れたキットの直しは「消したのに直された」でぶつかる。`docs/kit/catalog.yaml` の部品の単位で取り込む道も無い。
  - 🟡 取り込むかを決める材料はある: 部品のカタログ(何をするか・消すと困ること・つながり)と、使う側の記録 `docs/product/tailoring.md`(何を消したか)。
- 📚 世の中では: 雛形の更新を後から取り込む方法は、大きく3つ。① 作るときの答えを残しておき、新しい版の雛形で作り直して差分を当てる ② 仕組みの部分をパッケージやプラグインに分けて、版を上げるだけにする ③ 上流を remote にして、要る直しだけを選んで当てる。①② は雛形の側の作りが要り、③ は使う側の手間が要る。どれでも、**守りの直しと説明の直しを分けておく**と、取り込む量が減る。

## 演習の仕方

- 捨てるリポジトリで、キットの1か月前のコミットから作り、`git remote add kit` でいまの main を取って、危険度「高」の承認の人数の PR(仕様 0059)だけを取り込んでみる。ぶつかったファイル・振り直した番号・人がやった設定を書き出す。
- Claude Code で「`docs/scenarios/12-kit-updates.md` の 12-3 を、私が使う側のテックリードの役で演じて。キットの作者の役は、守りの直しを出したことをどう知らせるかを考えて」のように頼む。
