# 3. 機能の企画書・ロードマップ → 作って出す

> 入口は [README.md](README.md)。人は [companies.md](companies.md)。判定の印: ✅ 回る / 🟡 人の手か外の道具で回る / ❌ 穴([gaps.md](gaps.md))。
> 1つの機能の流れの本体は [../playbook.md](../playbook.md)。
> 「📚 世の中では」は、公開の事故報告・登壇・記事から一般化した学び(2026-10 時点。出どころは書かない)。

## 3-1 機能の企画書を書く(A 社・10人)

- 🎧 CS(小林): 「写真に手書きの印を付けたい」という問い合わせが、今月12件。
- 📝 PdM(田中): `/bet` で賭けを開く。親は動かしたい指標(「写真の画面を毎週開く会社の割合」)。合格と撤退の線・期限を先に書く。これが企画書になる(`docs/product/bets/B-NNNN-*.md`)。
- 🤖 Claude: 判断を小石(足すだけの記録)に残し、段階が変わるたびに資産か費用かの案を1行足す。
- 判定: ✅ 回る。

## 3-2 ロードマップを見せる(A 社・10人/B 社)

- 🤝 営業(中村): 商談で「手書きの印はいつ出ますか」と聞かれる。代表には「来月の展示会で、次の3か月に出す物を1枚で見せたい」と言われる。
- 📝 PdM: いまは `pnpm bets` で賭けの一覧(ID・段階・題名)が出るだけ。
- 判定: ✅ 回る(G-07 済み)。`pnpm bets --roadmap` が社内の版、`--public` が時期を約束しない社外の版を出す(`--write` でファイルに)。
- 足す前の判定: ❌ **ロードマップの1枚が無い**(穴 G-07)。賭けには段階・期限・親の指標があるので、「今やっている・次にやる・その後」を並べた1枚は作れる。社外に見せる版(約束しない書き方)と、社内の版を分けたい。B 社では、領域ごとのチームの賭けを束ねた1枚が要る。

## 3-3 仕様にして作る(A 社・10人)

- 📝 PdM: `/new-feature` で「写真に手書きの印」。賭けの ID を確かめ、1問ずつ(受け入れ条件 → 各ロールと他社の扱い → 悪用のされ方 → 大きさ)。
- 🤖 Claude: 仕様(`docs/specs/`)と設計書(`docs/designs/`)を1つの PR に。人に聞く4つ(事業判断・利用者の挙動・他チームとの契約・戻せないリスク)に当たる所は止まらずに仮に決め、未確定事項に残す。
- 📝 PdM: PR の本文(全体像・事実・理由・問い)だけを見て、未確定事項に「承認・変更・保留」で答えてマージ。親と子の Issue ができる。
- 🧑‍💻 エンジニア(伊藤): 子の Issue を Claude Code で実装。API を足すなら `add-api-endpoint`、表を変えるなら `db-migration`。
- 判定: ✅ 回る。

## 3-4 レビューする(A 社・10人)

- 🏭 鈴木: 人が増えたので `.github/setup.yml` を「👥 人が増えたら」の値(承認 1・CODEOWNERS の承認)に変え、マージの後に `pnpm setup:github --apply`。
- 🧑‍💻 エンジニア(高橋): 危険度「中」の PR を `/review-pr <番号>` で見る。冒頭の「人に判断してほしい所」から。危険度「高」(認証・移行・infra)は2人で、`/security-review` も手で回す。
- 📚 世の中では: 確認の画面を増やすほど「はい」が作業になる(承認疲れ)。確認の画面の1つを明らかに危ない操作に差し替える実験で、止められたのは人が1割強、自動の判定は9割、という報告もある。人の確認は「判断が要る所」に絞るほうが効く(キットの危険度と「人に聞く4つ」)。
- 判定: ✅ 回る。

## 3-5 本番に出す(A 社・10人)

- 🧑‍💻 伊藤: マージ → `deploy.yml` で stg → 疎通を確かめる → prod は Environment の承認(人)。ECS の blue/green で、5xx が増えたら自動で戻る。
- 🎧 CS(小林): `/release-notes` で利用者向けと社内向けのリリースノートの下書き。公開は人。
- 判定: ✅ 回る。いまは `deploy.yml` が手動(使い始める日を [../guides/automation.md](../guides/automation.md) の表に入れて有効にする)。

## 3-6 一部のお客さんにだけ出す(A 社・10人)

- 📝 PdM: 賭けを `rollout` に進め、運営のコマンドで5社にだけ機能フラグを入れる。使われたかは利用の記録(1日1人1機能1行)で、週ごとの数を見る。
- 📝 PdM: 組ごとに400前後の数が集まるなら A/B、それより少ないなら段階的な公開で十分([../guides/bets-and-assets.md](../guides/bets-and-assets.md) の「rollout の確かめ方」)。
- 判定: ✅ 回る。🟡 **プラン(契約)と機能の入切がつながっていない**(穴 G-03)。「上のプランの会社だけに出す」は、今は運営が組織ごとに手で入れる。

## 3-7 仕様の在庫が枯れる(B 社・100人)

- 🏭 B 社の EM: AI の PR が週300件を超え、エンジニアは待っていないのに、次に作る「承認済みの仕様」が足りない。
- 📝 PdM: 毎週の「仕様の在庫」を見る([../playbook.md](../playbook.md) の「毎週やること」)。賭けの線が先に決まっていれば、仕様に落とすのは速い。
- 判定: 🟡 考え方と毎週の確認はあるが、**仕様の在庫・人の介在率・DORA を数字で出す物が無い**(穴 G-12)。100人では、感覚ではなく数字で「どこが詰まっているか」を見たい。

## 3-8 不具合を直す(A 社・10人)

- 🎧 CS(小林): お客さんの画面に出た「問い合わせ番号」(request ID)を受け取り、`/report-bug` で再現の手順・期待と実際・影響の範囲・危険度をそろえた Issue にする。
- 🧑‍💻 渡辺: request ID でログを引き、誤りが入った工程を決めて `/rework`(コードだけを継ぎ当てない)。原因が「見る観点が無かった」なら `docs/review-viewpoints.md` に1行。
- 判定: ✅ 回る。

## 3-9 AI を組織に広げたら、効いたかを測る(A 社・10人/B 社)

- 👩‍💼 佐藤(A): 「AI の席にこれだけ払って、速くなったのか」。B 社の CTO は、全社に広げる前に経営会議で説明したい。
- 🏭 鈴木: 決めるための数字(使われているか・外に頼むより安いか)と、直すための数字(誰が伸びているか・何を横に広げるか)を分ける。PR の数・PR が出てからマージまで・**AI が手伝った PR の割合**・人が直した回数を、導入の前と後で比べる。
- 📚 世の中では: AI が手伝った PR は、コミットから見分けるより **GitHub Actions でラベルを付けて数える**ほうが確か。トークンの量だけでは測れない。3人の平均で「+64%」と出ても、役割が変わった人は下がるので、数字は決裁の材料にとどめる。ダッシュボードを整えても使う人と使わない人の差は開くだけで、チームごとの推進役と1対1の時間が要った。
- 判定: 🟡 PR の本文の「取り組み」「作業の種類」と、費用のページの人の時間はある。**AI が手伝った PR の割合・人の介在率を数える物が無い**(穴 G-12)。
