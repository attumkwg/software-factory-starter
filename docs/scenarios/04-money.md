# 4. コストと採算 → ムーンショット

> 入口は [README.md](README.md)。人は [companies.md](companies.md)。判定の印: ✅ 回る / 🟡 人の手か外の道具で回る / ❌ 穴([gaps.md](gaps.md))。
> 「📚 世の中では」は、公開の事故報告・登壇・記事から一般化した学び(2026-10 時点。出どころは書かない)。
> 仕組みの本体は [../guides/cost-dashboard.md](../guides/cost-dashboard.md)・[../guides/bets-and-assets.md](../guides/bets-and-assets.md)、段階ごとの費用は [../concepts/stages.md](../concepts/stages.md) の 4。

## 4-1 PMF の前に費用を抑える(A 社・2人)

- 🧑‍💻 鈴木: 本番は「払う人が出てから」。それまでは stg を本番の代わりに(月 約2.2万円〜)。NAT を1つに・使わない間はプレビューの土台を壊す・ログは14日([../getting-started.md](../getting-started.md) の「PMF の前の節約」)。
- 🧑‍💻 鈴木: AI の席は削らない(いちばんの速さの元)。
- ✅ Terraform が費用の警報(Budgets)を作る: 使った額が 80% のときと、月末の見込みが 100% を超えるときに Slack へ。
- 判定: ✅ 回る。

## 4-2 何にいくらかかっているかを見る(A 社・10人)

- 🗂 管理(加藤): 費用のページを始める(一度だけ。[../guides/cost-dashboard.md](../guides/cost-dashboard.md) の 2)。`cost.yml` が非公開の S3 に HTML の1枚を置く。
- 🗂 管理: SaaS の月額は `docs/cost/saas.yaml`、AI の費用は手で書く(管理用の鍵を GitHub に置かない)。時給・売上は非公開の S3 の `cost/inputs/` だけ(リポジトリに金額を置かない)。
- 🏭 鈴木: 見積もり(段階の表)と実際を毎月見比べる(点検の台帳の「費用の実績と見積りを見比べる」)。
- 判定: ✅ 回る。

## 4-3 賭けごとの損益(PL)を見る(A 社・10人)

- 👩‍💼 佐藤: 「写真の手書きの印は、作るのに人の時間をどれだけ使って、いくら稼いだのか」。
- 🤖 費用のページ: 賭けごとに、タグ `Bet` の AWS の費用+SaaS の按分+人の時間(PR の件数からの目安と、週1の手入力の割合を幅で)を並べ、売上と比べる。共通の費用は、既定では人の時間の割合で配る(導入時に決める)。
- 判定: ✅ 回る。🟡 売上は人が手で `revenue.csv` に入れる(プランの表は G-03 で入ったが、請求は外の会計ソフトで手でしているため)。

## 4-4 月の締め(A 社・10人)

- 🗂 管理: `/ledger` で前の月の賭けごとの人の時間とインフラを、「資産の候補・費用・除却の候補」に分けた案(CSV)にして、1件ずつ確かめる。確かめた案は賭けのファイルの「会計区分の判定」に足して PR。
- 🗂 管理: CSV を税理士に渡す。会計・税の当てはめは専門家が確かめる、と毎回添えられる。
- 📚 世の中では: 上場を目指すと「ソフトウェアの原価計算」が要る。よくある間違いは、開発の案件の管理・工数の管理・間接費の配り方・開発の段階(研究開発か、自社利用のソフトウェアか)の確認。監査では**見積もりの幅ではなく、工数の実績**を求められる(G-26 で実績の入れ方を足した)。
- 判定: ✅ 回る。

## 4-5 値段を決める(A 社・10人/B 社)

- 👩‍💼 佐藤: 「1社あたりの原価はいくらか。小さい工務店は月 4,980円で赤字にならないか」。
- 📝 B 社の CFO: 「大きな病院1院のために、DB を別にする判断の根拠がほしい」。
- 📚 世の中では: 料金は後から戻せる(可逆)。値を探るために話を聞く・誰が値を決めるかを決める・値引きに気をつける。失注が2〜3割は、むしろ健全という見方もある。
- 判定: ✅ 回る(G-10 済み。仕様 0042・ADR 0053)。費用のページが、利用の記録・データ量・リクエストの数の割合で組織ごとに按分した原価を出す(組織の ID は出さない。[../guides/cost-dashboard.md](../guides/cost-dashboard.md))。
- 足す前の判定: ❌ **1社あたりの原価が出ない**(穴 G-10)。費用のページは賭けごと・動いている物ごとで、組織ごとではない。[../concepts/stages.md](../concepts/stages.md) の 4 は「1社あたりの原価も出す」と書いているが、出す仕組みが無い。

## 4-6 採算が合わない賭けを止める(A 社・10人)

- 📝 PdM: 期限を過ぎて撤退の線を下回った賭けを、`/bet` で `dropped`(やめた)にする。何が分かったかを残すのも成果。
- 🧑‍💻 エンジニア: 定着した後に使われなくなった機能は `retired`(撤去)。機能フラグ・コード・表を消す PR(表は `db-migration` の段階で)。
- 判定: ✅ 回る。

## 4-7 ムーンショットに予算の枠を付ける(B 社・100人)

- 👔 CEO: 「介護施設の問診」に半年・月 300万円まで、と決めたい。止める線は「半年で有料の施設が20」。
- 📝 B 社の CFO: 毎月、その賭けに使った額(人の時間を含む)を見て、枠を超えそうなら知らせてほしい。
- 判定: ✅ 回る(G-19 済み)。賭けごとの予算の枠と、超えそうなときの知らせを費用のページが出す(`scripts/cost/budgets.mjs`)。新しい客層の計画は `docs/product/plans/` に並べる。
- 足す前の判定: 🟡 使った額は賭けごとの PL で見える。**賭けごとの予算の枠と、超えそうなときの知らせが無い**(Budgets は環境ごと)。新しい客層の計画を本業と並べる置き場も無い(穴 G-19)。

## 4-8 値上げをする(A 社・10人)

- 👩‍💼 佐藤: 機能が増えたので、月 4,980円 → 6,980円にしたい。今のお客さんは1年は据え置きにする。
- 🗂 管理: 規約の料金の条を変える版を足す(利用者に不利な変更なので同意し直し・30日前に公開。2-7)。
- 📚 世の中では: 値上げで失われるのは数百円ではなく「来月もこの条件で使える」という予測。今のお客さんを旧価格に残す(据え置き)と、**データの持ち方の問題になる**: 加入した日・どの価格表か・プランを変えたら据え置きが消えるか・席を足したら旧価格か新価格か。請求とプロダクトの両方が同じ状態を見る必要がある。
- 判定: ✅ 回る(G-03 済み。仕様 0047・ADR 0058)。組織ごとのプランの行に、どの価格表か・据え置きの権利(期限)を持つ。値上げは価格表の版を足し、据え置きの組織は期限まで前の版のまま([../runbooks/plans.md](../runbooks/plans.md))。
- 足す前の判定: 🟡 規約の版と同意し直しは回る。**プランの表に「どの価格表か」「据え置きの権利」を持つ形が無い**(穴 G-03)。

## 4-9 売上の指標を見る(A 社・10人/B 社)

- 👩‍💼 佐藤: 投資家に ARR・NRR(追加の購入込みの売上の維持率)・解約率を出したい。
- 📚 世の中では: NRR は100%が分かれ目・110%以上で優良、追加の購入を除いた維持率は85〜90%以上、月の解約率は中小企業向けで3〜5%・大企業向けで0.5〜1%、が目安とされる(多くは米国の数字)。
- 判定: 🟡 プランの表(G-03)はできた。売上の数字そのものは、請求を外の会計ソフトでしている間は手で入れる(費用のページの非公開の入力。リポジトリに金額を置かない)。
- 足す前の判定: 🟡 キットの利用の記録は「機能が使われたか」まで。**売上の指標は、プランと請求の仕組み(穴 G-03)ができてから**。それまでは会計ソフトの数字で手で出す。
