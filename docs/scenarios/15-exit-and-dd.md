# 15. 終わり方・売り方(サービスを終える・AWS を片づける・技術の DD・事業を譲る)

> 入口は [README.md](README.md)。人は [companies.md](companies.md)。判定の印: ✅ 回る / 🟡 人の手か外の道具で回る / ❌ 穴([gaps.md](gaps.md))。
> 01〜08 は「始めて伸ばす」。この台本は**終わる・手放す・外から中身を確かめられる**場面を通す。今あるのは1社ずつの解約(書き出しと `delete-tenant`。[../runbooks/offboarding.md](../runbooks/offboarding.md))まで。10-10(AI が写したコードのライセンス)もここで扱う。
> 2026-10-27 に、キットの main の手順書・Terraform・CI・台帳・稟議の束(`pnpm sales:pack`)を読んで判定した(本物の DD は受けていない)。「📚 世の中では」は、公開の事例・登壇・記事から一般化した学び(出どころは書かない)。法令の名前は「専門家に確かめる先の候補」。

## 📌 いまの結論(2026-10-27)

- **1社ずつ終わるのは回る**。管理者の書き出し(秘密と他社の物は入らない・監査ログに残る)・試し → 名前の確認つきの削除・消した後に何がいつまで残るか([../guides/data-retention.md](../guides/data-retention.md))がそろっている。
- **サービス全体を終える手順が無い**(穴 G-85)。全部の組織への予告と書き出しの期限・運営の組織と事前登録の削除・委託先を順に解約すること・AWS を片づける順番。しかも本番の保管庫は compliance のロックで**最長1年は誰にも消せない**ので、「すぐ全部消して AWS を閉じる」はできない。それを前提に段取りを組む物が要る。
- **技術の DD の材料は多くがある**: 構成(`docs/reference.md`・Terraform)・セキュリティの決まりと適用宣言書・委託先の台帳・個人データの台帳・監査の記録。**足りないのは、依存のライセンスの一覧(G-53)・AI が書いたコードの扱いの説明(G-87)・DD 向けの束(G-86)**。稟議の束はお客さん向けで、買う側・出資する側の問いには並びが合わない。
- **事業を譲るときの引き継ぎの手順が無い**(G-88)。人の入退社([../runbooks/joiner-leaver.md](../runbooks/joiner-leaver.md))と、リポジトリを組織に移す手順([../runbooks/move-to-org.md](../runbooks/move-to-org.md))はあるが、AWS のアカウント・ドメイン・鍵・委託先の契約の名義・お客さんの個人データを、別の会社に渡す道は書いていない。
- いちばん先は **G-86(DD の束)と G-87(AI が書いたコード)**。資金調達は終わり方より先に来る。

## 15-1 サービスを終える(A 社・10人・撤退の線を越えた)

- 👩‍💼 代表(佐藤): 賭けの撤退の線を2回越え、プロダクトをやめると決めた。お客さんは28社。「3か月後に終える」と知らせたい。
- 🎧 CS(小林): 28社に、書き出しの案内と終わる日を伝え、終わった後に消したい。
- 判定: ❌ **1社ずつの道を28回くり返すことになる**(穴 G-85)。
  - ✅ 書き出しは各社の管理者が画面からできる(`apps/api/src/export`・1ページずつ流して返す)。削除は `delete-tenant`(試し → `--execute --confirm-name`・2人で)。消した後に残る物と期間は [../guides/data-retention.md](../guides/data-retention.md) にあり、契約に書く文の例もある。
  - ✅ 知らせの先(組織の管理者)と、法令の知らせの部品(`apps/api/src/legal-notify`)はある。
  - ❌ 「サービスを終える」の手順書が無い: 予告の日数と契約の解約の申し出の期限の突き合わせ・書き出しの締め切りと、書き出さなかった組織の扱い・全部の組織を消す順番と記録・運営の組織と事前登録(`growth`)と利用の記録(`usage`)の削除・プライバシーポリシーの最後の版・問い合わせの窓口をいつまで残すか。
  - ❔ 予告の日数・返金・書き出さなかったお客さんにどう渡すかは、契約と事業判断。専門家に確かめる先の候補: 利用規約の変更と終了の条項・消費者向けなら消費者契約法。
- 📚 世の中では: サービスの終わりで揉めるのは「データが返ってこない」より「知らせが急」「書き出した物が使えない(他の道具に入らない)」。終える日の3か月以上前に知らせ、書き出しの形(CSV か JSON か・写真は入るか)を先に書いておく会社が多い。

## 15-2 AWS とまわりを片づける(A 社・10人)

- 🧑‍💻 テックリード(鈴木): 全社を消した後、AWS の費用を止めたい。`terraform destroy` でよいか。
- 判定: ❌ **片づける順番が無く、消せない物がある**(G-85 に含める)。
  - ✅ AI は apply・destroy をしない(人が CI で。`CLAUDE.md`)。消す前の確かめに使える一覧はある: 委託先の台帳(会社ごとの「こちらが使うのをやめたとき」の消え方)・費用のページ(動いている物ごと)・タグ `Component`。
  - ⚠️ 本番の DB の保管庫は compliance のロック(`infra/terraform/modules/backup`・prod の `lock_mode = "compliance"`)で、**毎月の分は最長365日、誰にも消せない**。AWS の管理操作の記録は400日(`modules/audit-trail`)・毎月の証跡は年単位のロック(`evidence_retention_years`)。これは「消えない」約束を守る仕組みで正しいが、終えるときは**最長1年は AWS のアカウントと保管の費用が残る**。
  - ❌ どの順で消すか(画面・API・DB → 送り待ち・ログ → 鍵 → ロックの期限が来た保管庫 → アカウント)・ドメインと DNS をいつ手放すか(手放した後に他人に取られると、メールやリンクが乗っ取られうる)・GitHub と Slack と Sentry の解約・台帳を `status: ended` にする、の手順が無い。
  - ❔ 期限が来る前にアカウントを閉じたとき、ロックされた保管庫がどうなるかは確かめていない(AWS の今の仕様で確かめる)。

## 15-3 資金調達で、技術の DD を受ける(A 社・10人)

- 👩‍💼 代表(佐藤): シリーズ A の出資の前に、出資する側の技術の顧問から問いの一覧が届いた。「構成図・セキュリティの体制・OSS のライセンス・AI が書いたコードの割合と権利・個人データの扱い・委託先・過去の事故・技術の負債」。
- 判定: 🟡 **材料はあるが、束になっていない**(穴 G-86)。
  - ✅ 構成と地図: [../reference.md](../reference.md)・`infra/terraform`・設計判断([../adr/](../adr/))。セキュリティ: [../security.md](../security.md)(番号つきの決まりと確かめ方)・適用宣言書 [../compliance/soa.md](../compliance/soa.md)・毎月の証跡(`pnpm evidence --list`)。個人データ: [../db/personal-data.md](../db/personal-data.md)(列の分類表から)。委託先: [../compliance/vendors.md](../compliance/vendors.md)。事故: `docs/incidents/` の振り返り。数字: `pnpm metrics`(DORA・AI が手伝った PR の割合)。
  - ✅ お客さん向けの束(`pnpm sales:pack`)と、質問票の下書き(`/security-questionnaire`)がある。届く・まだ直していない穴の中身は書かない決まりも同じ。
  - ❌ DD の問いの並び(会社の資産としてのコード・権利・ライセンス・負債・人への依存)に合わせた束が無い。sales:pack は SLA と取り決めが中心で、ライセンスと AI のコードの扱いと負債が入らない。
  - ❌ 依存のライセンスの一覧が無い(G-53 の足す物)。画面と API のイメージには SBOM を付けている(`deploy.yml` の `sbom: true`)が、それをライセンスの一覧として読める形にしていない。
  - ❔ 技術の負債の一覧(どこが重い・どこが1人しか分からない)は、キットの中に置き場が無い。`/checkup` の答えと週の振り返りから拾うのが候補。
- 📚 世の中では: 技術の DD は「全部見せる」より「聞かれた順に、根拠つきで、早く出せる」が信用になる。閲覧の期限つきの部屋に、出した版と日付を残す。届く脆弱性の中身・お客さんの名前・秘密は出さない(出すなら要旨と直す期限)。

## 15-4 「AI が書いたコードの権利は誰の物か」(A 社・DD の続き)

- 🧭 出資する側の顧問: 「コードの何割を AI が書いたか。AI が他の OSS を写していないとどう言えるか。AI の会社の約款で、出力の権利はどちらにあるか」。
- 判定: ❌ **数は出せるが、写しの確かめと説明が無い**(穴 G-87。10-10 の続き)。
  - ✅ AI が手伝った PR はラベル `ai:assisted` で数える(`ai-label.yml`・[../guides/metrics.md](../guides/metrics.md))。全部の PR は人がレビューして入る(危険度ごとの承認)。AI に依存を足させない(人が PR で)。
  - ❌ AI の出力が既存の OSS とほぼ同じかを見る検査が無い(機械では見つけにくい。10-10)。
  - ❌ 委託先の台帳に、AI の会社の約款で「出力の権利」「権利の主張を受けたときの補償」がどうなっているかの欄が無い(今は DPA と認証まで)。
  - ❔ AI が書いたコードに著作権が生じるか・誰の物かは国と事例で変わる。専門家に確かめる先の候補: 著作権法(AI の生成物の扱い)・AI の会社の商用の約款・OSS のライセンス(写した場合の条件)。
- 📚 世の中では: DD で問われるのは「AI を使ったか」ではなく「使い方を管理していたか」(使う道具の決まり・人のレビュー・ライセンスの検査・約款の確認)。数と管理の記録があると、AI の割合が高くてもそれ自体は減点されにくい。

## 15-5 事業の一部を別の会社に譲る(B 社・100人)

- 🏥 B 社の CEO: 予約の機能だけを、別の会社に事業ごと譲ることにした。お客さんの病院と、予約のデータと、担当のエンジニア3人が移る。
- 判定: ❌ **人の引き継ぎとリポジトリの移し方はあるが、会社をまたぐ道が無い**(穴 G-88)。
  - ✅ 人の出入り: [../runbooks/joiner-leaver.md](../runbooks/joiner-leaver.md)(アカウント・鍵・権限を外す)。リポジトリを組織に移す: [../runbooks/move-to-org.md](../runbooks/move-to-org.md)(移すと AWS への入口(OIDC の信頼)とアプリの連携が切れる、を書いている)。組織ごとの書き出しはある。
  - ❌ 一部の組織・一部の機能だけを別の会社の AWS に移す手順が無い(組織ごとの書き出しは「お客さんが持ち帰る」用で、別のシステムに入れ直す形ではない)。要配慮は組織ごとのデータ鍵で包んであり、鍵をどう渡すか・渡さずに入れ直すかを決めていない(ADR 0029)。
  - ❌ 引き継ぐ物の一覧が無い: AWS のアカウント(root・請求・連絡先)・ドメイン・Cognito の利用者(パスワードは持ち出せない前提で、利用者に再設定してもらうか)・KMS の鍵・秘密の差し替え・委託先の契約の名義・CODEOWNERS とラベル。
  - ❔ お客さんの個人データを譲り先に渡してよいか・お客さん(病院)と本人に何を知らせるかは、取り決めと法令で変わる。専門家に確かめる先の候補: 個人情報保護法(事業の承継に伴う提供・委託先の変更)・取り決めの「再委託・地位の移転」の条項・医療の業界のガイドライン。
