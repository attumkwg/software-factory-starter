# 手順書: 個人データが漏れた(かもしれない) — 委員会への報告と本人への通知

> 個人情報保護法の「漏えい等の報告」(法 26 条)。**期限は「知った日」から数える**。調べ終わるのを待たない。
> 来る所: [tenant-data-leak.md](tenant-data-leak.md)(他社のデータが見えた)・[secret-leak.md](secret-leak.md)(秘密が漏れて、お客さんのデータに触れられた疑い)・[incident.md](incident.md)(データに影響があった)。止血はそれぞれの手順書で先に。
> ここに書いたのは法令とガイドラインの**読み方の要点**。最後に決めるのは責任者と法務(専門家)。迷ったら「報告する」側に倒す(報告して対象外と分かっても困らない。出し遅れは困る)。

## 0. 最初にやる(知ってから1時間以内)

1. **知った日時を記録する**(期限の起点)。法人では「**どこかの部署が知った時点**」が起点で、責任者が知った時点ではない(ガイドライン 3-5-3-3・Q&A 6-24)。社員が気づいた・お客さんから知らされた・委託先から通知が来た、の最初の時刻。
2. 記録のファイルを作る: `docs/incidents/YYYY-MM-DD-<短い名前>.md`(形は [incident.md](incident.md) の 6。**「個人データの漏えい等」の欄を、振り返りを待たずに今から**埋めていく)。
3. 責任者と法務(いなければ外部の専門家)に「個人データの漏えい等の疑い」と伝える。
4. B2B のお客さんの利用者のデータなら、**お客さん(委託元)にすぐ知らせる**準備を始める(4 を見る)。

## 1. 何が漏れたかを特定する

漏れた(かもしれない)物を、**表と列の単位**で書き出す。分からない所は「おそれ」として広めに数える。

1. どの表・どの列か: ログ(`requestId`・`tenantId`)・監査ログ(`platform.audit_events`)・CloudTrail から、読まれた・持ち出された範囲を出す。
2. それぞれの列の区分を**分類表で引く**: `apps/api/src/db/classification.ts`(区分 public / internal / personal / sensitive)。**まだ無ければ** `docs/db/`(表ごとの説明書)の列を見て、下の目安で手で分ける。
3. 区分ごとに、2 の判定に使う:

| 区分 | このキットの例 | 判定での扱い |
|---|---|---|
| sensitive(要配慮の候補) | スキーマ `sensitive` の表の列(キットには要配慮の列は無い。足した機能の列)。値は組織ごとのデータ鍵で暗号化してある(ADR 0029) | **1件でも報告の対象**(2 の ①)。暗号文だけが漏れて、**データ鍵(KMS)が使われていない**なら、施行規則 7条の「高度な暗号化その他の個人の権利利益を保護するために必要な措置を講じたもの」に当たり、報告が要らない場合がある。CloudTrail で、その期間に要配慮の鍵を API のタスク以外が使っていないか・API のタスクの開いた数がふつうか(アラーム `…-sensitive-key-*`)を確かめ、**記録を付けて法務と決める**。鍵の役割が盗まれた疑いがあれば、暗号化は守りにならない(報告する側に倒す) |
| personal | `organizations.users` の `email`・`name`、`organizations.email_changes` の `previous_email`・`new_email`、`platform.outbox` の `payload`(送るメールの宛先) | 個人データ。2 の ②〜④ を見る |
| 自由に書ける文字 | `tasks.tasks` の `title`・`projects.projects` の `name`・`organizations.tenants` の `name` | 中身に何を書いたかはお客さん次第。**個人情報・要配慮個人情報が入っていないとは決めつけない**(委託元に確かめてもらう。こちらで中身を読み漁らない) |
| internal・public | ID・時刻・ロール・設定 | ふつうは個人情報に当たらないが、他の列と合わせて人が分かるなら personal として数える |

4. **人数**を数える: 漏れた行に出てくる人(`users.id` など)の重なりを除いた数。確定できなければ「最大で何人か」。

> 区分の決め方そのもの(例: 自由に書ける列を sensitive に寄せるか)は分類表の側で決める。ここでは引くだけ。

## 2. 報告が要るかを判定する

次の**どれか1つ**に当たれば、委員会への報告と本人への通知が要る(個人情報保護法施行規則 7 条)。**「おそれ」の段階でも対象**(漏れた確証が無くても、疑いがあれば当たる。ガイドライン 3-5-3-1)。

| # | 当たる事態 | 例 | 期限(確報) |
|---|---|---|---|
| ① | **要配慮個人情報**が入った個人データの漏えい等(**1件でも**) | 病歴・健康診断の結果・犯罪の経歴などが入った行 | 30日 |
| ② | 不正に使われると**財産的な被害**が出るおそれ | クレジットカード番号・送金や決済ができるサービスの ID とパスワード | 30日 |
| ③ | **不正の目的**による行為(外からの攻撃・社員の持ち出し)によるおそれ | 不正アクセス・ランサムウェア・社員が顧客の一覧を持ち出した。**これから DB に入れるつもりで集めている途中の情報**(入力フォームの盗み見など)も含む | **60日** |
| ④ | 本人の数が **1,000 人を超える** | 最初は 1,000 人以下でも、超えた時点で当たる。数が確定しなければ最大の見込みで | 30日 |

- ③ に当たれば、ほかに当たっても確報は **60日**。
- 「漏えい等」は、漏えい(外に出た)・滅失(無くなった)・毀損(壊れて使えない)の3つ。**誰にも見られないうちに全部取り戻した**ときは漏えいに当たらない(3-5-1-2)。
- **例外: 高度な暗号化**。データが高度な暗号で守られていれば、報告は要らない(3-5-3-1)。目安(Q&A 6-19): 電子政府推奨暗号リストや ISO/IEC 18033 などにある方式を正しく使っていて、かつ**鍵が漏れていない**(暗号の物と鍵を分けて守っている・遠隔で消せる・他人が鍵を使えない作り、のどれか)。
  - このキットでは DB とバックアップを保存時に KMS の鍵で暗号化している(`modules/aurora`・`modules/backup`)が、**アプリ経由・正しい接続での漏えいは、復号された中身が出る**ので例外に当たらない。例外に当たると判断するときは、必ず専門家に確認する。
- 4つのどれにも当たらないときも、委員会に**任意で報告できる**。社内の対応(調べる・範囲を決める・再発防止)は同じようにやる(3-5-2)。判定の理由を記録に残す。

## 3. 期限

| 何を | いつまでに | 中身 |
|---|---|---|
| **速報** | 知った時点から**おおむね3〜5日以内**(規則 8 条 1 項「速やかに」。3-5-3-3) | その時点で分かっていることだけでよい |
| **確報** | 知った日から **30日以内**(③ は **60日以内**)(規則 8 条 2 項。3-5-3-4) | 下の (1)〜(9) を全部。分からない所は分かった分を書き、分かりしだい足す |
| 本人への通知 | 事態の状況に応じて**速やかに**(規則 10 条) | 5 を見る |

- **数え方**: 知った日を **1日目**に数える。**土日・祝日も数える**。最後の日が土日・祝日・年末年始(12月29日〜1月3日)なら、その翌日まで(3-5-3-4)。例: 4月1日に知った → 30日目は4月30日、60日目は5月30日。
- 速報で全部を書ければ、1回で速報と確報を兼ねられる。

**報告に書くこと**(規則 8 条 1 項):

1. 概要(起きた日・気づいた日・何が起きたか・誰が見つけたか・①〜④のどれか・委託元と委託先の有無・経過)
2. 漏れた(かもしれない)個人データの項目(媒体・種類も)
3. 本人の数
4. 原因(誰のところで起きたか)
5. 二次被害(のおそれ)の有無と中身
6. 本人への対応の状況
7. 公表の状況
8. 再発防止(やったこと・これからやること)
9. その他

## 4. 誰が出すか(B2B の分担)

このキットで作る SaaS では、データが2種類ある:

| データ | 例 | 報告する人 |
|---|---|---|
| **お客さんの業務のデータ**(お客さんが入れた物・お客さんの社員の情報) | タスク・プロジェクト・利用者の名前とメール | **多くの場合、お客さんが「委託元」・自社が「委託先」**。法律上は**両方**に報告と通知の義務がある(3-5-3-2) |
| **自社が自分の目的で集めた物** | 契約・請求の担当者の連絡先・問い合わせ | **自社**が報告する |

委託先(自社)の動き:

1. **お客さん(委託元)にすぐ知らせる**。期限は**取り決めの期限が先**(既定は知ってから3日以内。[legal/data-processing.md](../legal/data-processing.md))。法の目安は知ってから3〜5日以内(規則 9 条・3-5-3-5)。その時点で分かっている (1)〜(9) を渡す。
2. 委託元に知らせれば、**自社の報告と本人への通知の義務は無くなる**(法 26 条 1 項ただし書・2 項。3-5-3-5・3-5-4-1)。そのかわり、委託元の報告と調べ物に協力する。
3. 委託元は、遅くとも自社から知らされた時点で「知った」ことになり、そこから委託元の期限が始まる。
4. 自社と委託元の**連名**で報告してもよい(3-5-3-2)。
5. 何社ものお客さんにまたがるときは、**お客さんごとに**知らせる(他社の名前・他社のデータは伝えない)。

> ⚠️ 自社が「委託先」か(個人データを**取り扱う**立場か)は、契約と実際の作りで決まる。クラウドの提供者でも、契約で個人データを取り扱わないことになっていれば委託先に当たらない場合がある(Q&A 7-53・6-22)。このキットにはサポートの代理ログイン([support-access.md](support-access.md))があり、社員が中身を見られるので、**委託先として扱う前提**で書いている。自社がどちらかは、**専門家に確認**して契約に書いておく([data-retention.md](../guides/data-retention.md) の 4)。
> ⚠️ 何社ものお客さんのデータが漏れたときに、④ の 1,000 人をお客さんごとに数えるか、自社の分を合わせて数えるかは、ガイドラインで確かめきれていない。**専門家に確認**する(迷ったら合わせた数で 1,000 人を超えるかを見て、報告する側に倒す)。

## 5. 本人への通知

- **いつ**: 事態の状況に応じて**速やかに**(規則 10 条)。ただし、通知すると被害が広がる(例: ネットに出た物の削除を頼んでいる途中)・まだほとんど分かっておらず混乱させるだけ、のときは、そうでなくなってから(3-5-4-2)。全部が分かるまで待つ必要はない。
- **誰が**: 委託先(自社)は、委託元に知らせればこの義務も無くなる。B2B ではふつう**委託元が自分の利用者に通知**し、自社は文面や対象者の一覧づくりを手伝う。
- **何を書くか**(規則 10 条。報告の (1)(2)(4)(5)(9)): 概要・漏れた項目・原因・二次被害(のおそれ)・その他(問い合わせ先・本人にしてほしいこと)。
- **どうやって**: 本人に直接届く方法で(メール・郵便など。決まった様式は無い。3-5-4-4)。
- **通知が難しいとき**(連絡先が無い・古い。法 26 条 2 項ただし書・3-5-4-5): 代わりに、**公表**するか、**問い合わせの窓口を作って公表**し、本人が「自分が対象か」を確かめられるようにする。公表の中身は通知と同じ。
- 最初は対象と判断したが、後で対象外と分かったときは、通知は要らない(3-5-4-3)。

**通知の型**(委託元が利用者に出す想定。自社が出すときは「当社が提供する」を消す):

> 件名: 個人情報の漏えい(のおそれ)についてのお知らせとお詫び
>
> {お客さんの名前}をご利用の皆さまへ
>
> {年月日}、当社がサービスの提供を委託している {サービス名} において、皆さまの個人情報が外部に漏えいした(おそれがある)ことが分かりました。ご迷惑とご心配をおかけし、深くお詫び申し上げます。
>
> 1. 概要: {いつ}から{いつ}の間、{何が起きたか(事実だけ)}。{いつ}に分かり、{止めた方法}により現在は止まっています。
> 2. 漏えいした(おそれがある)情報: {項目。例: お名前・メールアドレス}。{含まれない物。例: パスワードは含まれていません}
> 3. 原因: {分かっている範囲で。推測は書かない}
> 4. 二次被害(のおそれ): {例: 現時点で、不正な利用は確認されていません}
> 5. お願い: {例: 心当たりのないメールに記載されたリンクを開かないでください}
> 6. お問い合わせ: {窓口・受付時間}
>
> 今後、分かったことがあれば改めてお知らせします。

- 書かない物: 他社の名前・他の人の情報・内部の仕組みの名前・原因の推測([incident.md](incident.md) の 4 と同じ)。

## 6. 出し方

1. **報告先を確かめる**: 原則は個人情報保護委員会。ただし業種によっては、報告を受ける権限が**事業を所管する省庁に委任**されていて、そちらに出す(期限は同じ)。委任先は毎年見直されるので、**出す前に毎回**「権限の委任」のページで確かめる。社員の情報(雇用管理)・株主の情報は委員会へ。
2. **委員会の報告フォーム**(オンライン)から出す。Word の様式は下書き用で、提出には使わない。速報も確報もフォームから。
3. 出した日時・受付の番号・出した中身の写しを記録(下の 7)に残す。
4. ランサムウェアなどのサイバー攻撃のときは、フォームとは別の共通の様式(Excel・メールで出す)がある。委員会のページで確かめる。

## 7. 記録の欄

[incident.md](incident.md) の 6 の形の「個人データの漏えい等」の欄を使う。**知った日時を最初に書き、期限の日を計算して書いておく**(3 の数え方)。速報・確報・委託元への連絡・本人への通知を出したら、その日時を足していく。
