# 手順書: リポジトリを組織に移して、マージキューを使う

> **いつ**: PR が直列に詰まる(1本マージするたびに、ほかを main に追いつかせて CI を流し直す)ようになったら([guides/ci-speed.md](../guides/ci-speed.md))。人が増えて、チームで権限を持ちたくなったら。
> **キット自身は移さない**(この手順はキットから作ったリポジトリのため)。
> **戻しにくい操作**(移すと AWS への入口・アプリの連携が切れる)。2人で、デプロイを止めてから。設計書 [0051](../designs/0051-move-to-org.md) の U-1。
> GitHub の仕様は 2026-10-25 に公式の文書で確かめた。変わるので、移す前に公式で確かめ直す。

## 0. 先に決める

| 決めること | 既定 | なぜ |
|---|---|---|
| 移す先の組織 | 新しく作る(会社の名前) | 個人のアカウントに残すと、辞めたときに持ち主が個人になる |
| 組織のプラン | 公開のリポジトリなら Free でよい。**非公開のリポジトリでマージキューを使うなら Enterprise Cloud**(2026-10-25 時点。公開の組織のリポジトリはどのプランでも使える) | 非公開のリポジトリでは、プランで使える守りが変わる(Free の組織ではブランチの守りが使えない・Environments の承認者は上のプランが要る)。今と同じ守りが組織でも使えるかを、点検の `gh-plan` と公式の文書で確かめてから移す |
| 移す日 | デプロイと移行を止められる日 | 移した直後から、AWS への入口(OIDC)が通らなくなる(下の 1 の表) |
| 組織の人 | 今の共同作業者を組織のメンバーに・チームを作る | 移すと、共同作業者は組織の外の人のまま残る |

## 1. 移す前に洗う物

| 物 | 移すと | やること | いつ |
|---|---|---|---|
| **AWS への入口(OIDC の信頼の条件)** | 役割の信頼が `repo:<古い持ち主>/<名前>:…` なので、**全部の役割が引けなくなる**(デプロイ・plan・プレビュー・費用・証跡・試作) | Terraform の変数 `github_repository`(`envs/stg`・`envs/prod`・`envs/preview/base`・`envs/preview/prototypes`)を新しい名前にして apply(人。危険度「高」) | 移した直後(デプロイを止めている間) |
| URL・リモート | GitHub が古い URL から新しい URL へ転送する(同じ名前のリポジトリを古い場所に作ると転送が消える) | 手元は `git remote set-url origin <新しい URL>`。文書の中の持ち主の名前を `grep` で探して直す | 移した後 |
| `.github/setup.yml` の `template_repository` | キットから作ったリポジトリなら変えない(キットの名前を指す) | 確かめるだけ | — |
| 秘密・変数(Actions・Environments) | リポジトリに付いたまま移る(公式の文書) | 移す前に名前の一覧を控え(`gh secret list`・`gh variable list`・`gh secret list --env stg` など)、移した後に同じか見る。値は見えない・控えない | 前と後 |
| Environments | 設定ごと移る。承認者 `@me` は人に結び付いている | 移した後に `pnpm setup:github` で差分を見て `--apply`(承認者を組織の人に) | 移した後 |
| ルールセット・必須のチェック | リポジトリの設定ごと移る。組織の側のルールセットが足されることがある | `pnpm setup:github` で差分を見る(組織のルールセットはここに出ない。組織の設定で見る) | 移した後 |
| **Actions の設定** | 組織の決まり(使ってよい Action・既定の権限・SHA の固定)が**リポジトリの設定より強い** | 組織の Settings → Actions を、`setup.yml` の `actions` と同じかそれより厳しく(SHA で固定した Action だけ・既定は読むだけ・Actions に PR の承認をさせない) | 移す前(組織を作ったとき) |
| **Renovate**(GitHub App) | 個人のアカウントに入れた App は付いてこない | 組織に Renovate の App を入れ、このリポジトリを選ぶ。個人の側から外す | 移した後 |
| ほかの GitHub App(Claude・Slack など) | 同じく付いてこない | 組織に入れ直す。委託先の台帳は変わらない(同じ会社) | 移した後 |
| Webhook・デプロイの鍵 | 付いたまま移る | 確かめるだけ | 移した後 |
| CODEOWNERS | 人の名前のまま。人が組織にいないと効かない | 組織のチーム(`@<組織>/<チーム>`)に置き換える PR(危険度「高」) | 移した後 |
| 点検の台帳の担当者 | 人の名前のまま | そのままでよい(人が同じなら)。`pnpm checkup:adopt --by` は要らない | — |
| 費用のページ・証跡の取り込み | AWS の役割経由なので、上の OIDC を直せば戻る | 次の定期の実行が通るか見る | 移した後 |

## 2. 移す日の手順(2人で)

1. 前の日: 上の表の「移す前」をやる。今の設定を控える(`pnpm setup:github` の差分の出力・秘密と変数の名前の一覧・入れている App の一覧)。
2. マージとデプロイを止める(開いている PR の自動マージを外す。`deploy.yml` を流さない)。
3. GitHub の Settings → General → Danger Zone → Transfer で、組織へ移す(持ち主の権限が要る。人がやる)。
4. 手元のリモートを直す。
5. Terraform の `github_repository` を直し、stg → prod の順に apply(人。危険度「高」)。プレビューと試作の env も。
6. Renovate とほかの App を組織に入れる。
7. `pnpm setup:github` で差分を見て `--apply`(Environments の承認者・ルールセット)。
8. 確かめる: 文書だけの PR を1本出して CI が全部通る → main へのマージで stg へのデプロイが通る → 次の週の Renovate の PR が来る。
9. マージとデプロイを戻す。CODEOWNERS をチームにする PR を出す。

## 3. マージキューを入れる

組織のリポジトリ(公開か、非公開なら Enterprise Cloud)で:

1. **必須のチェックがキューの中でも流れるか**: キューは `merge_group` の出来事でワークフローを動かす。キットの `ci.yml`・`vrt.yml` は入っている。必須のチェックにほかのワークフローのジョブを足していたら、そのワークフローにも `merge_group:` を足す(`.github/**` は危険度「高」)。
2. **キューの中で流れないチェックを、必須から外す**: 「取り組みと作業の種類(PR の本文)」は PR の本文を見るので、キューの中では流れない(`setup.yml` の `required_checks` の注のとおり)。外す PR を出し、マージの後に `pnpm setup:github --apply`。
3. Settings → Rules → Rulesets → `main` に「Require merge queue」を足す(画面から。`pnpm setup:github` はキットが扱わない規則を消さずに残す)。既定の案(設計書 0051 の 6): マージの方法 squash・同時に流す数 5・1回にまとめる数 最大5・「失敗した PR は入れない」をオン・チェックの待ち 60分。
4. `setup.yml` の `strict`(最新に追いついてから)を `false` に(キューが最新の main に重ねて確かめるので要らない)。PR → `--apply`。
5. 自動マージ(`allow_auto_merge`)はそのまま。人が「マージ」を押すと、キューに並ぶ。
6. 1週間、キューの待ち時間と、キューで落ちた数を見る。落ちる PR が多ければ「1回にまとめる数」を下げる。

- ジョブを速くするこつ(文書だけの PR で重いジョブを省く等)は [guides/ci-speed.md](../guides/ci-speed.md)。キューの中(`merge_group`)では全部流す。

## 4. 困ったとき

| こんなとき | どうするか |
|---|---|
| 移した後、デプロイ・plan が `Not authorized to perform sts:AssumeRoleWithWebIdentity` | OIDC の信頼の条件が古い名前のまま。2 の 5 |
| Actions が「この Action は許されていない」 | 組織の Actions の決まり。1 の表の「Actions の設定」 |
| Renovate の PR が来ない | 組織に App が入っていない・リポジトリを選んでいない |
| キューから PR が外れ続ける | 必須のチェックに `merge_group` で流れない物がある(3 の 1・2) |
| 移したのを戻したい | 同じ手順で逆に移す(OIDC・App・承認者もやり直し)。古い場所に同じ名前のリポジトリを作らない(転送が消える) |
