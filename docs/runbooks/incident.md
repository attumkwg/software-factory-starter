# 手順書: 障害対応の型

> **利用者が困っている(か、困りそう)なら、それは障害。** 迷ったら宣言する(宣言して何も無かった、は損にならない)。
> 原因を探すより先に**止血**(戻す・止める)。直すのは落ち着いてから。終わったら必ず**振り返り**。
> 個別の手順: アラーム [alarms.md](alarms.md) / Sentry [sentry.md](sentry.md) / DB を戻す [db-restore.md](db-restore.md) / デプロイ・移行を戻す [deploy-rollback.md](deploy-rollback.md) / 秘密が漏れた [secret-leak.md](secret-leak.md) / 他社のデータが見えた [tenant-data-leak.md](tenant-data-leak.md) / 個人データが漏れた(委員会への報告・本人への通知)[personal-data-breach.md](personal-data-breach.md) / 攻撃を受けている(総当たり・大量のアクセス・API の悪用)[attack.md](attack.md)

## 1. 重さを決めて、宣言する(最初の5分)

| 重さ | 例 | 誰を呼ぶ | お客さんへの知らせ |
|---|---|---|---|
| **S1** | 全員が使えない・データが消えた・**他社のデータが見えた**・秘密が漏れた | 全員(夜中でも) | 30分以内に1報、以後1時間ごと |
| **S2** | 一部の機能・一部の会社が使えない・とても遅い | 担当の領域の人 | 1時間以内に1報 |
| **S3** | 回り道がある・見た目の崩れ・stg だけ | 次の営業時間に | 要らない(直したらリリースノート) |

宣言は Slack の `#incident` に1行: **「S2 宣言: タスクの完了が保存できない(10:05〜)。指揮は @誰」**。スレッドを立て、以後のやり取りは全部そこに書く(後で時系列になる)。

## 2. 役割(小さなチームでは1人が兼ねてよい。ただし指揮だけは決める)

| 役割 | やること | やらないこと |
|---|---|---|
| **指揮** | 重さ・止血の方法・知らせの判断を決める。15〜30分ごとに「いまどこ」をスレッドに書く | 自分で深く調べ込む(全体が見えなくなる) |
| **調べる・直す** | 手順書で原因を絞る・戻す・直す。やったことを都度スレッドに | 黙って本番を触る(誰が何をしたか分からなくなる) |
| **知らせる** | お客さん・社内への文面を出す(下の型) | 原因の推測を外に出す |

- AI(Claude Code)に一次調査を任せてよい: 「この requestId のログと、直前のデプロイの差分を読んで、原因の候補を3つ」。**本番に書き込む操作は人が打つ**。
  - 本番のログは人が出して貼る(AI は本番に入れない)。**貼るのは ID と集計まで**: 許可リストの項目(requestId・tenantId・userId・route・status・err.type)と件数。名前・メールアドレス・題名・本文・本番の画面のスクショ・要配慮は貼らない。急いでいても同じ([compliance/ai-data.md](../compliance/ai-data.md)。項目を決めたクエリはその 2)。
  - **要配慮個人情報は AI に渡さない**: スキーマ `sensitive` の表の中身(暗号文も)・復号した値・データ鍵・要配慮の接続(`sensitive-database-url`)。DB の行を写して貼らない。要配慮の事故の調べは、人が CloudTrail と件数で進め、AI には組織・利用者の ID と鍵の利用の記録の形(誰が・いつ)だけを渡す。要配慮の件数も渡さない(docs/security.md の AI-6・ADR 0029・[compliance/ai-data.md](../compliance/ai-data.md))。

## 3. 止血(原因が分からなくても、先に)

上から順に検討する:

1. **直前に何か変えたなら、戻す**: デプロイ → [deploy-rollback.md](deploy-rollback.md)。Terraform の apply → 前の状態に apply し直す。設定の変更 → 元に戻す。
2. **壊れている機能だけ止める**: 機能フラグの裏の機能なら、定義の状態を `off` にする PR をデプロイ(全部の組織で止まる。[feature-flags.md](feature-flags.md)・`docs/guides/feature-flags.md`)。フラグの無い機能は、その画面のボタンを隠す小さな修正。
3. **全体を止める(メンテナンス)**: データが壊れ続ける・他社のデータが見える、のように「動かしている方が悪い」とき。WAF で止める:
   - WAF のコンソール → Web ACL `<名前>`(例 `sfs-prod`)→ ルール → 「ルールを追加」→ 自分で作るルール: 「すべてのリクエスト」(条件 `URI path` が `/` で始まる)→ 操作「Block」→ カスタムの応答 **503**・本文「ただいまメンテナンス中です。復旧までしばらくお待ちください」→ **優先度を一番上**に。
   - 自分たちだけ通すなら、その前に「社内の IP なら Allow」のルールを置く。
   - 解くときはルールを消す。Terraform の外で足したルールは、次の `terraform apply` でも消える(足している間は apply しない)。
4. **負荷で落ちているなら、増やす**: ECS の台数・Aurora の `max_acu`(Terraform。急ぐならコンソールで変えて、あとで Terraform をそろえる)。

## 4. お客さんへの知らせ(型)

- **事実だけ。推測・言い訳・原因の決めつけは書かない。** 時刻は日本時間。
- 個人情報・他社の名前・内部の仕組みの名前(DB・AWS のサービス名)は書かない。
- **稼働状況のページがあれば、同じ文をそこにも載せる**(S1・S2。メールとページで違うことを書かない)。他社のデータが見えた・個人データの事故はページに書かない([guides/status-page.md](../guides/status-page.md) の 4)。

**第1報**(S1 は30分以内):

> 【障害】{サービス名}で、{何時何分}ごろから {何ができない}(例: タスクの保存ができない)状態になっています。現在、原因を調べて復旧に向けて対応しています。次のお知らせは {何時}ごろにします。ご不便をおかけして申し訳ありません。

**続報**:

> 【障害・続報】{何ができない}状態は続いています。{わかったこと・やっていること}(例: 直前の更新を取り消して様子を見ています)。次のお知らせは {何時}ごろにします。

**復旧**:

> 【復旧】{何時何分}に復旧しました。{影響}(例: {何時}〜{何時}の間、タスクの保存ができませんでした。この間に保存できなかった変更は、お手数ですがもう一度お願いします)。原因と再発防止は、まとまり次第お知らせします。

**データに影響があったとき**(戻した・消えた・他社に見えた)は、個別の連絡が要るかを指揮が決める(他社のデータが見えたときは [tenant-data-leak.md](tenant-data-leak.md) の連絡の手順。法律・契約上の期限がある)。**個人データが漏れた・無くなった・壊れた(かもしれない)とき**は、[personal-data-breach.md](personal-data-breach.md) で個人情報保護委員会への報告と本人への通知が要るかを判定する(速報は知ってから おおむね3〜5日)。

## 5. 終わり方

- 復旧を確かめる: アラームが OK に戻った・Sentry の件数が止まった・外形監視が緑・お客さんの報告の操作を自分でやってみた。
- 稼働状況のページに復旧の文を載せ、状態を戻す([guides/status-page.md](../guides/status-page.md))。
- 指揮がスレッドに「解決」と書く。**一時的にやったこと**(WAF のルール・手で変えた台数・横に置いた DB)の片付けを Issue にする。

## 6. 振り返り(S1・S2 は必ず。5営業日以内)

**誰が悪いかではなく、仕組みのどこが通したか**を書く。下の形で `docs/incidents/YYYY-MM-DD-<短い名前>.md` に残す(記録なので、書いた後は直さない)。

```markdown
# YYYY-MM-DD <何が起きたか>

- 重さ: S1 / S2
- 影響: 何時〜何時・どの機能・何社 / 何人(Sentry の Users・ログで数える)
- 指揮: @
- SLA: 外から開けなかった・全員が使えなかった時間(何時〜何時・何分)/ 原因の区分(自社・外のサービス・外のサービスの大規模な障害・お客さんの側・計画メンテナンス・緊急の保守)。**指揮が書いた物が SLA の事実の正**([legal/sla.md](../legal/sla.md) の 3・7)

## 時系列(日本時間)
- 10:05 アラーム `<名前>` が鳴る
- 10:08 S2 を宣言
- 10:20 直前のデプロイを戻す → 10:31 復旧

## 個人データの漏えい等(個人データが絡むときだけ。知った時点で書き始める)
<!-- 期限は personal-data-breach.md の 3。知った日を1日目に、土日・祝日も数える -->
- 知った日時: YYYY-MM-DD HH:MM(どの部署が・何で知ったか)
- 漏れた物: 表・列 / 区分(personal・sensitive)/ 人数(最大の見込み)
- 判定: 要配慮 / 財産的被害 / 不正の目的 / 1,000人超 / 当たらない(理由: )/ 高度な暗号化の例外(専門家の確認: )
- 自社の立場: 委託先(委託元は何社か。社名はここに書かず責任者の控えに)/ 自分で集めたデータ
- 委託元へ知らせた日時: (目安 知ってから3〜5日)
- 速報: 期限の目安 YYYY-MM-DD / 出した日時・受付の番号:
- 確報: 期限 YYYY-MM-DD(30日。不正の目的は60日)/ 出した日時・受付の番号:
- 本人への通知: 出した日時・方法 / 通知が難しい場合の代わり(公表・窓口):

## 何が起きたか
<仕組みとして。人の名前を主語にしない>

## なぜ気づけた / 気づくのが遅れたか
## なぜ止められなかったか(テスト・レビュー・検査・アラーム)

## 再発防止(どれにするかを必ず決める)
| 足す物 | 中身 | Issue |
|---|---|---|
| テスト | | |
| アラーム・見張り | | |
| ルール(CLAUDE.md・Semgrep・スキル) | | |
| 手順書 | | |
```

- 再発防止は「気をつける」で終わらせない。**テスト・アラーム・ルール・手順書のどれか**に変える(AI が同じ失敗をしない形に)。
- 手順書の通りに動けなかった所は、その手順書を直す。
