## 1. 見せ方: 魅力を ROI で見せる

> 使う人が最初に知りたいのは「自分に何が手に入って、いくらかかって、元が取れるか」。守りの細かさや部品の一覧(75件)は、その後でいい。

### ROI の見せ方

| | 中身 | 見せ方の例(数は作るときに確かめる) |
|---|---|---|
| 得: 作らずに済む物 | 会社向け SaaS で、どの会社も最初に作る物(他社のデータの分離・招待・権限・SSO・監査ログ・プラン・CI/CD・Terraform・監視) | 「自分で作れば ◯人月の土台が、clone した日から動く」 |
| 得: 速さ | 1行で頼むと、AI が仕様から PR まで。人はマージを決めるだけ | 「1件で人が呼ばれるのは、頼む・答える・マージの3回」 |
| 得: 避けられる事故 | 他社のデータが見える・AI が本番を壊す・鍵が漏れる | 「よくある事故を、仕組みで止める」(事例つき) |
| 得: 決めてから作る | ペルソナの合議で KPI を絞り、外れたらやめる | 「作ってから要らなかった、を減らす」 |
| 費用 | 手元と試作は0円・検証の環境 約2.2万円〜・本番 約8万円〜・覚える時間(最初の30分・1週間) | 「試すのは0円。本番は月8万円から」 |

- **一番上の2行で ROI が言える**ようにする(例: 「会社向け SaaS の土台 ◯人月ぶんを、試すのは0円・本番は月8万円から。作るのは AI、決めるのはあなた」)。
- 数は **【実測】**(キットの中で測った: テスト件数と時間・E2E の一周・キット自身を1人+AI で作った日数とコミット数)と **【目安】**(自分で作ったら何人日か)を分けて書く。目安には根拠(部品ごとの規模・公開の事例)を添える。
- 💡 見本: 今の [one-pager.md](one-pager.md) の「効果の見込み」と「費用」。これを README の頭に持ってきて、魅力の順に並べ直す。

### README の頭の並び

| 順 | 見出し | 中身 | 長さの目安 |
|---|---|---|---|
| 1 | 一言 | 何が手に入って、いくらで済むか(ROI の2行) | 2行 |
| 2 | 誰のためか | 1〜3人で会社向け SaaS を始める人。持ち帰る考え方は、AI の導入を支援する人・新規事業の EM にも | 3行 |
| 3 | できることのカタログ | 作る流れの順に、1行ずつ「何が楽になるか」「自分で作ると(目安)」「試し方」 | 15〜25行 |
| 4 | 5分で見る | 手元で動かして、カタログの頭の3つを目で見る(AWS も鍵も要らない)。後で GIF | 10行 |
| 5 | できないこと・確かめていないこと | G-129。短く。代わりにどうするか・穴の番号 | 10行 |

- 状態は、動く(手元のテストか E2E で確かめた)/ 型まで(使う側でつなぐ・決める)の2つ。確かめていない物は 5 へ。

1. あなたはソフトウェアファクトリーですか(依頼をブレイクダウンして、週100〜200本の PR に流し、完成まで導けるか)

### 工場(キット自身)の KPI(持ち主 2026-10-29)

> 持ち主「はい、それがいいと思います。それで進めてください」。測れない所は推測で埋めず「まだ」と書く。

| 種類 | 指標 | 数え方 | いま |
|---|---|---|---|
| ⭐ 北極星 | 意義があると判断した物が、使う人に届いて使われた数 ÷ 人の工数(人の1時間あたりに、使われる物をどれだけ届けたか) | 分子: 意義の判断役が「やる・条件つき」とした記録(`docs/product/verdicts/`・`docs/kit/verdicts/`)のうち、賭けが adopted になり、KPI の記録が見込みに届いた(`pnpm kpi` の「当たり」)数。分母: `docs/cost/people.yaml` の人の時間 | まだ |
| 入力(毎週いちばん目に見る) | 無人化率(1 − 人が使った工数の割合) | `pnpm metrics` の人の介在率と `docs/cost/people.yaml` の分数 | キット自身の13日で 約78〜86%【推定】([roi.md](roi.md) の 2)。週ごとは 2026-10-30 から |
| 入力 | 依頼から届くまでの日数 | 親 Issue を開いた日から受け入れまで(6 の 4 の管制で数える) | まだ |
| 🛡 守り | 事故(他社のデータ・鍵・本番)0件 | `docs/incidents/` の記録 | まだ数えていない |
| 🛡 守り | センサーが正しいかの判定が回っていること | 期限を過ぎて「人の判定」が未定の記録の数(`pnpm kpi`)・守る場所(センサー)を変えた PR に人が答えた数 | まだ |

- 無人化率は、ほかのソフトウェアファクトリーでも「それぐらいでしか測れない」から出されている数。測りやすいが、作る側の効率の数。**一番にすると「人の判断を飛ばす」圧がかかる**ので北極星にしない。人に残すのは、センサーの判定と、決めなければならない所に答える2つ。
- 「使われたか」は数週間しないと分からないので、毎週見る数は無人化率、北極星はその先、の二段にする。
- 意義の判断役の当たり外れは、北極星の分子(届いて使われた)と同じ記録を使う。最初の判断は [verdicts/2026-10-29-publish.md](verdicts/2026-10-29-publish.md)(条件つき: 公開の条件は 6 の1〜6 だけで、判断では足さない。北極星は公開の後に、使う人に届けた外のチームの数で測る)。
- 測れるようにするのは 6 の 2(人の出番)・3(重さを削る)・6(資産と ROI)の中で。

- 公開の後は「ROI が当たったか」を見る: 使ってみた人が、カタログの何を使って、何日ぶん浮いたと言ったか(報告と Issue)。外れた行は直す。
- **合議は見せ方の判定には使わない**。機能開発のレビュー(仕様・PR・受け入れ)では `/council` を任意の参考に使う(既定は反論役1人の軽い形。仕様 0084)。

## 6. 人の出番を極限まで絞る(持ち主 2026-10-29)

> 「人のレビューは極限まで絞るべき。人が判断するのは、サイクルを回すときのセンサーが正しいかの判定と、人が決めなきゃいけない所に端的に答えられること」

- **公開の前に、下の1〜6 を全部「できるはず」まで入れる**(持ち主 2026-10-29)。
- **人が見るのはセンサーと決めることだけ**。コードそのものはセンサー(テスト・型・検査・E2E・計測)が確かめる。人は、センサーを変える PR(テスト・守るパス・KPI の定義・計測)が正しいかを判定し、戻せない判断・お金と契約・顧客への連絡・鍵には端的な問い(1問1行・選択肢つき)で答える。
- **合議は判断の参考**(持ち主「重くなりすぎ。この遅さだと判断の参考ぐらいにしかならない」)。必須の関所にしない。2026-10-29 の合議で本当に効いた指摘は反論役1人から出たので、残すのは**任意の反論役1人**。
- 人に端的に聞く問いは、1件の依頼で多くても2問(多いと形だけの承認に戻る)。
