## 1. 見せ方: 魅力を ROI で見せる

> 使う人が最初に知りたいのは「自分に何が手に入って、いくらかかって、元が取れるか」。守りの細かさや部品の一覧(75件)は、その後でいい。

### ROI の見せ方

| | 中身 | 見せ方の例(数は作るときに確かめる) |
|---|---|---|
| 得: 作らずに済む物 | 会社向け SaaS で、どの会社も最初に作る物(他社のデータの分離・招待・権限・SSO・監査ログ・プラン・CI/CD・Terraform・監視) | 「自分で作れば ◯人月の土台が、clone した日から動く」 |
| 得: 速さ | 1行で頼むと、AI が仕様から PR まで。人はマージを決めるだけ | 「1件で人が呼ばれるのは、頼む・答える・マージの3回」 |
| 得: 避けられる事故 | 他社のデータが見える・AI が本番を壊す・鍵が漏れる | 「よくある事故を、仕組みで止める」(事例つき) |
| 得: 決めてから作る | ペルソナの合議で KPI を絞り、外れたらやめる | 「作ってから要らなかった、を減らす」 |
| 費用 | 手元と試作は0円・検証の環境 約2.2万円〜・本番 約8万円〜・覚える時間(最初の30分・1週間) | 「試すのは0円。本番は月8万円から」 |

- **一番上の2行で ROI が言える**ようにする(例: 「会社向け SaaS の土台 ◯人月ぶんを、試すのは0円・本番は月8万円から。作るのは AI、決めるのはあなた」)。
- 数は **【実測】**(キットの中で測った: テスト件数と時間・E2E の一周・キット自身を1人+AI で作った日数とコミット数)と **【目安】**(自分で作ったら何人日か)を分けて書く。目安には根拠(部品ごとの規模・公開の事例)を添える。
- 💡 見本: 今の [one-pager.md](one-pager.md) の「効果の見込み」と「費用」。これを README の頭に持ってきて、魅力の順に並べ直す。

### README の頭の並び

| 順 | 見出し | 中身 | 長さの目安 |
|---|---|---|---|
| 1 | 一言 | 何が手に入って、いくらで済むか(ROI の2行) | 2行 |
| 2 | 誰のためか | 1〜3人で会社向け SaaS を始める人。持ち帰る考え方は、AI の導入を支援する人・新規事業の EM にも | 3行 |
| 3 | できることのカタログ | 作る流れの順に、1行ずつ「何が楽になるか」「自分で作ると(目安)」「試し方」 | 15〜25行 |
| 4 | 5分で見る | 手元で動かして、カタログの頭の3つを目で見る(AWS も鍵も要らない)。後で GIF | 10行 |
| 5 | できないこと・確かめていないこと | G-129。短く。代わりにどうするか・穴の番号 | 10行 |
| 6 | 始め方・部品の一覧・費用の内訳 | 今の README の中身(部品の表は折りたたんだまま) | 今のまま |

- カタログの行は**使う人の得**で書く(「RLS」ではなく「他社のデータが見えない。自分で作ると ◯日」)。部品の名前は「試し方」に寄せる。
- 状態は、動く(手元のテストか E2E で確かめた)/ 型まで(使う側でつなぐ・決める)の2つ。確かめていない物は 5 へ。

## 2. できないこと・確かめていないこと(カタログの後に短く)

- できないこと: 部品だけを既存のリポジトリに持ち帰る道(G-51)・AWS や GitHub 以外への入れ替え(G-55)・保守の約束(MIT・無保証)。
- 1人の間は: 本番の承認も自分1人(G-64)・前の版に戻すのは `aws` のコマンド(G-65)・1人分の削除は手順書で(G-06)。AI のマージは既定でオフ。
- 確かめていないこと: 本物の AWS の上(G-120)・クラウドで Slack から頼む道(使う側でつなぐ)。

## 3. 道のり

| 段 | やること | 終わりの合図 | 目安 |
|---|---|---|---|
| ① カタログ | README の頭を 1 の順に作り直す(G-128)。one-pager を合わせる | 頭の2行で ROI が言え、カタログの全部の行に「得」と「試し方」がある | 10-30〜11-04 |
| ② できないこと | 2 を1か所に(G-129)。AWS で確かめていない物の一覧(G-120) | 散らばった「まだ」がそこを指す | 11-03〜11-06 |
| ③ 公開の形 | 依存のライセンスの一覧(G-108)・v0.1.0 と CHANGELOG・公開してよいかの点検 | 外に出して困る物が無い | 11-05〜11-12 |
| 🚀 公開 | リポジトリを公開する(持ち主が自分で) | — | 11-15(予備 11-22) |
| ④ 外の人の声 | 記事の1本目(魅力と ROI を軸に)。Issue と報告を見る | 外の人の1件目 | 公開の後 |

- ① が最初: 何を魅力として見せるかが決まれば、② の量も ③ の点検の範囲も決まる。② と ③ は触るファイルが違うので、並べて進めてよい。
- **穴埋めは別に並べて回す**(「使える前に」の小さい物から)。済んだら、カタログの状態を「型まで」→「動く」に上げる。
- 公開してよいかの点検: 秘密情報・個人や会社が分かる記述・キットの外の話・見本の題材が架空と分かるか。

## 4. 判定の物差し(ROI)

| 種類 | 指標 | 数え方 | 線(公開の前) |
|---|---|---|---|
| ⭐ 北極星 | 頭の2行で ROI が言えるか | 得(作らずに済む人月・速さ)と費用(月の額)が数で書けている | 言える |
| 入力 | カタログの行のうち「得」と「試し方」がそろった割合 | カタログの表を数える | 100% |
| 入力 | 「今すぐ」の穴の残り | `pnpm gaps` | 0 |
| 守り | カタログの「得」と実際の動きの食い違い | 見つけた件数 | 0(直すまで公開しない) |

- 公開の後は「ROI が当たったか」を見る: 使ってみた人が、カタログの何を使って、何日ぶん浮いたと言ったか(報告と Issue)。外れた行は直す。
- **合議は見せ方の判定には使わない**。機能開発のレビュー(仕様・PR・受け入れ)では、今までどおり `/council` を使う。
