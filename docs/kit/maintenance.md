# キットの保守の方針(約束はしない)

> 外部のコードの審査・契約で聞かれることを1ページに。**キットは公開しているが、保守の日数も期限も約束しない**(できる範囲で直す)。決まりは [仕様 0066](../specs/0066-kit-versions-and-maintenance.md)・[設計書 0066](../designs/0066-kit-versions-and-maintenance.md)。
> 変更の記録は [CHANGELOG.md](../../CHANGELOG.md)、穴の知らせ方は [SECURITY.md](../../SECURITY.md)、キットから作ったリポジトリへの取り込み方は [upgrade.md](upgrade.md)。
> **できないこと・確かめていないこと**(本物の AWS の上で確かめていない物を含む)は [limits.md](limits.md) に1か所にまとめた。審査の資料にはそれも添える。

## 1. 誰が

- 🧑 **持ち主の @attumkwg が1人で**、個人の時間の範囲で手入れしている(会社としての保守ではない)。
- 🤖 変更の多くは AI(Claude Code)が PR を出し、持ち主が判断してマージする(キット自身も、キットのライン — 危険度・守るパス・必須のチェック — で作っている)。
- 📄 ライセンスは [MIT](../../LICENSE)。**無保証**で、直す約束(SLA)も、返事や直すまでの日数の約束も無い。

## 2. どこまで直すか(できる範囲で)

| 直す | 直さない |
|---|---|
| キットの穴(他社のデータが見える・鍵が漏れる・認可の抜け) | キットから作った**あなたのリポジトリ**(取り込むのはあなた。[upgrade.md](upgrade.md) の手順で。点検の `kit-upstream` が新しい版を知らせる) |
| 守りの抜け(AI が危ない操作をできる・守るパスの漏れ・必須のチェックがすり抜けられる) | あなたのプロダクトに合わせた変更(題材・部品の選び方・クラウドの入れ替え) |
| 書いてある手順どおりに動かない(`pnpm setup:github`・`pnpm test`・手順書のコマンド) | 古い版(直すのは最新の版だけ。古い版に戻って直さない) |
| 文書と今の姿の食い違い | 使っている道具(GitHub・AWS・Claude Code)そのものの穴 |

- 🐛 不具合・要望は公開の Issue へ(テンプレート「キットの穴」「キットの直しの提案」)。**穴は公開の Issue に書かず** [SECURITY.md](../../SECURITY.md) の道で。外の PR はそのままマージせず、キットの決まりに合わせて取り込む([CONTRIBUTING.md](../../CONTRIBUTING.md))。

## 3. いつまで

- 🚧 **約束しない**。キットは公開しているが、手入れは持ち主1人ができる範囲で続ける。期限も、返事や直すまでの日数も決めていない。
- 🛑 手入れをやめるときは、README の頭と CHANGELOG に書き、リポジトリを読み取り専用(archive)にする。コードは MIT のまま残るので、続けたい人は自分のリポジトリで持てる。
- 🤝 日数や期限が要る会社は、下の 5 のとおり自社か支援する会社で持つ。

## 4. 版の付け方

- 🏷 タグは **`v0.Y.Z`**(main のコミットに注釈つきのタグ)。`0.` の間は、版のあいだで大きく変わることがある。
  - **Y を上げる**: 部品を足す・消す・ファイルを動かす・設定ファイル(`.github/setup.yml`・`docs/checkup/todo.yaml` など)の形が変わる・**取り込むときに手が要る**(移行・`pnpm setup:github --apply` の流し直し・使う側の設定)。
  - **Z を上げる**: 穴と守りの抜けの直し・文書の直しで、取り込むときに手が要らない物。
- 🗓 **いつ切るか**: Y はたまったら(多くて月に1回)。Z は穴を直したらすぐ。
- 1️⃣ `v1.0.0` は、版のあいだで大きく変わらなくなったとき(持ち主が決める。README の頭の「`v1.0.0` までは」も外す)。1 から後は、取り込むときに手が要る変更で1つ目の数字を上げる。
- 🔒 タグは**付け替えない・消さない**。間違えたら次の版で直す。正はこのリポジトリ(attumkwg/software-factory-starter)のタグとリリースだけ。
- ✍️ **版を切る手順**(持ち主):
  1. AI に「前の版から main に入った PR から、CHANGELOG の『未リリース』を版の節にして」と頼む(`gh pr list --state merged` から下書き。PR ごとには書かない — 並べた PR がぶつかるので)。
  2. 同じ PR で [upstream.yaml](upstream.yaml) の `version` を新しいタグにする(キットから作ったリポジトリが、どの版から来たかを持つ)。「取り込むときにすること」を確かめて、その PR をマージする。
  3. 公開の前の点検([release-check.md](release-check.md))を同じ見方で流し、結果をそこに書く。
  4. 持ち主が `git tag -a v0.Y.Z -m "v0.Y.Z"` → `git push origin v0.Y.Z` → GitHub のリリースに CHANGELOG のその版の節を写す。**AI はタグもリリースも作らない**。

## 5. 審査・契約に出すとき(使う会社へ)

- 📋 審査の資料には、この1ページ・[limits.md](limits.md)(できないこと・確かめていないこと)・[SECURITY.md](../../SECURITY.md)・[CHANGELOG.md](../../CHANGELOG.md)・使っている版(取り込んだ最後のタグ)を添える。
- 🤝 **保守を契約で約束してほしいとき**は、キットの持ち主ではなく、①自社で持つ(キットから作ったリポジトリはあなたの物で、MIT なので直してよい)か、②キットを使って支援する会社と契約する。キットの直しは「上流の更新」として取り込む。
- 🧾 キットから作ったプロダクトの穴の窓口は、**あなたの会社**。キットから来た `SECURITY.md` は、あなたの連絡先に置き換える([getting-started.md](../getting-started.md) の ②)。
