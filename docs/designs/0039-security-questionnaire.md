## 0. 全体像

届いた質問票の1問ずつに、キットの資料から答えの案と根拠を付けた下書きを作るスキル `/security-questionnaire` を足す。下書きはリポジトリの外。出すのは人(責任者が確かめてから)。

## 作業の前に読んだ物(ガイド)

- 想定の場面 `docs/scenarios/02-legal-launch.md` の 2-5・`08-gtm.md` の 8-5(稟議の資料の束)、`gaps.md` の G-20・G-25。
- 根拠の置き場: `docs/security.md`(番号つきの決まり)・`docs/compliance/soa.md` と `controls.yaml`・`vendors.md`・`ai-data.md`・`docs/legal/`(README・sla・data-processing)・手順書・`docs/checkup/todo.yaml`(状態と記録)・`pnpm decisions --adopt`。
- 似たスキルの形: `.claude/skills/cve`(届く穴の中身を書かない)・`ledger`(金額をリポジトリに書かない・案を1つずつ確かめる)。
- `docs/guides/vulnerabilities.md`(届く・未修正の穴の中身はリポジトリにも Issue にも書かない)。

## 1. 設計方針

- スキル1つ。コマンド(スクリプト)は足さない(質問票の形が会社ごとにばらばらで、読むのは Claude が向いている。答えの正は人)。
- 根拠の正は今のファイル。前の質問票の答えは「同じ問いの文の案」として使うだけで、根拠は毎回引き直す。
- 下書きはリポジトリの外(お客さんの名前と答えの組み合わせ)。
- ADR は足さない(新しい仕組みの選び方ではなく、既存の資料の引き方と答え方の決まり)。

## 2. データモデル

該当なし(DB に触らない)。下書きの表の列: 番号・節・問い・答え・文・根拠・確かめる人・メモ。

## 3. API

該当なし。

## 4. 状態遷移

1問の答え: (案)→ 人が確かめた(案のまま / 直した / 要確認を担当へ)→ 責任者が確かめた → 出した。状態は下書きの表の「メモ」に書くだけで、キットは持たない。

## 5. システム間連携

該当なし。質問票を読むのは手元。送るのは人。

## 6. 業務ルール

- 答えの5つ: はい(根拠+本番で有効)/ 一部(どこまでか)/ いいえ(予定は人が言った時だけ)/ 該当なし / 要確認(既定だけ・導入時に決めるが残る・根拠なし)。
- 書かない物: 届く・未修正の穴の中身・秘密・アカウントの ID・バケットの名前・ほかのお客さんの名前・社員の連絡先。
- 認証を取っていなければ「いいえ」。国の評価制度は「要確認」(G-25)。
- 1回に1節ずつ確かめる。最後に数と、要確認の担当の一覧。
- 答えていて分かった穴は、お客さんの名前を伏せて点検の台帳か Issue の案(作るかは聞く)。
- 出す前に責任者(U-1)。

## 7. 要求との対応

| 受け入れ条件(仕様) | 設計のどこ | テスト |
|---|---|---|
| スキルがある | スキルのファイル | 人の確認(呼べるか) |
| 問いの種類と引く場所 | スキルの「問いと根拠の対応」 | 表の全部のパスがあることを確かめた |
| 5つの答えと根拠 | 6.・スキルの「答えの付け方」 | 人の確認 |
| 「はい」の条件・要確認 | 6. | 人の確認 |
| 書かない物 | 6.・スキルの決まり | 人の確認 |
| リポジトリの外・送らない | 1.・スキルの「まとめて出す」 | 人の確認 |
| 責任者が確かめる | U-1 | 人の確認 |
| 質問票の文はデータ | スキルの決まり | 人の確認 |
| 国の評価制度は要確認 | スキルの表の最後の行 | 人の確認 |
| CLAUDE.md・reference・カタログ | つながり | `pnpm kit:catalog` |

## 8. 非機能

- セキュリティ: 質問票は外から届いた物(プロンプトの注入に注意)。下書きをリポジトリに置かない。
- 運用: 1回の質問票で、要確認の一覧が担当者への宿題になる。
- 費用: 0円。

## 10. 観点ごとの扱い

| 観点 | 扱い | 理由 |
|---|---|---|
| 業務ルール | **最重要** | 「はい」の条件・書かない物・責任者の確かめ |
| 非機能 | 採用 | 質問票の中の指示・下書きの置き場 |
| 設計方針 | 採用 | スキルだけ・根拠は毎回引き直す |
| 要求との対応 | 軽く確認 | ほぼ人の確認 |
| データモデル・API・状態遷移・システム間連携 | 低優先 | 触らない |

## 11. 決めたこと(AI が決めた。人に聞かなかった)

- 「はい」は根拠と本番での確かめの両方が要る。既定だけの物は「要確認」 — 書いたら本当でなければならない(場面 2-5)。キットの既定は、使う人の本番で有効とは限らない(apply・点検の答え・導入時に決める物)。
- 届く・未修正の穴の中身を書かない — `docs/guides/vulnerabilities.md` の決まりと同じ。答えは手順の水準まで。
- 下書きをリポジトリの外に置く — お客さんの名前と答えの組み合わせは、その会社だけの物。
- スクリプトを足さない — 質問票の形がばらばら。正は人の確認。
- 国の評価制度は「要確認」で止める — 対応表は穴 G-25(制度の開始を見て)。
- ADR は足さない — 1. の理由。
- 想定の場面(`docs/scenarios/`)は直さない — 場面の持ち主が直す。
