## 1. 設計方針

- **要求との対応**: `scripts/design-tests-lib.mjs`(読む・判定)と `scripts/design-tests.mjs`(入口・git で変えた物を拾う)。CI の速い検査(`ci.yml` の `fast`)に1段足す。新しい依存は足さない(node の標準と git だけ)。
- **変えた設計書だけを見る**。今の設計書 73本のうち 72本は、どこかの行がパスを書いていない(通り名か「画面の単体テスト」)。全部を見ると CI が落ちたままになる。見るのは「新しい設計書」と「7 の節か状態を変えた設計書」。リンクの付け替えなどの文の直しで触れただけなら見ない(その PR が昔の表を直す羽目にならないように)。
- **無いファイルは「完了」で落とす**。設計書は仕様の PR で実装より先に入る(`/design` の 6)。その時点ではテストのファイルはまだ無い。最初はパスを書くことだけを求め、作り終えて状態を「完了」にした PR で、ファイルがあることを求める。
- **監査ログの画面の文**: 画面の単体テスト(`audit-labels.test.ts`)に1件。API のコードは画面から import しない(別のサービス。ADR 0003)ので、ファイルを文字として読む。正規表現は使わない(Semgrep の regex_dos)。

## 6. 業務ルール

- 確かめる設計書: `docs/designs/` の直下の `.md`(`_template.md`・README を除く)のうち、元から変えた物(作業中の物・git にまだ無い物も)。消した物は見ない。さらに、元に無い(新しい)か、「要求との対応」の節か「> 状態:」が元と違う物だけ。
- 元: 引数 `--base`(CI は `HEAD^1`)。無ければ `origin/main`。元との分かれ目(merge-base)から比べる。比べられなければ落ちる(黙って通さない)。
- 引数にファイルを渡すと、変えたかどうかに関わらず、その設計書を見る(手元で昔の設計書を見るとき)。
- 表: 「## 」で始まり「要求との対応」を含む見出しから、次の「## 」まで。最初の表の頭の行から「テスト」の列を探す。区切りの行は飛ばす。
- パス: テストの欄の「`」で囲んだ物のうち、「/」を含み、最後の段に拡張子があり、空白が無い物。ファイル名だけ・通り名・コマンドは数えない。
- ある: リポジトリの根か、`apps/*`・`packages/*` の中から見てあれば、ある(昔の設計書は `test/integration/…` と `apps/api` の中から書いている)。
- 落とす物: 節・表・「テスト」の列・行が無い / パスの無い行 / 状態が「完了」なのに無いファイル。出すだけの物: 状態が「完了」でないときの無いファイル。
- 監査ログの名前: `actions.ts` の、コメントでない行の「"」で囲んだ物のうち、点を含み、空白と「/」を含まない物。画面の文の一覧に無い名前があれば落ちる。拾った中に `project.create`・`auth.login`・`support.read` が無ければ落ちる(拾い方が壊れて0件で通るのを防ぐ)。
- 足した画面の文(10件): `organization.task_mail_on`「タスクが完了したメールを送るに戻した」・`organization.task_mail_off`「タスクが完了したメールを止めた」・`data.export`・`sso.update`・`sso.connect`・`sso.disconnect`・`pre_registration.purged`・`deleted`・`converted`・`found`。

## 11. 決めたこと(AI が決めた。人に聞かなかった)

- 変えた設計書だけを見る — 昔の 72本はパスの無い行がある。全部を見ると CI が落ちたままになり、直すのも1本ずつ中身を確かめる要る仕事になる
- 変えた中でも、新しい物と「7 の節か状態を変えた物」だけ — リンクの付け替えなどで昔の設計書に触れた PR が、関係のない表を直す羽目にならないように
- 無いファイルは「完了」になってから落とす — 設計書は仕様の PR で実装より先に入る(`/design` の 6)。最初から求めると設計が書けない。#186 の形(通り名だけ)は、設計の PR の時点で落ちる
- パスは根からでもパッケージの中からでもよい — 昔の設計書(0089 など)は `apps/api` の中から書いている。根からだけにすると、その表に触れたときに全部書き直しになる。ひな形は根から書くように直した
- ファイル名だけ(`mail.int.test.ts`)はパスに数えない — 同じ名前が複数の場所にありうる。どれか分からない物は名指しにならない
- 比べる元は CI では `HEAD^1` — PR を合わせたコミットの1つ目の親が PR の元(`ci-scope.mjs` と同じ)。main への push・マージキューでも1つ目の親と比べれば、入った差分だけを見る
- 画面のテストは API のコードを import せずに文字で読む — 画面と API は別のサービス(ADR 0003)。名前の一覧は文字の形が決まっている(`action: "…"` と `名前: "…"`)
- 足りなかった画面の文は、#187 の2件のほかに8件(`data.export`・SSO の3件・事前登録の4件)も足した — 全部の名前に文があることを確かめるので、足さないと通らない。文は今ある文の言い回しに合わせた
- `actions.ts` のコメントが画面の文の場所を `messages.ts` と書いていたのを `audit-labels.ts` に直した
