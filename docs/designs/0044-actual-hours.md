## 0. 全体像

費用のページの非公開の入力に、人の時間の**実績**(週の記録 `actuals.csv`: 人・賭け・開発の段階・時間・確かめた人)を足す。実績があれば PL の人の費用は推定の幅ではなく実績になり、`ledger.csv` に賭け × 開発の段階(研究開発・制作・運用)の行と根拠(記録の数・未確認・段階の違い)が足される。区分は案まで。

```mermaid
flowchart LR
  W[人が週に1回<br/>actuals.csv] --> S[(非公開の S3<br/>cost/inputs/)]
  S --> R[pnpm cost --render]
  B[賭けの段階<br/>docs/product/bets] --> R
  R --> PL[PL の人の費用 = 実績]
  R --> L[ledger.csv<br/>賭け × 研究開発・制作・運用]
  L --> LG[/ledger で人が確かめる<br/>確定は専門家]
```

## 1. 設計方針

- 実績は**今ある非公開の入力に1つ足す**(時給・割合・売上と同じ置き場・同じ流れ)。勤怠の仕組みは作らない。
- 実績があれば実績を正にし、推定は比べるために残す(PL の人の費用は実績・`ledger.csv` には実績の行と推定の行の両方)。
- 開発の段階は記録する人が選ぶ。キットは賭けの段階からの案を出し、違えば根拠に書く(止めない)。
- 新しい依存は無い。

## 2. データモデル

DB は触らない。

非公開の入力 `cost/inputs/actuals.csv`:

| 列 | 意味 |
|---|---|
| `date` | 記録の始まりの日(`YYYY-MM-DD`。ふつうは週の月曜。月をまたぐ週は月ごとに2行で、2行目は月の1日)。この日の月の分として数える |
| `person` | 人(`@名前`。時給の `rates.json` と同じ書き方) |
| `bet` | `B-NNNN` か `core` |
| `phase` | `研究開発` / `制作` / `運用` |
| `hours` | 実際の時間(0以上) |
| `approved_by` | 確かめた人(`@名前`)。空なら未確認 |

`readActuals` の戻り値: `{ rows: [{ date, person, bet, phase, hours, approved_by }], bad }`(その月の行だけ。形の合わない行は `bad` に数える)。

`summary.json` の PL の行に足す(足すだけ): `hours_actual`(時間・小数1桁)・`people_actual_yen`(円)。

`ledger.csv` の行(見出しは今のまま9列):

| 月 | 賭け | 段階 | もと | 区分の案 | 時間 | 金額(自動の目安の列) | 金額(手入力の列) | 根拠 |
|---|---|---|---|---|---|---|---|---|
| 2026-10 | B-0002 | psf | 人の時間(実績・制作) | 資産の候補 | 6 | 36000 | (空) | 週の記録 1行・未確認 1行・賭けの段階からの案は「研究開発」 |

## 3. API

API は足さない。`pnpm cost --render <dir> --inputs <dir>` が `actuals.csv` を読み、PL と `ledger.csv` に使う。

## 4. 状態遷移

記録の行: 書いた(未確認)→ 確かめた人が欄を埋めた(確認済み)。直すのは人が置き場のファイルを置き直す(前の版は置き場に残る)。

## 5. システム間連携

非公開の S3(人が置く・`cost.yml` が落とす)。外のサービスは増えない。

## 6. 業務ルール

- **H-1 月**: `date` が `YYYY-MM` で始まる行がその月。
- **H-2 形**: `person`・`bet` が空・`phase` が3つのどれでもない・`hours` が数でないか負 → 数えない(`bad`)。
- **H-3 段階の案**: 賭けの段階が `idea`・`cpf`・`psf` → 研究開発、`rollout`・`adopted` → 制作、それ以外と `core` → 運用(`phaseOfStage`)。`bets-and-assets.md` の案の表と同じ考え(作業の種類の「保守」は記録の人が「運用」を選ぶ)。
- **H-4 区分の案**: 研究開発 → 費用・制作 → 資産の候補・運用 → 費用(`PHASES`)。
- **H-5 PL**: 実績のある月は、賭けごとの人の費用 = その賭けの人ごとの実績の時間 × 時給(`rates.json`)の合計。下と上は同じ値(幅にしない)。実績の無い月は今までどおり(自動の目安と手入力の幅)。PL は、PR・割合の手入力・実績のどれか1つでもあれば作る。共通の費用の配り方(`allocation`)は変えない。
- **H-6 ledger の根拠**: `週の記録 N行`・未確認があれば `未確認 N行`・記録の段階が H-3 の案と違えば `賭けの段階からの案は「…」`。
- **H-7 足りない物**: 実績が無い → 「推定の幅で出した(上場の準備には週の記録が要る)」。形の合わない行・未確認の行の数。
- **H-8 出さない物**: ページに人ごとの時間・金額は出さない(賭けごとの合計だけ)。`ledger.csv` も賭け × 段階の合計。

## 11. 決めたこと(AI が決めた。人に聞かなかった)

- 実績は今ある非公開の入力に CSV を1つ足す — 勤怠の道具を選ばない(道具の書き出しを形に合わせればよい)。時給と同じく人事の情報なので、リポジトリに置かない
- 週 × 人 × 賭け × 段階 — 日ごと・作業ごとにすると書く手間で続かない。週に1回なら PR の振り返り(毎週30分)と一緒にできる
- 月をまたぐ週は月ごとに2行 — 月の締めで、週の時間を勝手に割らない(割り方を人が決める)
- 確かめた人の欄を持ち、空なら未確認として数える(止めない) — 監査では「誰が確かめたか」が聞かれる。止めると書かなくなる
- 実績があれば PL の人の費用は実績(幅にしない)・推定は `ledger.csv` に比べるために残す — 監査に出すのは実績。推定とずれが大きければ、PR の目安の分数(`people.yaml`)を直す合図になる
- 段階の案は賭けの段階から出し、記録と違えば根拠に書く(直さない) — 記録した人のほうが仕事の中身を知っている。違いを人が確かめる
- 共通の費用の配り方は変えない — 配り方は設計書 0020 の U-1(導入時に決める)
- ADR を1つ書く — 記録の形と「実績を正にする」は、後から変えると前の月と比べられなくなる
