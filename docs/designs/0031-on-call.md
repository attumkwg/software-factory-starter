## 6. 業務ルール

- 役: 一次・予備・上げる先(責任者)。3人から。週ごとの交代なら4〜5人。交代は週ごと(月曜 10:00)、深夜が続けば日ごと。
- 連絡の段: 0分 一次 → 15分 予備 → 30分 上げる先。応答 = スレッドに「見ています」か道具で「受けた」。営業時間は Slack で15分以内に応答(道具で起こさない)。
- 起こす: `uptime-*`・`*-target-5xx`・`elb-5xx`・`*-unhealthy-hosts`・`{api,web}-running-tasks`・要配慮の鍵・管理操作の記録の root と記録を止める操作・Security Hub の CRITICAL。
- 朝: `task-stops`・`slow`・`db-*`・`mail-running-tasks`・`ses-*`・`waf-hits`・RDS のイベント・Backup の失敗・Security Hub の HIGH・`cert-expiry`・Budgets。理由はどれも「単独では利用者が困っていない・5xx などが一緒に鳴る」か「期限まで日がある」。
- 迷ったら起こす。翌日に表を直す。アラームを足すときは、手順書の見出しと夜の扱いを同じ PR で。
- 当番の間は改善だけ(しきい値・手順書・再発防止・点検)。夜中に起こされたら翌朝は休む(U-2)。
- 交代の引き継ぎは Slack に5分(鳴った物・続いている物・直した物)。
- 表(名前・電話)はリポジトリに置かない。
- SLA との対応(手引きの 7): 当番を置く前は営業時間で数える。置いた後は「起こす」物だけ夜も数える。夜中の S1 の最初の知らせは、段の最長30分を見込んで「応答から30分」にするかを契約で決める。

## 11. 決めたこと(AI が決めた。人に聞かなかった)

- 起こす線を「お客さんに影響がある・約束の水準を割りそう・漏えいのおそれ」にし、アラームごとに分けた — 想定の場面の 5-5 の世の中の例と、`monitoring.md` の各アラームの意味(単独で利用者が困るか)から。ADR 0042。
- 要配慮の鍵と管理操作の記録のアラームを「起こす」にした — 漏えいの報告の期限は「知った時点」から数える(personal-data-breach.md)。朝まで待つと知るのが遅れる。
- `task-stops`・`db-*`・`slow` は「朝」にした — 利用者が困っていれば `*-5xx`・`unhealthy-hosts`・`uptime-*` が一緒に鳴る作りなので、それで起きる。
- 当番の表をリポジトリに置かない — 名前と電話が履歴に残る。
- 手順書と結ぶ作業は足さなかった — アラームの説明は全部、手順書の見出しか節を指している(grep で確かめた)。足すときの決まりだけ書いた。
- 点検の項目は「半年ごと・3か月目から」にした — 使い始めの1〜2か月は有料の顧客がいないことが多い。人数と契約は半年で変わる。
- 想定の場面(`docs/scenarios/`)は直さない — 場面の持ち主が直す。
