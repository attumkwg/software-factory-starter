稼働状況のページは作らず、外のサービスの選び方・入れ方・障害の重さとの対応を手引き `docs/guides/status-page.md` に置く。障害の手順書の「お客さんへの知らせ」と「終わり方」から指す。

## 1. 設計方針

- 手引き1枚。ページそのものはキットの外(ADR 0043)。
- 委託先の台帳の「例」は、台帳(`vendors.yaml`)ではなく手引きの中に置く。台帳は実際に使っている会社の正で、状態は active / ended しか無い(候補を書く形が無い)。使っていない会社を足すと、委託先の一覧(`vendors.md`)がお客さんに渡す資料として嘘になる。
- 文はメールと同じ(incident.md の 4 を正にし、手引きは対応の表だけ)。

## 4. 状態遷移

ページの状態(稼働中 → 一部に影響 / 大きな障害 → 稼働中、メンテナンスの予定 → メンテナンス中 → 稼働中)は外のサービスが持つ。キットは重さとの対応だけ(手引きの 4)。

該当なし(この PR では外へ出さない)。入れたら、知らせる役が手で書く。購読を使わなければ、外のサービスに渡すのは公開の文だけ。

## 6. 業務ルール

- 要る目安: 同じ問い合わせが何件も来る・SLA を出した・情シスに聞かれた。
- 選ぶ条件: 自分の基盤と別・`status.<ドメイン>`・部品は画面・API・メール・手で更新・購読なし(U-1)・公開(U-2)・稼働率なし(U-3)・日本語。
- 対応: S1 → 大きな障害(第1報と同時・30分以内)/ S2 → 一部に影響(1時間以内)/ S3 → 載せない / 計画メンテナンス → 7日前まで。
- 載せない物: 他社のデータが見えた・個人データの事故(止めた事実だけ)・1社だけの障害(個別に)。
- アカウントは知らせる役の2人以上に個人ごと。

## 8. 非機能

- セキュリティ: 共有のアカウントにしない。漏えいの中身を公開の所に書かない。
- 運用: 第1報と同時にページも書く(知らせる役)。
- 費用: 0円(文書だけ)。入れたら外のサービスの月額。

## 11. 決めたこと(AI が決めた。人に聞かなかった)

- ページを自分の AWS の外に置く — 本番と一緒に落ちると意味が無い(ADR 0043)。
- 更新は人が手で — incident.md の 4 の文面の決まり(事実だけ・推測を書かない)を機械は守れない。
- 台帳の例を手引きに置き、`vendors.yaml` には足さない — 1. の理由。
- 外のサービスの名前は例として3つだけ挙げ、料金は書かない — 料金と機能は変わる。選ぶときに公式で確かめる、と書いた。
- `legal/sla.md` の「知らせる先」の行は直さない — 並行の PR(当番の決まり)が隣の行を直していて、ぶつかる。手引きから SLA を指せば足りる。
- 想定の場面(`docs/scenarios/`)は直さない — 場面の持ち主が直す。
