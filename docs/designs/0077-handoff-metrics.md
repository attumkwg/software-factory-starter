## 0. 全体像

`pnpm metrics` に「引き渡し」の節を足す。受け入れの記録(仕様 0075)の第1回の日付と、記録の頭の「実装の PR」のマージの日から待ちを出し、回ごとの点数と外れた理由を週で合わせ、設計書の「作り直しの記録」から設計が原因の割合を出す。

## 1. 設計方針

- 計算は `scripts/metrics/handoff.mjs`(GitHub もファイルも読まない)。集めるのは `collect.mjs`(`acceptanceFiles`・`designFiles`・`collectMergedAt`)と `run.mjs` の `collectHandoff`。
- `buildReport` は変えず、`collectReport` の最後で `handoff` を足す(既存のテストと JSON の形を壊さない。足すだけ)。
- 実装の PR のマージの日は、PR の番号で1つずつ読む(GraphQL の `repository.pullRequest(number)`)。期間の検索結果に頼らない(実装は期間より前にマージしていることがある)。
- 出すのは改善の節(決裁用の表に列を足さない)。

## 2. データモデル

DB は使わない。

- 受け入れの記録の頭: `> 実装の PR: #12, #13`(`#` の後の数字。仕様 0075 の型にある行)
- 回の事実(`acceptanceFact`): `path`・`no`・`week`・`waitDays`(第1回だけ。読めなければ null)・`unread`・`pdm`・`all`・`ok`・`judged`・`reasons`
- 作り直しの事実(`reworkFacts`): 「作り直しの記録」の見出しより後の表の行で、1列目が `YYYY-MM-DD` の物 → `{ week, stage }`(3列目の入った工程)
- 出力(`report.handoff`): `weeks`(週ごと: `rounds`・`waitDays`(中央値)・`acceptPct`・`reasons`・`rework`・`designReworkPct`)・`last`(先週の回)。読めなかった PR は `report.notes` に

該当なし(数えるだけ)。

## 5. システム間連携

- `metrics.yml` は `pnpm metrics --out` を流して要約に出す。変えない(節が足されるだけ)。
- 受け入れの記録は `/accept`(仕様 0075)、作り直しの記録は `/rework` が書く。

## 6. 業務ルール

- 週は日本時間の月曜から(`weekOf`)。受け入れは回の日付・作り直しは行の日付の週。
- 待ち = 第1回の日付 − 実装の PR のうち最後にマージした日(日本時間の日付)。日の差を丸める。第2回からは数えない。実装の PR が無い・1つでも読めない・まだマージしていない → 数えない。読めない番号は「読めなかった物」へ。
- 週の待ちは中央値。点数 = 週の回を合わせた 合 ÷(合+否)。理由は週の回を合わせた数。
- 設計が原因の割合 = 入った工程が「設計」の行 ÷ その週の作り直しの行。分母が0なら「—」。
- 期間の最初の週より前の回は読まない。
- 人ごとの数は出さない(見た人は読まない)。

## 11. 決めたこと(AI が決めた。人に聞かなかった)

- 確かめの開始 = 受け入れの記録の第1回の日付 — キットの中に「QA を始めた」記録はほかに無い。外の道具を読まない。
- 実装の完了 = 記録に書いた実装の PR のうち最後にマージした日 — 1つの機能に PR が何本もある。最後の1本が入って初めて確かめられる。
- 設計が原因の作り直しは、設計書の「作り直しの記録」の入った工程で数える — `/rework` が毎回書く所。受け入れの外れの「設計」は点数の内訳に出す(同じ物を二重に数えない)。
- 待ちが負なら負のまま出す — 記録の誤り(PR を書き間違えた)に気づける。
- `lib.mjs` に足さずに `handoff.mjs` — ファイルの長さの上限。
