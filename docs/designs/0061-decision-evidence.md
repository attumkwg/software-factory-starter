# 設計: 未確定事項の「承認」は、人が GitHub に書いた答えを指す

> **AI 用の設計書。省略せずに網羅的に書く(正はこちら)。** 人はこれを開かず、PR の本文の「人向けのまとめ」を見る([guides/human-review.md](../guides/human-review.md))。
> 仕様: [docs/specs/0061-decision-evidence.md](../specs/0061-decision-evidence.md)
> 状態: 下書き
> 観点の順は [review-viewpoints.md](../review-viewpoints.md)。当てはまらない節も消さずに「該当なし(理由)」と書く。

## 0. 全体像

必須のチェック「未確定事項の答えの出どころ」(`decision-evidence.yml` → `scripts/decision-evidence.mjs`)を足す。PR で変えた設計書の未確定事項のうち、状態が人の答え(承認・変更・保留・導入時に決める)になった行は、状態の文の GitHub のリンクを読み、リンク先の書き手が人(書き込める人・ボットでない・`@名前` と同じ)で、本文に番号があるかを確かめる。手元では Bash のフックが、AI が人のアカウントで答えを書くのを人に聞く。

## 1. 設計方針

- **答えは AI が書けない場所に置き、ファイルはそれを指すだけ**(台本 10-5 の「世の中では」)。背景の AI はボットの名前で書くので、書き手で見分けられる。
- 確かめるのは **この PR で変わった行だけ**(土台の版と比べる)。前から入っている「会話で回答」の行は見ない。
- **土台のブランチ(`base.sha`)を checkout** して、そのスクリプトで確かめる。PR の側の設計書は API(`contents?ref=head.sha`)で読む。
- 中身は `decisions-lib.mjs` に足す(表の読み方を1か所に)。正規表現を使わずに読む(今のファイルの決まり)。
- 手元の AI は人のアカウントで `gh` を使えるので、CI では見分けられない。Bash のフックで「書く前に人に聞く」。

## 2. データモデル

該当なし(DB を使わない)。

## 3. API

該当なし(アプリの API は変えない)。GitHub の REST を `gh api` で読むだけ: `pulls/{n}`(head の sha)・`pulls/{n}/files`(変えた設計書と元の名前)・`contents/{path}?ref=`(PR の側の中身。`Accept: application/vnd.github.raw`)・`issues/comments/{id}`・`pulls/{n}/reviews/{id}`・`pulls/comments/{id}`(リンク先)。

## 4. 状態遷移

- 人の答えの状態: `承認`・`変更`・`保留`・`導入時に決める`。この状態に「なった」(前の版に無い・状態の文が変わった)行にリンクが要る。
- `仮決め` は AI が書く。`取り下げ` は作り直しで問いが無くなったときに AI が書く(どちらもリンクは要らない)。

## 5. システム間連携

- 起動: `pull_request`(opened・synchronize・reopened)。人がコメントで答え、AI(か人)がリンクを足して push すると流れ直す。
- 権限: `contents: read`・`pull-requests: read`・`issues: read`。`GITHUB_TOKEN` だけ。
- 土台にまだスクリプトが無い(このチェックを足す PR)ときは確かめずに通す。
- `required_checks` に足す。GitHub の側のルールセットに入れるのは、マージの後に人が `pnpm setup:github --apply`。

## 6. 業務ルール

- リンクの形: `https://github.com/<owner>/<repo>/(pull|issues)/<番号>#issuecomment-<id>`・`#pullrequestreview-<id>`・`#discussion_r<id>`。このリポジトリの物だけ。
- 人とみなす書き手: `author_association` が OWNER・MEMBER・COLLABORATOR で、`user.type` が Bot でない。状態の最初の `@名前` と同じ(大文字小文字は問わない)。
- 本文に行の番号(`U-1`)。リンク先がこの PR でなければ、設計書の番号(ファイル名の頭の4桁)も。
- フック: `gh pr|issue comment|review`・`gh api` で、`U-数字` の後に `承認`・`変更`・`保留`・`導入時に決める` が続く文を書くときは聞く(`KIT_EDIT_GUARD` に関係なく)。PR の本文(`gh pr create`)に仮決めの行を写すのは聞かない。

## 8. 非機能

- 性能: 変えた設計書ごとに API 1回、答えの行ごとに1回。5分で打ち切り。
- セキュリティ: 仕様の STRIDE のとおり。式を run に書かない(番号とリポジトリの名前は env)。
- 運用: 落ちたら、行ごとに何が足りないか(リンク・書き手・番号)を出す。
- 費用: Actions の分数がわずかに増える(PR の push ごとに1分未満)。

## 11. 決めたこと(AI が決めた。人に聞かなかった)

- **会話の答えは証にしない**(人は同じ言葉を PR に書く) — 会話の答えは AI が「会話で回答」と書けば作れる。gaps.md の案(その人のコメントかレビューへのリンクを必須)のとおり。
- **承認だけでなく、変更・保留・導入時に決めるもリンクを要る** — どれも `--strict` を通す状態なので、AI が承認の代わりに保留や導入時に決めるへ書き換えて通すのを防ぐ。
- **取り下げはリンクを要らない** — 作り直しで問いが無くなったときに AI が書く物(手引きのとおり)。止めると作り直しが回らない。悪用はレビューで見る。
- **別の PR・Issue の答えは設計書の番号も要る** — `U-1` はどの設計書にもあるので、ほかの設計書への答えを指し直せてしまう。
- **PR を出した人の答えも数える**(高の承認の人数と違う) — 1人の間は、答えるのも PR を出すのも同じ人。見分けたいのは「人か AI か」で、手元の AI が人のアカウントで書く道はフックで聞く。
- **手元のフックは止めずに聞く** — 人が見ている前提。人が「はい」と押せば人の答え。
- **中身を `decisions-lib.mjs` に足し、それを「高」にする** — 表の読み方が2か所にずれない。確かめの中身を AI が緩めないよう、スクリプトと一緒に守る。
