## 1. 設計方針

- 手順書1枚(その日にやる手順なので `runbooks/`)。道具の一覧は手順書の 0 に置き、使う人が自社の道具に直す(委託先の台帳の会社と社内の道具)。
- AWS の人の入口は IAM Identity Center を既定に書く(点検の `access-review` と同じ。アクセスキーを作らない)。IAM のユーザーがある場合も書く。
- 運営の組織は、Cognito を止める → DB の行を消す、の順。Cognito の利用者はメールで引く(社員のメールは分かっているので、offboarding.md の 3 のように DB の `external_id` を先に控えなくてよい)。
- 点検の項目は毎月(棚卸しの四半期より短く)。答えは「いない / いた(そろっている)/ いた(無い)」。
- 記録は1人1回1枚。名前が入るので、置き場は `records/README.md` の表で決める。

## 4. 状態遷移

アカウント: 無い → 作った(入る日)→ 止めた(辞める日。本番に届く物は辞めると決まった日)→ 消した(止めてから 90日)。止めた → 作った、には戻さない(戻ってきたら作り直す)。

## 5. システム間連携

該当なし(この PR では外へ出さない)。

## 6. 業務ルール

- 役割ごと: エンジニア(AWS は dev と stg・prod は当番か要るとき・GitHub 書き込み・運営の組織は問い合わせを受ける人・Sentry・Slack・Claude)/ CS と営業(GitHub は Issue だけ要るなら・運営の組織は問い合わせを受ける人・Slack)。
- 入る日: 誓約と教育の後・要る物だけ・prod は渡さない・二段階認証を設定するまで prod と運営の組織は使わせない。
- 辞める日の順: AWS → GitHub → 運営の組織 → Sentry・Slack・Claude → 会社のメール → 秘密の入れ替え → 管理者が2人か・点検の担当者 → 端末 → 記録。
- いつ: 本番に届く物は辞めると決まった日、ほかは最終日の終わり、急な退職は告げる前に全部(U-1)。止めてから 90日で消す(U-2)。
- 点検の項目:

| 欄 | 値 |
|---|---|
| id | `people-changes` |
| title | 先月、入った人・辞めた人・役割が変わった人のアカウント |
| who / phase / every / verify | human / 1m / monthly / ask |
| 選択肢 | いない / いた(記録がそろっている)/ いた(記録が無い・途中 → after: open) |
| おすすめ | いない |
| controls | A.6.5(辞めた後・変わった後の責任)・A.5.18(アクセス権)・A.5.11(資産の返却) |
| evidence | github-collaborators・aws-iam-users |

## 11. 決めたこと(AI が決めた。人に聞かなかった)

- 止める順を「届く範囲の広い順」(AWS → GitHub → 運営の組織 → …)にした — 本番とお客さんのデータに届く物から先に止める。
- 入る日に prod の権限を渡さない — 最小の権限(基本方針の 8「要る権限だけ」)。
- 会社のメールを止めるだけでは足りない、と手順書の頭に書いた — パスワードと二段階認証でほかの道具に入れる。
- 点検の項目を毎月にした — 棚卸し(四半期)だけだと、辞めた人のアカウントが最長3か月残る。答えは1問で軽い。
- ADR は足さなかった — 仕組みの選び方ではなく、既存の基本方針を手順にした物。
- カタログ(`docs/kit/catalog.yaml`)には足していない — 並行の PR が同じ所(README の部品の数)を直していてぶつかる。手順書は基本方針・棚卸し・記録の置き場から指す。
- 想定の場面(`docs/scenarios/`)は直さない — 場面の持ち主が直す。
