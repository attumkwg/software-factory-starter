## 0. 全体像

受け入れの記録の型(`docs/acceptance/`)・解決済みの論点の一覧(`docs/domain/resolved-questions.md`)・それを回すスキル `/accept`・読んで点数を出し書き方を確かめる `pnpm acceptance` を足す。PdM に回す観点は4つを**おすすめ**として示し、外れた所は `pnpm acceptance` が知らせる(落とさない)。記録を取るかは使うときに決める(U-2)。

```mermaid
flowchart LR
  S[仕様 第1部・第2部] --> A[/accept が項目を作る]
  D[設計書 7・12] --> A
  R[解決済みの論点] --> A
  A -->|おすすめの4つ| P[PdM に1問ずつ]
  A -->|網羅の観点| Q[AI が流す / QA へ一覧]
  P --> M[docs/acceptance/NNNN 第N回]
  Q --> M
  M -->|否: 要求| R
  M -->|否: 設計・仮決め| W[/rework]
  M --> C[pnpm acceptance 点数・書き方]
```

## 1. 設計方針

- **記録はリポジトリの中の Markdown**(仕様・設計書と同じ置き場の流儀)。1つの仕様に1ファイル `docs/acceptance/NNNN-<名前>.md`、回は `## 第N回 YYYY-MM-DD` で足すだけ。DB・外のサービスは使わない。
- **観点はおすすめ**。おすすめの言葉と見る人の組み合わせから外れた所は知らせる(`notices`)が、CI は落とさない(U-1 の答え)。点数を分けるのに要る「見る人」・「結果」・「外れた理由」の言葉は決まった物にし、崩れたら CI で止める。
- **CI は `test:scripts` の1本のテスト(「今の記録」)で止める**。`.github/workflows` を変えない(危険度「高」に触れずに足せる)。手元の入口は `pnpm acceptance`。
- 読み方は `decisions-lib.mjs` と同じく正規表現を使わない。
- 週の数字(`pnpm metrics`)に点数と理由の内訳を出すのは仕様 0077(引き渡しの数字と一緒)。ここでは `readRepoAcceptance()` と `scoreOf()` を外から使える形で出す。

## 2. データモデル

DB は使わない。ファイルの形:

- `docs/acceptance/NNNN-<名前>.md`(`_` で始まる物は型として読まない)
  - 頭: 仕様・設計へのリンク・`実装の PR: #n, #m`(0077 が実装の完了の日を引く)
  - 回: `## 第N回 YYYY-MM-DD`(日付は始めた日)・見た人・見た所・表
  - 表: `| # | 観点 | 見る人 | 項目 | 結果 | 外れた理由 | 書き戻し先 |`。1列目が数字の行だけ項目として読む。回の見出しより前の表は読まない
- `docs/domain/resolved-questions.md`
  - 表: `| 番号 | 論点 | 答え | 分かった所 | 書き戻したナレッジ | 日付 |`。1列目が `R-数字` の行だけ読む

| 列 | 取りうる値 |
|---|---|
| 観点(PdM) | `流れ` / `ルール` / `作り込み` / `仮決め` |
| 観点(網羅) | `状態` / `境界値` / `権限` / `URL` / `スマホ` / `a11y` / `プラン` / `その他` |
| 見る人 | `PdM` / `AI` / `QA` |
| 結果 | `合` / `否` / `未` |
| 外れた理由 | `要求` / `設計` / `AI の仮決め` / `実装`(`否` のときだけ) |
| 書き戻し先 | 自由。`要求` なら `R-n` が1つ以上(論点の一覧にある番号) |

## 3. API

該当なし(アプリの API は変えない)。スクリプトの出入り:

- `scripts/acceptance-lib.mjs`: `readResolved(text, path)` → `{ ids, problems }`・`readAcceptance(files, ids)` → `{ rounds, problems }`・`scoreOf(round)` → `{ pdm, sweep, all, pdmItems, items, reasons }`・`readRepoAcceptance(root)`・`percent(v)`
- `scripts/acceptance.mjs`(`pnpm acceptance`): 回ごとの表を出し、問題があれば 1 で終わる

## 4. 状態遷移

項目の結果: `未` → `合` / `否`(同じ回の中で、答えを写すとき)。回を閉じたら書き換えない。直した後は次の回を足し、前に `否` だった項目を必ず入れる(`/accept` の 1)。

解決済みの論点: 足すだけ。答えが変わったら新しい `R-n` を足し、古い行の答えに「R-n で変わった」と書く(番号は消さない)。

## 5. システム間連携

- `/accept` の AI の項目は、プレビューか手元の docker compose を E2E の部品で叩く(`apps/web/e2e/helpers.ts`)。外のサービスには送らない。
- `/report-bug`・`/rework`・`/update-domain-docs`・`/new-feature` へ渡す(書き戻し)。
- 読むのは `gh pr list`(実装の PR の番号)だけ。

## 6. 業務ルール

- 観点のおすすめ: PdM の4つは見る人 `PdM`・網羅の観点は `AI` か `QA`。外れた所・おすすめに無い言葉は知らせる(落とさない)。見る人は `PdM` / `AI` / `QA` のどれか(書き方の問題)。
- `否` には理由が必須。`合`・`未` に理由を書くと書き方の問題。
- `要求` の `否` には `R-n` が必須。指した `R-n` は論点の一覧に必要。
- 点数 = 合 ÷(合+否)。`未` は分母に入れない。分母が0なら「—」。PdM・AI と QA(`AI` と `QA` を合わせる)・全体の3つ。
- 回の日付は `YYYY-MM-DD`。前の回より前の日付は書き方の問題。項目の無い回は書き方の問題。
- 論点の番号の重なりは書き方の問題。
- 人ごとの点数は出さない(見た人は記録に残すが、数えない)。

## 8. 非機能

- 性能: ファイルを読むだけ。記録が数百でも1秒未満。
- セキュリティ: 仕様の STRIDE のとおり。記録に利用者のデータを書かない決まりはスキルと手引きで(機械では確かめない)。
- 運用: `pnpm acceptance` が崩れた所を `ファイル:行` で出す。
- 費用: なし。

## 11. 決めたこと(AI が決めた。人に聞かなかった)

- 1つの仕様に1ファイル・回は見出しで足す — 同じ機能の回を並べて見られ、前の回を消さずに済む。
- 理由に `実装` を足して4つにした — 設計どおりに作れていない外れは要求・設計・仮決めのどれでもなく、入れないと上流に誤って振られる(直す工程が違う)。
- 迷ったら上流の理由に — 上流の穴を下流のせいにすると、書き戻しが起きない。
- CI は `test:scripts` の「今の記録」のテストで止める — `.github/workflows` を変えると危険度「高」になり、この部品のためだけに人の2人の確認を要らせない。
- 正規表現を使わずに読む — `decisions-lib.mjs` と同じ(Semgrep の regex_dos)。
- 試作(`prototypes/`)は対象外 — 試作は相手に見せて賭けの線で判断する(`/prototype`・`/bet`)。
- 週の数字に足すのは 0077 — 引き渡しの数字(実装の完了から受け入れまで)と同じ記録を読むので、まとめて決める。
