## 1. 設計方針

- 新しい仕組みを作らず、今ある3つ(観点の台帳・`/review-pr`・AI のマージ)をつなぐ。
- 「別の AI」は、エージェントの定義(`.claude/agents/`)で文脈を切る。意義の判断役(仕様 0084)と同じ作り。
- 人格は新しく作らず、製品のペルソナと携わる人の立場から、レビューで気持ちが違う5人を選ぶ。台帳の観点は、どれかの人格に必ず入れる(抜けると誰も見ない)。
- 機械で止めるのは「記録が有るか」だけ。中身の正しさは人の決めたことに任せる(CI は参考、決めるのは人 — 持ち主の言葉)。

## 2. データモデル

- 該当なし(DB は触らない)。記録は PR のコメント(GitHub)。

## 3. API

- 該当なし。`pr-merge-lib.mjs` に足す関数:

| 関数 | 入力 | 出力 |
|---|---|---|
| `reviewedShaOf(body)` | コメントの本文 | 「当てた版: \`…\`」の版(無ければ空) |
| `reviewState(comments, headSha)` | PR のコメントの並び・今の版 | `{}`(良い)/ `{ problem }`(止める)/ `{ note }`(知らせるだけ) |

## 4. 状態遷移

- PR: 記録なし → (`/review-pr` と人の答え)→ 記録あり → (直した版を積む)→ 記録あり・版が進んだ → マージ
- 記録はいちばん新しい物を見る。やり直したら新しい記録を足す

## 5. システム間連携

- GitHub の PR のコメント(REST の `issues/<番号>/comments`)を読むだけ。`pr-merge-when-green.mjs` は、緑を待つ前と、緑になった後の2回見る(待つ間に記録が付くこともある)
- レビュー役は `gh pr view` / `gh pr diff` / `gh pr checks` で読む(書かない)

## 6. 業務ルール

- 呼ぶ人格: 「低」は 🧑‍🔧(画面か API の動きを変えるなら 🧑‍💼 も)・「中」「高」は5人(台帳の表)
- 1つの人格で多くて7件
- 聞く順: ❓ → ❌ → ⚠️。⚠️ が4件を超えるときだけ、⚠️ を「おすすめどおり全部 / 1つずつ」で先に聞いてよい

## 8. 非機能

- 費用: 「中」「高」の PR は、レビュー役を5回呼ぶ(並べて呼ぶので時間は1回分に近い)。「低」は1〜2回
- 運用: 記録が無いと AI のマージが止まる。止まったら `/review-pr` を回す(手引きの 7)

## 9. このプロダクト特有

- 台帳の観点(共通の8つ+このプロダクト特有の9つ)を、5人の人格に分けた。テナント分離・権限の表 → 🦹、監査ログ・ログの個人情報・列の分類・代理ログイン → 🔍、解約で消す一覧・ページング → 🌙、画面の部品 → 🧑‍💼。抜けは無い

## 11. 決めたこと(AI が決めた。人に聞かなかった)

- 人格は5人: レビューで気持ちが違う人に絞った(製品のペルソナ10人・携わる23人を全部回すと、低い PR にも重い)
- 機械で見るのは記録が有るかと当てた版だけ: 記録の中身(人格を本当に別の AI で回したか)は機械で確かめられない。書けば通る割り切りで、手順と受け入れの外れで戻す。人が増えたら人の承認に戻る(仕様 0080 のまま)
- 当てた版が進んでも止めない: 「直す」を直すと必ず版が進むので、止めると毎回やり直しになる。知らせて、記録の「直したこと」で見る
- 問いの上限(本文の「🧑‍⚖️」は多くて2つ。仕様 0080)とは別に数える: そちらは書いた側が出す問い。レビューの所見は人が決める材料で、まとめ方(⚠️ は全部で1問)で量を抑える
- 「低」でも 🧑‍🔧 は回す: 2026-10-29 の外れの1つ(画面のテストが無い)は、書いた側が「低」に近い見立てで出した画面の PR だった
