## 1. 設計方針

- 手引き1枚+既存のスキルと申込書の型に数行。新しいスキルは足さない(`/release-notes` の続きで足りる)。
- 許可の記録はリポジトリの外(申込書と同じ契約の管理の置き場)。リポジトリには欄の型だけ。
- 既定は「出さない」(お客さんが選んだ範囲だけ)。
- ADR は足さない(仕組みの選び方ではなく、決まりと置き場)。

## 2. データモデル

該当なし(DB に触らない)。許可の記録の欄: 会社(組織の ID と名前)・範囲・許可した人(役職)・日付と取り方(写しの場所)・期限・取り消し。

## 3. API

該当なし。

## 4. 状態遷移

許可: 無い(出さない)→ 許可あり(範囲)→ 取り消し / 解約 → 30日以内に外した。許可の範囲を広げるときは取り直す。

## 5. システム間連携

該当なし。配信の道具を使うなら委託先の台帳に1件(手引きの 1)。

## 6. 業務ルール

- 出す物: リリースノート(開発の人)・お知らせ・プレスリリース・導入事例(広報か責任者)。下書きは Claude、出すのは人。
- 書かない: 言わないこと・根拠の無い数字・比べる言い方・許可の無い名前・まだ出していない物の約束・中の言葉。料金は料金表と同じ値。
- 許可の段: 出さない(既定。U-1)/ 名前 / 名前とロゴ / 事例の記事・声(本人の同意も)。
- 取り方: 申込書の任意の欄か、書面・メール。口頭だけで出さない。
- 出す前: 記録と範囲を確かめる。事例の原稿はお客さんに見せる。
- 取り消し・解約: 自社のサイト・資料から30日以内に外す(U-2)。印刷物と相手の媒体は外せないと、許可のときに伝える。

## 11. 決めたこと(AI が決めた。人に聞かなかった)

- 新しいスキルを足さず、`/release-notes` に1段足した — 広報の文の元は利用者向けのリリースノート。呼ぶ所を増やさない。
- 「言わないこと」(positioning.md)を下書きの決まりの最初に置いた — 約束できない物を広報で言うと、営業・LP とずれる。
- 許可の記録をリポジトリの外に置いた — 会社の名前と許可の組み合わせは、契約の一部(申込書と同じ所)。
- 解約したら名前を外す — 使っていない会社を「導入している」と見せない。
- 声と写真は本人の同意も要る、と分けた — 会社の許可は会社の名前とロゴまで。人の名前と顔は個人データ。
- ADR は足さない — 1. の理由。
- 想定の場面(`docs/scenarios/`)と `docs/product/` は直さない — 持ち主が直す・読むだけ。
