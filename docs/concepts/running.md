# 長く回す(落ちても戻る作り・ログ・監視・点検)

> 入口は [README.md](README.md)。ファクトリーは「作る」を速くするが、「持つ」は消えない。長く回るかは、道具より「誰が持つか」と「点検の決まり」で決まる。
> このキットでの具体の手順は [../guides/monitoring.md](../guides/monitoring.md)・[../runbooks/](../runbooks/)・[../playbook.md](../playbook.md) の「毎月・四半期にやること」。

## 1. 「落ちない」ではなく「落ちても戻り、理由が残る」

TypeScript(Node.js)の API は、DB や外部 API を待つ時間が長いふつうの業務 API なら本番で十分持つ。苦手なのは重い計算(画像処理・大きな集計・PDF の生成)で、1つの重い処理がその間ほかを止める → **重い処理はキューと別のワーカーに分ける**。

| 落ち方 | よくある原因 | 対策 |
|---|---|---|
| プロセスが死ぬ | 捕まえていない例外・Promise の失敗 | 最後にログを出して終わる → ECS が立て直す。Sentry に積む |
| メモリ不足で殺される | 大きなデータを一度に読む | 終了コード 137 で分かる。メモリの警報+ページ分割(一覧は必ずページング) |
| 応答が止まる | 重い処理で1本のスレッドが詰まる | 重い処理はワーカーへ。DB のクエリには時間切れ |
| 変な入力で壊れる | 型は実行時に守ってくれない | 入口で Zod で必ず確かめる(型と検証を同じ定義から作る) |
| デプロイで壊れる | 新しい版が起動しない・すぐ死ぬ | blue/green とアラームで旧版に戻す |

- 🔁 **最低2台を別の AZ に**。ALB はヘルスチェックに落ちた台に流さない。
- 🛑 **止め方を決めておく**: 終わりの合図(SIGTERM)を受けたら、新しい受付をやめ、処理中を終えてから閉じる。

## 2. ログが「残らない」を防ぐ

- 🔴 **コンテナの中のファイルにログを書かない**(コンテナと一緒に消える)。**標準出力に JSON で出す**だけ。ECS が CloudWatch Logs に逐次送るので、死ぬ直前まで残る。
- 🧵 **1リクエストに1つの ID** を全部のログに付け、応答のヘッダーにも返す。「この画面のこのエラー」から一発でログに辿れる。
- 🙈 **個人情報はログに出さない**: 出してよい項目だけを出す(許可リスト)。**AI はオブジェクトを丸ごとログに出しがち**なので、検査のルールで止める([ADR 0019](../adr/0019-log-allowlist.md)・`packages/logging`)。
- 📉 **本番は INFO 以上**。数えたい物(件数・時間・割合)はログで数えずにメトリクスで出す。
- 🚨 **ログの量に予算と警報**: AI が足したループの中のログ1行で、月数十万円増えることがある。

### ログの種類と置き場所(規模が大きくなったら)

| 種類 | 中身 | 送り先 | 保存 |
|---|---|---|---|
| アプリのログ | エラー・警告・大事な業務の出来事 | CloudWatch Logs | 14〜30日 |
| アクセスログ | ALB・CloudFront の全リクエスト | S3 に直接 → Athena で検索 | 90日〜1年 |
| 監査ログ | 誰が何をした(権限の変更・書き出し等) | 別アカウントの S3(書き換えられない設定) | 法令・契約どおり(数年) |
| セキュリティ | CloudTrail・GuardDuty・VPC のフローログ | 専用の S3 | 1年〜 |
| 数えられる物 | 件数・時間・割合 | **ログではなくメトリクス** | — |

- 💰 1日500GB を全部 CloudWatch Logs に入れると月 約170万円。種類で分けて DEBUG を止めると 約23万円。
- このキットの監査ログは、まず DB の表に置く([ADR 0013](../adr/0013-audit-log.md))。別アカウントの S3 への写しは PMF の後。

## 3. 監視の型(最初に入れる一式)

| 見るもの | 道具 | 鳴らす条件の例 |
|---|---|---|
| エラー(スタックトレースつき) | Sentry | 新しい種類のエラー・急増 |
| 応答時間・エラー率 | ALB のメトリクス | 5xx が5分で1%超・p95 が1秒超 |
| 台数・再起動 | ECS | 10分で3回以上の再起動 |
| DB | Aurora | CPU 80% 超・接続数・遅いクエリ |
| 外から見た死活 | 外形監視 | トップとログインが2回続けて失敗 |
| 費用 | AWS Budgets | 月の予算の80%・急増 |

- 📣 鳴ったら Slack の障害のチャンネルへ。**夜中に人を起こすのは「利用者が使えない」物だけ**。
- 🤖 AI に一次調査させる: エラー → Issue → AI が dev・stg のログを読み、原因の案と直す PR を出す。**本番のログは読み取りだけ・個人情報を伏せた形で**。
- 🔥 障害のときは、まず**直前のデプロイを戻す** → 落ち着いてから原因 → 振り返りで「テスト・アラーム・ルールのどれを足すか」を決める([../runbooks/incident.md](../runbooks/incident.md))。

## 4. PR ごとの環境(プレビュー環境)の安全

共有の ALB の後ろに「PR 番号のコンテナ」を1組立てるだけ。10本並べても、夜と休日に止めれば月1〜2万円ほど。本番と同じ水準は要らないが、次の5つを守る。

1. 🏢 **本番とは別の AWS アカウント**。プレビュー用の役割は dev のアカウントにしか入れない。
2. 🧪 **本物の個人データを入れない**。種データは作り物だけ。
3. 🔒 **社外から見えなくする**(ログインか、許した IP だけ)。
4. 🍴 **外の人の PR では動かさない**。フォークの PR には秘密も AWS の役割も使わせない。
5. 🧹 **必ず壊す**: 閉じたら消す・毎晩の掃除・予算の警報。

## 5. E2E はどこまで厚くするか

- 🧱 **土台に数日**(ログイン済みの状態・テストデータの出し入れ・`getByRole` で取れる作り)。**ここが一番大事で、AI に任せきりにしない**。1つのシナリオは AI で15〜60分。
- 🔺 **E2E は「大事な流れ」だけ(20〜50本)、細かい分岐は API の結合テスト**(本物の Postgres で数百本)、計算と変換は単体テスト。E2E は遅く不安定になりやすく、増やすほど手入れが重い。
- ✅ それでも一気通貫の E2E は「AI の PR を信じる根拠」として一番強い(画面から DB まで本物で動いた証拠)。
- 🧯 **不安定なテストの扱いを決めておく**: 理由なく続けて落ちたら必須から外して Issue にし、直す。放置すると誰も結果を信じなくなる。

## 6. Terraform を選んだ理由

| 観点 | Terraform | CDK |
|---|---|---|
| 変える前の確認 | `plan` で「何が増える・変わる・消える」が一覧で出る | 差分は出るが CloudFormation の形で読みにくい |
| AWS 以外 | GitHub・Sentry なども同じ道具で | AWS だけ |
| 失敗したとき | ずれは `plan` で分かり、直して再実行 | スタックが「更新失敗で戻せない」状態に詰まることがある |
| 書く量 | 多め(モジュールで減らす) | 少なめ |

- 🔑 **一番の理由は「plan を人と AI が読んでからレビューできる」こと**。インフラの変更は危険度「高」なので、「何が消えるか」を必ず見る。人が見る所を絞って、そこは確実に見る、という考えと合う。
- 🔒 ロックインの本体は道具ではなく**使う AWS のサービス**。弱めるのはコンテナ・PostgreSQL・OpenTelemetry のような標準の部品を選ぶこと。ライセンスが気になれば互換の OpenTofu に移れる。
- 🤔 AWS だけ・全員 TypeScript・小さく速く作りたいなら CDK でもよい。長く運用し、人が入れ替わる前提なら Terraform。

## 7. 持ち主と点検表

- 👤 **サービス・領域ごとに持ち主**(CODEOWNERS と同じ人)。AI が書いたコードでも、判断と説明の責任は持ち主にある。
- 📚 **リポジトリに手順書**(`docs/runbooks/`)。AI も読めるので、障害の一次調査を任せられる。
- 🧠 **設計の全体像は人の頭に残す**: ADR を人がレビューする。境界(モジュールの分け方・表の設計)は人が持てば、中身は AI が書き直せる。

| 頻度 | やること | 主に誰 |
|---|---|---|
| 毎日 | アラート・新しいエラー・デプロイの失敗を5分見る | 当番 |
| 毎週 | ラインの振り返り / 依存の更新をまとめて入れる / Terraform のずれ | テックリード+AI |
| 毎月 | 費用 / ベースイメージの更新 / CLAUDE.md・スキルの整理 / 不安定なテストの棚卸し | テックリード |
| 四半期 | バックアップから実際に戻す訓練 / 障害の訓練 / 指標の見直し | チーム |
| 毎年 | Node.js の LTS の更新 / 外部の脆弱性診断 / 権限の棚卸し | 持ち主 |

- 🔄 **依存の更新をためない**。ためると1年後に「上げられない」状態になるのが、長期運用の一番の失敗。
- 💾 **バックアップは「戻せる」ことまで確かめる**([ADR 0012](../adr/0012-backup-vault-and-restore-drills.md))。
- 📉 **質が落ちていくのを防ぐ**: 複雑さ・ファイルの長さを CI で測って上限を超えたら止める。片づけの PR を毎週 AI に出させる。新しい機能より先に境界を決める。
