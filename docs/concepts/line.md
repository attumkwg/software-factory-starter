# ラインの作り(7工程・ハーネス3層・危険度で分けるレビュー)

> 入口は [README.md](README.md)。「AI エージェントが PR を出す」前提で、道具・流れ・体制をどう組むか。
> このキットでの日々の進め方は [../playbook.md](../playbook.md)、ファイルとの対応は [../reference.md](../reference.md) の「🧭 考え方とこの雛形の対応」。

## 1. 5つの原則

1. **人の開発者に速いものは、AI にも速い**。環境の起動・lint・テストの速さに先に投資する。
2. **決まった手順は仕組みで、考える所だけ AI**。整形・lint・型・テスト・push を AI のやる気に任せない(フックと CI で必ず走らせる)。
3. **AI は自分で確かめられる所まで連れていく**。本物と同じ形の環境・画面・ログを見られるようにする(手元の docker compose・プレビュー環境・偽物の Cognito)。
4. **人の判断は前(仕様)に寄せ、後ろ(レビュー)は危険度で絞る**。
5. **同じ失敗は2回目でルールにする**。ルール・テスト・lint・スキルに変えて、ラインそのものを直す。

## 2. 全体の流れ(7工程)

| 工程 | 何をする | 誰が | 道具 |
|---|---|---|---|
| ① 受付 | 要望・不具合・アラートを Issue にする | 誰でも+AI | GitHub Issues(Slack から起票してもよい) |
| ② 振り分け | 大きさ・曖昧さ・危険度を付ける | AI が案 → PdM | Issue テンプレート+ラベル |
| ③ 仕様 | 業務の要求とルールは PdM が書き、システムの振る舞い(状態・境界値・権限の組み合わせ)と悪用のされ方は AI が網羅してエンジニアが見る([people-and-ai.md の 1.1](people-and-ai.md#11-段を決める問い説明の責任)) | PdM+AI、大きい物はテックリード | `docs/specs/`・`docs/designs/`・`docs/adr/` |
| ④ 実装 | ブランチを切り、実装とテストを書く | AI(背景エージェント) | Claude Code(手元 / GitHub Actions) |
| ⑤ 検証 | 型・lint・テスト・プレビューで動作確認 | 仕組み+AI | GitHub Actions・Playwright |
| ⑥ レビュー | AI が一次、人は危険度に応じて | AI → 領域の持ち主 | AI のレビュー+CODEOWNERS |
| ⑦ 出荷と監視 | 自動デプロイ、異常なら自動で戻す | 仕組み | ECS の blue/green・CloudWatch |

- 🔁 ⑦の結果(エラー・遅さ・使われ方)は ① に戻す。アラートから Issue を起こす。
- 🧑‍⚖️ **人が必ず止まる所は3か所だけ**: ③ の仕様の承認・⑥ の危険度「中・高」のレビュー・本番に出す承認([../playbook.md](../playbook.md)・ルートの README の「1つの機能が出るまで」)。ほかは仕組みで流す。
- 🚦 **③ の仕様の承認の基準は「ブロッカーがゼロ」**(欠陥ゼロではない)。設計の向きを変える事柄に印があり・矛盾が無く・捨てた仮説が混ざらず・未確定に印があり・やり方を書きすぎていなければ、中・小の指摘が残っていても流す。仕様を完璧にしてから進めると、仕様が人の詰まり所になる(下の 6)。5つの中身は [../guides/human-review.md](../guides/human-review.md) の 6。
- 🤖 ⑥ の「AI が一次」は目指す形。**このキットでは AI のレビューの道具はまだ入れていない**(見逃しを数えてから。[../reference.md](../reference.md) の「わざとやっていないこと」)。いまの一次の確かめは、CI の検査と、書いた AI が終わる前に回す型とテスト。
- 📏 **1 Issue = 1 PR = 戻せる単位**。大きい仕様は親 Issue → 子 Issue に割ってから AI に渡す。
- 🙋 **人に聞くのは4つだけ**(事業判断・利用者の挙動・他チームとの契約や制約・戻せないリスク)。それ以外は AI が決めて理由を残す。詳しくは [../guides/human-review.md](../guides/human-review.md)。

## 3. 技術の既定

| 層 | 選ぶもの | 理由 |
|---|---|---|
| 言語 | TypeScript(strict)一本 | 画面〜API〜インフラ〜E2E が1言語。型チェックが「AI の答え合わせ」として一番安く速く効く。言語を増やすとルール・スキル・テストが二重になる |
| リポジトリ | モノレポ(pnpm workspaces+Turborepo) | 変更の影響範囲だけテストできる |
| 画面 | React(TanStack Start。SSR) | AI が一番書き慣れている |
| API | Hono+Zod(OpenAPI を作る) | 型と契約が1か所 |
| DB アクセス | Drizzle | SQL に近く、移行ファイルが読める(移行は人が必ず見る対象なので、差分が読めることを優先) |
| lint・整形 | Biome | 1秒未満で終わる。フックで毎回回せる速さが大事 |
| AWS | ECS Fargate+ALB・Aurora PostgreSQL・Secrets Manager・CloudWatch | コンテナ単位で本番・stg・プレビューが同じ形 |
| インフラ定義 | Terraform | `plan` で「何が消えるか」を人と AI が読んでからレビューできる([running.md の 6](running.md#6-terraform-を選んだ理由)) |
| CI/CD | GitHub Actions → AWS は OIDC | 長期のアクセスキーを作らない。役割はリポジトリ・ブランチ・環境ごとに分ける |
| デプロイ | ECS の blue/green+アラームで自動で戻す | 壊れたら数分で旧版に戻る |

- 🐍 Python は ML・データ処理だけ。チームが Go に強いなら API を Go にするのはあり(その場合も画面と E2E は TypeScript)。
- 📱 スマホも作るなら React Native(Expo)で TypeScript を共有する。**古いアプリが何か月も残るので、API は項目を足すだけ・消さない・意味を変えない**(このキットの「API の互換」の検査はそのため)。

### CI の段と速さ

| 段 | 何をする | 目安の時間 |
|---|---|---|
| コミット前(フック) | 整形・lint・型(変更分だけ) | 数秒 |
| PR: 速い検査 | 型・lint・単体・影響範囲だけ | 3分以内 |
| PR: 結合 | 本物の Postgres で API のテスト・契約テスト | 5〜10分 |
| PR: セキュリティ | [../security.md](../security.md) の「毎回の検査」 | 並行で |
| PR: プレビュー | 環境を立てて E2E、スクショと動画を PR に貼る | 10分前後 |
| main へマージ後 | イメージを作り → stg に自動デプロイ → スモークテスト | 自動 |
| 本番 | 承認 → blue/green → アラームで自動で戻す | 承認1回 |

- 🎯 **速さが品質**: PR の最初の結果が3分で返らないと、AI も人も待つ。遅くなったら「影響範囲だけ回す」を先に直す。

## 4. ハーネスは3層で育てる

ハーネス = AI を動かし、守り、確かめさせる仕組み一式。**いきなり③を作らない。**

### ① 手元の Claude Code(初日から)

- 📏 **ルールは短く、場所ごとに**。全体の `CLAUDE.md` は最小限(コマンド・禁止事項・どこに何があるか)、画面と API のルールはそれぞれのフォルダの `CLAUDE.md`。長くなったらスキルか場所ごとのルールに移す。
- 🪝 **フックで「決まった手順」を固定**: 書いたら整形、作業を終える前に型と影響範囲のテスト。AI が忘れても必ず走る。
- 🧰 **スキルは「2回目にやった作業」から作る**(API を足す・DB を移行する・リリースノート など)。
- 🔌 **MCP は少なく**。増やすほど迷う。

### ② Issue から PR を出す背景エージェント(2〜4週目から)

- 🚦 入口: Issue や PR に `@claude` → GitHub Actions の上で実装して PR を出す。**起動できるのは組織のメンバーだけ**(Issue の文章は外の人が書けるデータ。[../security.md の AI-3](../security.md#決まり-1-ai-ならではの守りai-1ai-5))。
- 🔁 手順を固定する: 仕様を読む → 実装 → 整形・lint・型・単体を手元で通す → push → CI が落ちたら直す(**最大2回**)→ だめなら人に渡す。
- 🧾 PR に必ず付ける証拠(PR テンプレートで強制): どの仕様・Issue か / 何を変えたか / 危険度 / テスト結果・プレビューの URL・スクショ / **「人に判断してほしい所」を一番上に**。

### ③ 自前のファクトリー(PR が週に数十件を超えてから)

- 🏗 作る合図: ① 並列で何本も走らせたいのに GitHub の実行環境では足りない ② 本物に近い環境(DB・画面)の中で AI に確かめさせたい ③ Slack から誰でも頼みたい。
- 🧩 中身の例: Agent SDK をコンテナ(かサンドボックス)で1件1台。イメージを温めて起動を速く。
- ⚖️ **作らない判断も大事**。運用費まで含めて、作るか買うかを決める。

## 5. 危険度で人が見る量を決める

| 危険度 | 例 | AI のレビュー | 人 |
|---|---|---|---|
| 低 | 文言・ドキュメント・テストの追加・依存の小さい更新 | 必須 | 0人(チェックが緑なら自動マージも可) |
| 中 | ふつうの機能追加・不具合の修正・スキル(AI の手順) | 必須 | 1人(その領域の持ち主) |
| 高 | 認証・認可・課金・個人データ・DB の移行・インフラ・CI の設定・分離を確かめるテスト・「してはいけない」を書いた CLAUDE.md | 必須 | 2人(必須のチェックで人数を数える。1人の間は 0) |

- 🤖 上の表の「AI のレビュー 必須」も目指す形(いまのキットでは CI の検査が代わり。上の 1)。
- 🏷 危険度は **変えたパスで自動で付ける**。AI の自己申告に頼らない(このキットでは `.claude/hooks/protected-paths.json` が一覧の正)。
- 🧪 最初の1〜2か月は「低」も人が見て、AI のレビューの見逃しを数えてから外す。

## 6. どれだけ回せるか

- 🧮 **目安**: 危険度「中」の小さな PR の確認に10〜20分。レビューに1日1〜2時間使える人が1人いると、**週30〜50件**。危険度「低」を自動マージにできれば、その分は人の時間を使わない。
- 📝 **もう1つの上限は仕様**: AI に渡せる「受け入れ条件つきの Issue」が無ければ、AI は止まる。仕様を固められる量が、そのまま上限になる(毎週「仕様の在庫」を見るのはそのため)。
- ➕ **回す量を増やす順番**: PR を小さくする → 危険度「低」を増やす(テストを厚く)→ 人の確認を「判断すべき所だけ」に並べ替える → レビューできる人を増やす。

## 7. 体制(小さく始める形)

| 役割 | 何をするか | 最初の人数 |
|---|---|---|
| 🏭 テックリード(ラインの持ち主) | ハーネス・CI・環境・ルール・危険度の線引き。週の振り返りの持ち主 | 1人(兼任可) |
| 📝 PdM | 仕様と受け入れ条件・優先順位。**仕様の在庫を枯らさない**のが一番の仕事 | 1人 |
| 🧑‍⚖️ 領域の持ち主(エンジニア) | 設計判断・中と高のレビュー・AI が詰まった所の手作業 | 2〜3人 |
| 🧪 QA・評価 | E2E のシナリオ・「人が見るべき所」の一覧づくり | 兼任から |

1人で始めるなら全部を兼ねる。そのときも「仕様を決める時間」と「レビューの時間」を分けて取る。

- 🔁 **毎週30分「ラインの振り返り」**: AI が同じ失敗をした所 → ルール・テスト・lint・スキルのどれに変えるかを決める。これが改善の本体。
- ⚠️ **企画が詰まりになる**: 実装が速くなると「次に何を作るか」が足りなくなる。仕様を書く時間と、顧客に近づく時間を最初から取っておく。

## 8. 測るもの

| 指標 | 見方 |
|---|---|
| DORA の4つ(デプロイの頻度・変更のリードタイム・変更の失敗率・復旧の時間) | 「速くなったか」と「壊れていないか」を同時に見る |
| AI が書いた PR の割合・人の介在率 | 人の介入なしで終わった割合。失敗率とセットで見る(DORA と一緒に `pnpm metrics` が毎週出す。[../guides/metrics.md](../guides/metrics.md)) |
| レビュー待ちの時間・往復の回数 | 伸びたら危険度の線引きか PR の大きさを直す |
| PR の種類の比率(機能・修正・保守・テスト) | 保守ばかりなら仕様の在庫が枯れている合図 |
| 静的解析の警告・複雑さの推移 | AI を入れると数か月で質が落ちやすい。上がり始めたら lint とルールを強める(このキットは複雑さとファイルの長さに上限を持つ。[../guides/ci-limits.md](../guides/ci-limits.md)) |

## 9. やらないこと・落とし穴

- ❌ **最初から「人がコードを読まない」を狙わない**。シナリオでの検証と、本物を写した環境がそろってからの話。
- ❌ **道具を増やしすぎない**。エージェント・MCP・レビューの道具は各1つから。
- ❌ **AI の生成量を成果にしない**。PR の数は増えて当然。見るのは 8 の指標。
- ❌ **本番の鍵を AI の環境に置かない**。便利さで一度例外を作ると戻せない([../security.md の AI-1](../security.md#決まり-1-ai-ならではの守りai-1ai-5))。
