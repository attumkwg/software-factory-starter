# 人と AI の分担

> 入口は [README.md](README.md)。運用しながら決めていく部分はあるが、**立ち上げの時点で「ここは人・ここは AI」は決められる**。
> このキットでの日々の分担の早見表は [../playbook.md の「人と AI の分担」](../playbook.md#人と-ai-の分担)。

## 1. 4段の分け方

| 段 | 意味 | 例 |
|---|---|---|
| ① 人が決める | AI は案・比較表・下書きまで。決めるのは人 | 何を作るか・領域の境界・権限の表 |
| ② AI が作り、人が確かめる | AI が書き、人が毎回中身を見て承認 | Terraform・DB の移行・CI の初期設定 |
| ③ AI に任せる | AI が書き、テスト・検査・AI のレビューで確かめる | 危険度が低〜中の実装・テスト・ドキュメント |
| ④ AI にやらせない | AI の環境から手段そのものを外す | 本番の鍵・本番のデータ・支払い・署名 |

- **人が持つのは「ラインそのもの」と「取り返しのつかない判断」**: 何を作るか・領域の境界・テナントの分け方・権限の表・お金と契約・本番の操作・ラインのルール(CI・レビューの決まり)。
- **AI に任せるのは「ラインの上を流れる物」**: 危険度が低〜中の実装・テスト・ドキュメント・依存の更新・不具合の一次調査。
- 🔑 **④は「お願い」ではなく「手段を持たせない」で守る**(鍵を渡さない・権限を付けない・ブランチ保護とフックで止める)。CLAUDE.md に「やらないで」と書くだけでは足りない。このキットの守りの3層は [../guides/local-guards.md](../guides/local-guards.md)。

### 1.1 段を決める問い(説明の責任)

- 🗣 **「なぜそうするかを、その人がチームに説明する責任を持てるか」で分ける**。持てる物は ①(人が書く・決める)。持てない物は AI に網羅させて、人が確かめる(② か ③)。
  - 例: 「承認は2段にする」は業務ルールなので PdM が書く。「7つの状態 × 各操作でボタンがどうなるか」はシステムの振る舞いなので AI が網羅し、エンジニアが見る。
  - 理由が「整合性のため」「エラーを防ぐため」としか言えない決まりは、業務ルールではなくシステムの振る舞い(AI の側へ)。
- ✂️ **仕様を短くするのは「削る」ではなく「書く責任を分ける」**。文字を削るだけでは読む量は2割ほどしか減らない。業務の要求とシステムの振る舞いを分けて、人が読むのを前者だけにすると、3分の1ほどになる(世の中の例)。仕様の型は [../specs/_template.md](../specs/_template.md)。
- 🧑‍⚖️ **確かめる作業を AI に渡しても、「マージしてよい」「出してよい」の説明の責任は人に残る**。③ は「人がいない」ではなく「人が見る所を決まりで絞った」状態。
- 🏷 **AI の仮決めは、人の決定と混ぜない**。AI は決まっていない所も書き切るので、放っておくと譲れない要求と仮決めが同じ重さで並ぶ。印を付けて未確定事項に載せ、人の承認で初めて確定にする([../guides/human-review.md](../guides/human-review.md) の 2)。確かめていない思い込み(仮説)にも印を付け、確定した要求と混ぜない。

## 2. 立ち上げ時点の分担表

### プロダクトと設計

| 作業 | 段 | ひと言 |
|---|---|---|
| 何を作るか・誰のためか・優先順位 | ① | AI は顧客の声の整理と案出しまで(`/kickoff`・`/bet`) |
| 受け入れ条件(仕様) | ② | 箇条書きから AI が清書 → 人が承認(`/new-feature`) |
| 領域の境界・主なエンティティ・表の骨格 | ① | ここを人が持てば、中身は AI が書き直せる |
| テナントの分け方・ID・時刻・お金の決まり | ① | 後から変えると高い8つ([stages.md の 2](stages.md#2-最初の日に決めておく8つ)) |
| 受け入れ(作った機能を出してよいか) | ① と ③ | PdM は PdM にしか判断できない4つだけ。網羅の確かめは AI と QA(`/accept`) |
| ADR(設計判断の記録) | ② | AI が下書き、人が「なぜ」を確かめて承認 |
| 画面のデザインの方向 | ① | 部品化と個々の画面は ③ |

### 土台(インフラ・CI・ハーネス)

| 作業 | 段 | ひと言 |
|---|---|---|
| AWS のアカウント構成・IAM の境界・OIDC | ① → ② | 方針は人、Terraform は AI が書いて人が plan を読む |
| Terraform のモジュール | ② | 毎回 plan を人が読む(何が消えるか) |
| CI のワークフローの初版 | ② | 初版は AI。以後の変更は危険度「高」 |
| 必須チェック・ブランチ保護・CODEOWNERS | ① | ラインのルールそのもの。AI に変えさせない |
| CLAUDE.md の核のルール・危険度の線引き | ① | 細かい場所ごとのルールは ② |
| スキル・フック | ② | 2回目にやった作業から AI に作らせる |
| Dockerfile・監視のアラーム | ② | 雛形は AI が速い |
| E2E の土台(ログイン・データの出し入れ) | ② | ここは任せきりにしない([running.md の 5](running.md#5-e2e-はどこまで厚くするか)) |

### セキュリティ

| 作業 | 段 | ひと言 |
|---|---|---|
| 認証の製品選び・ログインの方式 | ① | 契約と費用が絡む |
| ロールの定義・権限の表の各行 | ① | AI が API を足したら1行の案を出し、人が承認 |
| 脅威の洗い出し | ② | AI が STRIDE で下書き → 人が足す |
| テナント分離の部品(文脈・RLS・キャッシュのキー) | ① → ② | 作りは人が決め、書くのは AI でも、変更は人が2人で見る |
| 検査の設定(Semgrep・Trivy・ZAP) | ② | 見つかった穴のルール化は ③ |
| 外部の脆弱性診断の発注 | ① | 範囲と業者を人が決める |

### 日々の開発

| 作業 | 段 | ひと言 |
|---|---|---|
| 危険度「低」の変更(文言・ドキュメント・テストの追加) | ③ | 初めの1〜2か月は人も見る |
| 危険度「中」の機能追加・修正 | ③+人1人 | AI のレビューの後に領域の持ち主が1人 |
| 危険度「高」(認証・課金・移行・インフラ・CI) | ② | 人が2人 |
| 単体・結合テスト・E2E のシナリオ | ③ | 「何を確かめるか」は仕様から |
| 依存の更新(パッチ) | ③ | 緑なら自動マージ。メジャー版と、認証・暗号・DB に触る依存は ② |
| 片づけの PR | ③ | 週1で AI に出させる |
| PR の説明・リリースノート | ③ | 人は読むだけ |

### 運用

| 作業 | 段 | ひと言 |
|---|---|---|
| アラートの一次調査(ログを読む) | ③ | 本番は読み取りだけ・個人情報は伏せて |
| 直す PR を作る | ③ / ② | 危険度に従う |
| 本番へのデプロイの承認 | ① | 始めは人。数字が良ければ自動へ(下の 4) |
| 戻す・障害の宣言・顧客への連絡 | ① | 人が判断し、人の言葉で伝える |
| 障害の振り返りの下書き | ② | AI が時系列を作り、人が「何を変えるか」を決める |
| 費用の確認・予算 | ① | AI は異常の検知と内訳の説明まで |

## 3. AI にやらせないこと(④)

- 🔐 本番の鍵・本番のデータへの書き込み・本番の DB への直接の接続
- 💳 支払い・契約・規約への同意・アカウントの作成
- 🔏 アプリの署名・ストアへの提出の最後の操作
- 🛡 IAM・組織の設定の適用、ブランチ保護・CODEOWNERS・必須チェックの変更
- ✅ 自分(AI)が書いた PR の承認とマージ(危険度「低」の自動マージは「仕組み」が判断する)
- 🗑 データ・バックアップの削除
- 📣 顧客・社外への連絡

このキットでは、ルートの `CLAUDE.md` の「してはいけない」と、`.claude/settings.json`・フック・GitHub のルールセットがこれを手段の側で止めている。

## 4. 時期ごとの人と AI の比重

| 時期 | 人の比重 | 人がやること | AI がやること |
|---|---|---|---|
| 1〜2週目(土台) | 6〜7割 | 境界・テナント・権限の表・アカウント構成・ラインのルール | Terraform・CI・雛形・ドキュメントの下書き |
| 3〜4週目(確かめられるライン) | 5割 | E2E の土台・危険度の線引きの確認・最初の機能の仕様 | プレビュー環境・最初の機能・テスト |
| 2か月目(背景エージェント) | 3〜4割 | 仕様・中と高のレビュー・週の振り返り | Issue からの実装の大半・スキル |
| 3か月目から | 2〜3割 | 何を作るか・設計の判断・高のレビュー・障害の判断 | 実装・テスト・依存の更新・一次調査 |

- ⚠️ 人の「量」は減っても、**判断の重さは減らない**。人の時間は「書く」から「決める・見る」へ移るだけ。

## 5. 任せる範囲を広げる条件(1段ずつ AI の側へ)

| 広げるもの | 条件の例(2か月ぶんの数字で) |
|---|---|
| 危険度「低」を人なしで自動マージ | AI のレビューの見逃しが一定以下・低の PR で戻しがほぼ無い |
| 本番デプロイの承認を自動に | 変更の失敗率が安定・段階的な公開と自動で戻す仕組みが動いた実績 |
| 危険度「中」のレビューを AI+人の抜き取りに | 中の PR の不具合の流出が十分少ない・その領域のテストが厚い |
| アラートから直す PR → 人の承認だけ | 一次調査の当たりが多い |

- 🔙 **戻す条件も決めておく**: 事故が1件出たら、その領域は1段戻す。戻すのは恥ではなく、ラインの調整。
- 📊 判断は週の「ラインの振り返り」で。指標は [line.md の 8](line.md#8-測るもの)。

## 6. 段階で変わること

| 段階 | 分担の考え方 |
|---|---|
| PMF の前 | AI に大きく任せて速く作る。ただし**テナント分離・認証・秘密情報・バックアップは人が持つ**(雑にすると取り返せない所) |
| PMF の後 | この表のとおり。危険度で分けたレビューと、権限の表の承認をきちんと回す |
| 規模拡大 | 領域ごとに持ち主。DB・性能・セキュリティの専門の持ち主を CODEOWNERS に |
