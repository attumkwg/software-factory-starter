# ADR 0027: GitHub の設定はファイルを正にして `pnpm setup:github` で一括で整え、ひな形と使う側を変数 `KIT_ROLE` で見分ける

- 状態: 提案
- 日付: 2026-10-24
- 決めた人: @attumkwg(方針は 2026-10-24 の会話。この ADR は形にした物)

## 背景

- キットに部品を足すたびに、PR に「マージの後に人がやる設定」(ラベルを作る・必須のチェックに足す・最初の `/checkup-refresh`)が溜まり、GitHub の画面で手で直していた。README の手順と実際の設定もずれていた(必須のチェックの1つが入っていなかった)。
- ラベルが無いと `gh issue create --label` が落ち、ラベルで動くワークフローが動かない。どこでどのラベルを使っているかの一覧が無かった。
- ひな形のリポジトリ自身で、毎週の点検の Issue・定期の脆弱性チェックが回っていた。持ち主は「ひな形では運用を回したくない」「使い始める前に一括でやる仕組みにしたい」。

## 選択肢

### 設定をどう整えるか

| 案 | 良い所 | 弱い所 |
|---|---|---|
| A. 設定をファイル(`.github/setup.yml`・`.github/labels.yml`)に書き、自前のスクリプトが `gh` で差分を出す・反映する | 依存を足さない。持ち主の `gh` のログインのまま。試しで差分を見てから反映できる。CI がファイルとコードのずれを見られる | GitHub の API の変化に自分で追いつく |
| B. Terraform の GitHub プロバイダ | 差分と反映の仕組みが揃っている | 状態の置き場と、設定を書けるトークンが要る。AWS より前に使い始めたいのに、Terraform の準備が先に要る |
| C. 外の App(Settings の App など)にファイルを読ませる | push だけで反映される | 設定を書ける広い権限の App を入れる。ルールセット・Environments・Actions の設定まで届かない物がある |
| D. 今のまま README の手順で手でやる | 何も作らない | 溜まる・ずれる(今の困りごと) |

### ひな形と使う側をどう見分けるか

| 案 | 良い所 | 弱い所 |
|---|---|---|
| A. リポジトリの変数 `KIT_ROLE`。セットアップが名前を見て `template` / `product` を書き、定期の運用は `product` のときだけ | 使う人がセットアップを流すまで運用が始まらない(台帳の担当者がキットの持ち主のまま Issue が立たない)。変数はキットから作ったリポジトリに写らない | セットアップを流し忘れると、点検の知らせが来ない |
| B. ワークフローの `if` にひな形の名前を書く(`github.repository != 'owner/name'`) | セットアップが要らない | 作ったばかりで、台帳がキットの持ち主のまま Issue が立つ。名前を変えると外れる |
| C. GitHub の「Template repository」の印(`is_template`) | GitHub の印なので分かりやすい | このキットには付いていない。付けるのは公開の判断(README の注意) |

## 決めたこと

**設定は A、見分けは A。**

- 設定の正は `.github/setup.yml`(リポジトリ・守りの機能・Actions・ルールセット・Environments・秘密の名前)と `.github/labels.yml`(ラベル)。GitHub の画面で直した値は、次の `pnpm setup:github` で差分として出る。
- `pnpm setup:github` は試しが既定。`--apply` で差分のある所だけ書く(何度流しても同じ)。消さない(一覧に無いラベル・扱わない規則)。秘密は名前だけ。
- CI の `pnpm setup:check` が、使われているラベル・必須のチェックの名前・Environment・定期のワークフローの見分けが、ファイルとずれていないかを見る。
- 定期で動くワークフローは `vars.KIT_ROLE == 'product'` のときだけ定期で動く(手では流せる)。ひな形でも回す物は `template_schedules` に理由つきで足す。
- ひな形で動かし続けるのはライブラリの更新(Renovate・Dependabot の通知)だけ。古くなった仕組みの点検と直しは、持ち主が呼んだときに `/checkup-refresh` を1回。溜まった最新化は、使う人が作り始める `pnpm setup:github` で知らせる(持ち主の方針。2026-10-24)。
- ラベルの意味・誰が付けるか・付いたらどうするかは `.github/labels.yml` に持ち、人が読む手引き `docs/guides/labels.md` をそこから作る。
- 使う人の入口は README の「使い始めたらやること」の最初・`docs/getting-started.md` の ③・`/kickoff` と `/tailor`。部品を足した PR は「マージの後に人がやる設定」を書く代わりに、設定ファイルを直す(マージの後は `pnpm setup:github --apply` だけ)。

## 結果として起きること

- 良くなること: ラベルと必須のチェックが「足したら必ずある」。ひな形では運用が回らない。使う人は1つのコマンドで GitHub を整えられ、何が足りないかが一覧で出る。
- 我慢すること: GitHub の API が変わったらスクリプトを直す。設定を変えたら PR のマージの後に人が `--apply` を流す(Actions には設定を書く権限を持たせない)。
- 見直す合図: GitHub が設定をファイルで持てる公式の仕組み(ルールセットの読み込みなど)を出したとき・Organization で複数のリポジトリをそろえたくなったとき(Organization のルールセットに移す)。
