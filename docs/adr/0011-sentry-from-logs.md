# ADR 0011: Sentry には「error 以上のログの1行」を、値を落としてから送る

- 状態: 採用
- 日付: 2026-10-18
- 決めた人: @attumkwg

## 背景

アラーム(ADR 0010)で「全体としておかしい」は分かるが、「この1件がなぜ失敗したか」(スタック・どの版から・どのリクエスト)は Logs Insights で探すしかなかった。ブラウザで起きた失敗は、どこにも残っていなかった。

一方で Sentry は外の会社で、置き場所はアメリカか EU。テナント(他社)のデータを外に出さない決まり(ADR 0001)と両立させる必要がある。しかも Sentry の SDK v11 は、既定でヘッダー・Cookie・リクエストの本文・利用者の情報を集める。

## 選択肢

| 案 | 良い所 | 弱い所 |
|---|---|---|
| A. SDK の自動の仕組み(Hono や HTTP の計装)で、失敗を自動で拾う | 書くコードが少ない・リクエストの情報が付く | 何が送られるかを SDK の版が決める(版が上がると増える)。esbuild で1つにまとめると計装が効かないことがある |
| B. **ログの error 以上の行を、そのまま Sentry の1件にする** | 失敗はいままでどおり `logger.error` で残すだけ。送る中身を自分で決められる(ログに出した物より少ない) | リクエストの情報は requestId だけ(本文などは付かない)。ログに残さなかった失敗は届かない |
| C. Sentry を使わず、Logs Insights と CloudWatch のアラームだけ | 外に出さない・無料 | 同じ失敗をまとめる・版ごとの増減・ブラウザの失敗が無い |

## 決めたこと

**B**。`packages/error-reporting` が pino の出口を1つ増やし、error 以上の行から決めた項目(種類・値を伏せた文・スタック・requestId・tenantId・traceId・code・どの API か・users の ID)だけを拾って送る。

- Sentry の画面だけで原因まで分からなくてよい。そのかわり **Sentry の1件に、そのリクエストのログ(Logs Insights)を開くリンクを付ける**。調べ方は runbooks/sentry.md。

- Sentry の自動の仕組みは全部切る(`dataCollection` をすべて false・既定の計装を使わない)。
- 失敗の文からは、メールアドレス・`key=value` の値・引用符の中・長い数字・URL の `?` 以降を伏せる。
- 1つのプロセスで1分に30件・同じ失敗は3件まで。
- ブラウザは DSN があるときだけ、使う関数だけを後から読み込む(約30KB)。API の失敗・通信の失敗・SSR の失敗(サーバーが送った)は送らない。
- DSN は環境変数で、ブラウザには `<html data-sentry-dsn>` で渡す(イメージは stg と prod で同じなので、ビルドのときに決めない)。

## 結果として起きること

- 良くなること: 失敗を残す書き方は1つ(`logger.error({ err }, "…")`)のまま。Sentry に何が行くかは `scrub.ts` を読めば分かり、テストが確かめる。SDK を上げても送る中身は増えない。
- 我慢すること: Sentry の画面で「どの本文で」は見えない。リンクから Logs Insights を開く(AWS のコンソールに入れる人だけが見られる)。トレース(どこで時間がかかったか)も送らない(OpenTelemetry は PMF 後)。
- 見直す合図: 「requestId からログを引く」手間が週に何度も出るようになったら、送る項目を足す(足すときは scrub.ts とテストを一緒に)。Sentry の無料の枠を超えるようになったら、上限か送る level を見直す。
