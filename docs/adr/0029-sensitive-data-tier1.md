# ADR 0029: 要配慮個人情報の段1は、別の接続と組織ごとのデータ鍵(KMS で包む)で作り、1つのモジュールからだけ触る

- 状態: 提案
- 日付: 2026-10-25
- 決めた人: @attumkwg(段を分ける方針は ADR 0018 で採用済み。段1を作ることは 2026-10-25 に持ち主が選んだ。作りの細部は AI が書いた。設計書 0016 の「決めたこと」)

## 背景

ADR 0018 で、要配慮個人情報(病歴・障害・信条・犯罪の経歴など)は段を踏んで分けて置く、と決めた。段1は「同じ DB の別スキーマ `sensitive`+専用のロール `app_sensitive`+専用の KMS の鍵で列ごとに暗号化」。この ADR は、段1を**どう作るか**を決める。決めることは次の5つ。

1. アプリはどうやって `sensitive` に入るか(接続)
2. 鍵の持ち方(KMS の鍵1本か、組織ごとか)と、暗号による消去がどこまで効くか
3. どこから読み書きしてよいか
4. 社員の代理ログインから見えるか
5. 段2・段3へ上げるときに、作り直さずに済むか

## 選択肢

### 1. 接続

| 案 | 良い所 | 弱い所 |
|---|---|---|
| A. いまの接続(`app`)を `app_sensitive` にも入れる | 接続もトランザクションも1つ | バグ1つ・SQL の書き間違い1つで、ふつうのデータと要配慮を同じ接続で読める。ADR 0018 の「混ぜない」にならない |
| **B. 要配慮だけの接続(`app_sensitive_login`。`app_rw` に入れない)をもう1本** | 接続ユーザーで分かれる。段2(別のクラスター)は接続先を変えるだけ | ふつうのデータとの書き込みが1つのトランザクションにならない |

### 2. 鍵

| 案 | 良い所 | 弱い所 |
|---|---|---|
| A. KMS の鍵1本で、値ごとに KMS を呼ぶ | 作りが少ない | 値の数だけ KMS を呼ぶ(遅い・費用)。組織ごとに消せない |
| **B. 組織ごとのデータ鍵(AES-256)を KMS の鍵1本で包み、包んだ物を DB に置く(エンベロープ暗号化)** | KMS を呼ぶのは組織ごとに数分に1回。鍵の行を消せば、その組織の暗号文はどこにあっても読めない。KMS の呼び出しに組織の ID が残る | 包んだ鍵も DB のバックアップに入る(下の「消去の範囲」) |
| C. 組織ごとに KMS の鍵 | 鍵を消せばバックアップの中も読めない | 鍵1本 月 約150円 × 組織の数。PMF の前には重い(ADR 0018 で外した) |

### 3. 読み書きの場所

| 案 | 良い所 | 弱い所 |
|---|---|---|
| A. 領域のリポジトリから、要配慮の表も読む | いつもの書き方 | 暗号化を忘れた書き込み・ログへの出力が、どこからでも起きうる |
| **B. `apps/api/src/sensitive/` の中からだけ。外は `index.ts` の関数だけ(Semgrep で止める)** | 暗号化・ログ・権限の確かめを1か所で見られる | 要配慮の表が増えると、このフォルダに表ごとの関数が増える |

## 決めたこと

**1は B、2は B、3は B**。加えて次を決める。

- **接続**: `SENSITIVE_DATABASE_URL`(ロール `app_sensitive`)。`app_rw` には `sensitive` のスキーマの USAGE も渡さない。`app_sensitive` には、ほかのスキーマの表を何も渡さない。データ鍵の表は「読む・足す」だけ(書き換え・削除は無い)。RLS はほかの表と同じ。
  - ふつうのデータと1つのトランザクションにならない。要配慮の行は「ふつうの行を書いた後に書く・読めなければ無い物として扱う」順で作る(要配慮の表を足す設計書で決める)。
- **鍵**: KMS の鍵1本(環境ごと)で、組織ごとのデータ鍵を包む。KMS には文脈 `{ purpose: "tenant-data-key", tenant_id }` を必ず付け、鍵のポリシーも文脈の無い呼び出しを断る。使えるのは API のタスクの役割だけ(移行・運営のコマンドの役割は分けて、何も許さない)。管理者(IAM)は鍵の設定はできるが、鍵で復号はできない。
  - 開いたデータ鍵はメモリに **5分** だけ置く。KMS を呼ぶのは**トランザクションの外**だけ(1回 2秒で打ち切る)。
  - 値は AES-256-GCM で暗号化し、「どの組織の・どの列の・どの行の値か」を結びつける(別の行へ写した暗号文は開けない)。
  - 手元・テスト・プレビューは、コードに書いた包み鍵(秘密ではない)。stg・prod では起動しない(`config.ts`)。
- **消去の範囲(正直に)**: 解約のコマンドがデータ鍵の行を消すと、**動いている DB・書き出し・ログに紛れた写し**など、鍵の行を持たない所の暗号文は読めなくなる。けれども**バックアップには包んだ鍵も入っていて、KMS の鍵1本で開ける**ので、バックアップの中の要配慮のデータは、ふつうのデータと同じく保存期間(最長365日)が過ぎて消える(`docs/guides/data-retention.md`)。バックアップの中まで暗号で消すのは T-5(組織ごとの KMS の鍵)で、そのときは `kms_key_id` の列に組織の鍵を入れて包み直す(表の形は変わらない)。
- **読み書きの場所**: `apps/api/src/sensitive/` の外からは `index.ts` だけ。要配慮の表の SQL は、表ごとの関数としてこのフォルダの中に書く。`@aws-sdk/client-kms`・`pgSchema("sensitive")`・SQL での `sensitive.` の名指し・`process.env.SENSITIVE_*` も、外では Semgrep の `sensitive-data-only-in-module` が落とす。
- **代理ログイン**: 社員の代理ログインの最中は、モジュールが 403 で断る。見せる必要がある機能は、その仕様で決めて関所に足す。
- **段2・段3への備え**: `sensitive` のスキーマの表から、ほかのスキーマの表へ外部キーを張らない。接続は最初から別。だから段2は「別のクラスターを作り、表を移し、`SENSITIVE_DATABASE_URL` を向け直す」で済む(`docs/runbooks/sensitive-data-tiers.md`)。
- **使わない間は作らない**: Terraform の `sensitive_data_enabled`(既定 `false`)。DB には空のスキーマとデータ鍵の表だけができる(費用0)。要配慮の列を足す仕様が承認されたら `true` にする。
- **見張り**: CloudTrail のロググループから、① API のタスク以外が鍵を使った ② 鍵を消す予約・止める・ポリシーを変えた ③ API のタスクが5分に開いた数が多すぎる、で鳴らす(`modules/sensitive-data`)。

## 結果として起きること

- 良くなること: 要配慮の値は、DB・バックアップ・DB のログ・Performance Insights には暗号文でしか残らない。アプリの接続(`app`)のバグや SQL の書き間違いでは、要配慮のデータに届かない。鍵を開いた記録(どの組織の鍵を・いつ・どの役割が)が CloudTrail に残る。解約で鍵の行を消せば、写しは読めない。
- 我慢すること: 要配慮の値は DB の中で検索・並べ替えできない(要るなら、別の列にハッシュを足す。設計書で決める)。ふつうの行と1つのトランザクションにならない。KMS の鍵を消すと、全部の組織の要配慮のデータが戻せなくなる(消す予約は30日待ち・鳴る)。API のタスクのメモリには、開いたデータ鍵が最長5分ある。
- 見直す合図: ADR 0018 の「上げる合図」(要配慮の行が数千件を超えた・大きなお客さんが求めた・監査で求められた)。大きなお客さんが「バックアップの中も暗号で消して」と求めたら T-5(その組織だけ KMS の鍵を分ける)。
