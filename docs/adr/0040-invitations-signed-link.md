# ADR 0040: 招待のリンクは署名つきの札、人を足すのは DB の関数だけ

- 状態: 提案
- 日付: 2026-10-25
- 決めた人: @attumkwg(承認待ち)

## 背景

お客さんの管理者が人を足す道が無く、運営が SQL で users に行を足していた。決まり T-8 は「招待はリンクの期限と1回きり」。メールはアウトボックスの受け手が送る直前に組み立て、出来事の中身は ID だけ(ADR 0006・0008)なので、リンクの札をどこに持つかを決める必要があった。また、アプリの接続(app_rw)はいま users に行を足せない(人が増えるのは運営の SQL だけ)。仕様は `docs/specs/0027-invitations.md`。

## 選択肢

| 案 | 良い所 | 弱い所 |
|---|---|---|
| **A. 札 = 招待の ID + サーバーの秘密の署名(DB に持たない)。受けるのは DB の関数** | DB に秘密が残らない。送る直前に作れる。人を足す道は関数1つに閉じる | 秘密を入れ替えると、受けていない招待が全部切れる |
| B. 乱数の札を作り、ハッシュだけを DB に(サポートの番号と同じ) | 札ごとに独立 | 送り出しが札を知れない。出来事の中身に札(秘密)を入れることになる |
| C. 乱数の札をそのまま DB に | 単純 | DB が漏れると、受けていない招待が全部使える |
| D. 招いた時点で users に行を作る(リンクは案内だけ) | 作りが一番少ない | 期限・1回きりにならない(T-8 を満たさない) |
| E. Cognito の管理の API で人を作り、仮のパスワードを送る | Cognito が招待のメールを送る | 開発用ログインでは動かない。運営の外の画面になる。パスワードを人づてに渡す形 |

## 決めたこと

- **A**。札 = `<招待の ID>.<HMAC-SHA256(鍵, 招待の ID)>`。鍵は `SESSION_SECRET` から用途の名前で HMAC して作る(Cookie の署名の鍵をそのまま使わない)。期限・1回きり・取り消しは招待の行で決める。
- 受けるのはログインの前の公開の API。**署名を確かめてから** DB の関数 `auth_accept_invitation`(app_auth が持ち主の SECURITY DEFINER)を呼ぶ。関数は生きている招待を1回だけ受けた印つきにし、同じ招待の組織・メール・ロールで users に1行足す。app_rw には users の INSERT を渡さない。users への INSERT のポリシーも「受けた招待とそろう行だけ」。
- 組織は札が指す招待で決まる(リクエストの値・セッションでは決めない)。受けてもログインさせない(本人の確認は Cognito の登録とログイン)。
- リンクは URL の `#` の後ろ(サーバーのログ・Referer に残さない)。

## 結果として起きること

- 良くなること: お客さんが自分で人を足せる。招いた・取り消した・受けたが監査ログに残る。DB が漏れても招待のリンクは作れない。アプリのどこに穴があっても、人を勝手に増やせない。
- 我慢すること: `SESSION_SECRET` を入れ替えると、受けていない招待のリンクが全部切れる(招き直す)。送り直しは「取り消して招き直す」。
- 見直す合図: 秘密を定期的に入れ替えるようになった → 招待用の秘密を分ける。SSO を足す → ドメインを確かめてから、その IdP の人を招待なしで入れる形(T-8 の後半)。複数の組織に入る形(G-21)→ 受けるときに「もう他社にいる」で止めず、所属を足す形に。
