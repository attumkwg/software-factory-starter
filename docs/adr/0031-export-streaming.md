# ADR 0031: データの書き出しは、1ページずつ読んで同じ JSON を流して返す。非同期(S3 と署名つき URL)は大きくなってから

- 状態: 採用
- 日付: 2026-10-25
- 決めた人: @attumkwg(TODO「書き出しが1社の全データをメモリに載せる」の依頼で。案の選択は AI。PR で)

## 背景

データの書き出し(`POST /api/exports`。ADR 0015・`docs/specs/0005-offboarding.md`)は、1社の全部の行を JS の値にしてから、1つの JSON の文字列にして返していた。大きい会社では次の3つに当たる。

- **API のメモリ**: 行の値+JSON の文字列で、中身の2〜3倍が一度に載る。Fargate のタスクは小さい(ADR の段階の決まり)ので、1回の書き出しでほかのリクエストまで道連れに落ちうる。
- **ALB の60秒**: ALB は「何も流れない時間」が60秒を超えると切る。全部を読み終えるまで1バイトも返さないので、読むのに60秒かかれば必ず切れる。
- **DB の時間切れ**: 1つのクエリ5秒(`DB_TIMEOUTS`)。タスクを一度に全部読むクエリが、いずれ5秒を超える。

画面の側も、`fetch` に15秒の時間切れがあり、受け取った JSON を値に戻してから整形し直して保存していた(ブラウザでも2倍載る)。

## 選択肢

| 案 | 良い所 | 弱い所 |
|---|---|---|
| **A. ストリーム: 1ページずつ読んで、同じ JSON(export@1)を少しずつ流す** | 足す物が無い(表・バケット・ワーカー・メールの文面が要らない)。形が変わらないので、画面・お客さんの取り込み・契約の文面がそのまま。メモリは1ページ分で一定。バイトが流れ続けるので ALB の60秒に当たらない | 流している間は API のプロセスと接続を(ページごとに短く)使う。途中で失敗すると、状態コード 200 のあとで切れる(受け手は壊れた JSON で気づく)。何時間もかかる大きさには向かない |
| A'. ストリームで JSON Lines か ZIP | 1行ずつ・表ごとに分けられる | 形が変わる(export@2・画面・お客さんの取り込みを直す)。ZIP は依存を足す。今の大きさでは得が無い |
| B. 非同期のジョブ: アウトボックスで作って S3 に置き、終わったら署名つき URL(期限つき)をメールと画面で渡す | 何時間でも作れる。API の応答と切り離せる。何度でも取り直せる | 足す物が多い: S3 のバケット(暗号化・期限で消す・公開しない)・IAM・手元の偽物(S3 の代わり)・ジョブの表と状態(作成中・失敗・期限切れ)・画面(待つ・取り直す)・メールの文面・**署名つき URL という「鍵を持たない入口」**(漏れれば期限まで誰でも全データを取れる)。消す一覧・保存期間の契約にも1つ増える |

既存の仕組み: アウトボックス(ADR 0006)と送り出しは API のプロセスの中にあり、別のワーカーのサービスは無い(重くなったら分ける段)。S3 は試作の置き場(ADR 0020)だけで、アプリからは使っていない。

## 決めたこと

- **A**。PMF の前は軽く(足す物を増やさない)、今の困りごと(メモリ・60秒・5秒)はAで全部消える。B は「見直す合図」が来たら。
- 形は今までと同じ `format: "software-factory-starter/export@1"` の1つの JSON。項目の順も同じ。並び順は、タスクだけ「プロジェクト → 古い順」に変わる(索引に合わせた。形の約束には並び順は入っていない)。
- 各領域が `export…Page(s, 続きの印, 件数)` で1ページ(500行)ずつ出す(写す項目は領域が決める。表を丸ごと出さない、は今までどおり)。並びは「時刻+ID」の続きの印で、すでにある索引を使う(タスクは `tasks_tenant_id_project_id_created_at_id_idx` をプロジェクトをまたいで読む)。移行は足さない。
- **ページごとに短いテナントのトランザクションを開く**。本文は認可の関所のトランザクションが閉じた後に流れるので、ルート(`src/export/routes.ts`)が `withTenant` を開く(テナントは関所が決めた actor = セッションから。リクエストの値は見ない。`src/auth/account-routes.ts` の `inTenant` と同じ形)。RLS は効き、リポジトリは `tenant_id` でも絞る。
  - 受け手が遅くても、トランザクションを開いたまま待たない(`idle_in_transaction` の10秒・10本しかない接続プールを握らない)。
  - 受け手が読みに来たときだけ次のページを読む(`highWaterMark: 0`)。関所のトランザクションが開いている間に2本目の接続を取らない(1つのリクエストが同時に握る接続は1本まで)。
  - ページの間に1つの時点をそろえない(書き出しの途中で変わった行は、入ることも入らないこともある)。続きの印で読むので、ずっとある行は欠けも重なりもしない。
- 書き出したことは、今までどおり関所が監査ログに残す(`data.export`)。**流し始めた時点で**残る(途中で切れても「書き出した」と残る。持ち出された可能性がある側に倒す)。
- 途中で失敗したら、`logger.error({ err }, "…")` で残して流れを切る(本文を最後まで出さない)。状態コードはもう 200 で返っているので、受け手は壊れた JSON・途中で切れたダウンロードとして気づく。失敗の中身は応答にもログの文にも出さない。
- 画面は、本文を値に戻さずにそのまま Blob にして保存する。時間切れは「応答が始まるまで」の15秒だけにする。

## 結果として起きること

- 良くなること: 書き出しのメモリは中身の大きさに比例しない(結合テストで、20MB の書き出しで JS の値の増えが 0.3MB ほど)。ALB の60秒・DB の5秒に当たらない。足した部品は無い。
- 我慢すること: 途中で切れたときに「どこまで出たか」は受け手に分からない(最初からやり直す)。流している間は API のタスクの CPU と、ページごとに接続を1本ずつ使う。書き出しの途中の変更は混ざりうる(1つの時点の写しではない)。
- 見直す合図: 1回の書き出しが数分を超える(目安: 10分。ブラウザを開いたまま待てない)/ 書き出しが API の CPU を食って、ほかの応答が遅くなる / 「1つの時点の写し」が契約で要る / 書き出しを定期で自動に送りたい(→ B: アウトボックスのジョブで作って S3 に置き、期限つきの署名つき URL を渡す。そのときは送り出しを別のワーカーに分ける段(ADR 0006)と合わせる)。
