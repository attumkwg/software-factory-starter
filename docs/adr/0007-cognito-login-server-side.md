# ADR 0007: Cognito でのログインは API が受け取り、トークンはサーバーの中だけで扱う

- 状態: 採用(「3. ログインの画面」は ADR 0009 で自前の画面に置き換え。「Cognito の画面へ移る流れ」は消した)
- 日付: 2026-10-18
- 決めた人: @attumkwg

## 背景

これまでは、API に「ID トークンを受け取って確かめる口」(`POST /api/auth/cognito`)があるだけで、画面から Cognito へ行って戻る部分が無かった。stg・本番で人がログインできない。決めることは3つあった。

1. Cognito から戻ってきた code とトークンを、どこが受け取るか
2. 新しい人のアカウントをどう作り、アプリの利用者(`organizations.users`)とどう結びつけるか
3. ログインの画面をどこが出すか

## 選択肢

### 1. どこが受け取るか

| 案 | 良い所 | 弱い所 |
|---|---|---|
| A. API が受け取る(戻り先 `/api/auth/callback`。認可コード+PKCE) | トークンがブラウザの JS に一度も出ない(XSS で盗まれない)。画面のサーバーは秘密を持たないまま | API に入口が2つ増える。API から Cognito への通信が要る |
| B. ブラウザが受け取って API に渡す | 作りが小さい(今の口をそのまま使える) | トークンが JS に出る。盗まれたトークンでセッションを作られうる |

### 2. アカウントの作り方

| 案 | 良い所 | 弱い所 |
|---|---|---|
| A. Cognito への登録は誰でも。アプリに入れるのは users にいる人だけ。初めてのログインで、確認済みのメールが users の行と一致したら結びつける | 招待の画面が無くても回る。知らない人は Cognito に登録できてもアプリには入れない | 知らない人の Cognito のアカウントが増える(月1万人までは無料。増えたら見直す) |
| B. 管理者が招待(API が Cognito に人を作る) | 登録できる人を絞れる | 招待の画面・API の IAM の権限まで要る |
| C. 自分で登録して新しい組織を作る(セルフサーブ) | 売り方によっては必須 | 組織を作る画面と、勝手に作られる組織への対策が要る |

### 3. ログインの画面

| 案 | 良い所 | 弱い所 |
|---|---|---|
| A. Cognito の画面(Managed Login) | MFA・パスワードの再設定・確認コードの画面が最初からある | デザインシステムと見た目がそろわない |
| B. 自前の画面で Cognito の API を呼ぶ | デザインシステムどおりの見た目 | 登録・確認コード・再設定・MFA の画面を全部作る |

## 決めたこと

**1 は A・2 は A・3 は A**(本人の選択。1 は本人「トークンはサーバーで閉じるべき」)。

- `GET /api/auth/login` が state・nonce・PKCE を作って署名つきの Cookie(10分)に置き、Cognito の画面へ送る。
- `GET /api/auth/callback` が state を比べ、code を ID トークンに替え、署名・発行元・宛先・nonce を確かめて、セッションの Cookie を発行する。途中の状態は成否にかかわらず消す(2回使わせない)。
- 結びつけは DB の関数 `auth_link_external_id`(`drizzle/0005_login_link.sql`)だけが行う。**まだ誰とも結びついていない行**の `external_id` を1回だけ埋められる(付け替えはできない)。
- 戻り先はアプリの中のパスだけ(`@app/shared` の `safeReturnTo`)。
- 失敗は `/login?error=<code>` に返し、画面は固定の文だけを出す。
- `POST /api/auth/cognito` は stg の ZAP のスキャン用に残す。スキャン用のクライアント宛てのトークンだけを受け付け、prod では起動時に止める。
- 手元とテストでは、偽物の Cognito(`packages/fake-cognito`)が同じ入口で答える。普段の開発は今までどおり開発用ログイン。

## 結果として起きること

- 良くなること: トークンを盗まれる経路が減る。stg・本番で人がログインできる。手元で AWS なしに流れを確かめられる(結合テスト・E2E)。
- 我慢すること: 画面は Cognito の見た目(3 の A)。
- 次にやること: **ログインの画面は自作する**(本人「デザインシステムを作っている以上、それに合わないデザインが入ってくる」2026-10-18)。3 を B に置き換える ADR を書く。
  - 自作するのは画面だけ。パスワードの保管・照合・MFA・確認コードの送信は Cognito のまま(API が Cognito の API を呼び、トークンはサーバーの中のまま)。
  - 今回の「Cognito の画面へ移る流れ」は、Google などの外部のログインを足すときにそのまま使える。
- 見直す合図: 知らない人の Cognito の登録が月に数千を超える(費用・迷惑な登録)。そのときは登録を管理者だけにする(2 を B に)か、Cognito の不正対策(Plus)を入れる。
