# ADR 0019: 規約の本文はリポジトリの Markdown、版の一覧はコード、同意の記録は DB の足すだけの表に持ち、関所で止める

- 状態: 提案
- 日付: 2026-10-22
- 決めた人: (人の承認待ち。docs/designs/0008-legal-consent.md の未確定事項と一緒に)

## 背景

利用規約とプライバシーポリシーの置き場所が無く、**誰が・どの版に・いつ同意したか**の記録も無い(仕様 `docs/specs/0008-legal-consent.md`)。規約は後から変わり、利用者に不利な変更は効く日と中身を前もって知らせる必要があり(民法 548条の4)、大事な変更は同意し直してもらうのが安全。このキットで作るサービスは P マーク・ISMS を求められることが多く、同意の記録を見せる必要がある。

決めること: 本文と版をどこに持つか・同意をどこに記録するか・同意していない人をどう止めるか。

## 選択肢

本文と版の置き場所:

| 案 | 良い所 | 弱い所 |
|---|---|---|
| **A. 本文はリポジトリの Markdown、版の一覧は `@app/shared` のコード** | 変更が PR の差分で見え、人(法務)がレビューできる。画面と API が同じ一覧を見る。公開の日時を一覧に書けば、マージしておいて決まった時刻から出せる | 版を足すのに PR とデプロイが要る(運営が画面から出せない) |
| B. DB に本文と版を持ち、管理画面で出す | 運営がデプロイなしで出せる | 管理画面・権限・本文の差分の見方を作る必要がある。誰がどこを変えたかが PR に残らない |
| C. 外の同意管理のサービス(CMP など) | 法務の機能がそろう | 外部の契約と費用。同意の記録がアプリの外にあり、関所が毎回外に聞く |

同意の記録:

| 案 | 良い所 | 弱い所 |
|---|---|---|
| **A. 新しい領域 `legal` の足すだけの表(`SELECT, INSERT` だけの権限)+監査ログに名前** | 関所が1回の問い合わせで「同意したか」を引ける。記録は書き換えられない。組織の監査ログからも見える | 表が増える(解約で消す一覧・書き出しに足す) |
| B. 監査ログだけ | 表が増えない | 監査ログは値を持たない決まり(ADR 0013)。どの版かを持てず、関所が毎回探すのも遅い |

止め方:

| 案 | 良い所 | 弱い所 |
|---|---|---|
| **A. 認可の関所で 403 `terms_acceptance_required`(二段階認証の「設定待ち」と同じ形)** | API で止まる(画面で隠すだけにしない)。既にある型 | 関所の問い合わせが1回増える |
| B. 画面だけで回す | 簡単 | API を直接叩けば使える |

## 決めたこと

- 本文と版は **A**、記録は **A**、止め方は **A**。
- 公開した版の本文は変えない(版の一覧に本文の SHA-256 を持ち、単体テストが確かめる)。直すときは新しい版。
- 同意し直しが要るか(`reconsent`)は版ごとに PR で決める。2つ目からの版は公開から効力まで30日以上(単体テスト)。
- 予告のメールは運営のコマンドで送る(API にしない)。送った記録を足すだけの表に持つ(周知の証拠・2回送らない)。
- 詳しい形は `docs/designs/0008-legal-consent.md`。

## 結果として起きること

- 良くなること: 規約の変更が PR で人に見え、決まった時刻に出て、同意し直しが要る人は API で止まる。誰が・どの版に・いつ・どの画面から・組織としてか本人としてか同意したかを示せる。
- 我慢すること: 版を足すのに PR とデプロイが要る。関所の問い合わせが1回増える。お知らせのメールは運営が手で流す(決まった日に自動では送らない)。組織ごとに違う規約・言語ごとの版は持てない。
- 見直す合図: 版の更新が月に1回を超える・法務が PR を使えない(→ B の管理画面)。組織ごとの個別の契約が増える(→ 組織ごとの版)。関所の問い合わせが遅さの上位に出る(→ セッションに「同意済みの版」を持つ)。
