# ADR 0001: マルチテナントは「共有の表+RLS」にする

- 状態: 採用(「いまは1人 = 1組織」と、その見直す合図は ADR 0066 で置き換え)
- 日付: 2026-10-17

## 背景

1つのシステムに複数の組織(テナント)が同居する。一番重い事故は「他社のデータが見える」で、1件でも信用を失う。
コードの多くを AI が書くので、**書き忘れても漏れない**作りにしたい。

## 選択肢

| 案 | 良い所 | 弱い所 |
|---|---|---|
| 共有の表+テナント ID | 安い・運用が1つ・新しい組織をすぐ足せる | 絞り忘れで漏れる |
| 組織ごとのスキーマ | ある程度分かれる | 組織が数千になると移行と運用が重い |
| 組織ごとの DB | 最も強く分かれる | 高い・組織ごとに運用が増える |

## 決めたこと

**共有の表+層を重ねて守る**。大企業・規制の重い顧客だけ、後で専用 DB に切り出せるようにしておく。

1. 全テーブルに `tenant_id`(UUIDv7)。表どうしの参照は `(tenant_id, id)` の組で張る(別テナントの行を指せない)。
2. テナントは**ログインのセッションからだけ**決める。URL・本文・ヘッダーの値は使わない。
3. アプリの入口(`authz/middleware.ts`)でテナントの文脈つきのトランザクションを開き、リポジトリはそれだけを使う。リポジトリも `tenant_id` で絞る。
4. **RLS を最後の砦に**: 全テーブルで `ENABLE` と `FORCE ROW LEVEL SECURITY`。トランザクションごとに `set_config('app.tenant_id', $1, true)`(`SET LOCAL` と同じ)。
5. アプリの接続ユーザー(`app`)は**表の持ち主ではない**・superuser でも BYPASSRLS でもない。持ち主(`app_owner`)は移行だけに使う。
6. ログイン時の「このメールは誰か」だけは、テナントが決まる前に引く必要がある。これは `users` を読むだけの `SECURITY DEFINER` 関数に閉じ込める。
7. テストは必ず2社。結合テストで「全テーブルに RLS と FORCE があるか」「接続ユーザーが持ち主でないか」を毎 PR で確かめる。
8. テナント分離の部品(文脈・RLS・関所)を変える PR は危険度「高」(CODEOWNERS)。

## 結果として起きること

- 良くなること: アプリの書き忘れがあっても DB が他社の行を返さない。新しい組織は行を足すだけ。
- 我慢すること: 全クエリがトランザクションの中。ログインだけ特別な関数を通る。いまは「1人 = 1組織」。
- 見直す合図:
  - 複数の組織に入る人が必要になった → 所属の表を足し、組織の切り替え(トークンは1社分だけ有効)を作る。
  - 1社の重さが全体に響き始めた → テナントごとの流量の上限、重い組織は専用 DB へ。
  - 組織が数千を超えた → 本番の「おとりのテナント」とテナント単位の監視を足す。
