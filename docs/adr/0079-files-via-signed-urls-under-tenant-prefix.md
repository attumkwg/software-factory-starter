# ADR 0079: 写真・ファイルは、組織の ID を頭にしたキーに置き、その組織だけに絞った権限で署名した短い URL で上げ下げする

- 状態: 採用
- 日付: 2026-10-27
- 決めた人: @attumkwg(会話で「ADR は基本おすすめで良い」)

## 背景

看板の A 社の中核は現場の写真(穴 G-45)。DB の行は RLS で組織ごとに分かれるが、S3 の中身は RLS の外にある。キーの付け方・URL の出し方・権限のどれかを1つ誤ると、他社の写真がそのまま見える(`docs/security.md` の L-4)。決まり T-4 は「S3 はテナントごとの置き場所+テナントで絞った一時的な権限」と言っているが、形がまだ無かった。写真は 2〜20MB で、現場の回線は遅い。

## 選択肢

| 案 | 良い所 | 弱い所 |
|---|---|---|
| A. API が中継する(画面 → API → S3) | 認可も中身の確かめも API の中で済む | 20MB を Fargate・ALB(60秒)に通す。遅い回線で切れる。API のメモリと転送の費用が増える |
| B. 署名つき URL で画面と S3 が直接やりとりする。署名は API のいつもの権限 | 速い・API が軽い | キーの関数に誤りがあると、他社のキーにも署名できてしまう(守りが1層) |
| C. B に加えて、署名をその組織のキーの頭だけに絞った一時的な権限(STS のセッションのポリシー)で行う | キーの関数に誤りがあっても、他社のキーへの署名は S3 が断る(層を重ねる。T-4) | STS を待つ(関所のトランザクションの外で署名する)。手元の MinIO では絞りを確かめにくい |
| D. 組織ごとにバケットを分ける | 分かれ方が見える | バケットの数の上限(既定 1万だが作るのが運営の手間)・Terraform で組織を足すたびに変更・費用のタグが散る |

## 決めたこと

**C**。キーは `<段>/<組織の ID>/<ファイルの ID>`(段は `incoming` か `files`)で、作る関数は1つだけ。組織の ID はセッションからだけ(T-1)。URL は認可の関所を通った後でだけ作り、期限は5分。署名の権限は役割 `files-access` を STS で引き受け、セッションのポリシーで `incoming/<組織>/*`・`files/<組織>/*` に絞る(組織ごとに1時間覚えておく)。手元・CI は S3 互換の MinIO(`docs/guides/local-environment.md` の決まり)で、署名の書き換えが断られることを結合テストで確かめ、絞りの効き目は stg で確かめる。

## 結果として起きること

- 良くなること: 写真が API を通らない。他社のファイルに届くには、キーの関数・関所・一時的な権限の3つを同時に誤る必要がある。CloudTrail で、組織ごとのセッションの名前(`files-<組織の ID>`)で追える。
- 我慢すること: ファイルの API は関所のトランザクションの外で動く(自分で `withTenant` を開く)。手元では絞りが効かない(MinIO は固定の資格情報)。画面の CSP(G-17)を入れるときに置き場の出どころを足す。
- 見直す合図: 1つの組織の STS の呼び出しが1時間に1回を大きく超える(覚えておく仕組みが効いていない)・大きなお客さんが「自社専用の鍵・置き場」を求める(T-5。そのときは組織ごとの KMS の鍵か案 D)。
