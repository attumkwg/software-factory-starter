# ADR 0080: 上げたファイルはそのまま見せず、API が読み直して種類を確かめ、写真の付いた情報を消してから見せる

- 状態: 提案
- 日付: 2026-10-27
- 決めた人: (未。設計書 0072 の人の確認を待つ)

## 背景

署名つき URL(ADR 0079)では、画面が S3 に直接上げる。署名で縛れるのは「言った種類(Content-Type の見出し)と大きさ」までで、**中身が本当に写真か**は分からない。写真の EXIF には撮った場所(GPS)が入っていて、工務店の現場 = 施主の家の位置が漏れる(穴 G-45)。上げた物をそのまま見せると、HTML を写真と偽って置く・位置情報つきの写真が他の職人や代理の社員に渡る、が起きる。

## 選択肢

| 案 | 良い所 | 弱い所 |
|---|---|---|
| A. 上げた物をそのまま見せる。画面(ブラウザ)で EXIF を消してから上げる | 作るのが軽い | 画面を通さずに上げれば消えない(信じられない)。中身の種類も確かめられない |
| B. 上げた物は仮の置き場(`incoming/`)に置き、送り出し(アウトボックス)が読み直して確かめ、付いた情報の塊を外して `files/` に書いた物だけを見せる。外すのは自分で書いた小さな関数 | 依存が増えない・画素を作り直さないので画質が落ちない・速い | JPEG・PNG・WebP の形を自分で読む(テストで固める)。HEIC などは受けられない |
| C. B と同じ流れで、画像の部品(sharp など)で作り直す | 縮小版も作れる・多くの形を読める | ネイティブの依存(イメージが大きくなる・脆弱性の通知が増える)・画質が変わる・遅い |
| D. S3 の出来事で Lambda を動かす | API が重くならない | Lambda・出来事の配線が増え、手元(RustFS)で同じ流れを再現しにくい |

## 決めたこと

**B**。見せるのは `status = ready`(書き直した後)の物だけ。種類は先頭の数バイトで確かめ、言った種類と違えば断って中身を消す。JPEG は APP1(EXIF・XMP)・APP13・COM を外し、向きが 1 以外なら向きだけの小さな EXIF を入れ直す。PNG は文字・時刻・EXIF の塊、WebP は EXIF・XMP の塊を外す。PDF は種類だけを確かめる。縮小版が要るようになったら、C をこの流れの中に足す(仕様の「やらないこと」)。

## 結果として起きること

- 良くなること: 位置情報つきの写真・偽った中身が、ほかの人に届かない。手元でも同じ流れ(送り出しが S3 互換の RustFS を読む)で確かめられる。
- 我慢すること: 上げてから見られるまで数秒かかる(送り出しは1秒ごと)。受けられる種類が少ない。写真の撮った日時も消える(設計書 0072 の U-5)。
- 見直す合図: 送り出しの書き直しが遅れて「上げたのに出ない」の問い合わせが来る・縮小版が要る・HEIC や動画を受けたい(そのときは C か D)。
