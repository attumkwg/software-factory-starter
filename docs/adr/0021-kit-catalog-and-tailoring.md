# ADR 0021: キットの部品を1つのカタログにし、`/tailor` で残す・消すを決める。README の「使い始めたらやること」はカタログから作る

- 状態: 提案
- 日付: 2026-10-22
- 決めた人: @attumkwg(作者の求め 2026-10-22「ひな形で開発を始めるとき、そのプロダクトで要るかを確かめて、要らないなら消せるチェックシート」「使い始めたらやることは最終的に README に出したい」)

## 背景

点検のたびに、要る物を足してきた(監査ログ・代理ログイン・解約・メール・見張り・プレビュー環境など)。どれも「たいていの B2B SaaS で要る」物だが、使う人のプロダクトによっては要らない(個人向けなら代理ログインは要らない、など)。

いまは、何が入っていて・どれが消せて・消すと何が困るか・どう消すか、が README・ADR・仕様に散らばっている。使い始めた人が「消してよいか」を決めるには、全部を読むしかない。消し方も書いていないので、消し漏れ(表は消したが権限の表の行が残る、など)が起きやすい。

## 選択肢

| 案 | 良い所 | 弱い所 |
|---|---|---|
| A. 部品のカタログ(YAML)を1つ作り、`/tailor` が読む。消し方のパスは CI が実在を確かめる。README の節はカタログから作る | 1か所を見れば決められる。部品を足し忘れても、消し方が古くなっても CI が落とす | カタログを書き足す手間。部品の切り方に判断が要る |
| B. README に「消せる物」の表を手で書く | すぐできる | 消し方が古くなっても気づけない。`/tailor` が機械で読めない |
| C. 機能フラグで、消さずに切る | 戻すのが楽 | 使わないコード・表・権限の行が残り続け、検査と読む量が減らない |

## 決めたこと

**A。** `docs/kit/catalog.yaml` を正にする。

- **土台は消さない**(`removable: false`): テナント分離と RLS・組織とロール・認可の関所と権限の表・ログイン・秘密・バックアップ・CI の検査・ログの決まり・ログの許可リスト(#10)・AI のハーネス・列の分類表。土台を入れ替えたいときは、消すのではなく `/design` と ADR で。
- **迷ったら残す**を、`/tailor` のおすすめの決まりにする。消すのは後からでもできるが、足し直すほうが高い。
- 消す部品は**1つずつ PR**。消し方(`remove`)どおりに消し、カタログを `status: 消した` にする。昔の移行・仕様・ADR は書き換えない(消す移行を足す・記録に1行足す)。
- 決めたことは `docs/product/tailoring.md` に**足すだけ**で残す。`pnpm kit:catalog` が記録も読み、土台を消す答え・残す部品が頼っている物を消す答えを落とす。
- 「作成中」(PR が開いている)の部品は、パスを確かめない。マージした PR が「あり」に直す。
- README の「使い始めたらやること」(① `/kickoff` → ② `/tailor` → ③ 手でやる設定 → ④ 点検の立ち上げ)と部品の一覧は、`pnpm kit:readme` でカタログから作る。印の間だけを書き換え、生成し忘れは CI が落とす。
- 点検の台帳(docs/specs/0007-checkup.md)ができたら、消した部品の項目を「該当なし」にする。いまは `/tailor` に、つなぎ方だけを書く。

## 結果として起きること

- 良くなること: 使い始めた人が1か所を見て、理由つきで部品を選べる。消し漏れを CI が落とす。部品を足した PR が、カタログと README を同じ PR で直す。
- 我慢すること: 部品を足す・ファイルを動かすたびに、カタログの消し方も直す(CI が落ちて気づく)。法令・認証の欄は「分かる範囲」で、専門家の確かめの代わりにはならない。
- 見直す合図: 部品が60件を超えて1枚で読めなくなったら、区分ごとに分ける。`/tailor` で「消す」と決めた部品を、あとで足し直すことが続いたら、既定とおすすめの決まりを見直す。
