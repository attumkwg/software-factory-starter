# ADR 0018: 要配慮個人情報は、ほかのデータと分けて置く(段階を踏んで)

- 状態: 採用
- 日付: 2026-10-21
- 決めた人: @attumkwg(作者の希望「要配慮を扱う場合は、物理的にデータを隔離して混ざらないようにする」から AI が案を書いた。2026-10-22 に採用)

## 背景

このキットは、全社のデータを1つの DB に置き、RLS で会社ごとに分けている(ADR 0001)。会社をまたぐ漏れには強いが、**同じ会社の中で、ふつうのデータと要配慮個人情報(病歴・障害・信条・犯罪の経歴など。個人情報保護法 2条3項)が同じ権限・同じ鍵・同じバックアップに入る**。

- アプリの接続ユーザー(`app_rw`)が読める物は、バグ1つ・SQL の書き間違い1つで全部読める
- DB の暗号化の鍵(KMS)は1本で、バックアップ・ログ・Performance Insights も同じ鍵
- 要配慮個人情報は、取るときに本人の同意が要り、漏れたら(1件でも)個人情報保護委員会への報告と本人への通知が要る(法 26条・規則 7条)。ふつうの個人情報より、守りを一段厚くする理由がある

いまのキットには要配慮個人情報の列は無い。だから**入れる前に「どこに・どう分けて置くか」を決め、決めた形でしか入れられないようにする**。

## 選択肢

| 案 | 良い所 | 弱い所 |
|---|---|---|
| A. 同じ表に置き、RLS と列の権限だけで守る | 作りが増えない | 鍵・バックアップ・接続ユーザーがふつうのデータと同じ。混ざる |
| **B. 段階を踏む(下の表)。いまは「分けて置くまで入れられない」にだけする** | 要らないうちは費用0。入れるときに段1から始めれば、最初から混ざらない。段を上げる合図を決めておける | 段1を作るまで、要配慮の列は1つも足せない(足したい機能が来たら先に段1の PR) |
| C. 最初から別の AWS アカウントの別の DB | いちばん固い | 使わないうちから費用と運用が倍。PMF 前のキットに重い |

## 決めたこと

**B**。分類表(`apps/api/src/db/classification.ts`)で `sensitive` にした列は、**Postgres のスキーマ `sensitive` の表にしか置けない**(単体テスト `classification.test.ts` が落ちる)。いまはスキーマ `sensitive` が無いので、要配慮の列を足すには、まず下の段1を作る PR が要る(危険度「高」。人が2人で見る)。

### 分ける段

| 段 | 形 | 分かれるもの | 混ざったままのもの | 上げる合図 |
|---|---|---|---|---|
| 0(いま) | 置けない | — | — | 要配慮の列を足す機能の仕様が承認された |
| 1 | 同じ DB の**別スキーマ `sensitive`**+**専用のロール**(`app_sensitive`。`app_rw` には何も渡さない)+**専用の KMS 鍵で列ごとに暗号化**(アプリが書く前に暗号化する。DB には暗号文だけ) | 読める接続ユーザー・読める鍵(鍵の利用は CloudTrail に残る)。DB のバックアップ・ログ・スナップショットからは暗号文しか読めない | DB のクラスター・バックアップの保管庫・DB の管理者 | 要配慮の行が数千件を超えた・大きなお客さんが求めた・監査で求められた |
| 2 | **別の Aurora クラスター**(同じ AWS アカウント) | 上に加えて、ネットワーク(セキュリティグループ)・バックアップ・DB の管理者のパスワード・負荷 | AWS アカウントの管理者・CloudTrail・請求 | 社員の誰が読めるかを、アカウントの権限で分ける必要が出た |
| 3 | **別の AWS アカウント**(Organizations の中) | 上に加えて、AWS の管理者・ログの置き場所・SCP(組織のルール) | 会社 | 法令・契約で「別の環境」と求められた |

- 段1の列ごとの暗号化は、**会社ごとに鍵を分けない**(鍵の数が会社の数だけ増える)。会社ごとの鍵は `data-retention.md` の次の一歩(暗号による消去)と一緒に考える。
- 段1でも、**要配慮の列はログ・監査ログの `details`・送信待ちの `payload`・Sentry に入らない**(分類表のテストと、ログの許可リスト)。
- 段を上げるのは、移行の決まり(`db-migration`。拡張 → 移し替え → 縮小)に沿う。段2・3は ADR を足してから。

## 結果として起きること

- 良くなること: 要配慮の列が、ふつうの列と同じ権限・同じ鍵に混ざって入ることが無い(入れようとすると CI が落ちる)。いまの費用は増えない。
- 我慢すること: 要配慮の列を足したい機能は、先に段1(スキーマ・ロール・鍵・暗号化の部品)の PR を作る。段1は、ふつうの検索・並べ替えができない(暗号文なので)。要るなら、検索用の別の値(ハッシュ)を足す。
- 見直す合図: 上の表の「上げる合図」。それと、要配慮の列を初めて足す仕様が来たとき(この ADR を「採用」にして、段1の設計書を書く)。
