# ADR 0015: 解約の書き出しは管理者が画面から、削除は運営がコマンドで

- 状態: 採用
- 日付: 2026-10-19
- 決めた人: @attumkwg

## 背景

解約したお客さんのデータの書き出しと削除の手順が無かった。マルチテナントでは「1社分だけを確実に・ほかに触れずに消す」が難しく、バックアップやログにも写しが残る。仕様は `docs/specs/0005-offboarding.md`。

## 選択肢

| 案 | 良い所 | 弱い所 |
|---|---|---|
| **A. 書き出しは画面から・削除は運営がコマンドで** | お客さんはいつでも持ち出せる。戻せない削除は、契約を確かめた人が2人で | 削除に運営の手間がかかる |
| B. どちらも画面から(解約を申し込む → 30日後に自動で削除) | 運営の手間が無い | 戻せない削除が、管理者の鍵1本・自動の処理で起きる。猶予と取り消しの仕組みが要る |
| C. どちらも運営が手順書で | 仕組みが一番少ない | お客さんが自分で持ち出せない(乗り換えの妨げ・問い合わせが増える) |

## 決めたこと

- **A**(作者 @attumkwg の選択)。
- 書き出しは `POST /api/exports`(管理者だけ)。各領域が自分の行を出し、写す項目を決めて JSON にする(表を丸ごと出さない: Cognito の ID・番号のハッシュは入らない)。書き出したことは監査ログに残る。
- 削除は CLI `delete-tenant`(ECS の1回きりのタスク・表の持ち主)。**既定は試し**で、`--execute --confirm-name <組織の名前>` のときだけ消す。1つのトランザクションで、`TENANT_TABLES` の順(子から親)に。
- `tenant_id` を持つ表を足したのに `TENANT_TABLES` に足していなければ、結合テストが落ちる(消し漏れを仕組みで防ぐ)。
- 消した組織の監査ログも消す(残すと「消した」ことにならない)。そのかわり**運営の組織の監査ログ**に、組織 ID と件数だけを残す。
- バックアップ・ログ・Sentry に残る物と期間は `docs/guides/data-retention.md` にまとめ、契約の文面の元にする。

## 結果として起きること

- 良くなること: 「持って出られる」「消してもらえる」を契約に書ける。消し漏れが CI で分かる。誰がいつ消したかが残る。
- 我慢すること: 削除は運営の作業(手順書で30分ほど)。大きな組織の書き出しは1回の応答なので、重くなる。バックアップからは1社だけ消せない(最長1年残る)。
- 見直す合図: 解約が月に数件を超えたら、B(画面から申し込み+猶予つきの自動の削除)。書き出しが数十秒を超えるようになったら、非同期(作って S3 に置き、リンクを知らせる)。大きなお客さんが「バックアップからもすぐ消して」を求めたら、テナントごとの鍵。
