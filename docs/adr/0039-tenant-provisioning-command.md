# ADR 0039: 組織を作るのは運営のコマンド(試し → 名前の確認 → 実行)

- 状態: 提案
- 日付: 2026-10-25
- 決めた人: @attumkwg(承認待ち)

## 背景

申し込みを受けた会社を組織にするのに、本番の DB に SQL で行を足していた(`docs/runbooks/support-access.md` の 1 と同じ形)。CS が本番の DB を触り、打ち間違い(メールの大文字・時間帯の名前)が起き、監査ログに残らない。解約の側には `delete-tenant`(ADR 0015)がある。仕様は `docs/specs/0026-tenant-provisioning.md`。

## 選択肢

| 案 | 良い所 | 弱い所 |
|---|---|---|
| **A. 運営のコマンド `create-tenant`(ECS の1回きりのタスク・表の持ち主)** | `delete-tenant` と同じ形。API の鍵が漏れても組織は増えない。試しで本番と同じ理由の失敗を前もって見られる | 流すのに本番の AWS の権限が要る(開発の人に頼む) |
| B. 運営の組織の社員だけが呼べる API と画面 | CS が自分で流せる | 全部の組織を作れる API が1本増える(関所の外の権限)。運営の組織の鍵1本で増やせる |
| C. 申し込みの画面(セルフサーブ) | 運営の手間が無い | 契約の前に組織ができる。請求・審査の仕組みが先に要る(G-03 の後) |
| D. SQL のまま、手順書だけ直す | 何も作らない | 監査ログに残らない・打ち間違いが残る |

## 決めたこと

- **A**。`node dist/cli.js create-tenant applications/<申込番号>.json [--execute --confirm-name <名前>]`。
- **申し込みは非公開の S3(申し込みの置き場)に置き、引数はキーだけ**(@attumkwg 2026-10-25。ECS のタスクの引数は CloudTrail に残り消せないので、管理者の名前・メールを渡さない)。置き場は `modules/record-store` を使い回し、今の版は7日・古い版は1日で消える。移行のタスクの役割には、その置き場の `applications/*` を読む権限だけ。読み終えたら人が消す。
- 既定は試し。**試しは同じ処理を流して最後に取り消す**(数えるだけでは、ほかの組織にあるメールの重なりを RLS の外から見られない)。
- 申し込みは JSON 1つ。知らない項目は読み飛ばして名前を出す(申込書・事前登録の項目をそのまま置ける)。
- 組織と最初の管理者(users の行。Cognito とはまだ結びつけない)と監査ログを1つのトランザクションで。監査ログは作った組織と運営の組織の両方(`tenant.create`・名前とメールは残さない)。
- 出力は JSON 1行で、名前とメールを出さない。

## 結果として起きること

- 良くなること: 本番の DB に SQL を打たない。誰がいつ作ったかが両方の監査ログに残る。2回流しても2つ目はできない。
- 我慢すること: 流すのは本番の AWS の権限を持つ開発(CS は申込書を渡して一緒に確かめる。設計書 0026 の U-2)。置き場に置く・消す手間が増える(消し忘れは7日で消える)。組織の名前は `--confirm-name` として CloudTrail に残る(`delete-tenant` と同じ)。
- 見直す合図: 開通が週に数件を超えて開発の人の手が回らない → B(運営の組織だけの API と画面)。お客さんが自分で申し込む形にする → C(G-03 のプランと請求の後)。
