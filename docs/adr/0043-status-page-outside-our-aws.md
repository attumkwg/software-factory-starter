# ADR 0043: 稼働状況のページは自分の AWS の外に置き、文は障害の知らせと同じにする

- 状態: 提案
- 日付: 2026-10-25
- 決めた人: (PR で承認)

## 背景

障害のとき、お客さんが「いま落ちているのか」を見られる所が無く、問い合わせが CS に集まる。ページを持つなら、どこに置くか・誰がどう更新するか・メールの知らせとどう合わせるかを決める必要がある。

## 選択肢

| 案 | 良い所 | 弱い所 |
|---|---|---|
| A. キットの中(本番の AWS の上)に作る | 費用が少ない・1か所 | 本番・DNS・CloudFront が落ちると、ページも一緒に落ちる。作って保つ手間 |
| B. **外のサービスを使う**(手引きで選び方だけ持つ) | 本番と別の基盤で動く。購読・予告・履歴がそろっている | 月の費用。購読を使うと、メールアドレスを外の会社に預ける |
| C. 持たない(メールだけ) | 何も要らない | 問い合わせが CS に集まる。計画メンテナンスの予告の置き場が無い |

更新のしかた:

| 案 | 良い所 | 弱い所 |
|---|---|---|
| 外形監視から自動 | 速い | 誤報も外に出る。文面の決まり(事実だけ)を機械は守れない |
| **人が手で(知らせる役)** | メールと同じ文を、決まりどおりに出せる | 人が書くまで出ない(S1 は30分以内の決まりで縛る) |

## 決めたこと

- **B**。キットは選び方と入れ方・障害の知らせとの対応だけを持つ(`docs/guides/status-page.md`)。いちばん大事な条件は「自分の AWS と別の所で動く」。
- 更新は**人が手で**。ページに載せる文は、障害の知らせ(`runbooks/incident.md` の 4)と同じ文。他社のデータ・個人データの事故はページに書かない。
- 既定は、購読を使わない・公開・稼働率の数字を出さない(設計書 0032 の未確定事項)。

## 結果として起きること

- 良くなること: 障害のときに「ページを見てください」と1回で答えられる。計画メンテナンスの予告の置き場ができる。
- 我慢すること: 外のサービスの月の費用。人が書くまでページに出ない。
- 見直す合図: 夜中の障害で、ページの更新が第1報の時間に間に合わないことが続いたら、外形監視から「調べています」だけを自動で出す。お客さんが購読を求めたら、委託先の台帳と同意の扱いを決めてから入れる。
