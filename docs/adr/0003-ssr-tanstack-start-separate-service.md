# ADR 0003: 画面は TanStack Start の SSR にし、API とは別の ECS サービスで動かす

- 状態: 採用
- 日付: 2026-10-18
- 決めた人: @attumkwg

## 背景

これまでの画面は React+Vite の SPA で、ビルドした HTML と JS を API のコンテナが配っていた。

- 最初の HTML が空なので、検索エンジンや共有のプレビュー(OGP)に中身が出ない。
- 画面を開くたびに「JS を読む → API を呼ぶ → 描く」の順になり、最初の表示が遅い。
- URL と画面が結びついておらず(状態で切り替え)、再読み込みや共有で同じ画面に戻れない。
- 将来の「サイト型」(SEO が要る)の雛形を作るときの土台にならない。

## 選択肢

| 案 | 良い所 | 弱い所 |
|---|---|---|
| A. TanStack Start の SSR・**別の ECS サービス** | 素直な使い方。画面と API を別々に出せる・縮められる。画面に秘密も DB の接続も無い | Fargate が1つ増える(stg 月 約1,700円・本番 約3,400円)。ALB の振り分けと Service Connect が要る |
| B. TanStack Start の SSR・API と同じコンテナ | 安い。今の形に近い | TanStack Start の素直な使い方から外れる。画面の変更でも API ごと出し直す。1つの穴で両方に届く |
| C. Next.js | 情報が多い | 型安全なルーティングと「loader でデータを読む」形が TanStack Router ほど素直でない。Vercel 以外での運用の知見が要る |
| D. SPA のまま | 何もしなくてよい | 上の背景が解けない |

## 決めたこと

**A**。画面(`apps/web`)は TanStack Start の SSR にし、ALB で振り分ける:

- `/api/*` → API のサービス(これまでどおり)
- それ以外 → 画面のサービス。HTML を作るときに API を **Service Connect の `http://api:3000`** で読む

決まり:

1. **同じオリジンのまま**(ALB で振り分けるだけ)。Cookie は `SameSite=Lax`・`HttpOnly` のまま、CORS も要らない。
2. **画面のサーバーは読むだけ**。SSR から API に送るのは GET だけで、来た Cookie と request ID だけを渡す。書き込みはブラウザから API へ直接(CSRF の守りを API の1か所に)。画面のサーバーは POST などを 405 で断る。
3. **画面のサーバーは秘密を持たない**。DB の接続も `SESSION_SECRET` も無い。テナントを決めるのは今までどおり API(セッションから)。
4. 本番のイメージは「1つにまとめた JS+配る JS・CSS」だけ(node_modules を入れない。API と同じ考え)。
5. 手元でも同じ形: docker compose の `alb`(Caddy)が ALB の代わりに振り分ける(http://localhost:8080)。

## 結果として起きること

- 良くなること: 最初の HTML に中身が入る(SEO・OGP・表示の速さ)。URL で画面が決まる(再読み込み・共有で同じ画面)。画面と API を別々に出せる。
- 我慢すること: 出すもの(イメージ・ECR・ECS サービス)が2つになる。SSR とブラウザで表示が同じになるように書く必要がある(日時は表示のタイムゾーンを固定する・描画中に `window` を触らない)。
- 見直す合図: 画面の SSR の CPU が張り付く(キャッシュか、静的に作れるページを先に作る)/ 画面から API を呼ぶ回数が1画面で5回を超える(画面向けの API をまとめる)/ サーバー関数(`createServerFn`)を使いたくなった(画面のサーバーが書き込みも受けることになるので、この ADR を見直す)。
