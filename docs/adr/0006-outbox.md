# ADR 0006: 起きたことは「送信待ちの表(アウトボックス)」に同じトランザクションで積み、API の中で送り出す

- 状態: 採用
- 日付: 2026-10-18
- 決めた人: @attumkwg

## 背景

「タスクが完了したら Slack に知らせる」「検索の索引を直す」「キャッシュを消す」のように、DB の変更のあとで外に何かを送る場面は必ず増える。素直に書くと次のどちらかの事故が起きる。

- DB に書いたあと送る前に落ちる → **送り漏れ**(索引やキャッシュが古いまま)
- 送ったあと DB の書き込みが取り消される → **起きていないことを送る**

## 選択肢(送り出しをどこで動かすか)

| 案 | 良い所 | 弱い所 |
|---|---|---|
| A. API のプロセスの中で回す | 追加の費用 0円。仕組みが少ない | API の負荷と混ざる。重くなったら分ける必要がある |
| B. 別のワーカーのサービス | 負荷が分かれる | 環境ごとに Fargate が1つ増える(約 +1,700円/月)。PMF 前には早い |

## 決めたこと

**A**(作者 @attumkwg の選択)。重くなったら同じイメージで別のサービスに出せる形にしておく(`OUTBOX_RELAY=off` を API 側に)。

- 表は `platform.outbox`。業務の変更と**同じトランザクション**で `enqueue(scope, "<領域>.<出来事>", 中身)` を呼ぶ。取り消されれば一緒に消える。
- 出来事の一覧と中身の形は `apps/api/src/outbox/topics.ts`。中身は ID だけ(個人情報や本文は入れない。受け手が必要なら読み直す)。
  - 補足(2026-10-29・設計書 0089 の 13): 受け手が後から読み直しても分からない「その時点の真偽」(個人情報でない)は積んでよい(例: タスクが完了した時点で組織がメールを止めていたか `mailOffAtCompletion`)。値・本文・名前は今までどおり入れない。
- 送り出し(`relay.ts`)は1秒ごとに、送るべき物を「借りて」宛先(`handlers.ts`)へ送る。
  - API が何台あっても、DB の `FOR UPDATE SKIP LOCKED` で同じ物を2台が取らない。
  - 送れなければ 1秒・2秒・4秒…(最大1時間)あとでやり直し、10回でやめる(`dead_at`。人が見て直す)。
  - 宛先の無い出来事は送らずに dead にする(宛先の書き忘れに気づけるように)。
- **アプリは書くだけで、読めない**(他社の出来事を読めないように)。読む・印を付けるのは移行 0004 の3つの関数だけ(0001 のログイン用の関数と同じ形)。

## 約束すること・しないこと

- ✅ 業務の変更が確定したものだけが、いつか必ず届く(少なくとも1回)。
- ⚠️ **同じ出来事が2回届くことがある**(送った直後に落ちて、印を付けられなかったとき)。受け手は `event.id` で重ねて処理しないように書く。
- ⚠️ 順番は保証しない。順番が要るなら、受け手が中身の時刻や版で判断する。

## 結果として起きること

- 良くなること: 送り漏れと「起きていないことを送る」が無くなる。領域をまたぐ処理を、外部キーや直接の呼び出しではなく出来事でつなげる(ADR 0004 の分割の道筋)。
- 我慢すること: 届くまでに数秒かかる。受け手を「2回届いても大丈夫」に書く手間。送り終わった行が溜まる(下の合図)。
- 見直す合図: 送り出しが追いつかない(未送信の数が増え続ける)→ 別のサービスに分ける / 送り終わった行が数百万を超える → 古い行を消す仕組み(毎晩、30日より前の送り終わった行を消す)/ 出来事の受け手が増えた → SQS や EventBridge に送る形にする。
