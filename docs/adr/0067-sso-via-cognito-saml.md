# ADR 0067: SSO は Cognito の SAML の IdP でつなぎ、組織は IdP で決める。強制ログアウトはいまの仕組みで

- 状態: 提案
- 日付: 2026-10-25
- 決めた人: @attumkwg(承認待ち)

## 背景

大きなお客さんの情シスは SSO(SAML)・SCIM・IP の制限・監査ログの書き出しを求める(穴 G-14)。決まり T-8 は「SSO は会社のドメインを DNS で確かめてから」。ログインは API が Cognito の API を呼ぶ形(ADR 0009)で、トークンは API の中だけ(ADR 0007)。サーバー側のセッション保存は作らないと決めている(ADR 0017)。仕様は `docs/specs/0056-sso-scim-ip-audit-export.md`。

## 選択肢

SAML の受け方:

| 案 | 良い所 | 弱い所 |
|---|---|---|
| **A. Cognito の SAML の IdP(OAuth のコードを API が交換)** | SAML の署名・時刻・宛先の確かめを Cognito がする。いまの Cognito のまま | ユーザープールのドメインと OAuth の入口が要る。偽物の Cognito に OAuth を足す。SAML の利用者の料金が高い |
| B. API で SAML を直接読む(ライブラリ) | Cognito の料金がかからない | 署名の確かめを自前で持つ(穴になりやすい)。ライブラリの脆弱性の追いかけ |
| C. 外の IdP の仲介(Auth0 などの SaaS) | 多くの IdP にすぐつながる | 委託先が増える。ログインの正が2つになる |

強制ログアウト:

| 案 | 良い所 | 弱い所 |
|---|---|---|
| **A. `users.sessions_valid_after` を今にする(関所が毎回見ている)** | 表も Valkey も要らない | 端末を選んで切れない |
| B. サーバー側のセッション保存(ADR 0017 の B) | 端末の一覧・端末ごとに切れる | 表か Valkey・毎回の読み・掃除 |

## 決めたこと

- **SAML は A**。ユーザープールのドメインとアプリクライアントの OAuth(コード・PKCE)を足し、組織ごとの IdP は運営のコマンドが作る。API はコードを交換し、ID トークンの署名・発行元・宛先・IdP の名前を確かめる。トークンは API の中で使い捨て。
- **組織は IdP で決める**。戻ってきた人のメールのドメインは「その組織の確かめたドメインか」の確かめにだけ使う(T-8・L-8)。確かめたドメインは全体で1つの組織だけ。
- **強制ログアウトは A**(ADR 0017 はそのまま)。SCIM で止めたときも同じ。
- SCIM は `/api/scim/v2`(鍵で組織が決まる)。監査ログの書き出しは、データの書き出しと同じく1ページずつ流す(ADR 0031)。
- 作る順は SSO(ドメイン・必須・緊急用・IP の制限・強制ログアウト)→ SCIM → 監査ログの書き出し。段ごとに別の PR。

## 結果として起きること

- 良くなること: 大きなお客さんの条件(SSO・止めたらすぐ切れる・IP・監査ログ)に答えられる。SAML を自前で読まない。サーバー側のセッション保存を作らずに済む。
- 我慢すること: Cognito の OAuth の入口・ドメイン・IdP の運用(証明書の更新)が増える。偽物の Cognito に OAuth を足し、本物の SAML は stg で人が確かめる。端末を選んで切るのはできないまま。
- 見直す合図: OIDC の IdP が要る → Cognito の OIDC の IdP を同じ形で足す。SSO の組織が数百に近づく → ユーザープールを分けるか C。端末ごとのログアウトを契約で求められる → ADR 0017 の B。
