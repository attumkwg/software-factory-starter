# ADR 0005: お金は「最小単位の整数+通貨」、時刻は UTC で持ち組織の時間帯で見せる

- 状態: 採用
- 日付: 2026-10-18
- 決めた人: @attumkwg

## 背景

お金と時刻は、作った後で持ち方を変えると、全部の表・API・画面・集計を直すことになる。しかも間違いはテストが緑のまま本番で見つかる(1円ずれる・日付が1日ずれる)。

本人の問い: 「お金の整数の話、合ってるのか」「UTC にする場合のタイムゾーンの取り扱いが気になる」。

## お金

**整数は手段で、本当に避けたいのは小数(浮動小数点)**。`0.1 + 0.2` は `0.30000000000000004` になる。整数だけでは足りないので、次の4つを一緒に決めた(本人の選択「金額は整数+率は小数」)。

| 決めたこと | 中身 | なぜ |
|---|---|---|
| 金額 = 最小単位の整数+通貨 | 円は1円、ドルは1セント(`MoneySchema`)。DB は `bigint`+`char(3)` | 通貨で小数の桁が違う(円0・ドル2・クウェート・ディナール3)。通貨の無い金額は後から海外に出せない |
| 単価・率は小数の文字列 | 税率 `"0.1"`・0.5円/回・為替(`DecimalSchema`)。DB は `numeric` | 整数にならない物を整数にすると、桁を決め打ちして崩れる |
| 計算は1か所・丸めは最後に1回・丸め方を必ず渡す | `@app/shared` の `money.ts`(BigInt で正確に) | 途中で丸めると誤差が積もる。丸め方(切り捨て・四捨五入・銀行丸め)は仕様で決まる |
| 消費税は「1つの請求書の税率ごとに1回」丸める | `taxByRate`(インボイス制度の考え方) | 明細ごとに丸めて足すと数円ずれる(テストに例がある) |

- DB の `bigint` は node-postgres が文字列で返すので、数への直しを `db/columns.ts` の `moneyAmount` にまとめた。JS の数で正確なのは約9千兆まで(円なら十分)。
- 全部を `numeric`(固定小数点)にする案も正しい。整数を選んだのは、JS で扱いやすく、丸める場所がコードに必ず出るから。
- Semgrep の `no-float-money` が、金額らしい名前の変数を小数で掛ける・`toFixed` を止める。

## 時刻

**保存は UTC、見せるときに時間帯へ直す**。ただし時刻には3種類あり、UTC にしてよいのは1つ目だけ。

| 種類 | 例 | 持ち方 |
|---|---|---|
| ある瞬間 | 作った時刻・ログイン | `timestamptz`(UTC)。API は末尾 `Z`(`InstantSchema`)。`+09:00` 付きは受け付けない |
| 日付だけ | 期限・誕生日・締め日 | `date`(`DateOnlySchema`・`dateOnly`)。**UTC の0時にしない**(日本の 10/18 0:00 は UTC で 10/17 15:00。1日ずれる) |
| 土地の時計の時刻 | 「毎朝9時に通知」・営業時間 | 時刻+時間帯の名前(`"09:00"`+`"Asia/Tokyo"`)。UTC に直して保存しない(夏時間・制度の変更で崩れる) |

- **どの時間帯で見せるか・「1日」をどこで区切るか**は、組織の時間帯 `organizations.tenants.time_zone`(IANA の名前。既定 `Asia/Tokyo`)で決める(本人の選択「組織ごと」)。`/api/me` が返し、画面はその時間帯で表示する。SSR とブラウザで同じ時間帯を使うので、表示がずれない。
  - 利用者ごとに変えたくなったら、`users` に上書き用の列を足す。集計の「1日」は組織のまま。
- 日ごとの集計は、組織の時間帯で区切る: SQL なら `(created_at AT TIME ZONE $tz)::date`、範囲で探すなら `localDayRange(date, tz)`(夏時間で23・25時間の日も正しい)。UTC で区切ると、日本の朝9時が日付の境目になる。
- DB の接続の時間帯は UTC に固定する(`TimeZone=UTC`)。`now()::date` が DB の設定で変わらないように。
- 時間帯は `"+09:00"` や `"JST"` ではなく名前で持つ(夏時間の国でも正しく動く)。
- Semgrep の `no-local-time` が、端末・サーバーの時間帯に頼った書き方(`getHours()`・時間帯なしの `toLocaleDateString` など)を止める。

身近な例: Google カレンダーの終日の予定に `+09:00` を付けて登録すると1日前にずれる。「日付だけ」を「ある瞬間」として扱うとこうなる。

## 結果として起きること

- 良くなること: 1円・1日のずれが、型と検査で起きにくくなる。海外の組織・夏時間の国にもそのまま出せる。
- 我慢すること: お金の計算は `money.ts` を通す手間がある。表示や集計のたびに組織の時間帯を渡す。
- 見直す合図: 使う通貨が増えた(`CURRENCY_DIGITS` に足す)/ 利用者ごとの時間帯が要る / 小数の桁が多い単価(従量課金など)を大量に扱う(`numeric` の精度を見直す)。
