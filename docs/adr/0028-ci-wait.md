# ADR 0028: CI の待ちは、検査を減らさずに縮める。文書だけの PR では重いジョブの中身を省き、成功を返す

- 状態: 採用(文書だけの PR で重い検査を省くのは、2026-10-24 に持ち主が承認)
- 日付: 2026-10-24
- 決めた人: @attumkwg(PR で)

## 背景

PR を並べて入れると、CI の待ちが長い(1回 3〜7分)。main のルールセットは「最新の main に追いついてから」(`strict`)で、個人のリポジトリではマージキューが使えない。1本マージするたびにほかの PR を追いつかせて CI を全部流し直すので、待ちは「1回の長さ × 本数」で積み上がる。
1回の長さを決めているのは E2E(約4分)で、その半分近くは「起動を待つ」「ブラウザを入れる」など、確かめていない時間だった(内訳は [ci-speed.md](../guides/ci-speed.md))。

## 選択肢

| 案 | 良い所 | 弱い所 |
|---|---|---|
| A. 守りを外す(必須のチェックを減らす・`strict` を外す) | いちばん速い | 並べた PR が合わさって main を赤くする。落とすべき物が通る |
| B. 確かめていない時間を削る(起動の待ち・ブラウザを入れる・並列の数) | 検査は1つも減らない | 縮む幅には限りがある |
| C. B+**文書だけの PR では重いジョブの中身を省く**(成功を返す) | 文書だけの PR(main の commit の約2割)は1分ほどで緑になる | 見分けを誤ると、コードの変更が重い検査なしで通る |
| D. 重いジョブを機械ごとに分ける(シャード)・層のキャッシュの共有 | E2E がさらに縮む | 仕組みが増える。シャードは同時に動くジョブが増えて、上限(20)に当たりやすい。層のキャッシュは試したが、読み込みに作り直しと同じだけかかり、ほぼ縮まなかった |

## 決めたこと

- **B と C**。D は見直す合図が来たら(ci-speed.md)。測った前と後は ci-speed.md(コードの PR の CI は中央値 254秒 → 162〜193秒・文書だけの PR は 43秒)。A はしない(やるなら持ち主が決める)。
- C の見分けは許可リスト(`.github/scripts/ci-scope.mjs`)。文書とみなすのは `docs/`(`docs/authz/` を除く)と、`apps/`・`packages/` の外の `.md` だけで、迷ったら流す。PR 以外(main への push・マージキュー)では全部流す。見分けは `.github/**`(危険度「高」)に置き、テストを付ける。
- 省いたジョブは「成功」を返す(ジョブの中の手順を飛ばす)。必須のチェックの名前と数は変えない。

## 結果として起きること

- 良くなること: コードの PR の CI が縮み、追いつかせのたびの待ちも同じだけ縮む。文書だけの PR は重い検査を待たない。
- 我慢すること: 重いジョブの手順に `if` が並ぶ。文書だけの PR でも、重いジョブの数だけ機械は起動する(数秒ずつ)。
- 見直す合図: 文書だけと見た PR の後で、main の重い検査が落ちた(→ 見分けを狭める)/ E2E が再び 3分を超えた(→ D)。
