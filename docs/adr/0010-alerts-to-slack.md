# ADR 0010: 見張りの知らせは SNS に集め、AWS の公式の連携で Slack に流す

- 状態: 採用
- 日付: 2026-10-18
- 決めた人: @attumkwg

## 背景

これまでのアラームは API と画面の 5xx の2つだけで、通知先(SNS)も作っていなかった(`alarm_topic_arns` を人が渡す形)。タスクが落ち続ける・DB が上限に張りつく・メールの評判が落ちる・費用が増える、のどれも誰にも届かなかった。PMF の前で当番は置かないので、**気づける場所(Slack)に、必要なものだけを流す**道を作る。

## 選択肢

| 案 | 良い所 | 弱い所 |
|---|---|---|
| A. AWS の公式の連携(Amazon Q Developer in chat applications。旧 AWS Chatbot) | コードを持たない・無料・グラフつきで出る・Terraform で持てる | 最初に1回、人がコンソールで Slack を許可する。設定の API が東京に無い(シンガポールに置く) |
| B. Lambda で Slack の Incoming Webhook に送る | 文面を自由に作れる・手作業が少ない | Lambda のコード・依存・秘密(Webhook の URL)を持ち続ける |
| C. メールだけ | いちばん簡単 | 埋もれる。チームで「誰が見ているか」が分からない |

## 決めたこと

**A**。知らせはすべて環境ごとの SNS(KMS で暗号化)に集め、そこから Slack(とメール)へ。

- 鳴ったときと戻ったときの両方を流す。
- Slack から AWS を操作はさせない(連携の権限とガードレールを CloudWatch の読み取りだけに。指定しないと AdministratorAccess になる)。
- ECS のタスクの停止は、1回ずつ流すと再起動の繰り返しで Slack が埋まるので、**EventBridge → ログ → 数 → アラーム**(15分に3回)にした。理由はログに残る。
- 費用は AWS Budgets(使った額 80% と、月末の見込み 100%)。
- 外形監視は Route 53 のヘルスチェック(作者 @attumkwg の選択。安く、知らせの道を AWS の中にそろえられる)。数字がバージニアにしか出ないので、そこにも SNS を置き、同じ Slack 連携に足す。本物のブラウザで流れを見る Synthetics は PMF 後。

## 結果として起きること

- 良くなること: 落ちた・遅い・DB・メール・費用・セキュリティが、同じ1つのチャンネルに出る。アラームを足すときは `alarm_actions = [module.alerts.topic_arn]` だけ。
- 我慢すること: Slack の文面は AWS の決まった形。Slack の許可は人の手作業。
- 見直す合図: 有料の顧客が付いて夜中の対応が要るようになったら、SNS に当番の仕組み(PagerDuty など)を足す。1週間に鳴る回数が10回を超えたら、しきい値を見直す(慣れて見なくなる前に)。
