# ADR 0026: プロダクトごとに答えが違う未確定事項は「導入時に決める」にし、キットの既定でマージして、本番の前に止める

- 状態: 提案
- 日付: 2026-10-24
- 決めた人: @attumkwg(方針は 2026-10-21〜22 の会話で決めた。この ADR は形にした物)

## 背景

設計書の未確定事項は「AI の仮決め」と「人の承認」を分けて追い、仮決めが残る PR は CI(`pnpm decisions --strict`)で落ちる([guides/human-review.md](../guides/human-review.md) の 2)。

キットには、**プロダクトごとに答えが違う問い**がある(利用規約の同意し直しの基準・周知の日数・点検の担当者・検索に載せるか など)。キットの持ち主はキットの既定として承認できるが、それは使う人のプロダクトの答えではない。いまは `承認` にするしかなく、使い始めた人には「自分が決める所」と分からないまま、本番に出てしまう。

## 選択肢

| 案 | 良い所 | 弱い所 |
|---|---|---|
| A. 状態 `導入時に決める` を足す。`--strict` では落とさず、`--adopt` で一覧・`--launch` で本番の前に止める | 表の形はそのまま。使う人のリストと公開の前の止めが、同じ表から出る | 状態が1つ増え、覚えることが増える |
| B. `承認` のまま、別の一覧(Markdown)に「使う人が決める物」を手で書く | 状態を増やさない | 設計書と一覧がずれる。止める仕組みが無い |
| C. `仮決め` のまま残し、キットの CI だけ `--strict` を外す | すぐできる | キットで本当の仮決めを見落とす。持ち主の承認が記録に残らない |

## 決めたこと

**A。**

- 状態は `導入時に決める(キットの既定は @名前 YYYY-MM-DD に承認)`。括弧に `@` が無いと書き方の問題(人の答えを経ずに、仮決めを書き換えてすり抜けるのを防ぐ)。
- `pnpm decisions --strict`(CI)は落とさない。`pnpm decisions --adopt` は導入時に決めるの行だけを設計書ごとに出す。`pnpm decisions --launch` は仮決め・導入時に決める・書き方の問題が残れば 1 で終わる。
- 使う人の入口は `pnpm decisions --adopt`・`/tailor` のチェックシート・README の「使い始めたらやること」⑤・点検の台帳の `launch-decisions`。
- 使う人が答えたら、今までどおり `承認` / `変更`(→ `/rework`)にする。
- どの行を導入時に決めるにするかは、キットの持ち主が決める(AI は候補を出すだけ)。
- `--launch` を本番のデプロイ(`.github/workflows/deploy.yml` の prod)で流すかは、CI(危険度「高」)なので別に人が決める。

詳しくは [designs/0013-decisions-at-adoption.md](../designs/0013-decisions-at-adoption.md)。

## 結果として起きること

- 良くなること: キットの既定のまま、知らずに本番へ出ることが無くなる(`--launch`)。使い始めた人が「自分が決める所」を1つのコマンドで見られる。
- 我慢すること: 状態が6つになる。キットの持ち主は、問いを足すたびに「プロダクトごとに違うか」を決める。
- 見直す合図: 使う人が導入時に決めるの行を、ほとんど「既定のまま」で承認するなら、行を減らす(キットの既定を信じてよい)。逆に「変更」が多い設計書は、既定の作りを見直す。
