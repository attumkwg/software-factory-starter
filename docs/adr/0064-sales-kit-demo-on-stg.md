# ADR 0064: 営業のデモ用の組織は stg に1つ置き、毎晩 stg の移行のタスクで決まったデモのデータに戻す

- 状態: 採用
- 日付: 2026-10-25
- 決めた人: @attumkwg(2026-10-25。会話で回答。見込み客に stg のアカウントを渡さない既定を承認し、触ってもらうかは使う人が導入時に決める)

## 背景

商談のデモを毎回手で掃除している(仕様 0053・穴 G-35)。本番には本物のお客さんのデータがあり、手元の種データは商談で開けない。どこにデモを置き、どう戻すかを決める必要があった。

## 選択肢

| 案 | 良い所 | 弱い所 |
|---|---|---|
| A. 本番にデモの組織を置く | 本物と同じ速さ・同じ版 | 戻す処理が本番の DB に書く(間違えると本物の組織を消す)。営業の手で本番に触る |
| B. stg にデモの組織を置き、新しい ECS の予定のタスクで戻す | 本番に届かない | 新しいタスク定義・役割・予定の仕組み(infra の apply)が要る |
| C. stg にデモの組織を置き、GitHub Actions の毎晩の仕事が、今ある stg の移行のタスクをコマンドだけ上書きして戻す | 本番に届かない(stg の役割だけ)。infra を足さない。失敗が Actions に見える | 移行のタスク(表の持ち主の接続)を借りる。stg のデプロイの役割に頼る |
| D. プレビュー環境を毎回作る | いつも新しい | 起動に時間がかかり、商談の直前に作れない。ログインがデモ用でない |

## 決めたこと

**C**。戻すコマンドは `APP_ENV` がはっきり stg(か手元・プレビュー)で、`DEMO_TENANT_ID` があるときだけ動く(移行のタスクは `APP_ENV` を持たないので、ワークフローが渡す)。戻すのは `TENANT_TABLES` から残す表(組織・人・プラン・機能・同意・監査ログ)を引いた物で、決まったデモのデータを入れ直す。見込み客に stg のアカウントを渡さないのがキットの既定で、触ってもらうか(共有のアカウント・本番の試用の組織)は使う人が導入時に決める(設計書 0053 の U-1)。

## 結果として起きること

- 良くなること: 毎朝きれいなデモで商談に出られる。本番に触らない。infra を変えない。
- 我慢すること: デモは stg の版(本番より先の版のことがある)と stg の速さ。デモの中で増えた人は残る。
- 見直す合図: 見込み客に触ってもらう試用が増えた(本番の試用の組織にする)・stg の移行のタスクの形が変わった・デモの組織を2つ以上持ちたくなった。
