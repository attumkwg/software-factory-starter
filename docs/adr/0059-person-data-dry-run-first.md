# ADR 0059: 利用者1人分の開示・削除は、まず「試し」と手順書から

- 状態: 提案
- 日付: 2026-10-25
- 決めた人: @attumkwg(承認待ち)

## 背景

利用者1人から開示・削除を求められたとき(個人情報保護法 33条・35条)に答える手段が無い。組織を丸ごと消す `delete-tenant` はあるが、1人分は無い。誰が答えるかも決まっていない(取り扱いの取り決めの型では、自社は委託先)。仕様は `docs/specs/0048-person-data.md`。

## 選択肢

| 案 | 良い所 | 弱い所 |
|---|---|---|
| **A. 試し(数えるだけ)のコマンドと手順書。消す・匿名化は次の一歩** | 戻せない操作を、扱い(何を消し何を残すか)を人が決める前に作らない。どこに何があるかは今すぐ答えられる | 消すのはまだ手で(手順書で2人) |
| B. 試し → 消す(`--execute`)まで一度に作る | 求めに一気に答えられる | 監査ログ・同意の記録を残すか、匿名化の形が決まっていない(戻せない) |
| C. 手順書だけ(SQL を書く) | 作る物が無い | 表が増えるたびに SQL を探し直す。足し忘れに気づけない |
| D. 画面から本人が求める窓口 | 本人が直接使える | 委託先の立場では、本人を確かめられるのはお客さん。窓口が二重になる |

## 決めたこと

- **A**。`person-data <組織の ID> <利用者の ID>`(引数は ID だけ・何も変えない・出すのは表と列の名前・件数・扱い)。
- 利用者を指す列の一覧 `PERSON_REFERENCES` をコードに持ち、利用者の ID を持つ列が DB に増えたのに一覧に無ければ結合テストが落ちる(解約の `TENANT_TABLES` と同じ守り)。
- 求めはお客さん(委託元)が受けて答え、運営は書面の指示で手伝う(設計書 0048 の U-1)。開示の中身は、お客さんが自分の書き出しから作る(U-3)。

## 結果として起きること

- 良くなること: 「どこに何件あるか」をすぐ答えられる。新しい表で足し忘れても CI が気づく。値は運営の手を通らない。
- 我慢すること: 消す・匿名化は手順書で手作業(2人)。扱いの案(U-2)が承認されたら、`--execute` を足す仕様を別に出す。
- 見直す合図: 求めが月に数件を超える → B(消すコマンド)。自社が直接答える契約の形を取る → 受付と本人確認を運営が持つ形(D を含めて)。
