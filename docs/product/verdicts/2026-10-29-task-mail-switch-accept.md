## 理由

- [記録] できた物は意義に届く作り: 管理者だけの API 3本(`task_mail:manage`・権限の表3行・監査ログ2つ)、送る直前に読んで `skip: mail_off_by_organization`(#181。止める前に積んだ物も送らず、戻しても止めていた間の分は届かない — `mail.int.test.ts` の2件)、設定のカード(#182)。集計で止めた組織を数えられることは `task-mail.int.test.ts` の4件目が確かめている。仕様の「やらないこと」(人ごとに止める・ほかのメールを止める・まとめて1通や時刻)は作っていない — 列を読むのは `taskCompletedMail` の1か所だけ。守り(関所・監査ログ・テナントはセッションから・列ごとの GRANT)は削っていない。
- [記録] 止める線は中身では守られ、順番では守られていない。①の最初のコミットは 03:19、②は 03:21、③は 03:23(すべて UTC)で、③は ①② がマージされる(04:07・04:31)前に並べて作られた。「①②が済んだ時点で費用を見る」確かめは、PR にもシナリオの記録(`docs/scenarios/03-roadmap-build.md`)にも残っていない。①② の費用は 0.1 人日前後【推定】(①は +3,089 行のうち 2,847 行が生成された移行の snapshot で、手で書いたのは 240 行ほど。②は +36 行。人のレビューは0件)で、4 人日の線から2桁下なので、作った物は取り消さない。
- [記録] 費用の見込み(2〜5 人日)は 10倍以上外れた(良い向き)。AI が1時間で作る作業に人日の上限を止める線として置いても、確かめる前に作り終わる。歯止め3の「物差しの見直し」として、次からの分解の前の止める線は、子 Issue の「待つ」に入れる(③ は ①② の確かめを待つ)か、人日ではなく「答えを待つ問いの数」など AI の速さでも先に来る物にする。
- [推測] 得る物(月)は前の判断の架空の幅のまま(運営の手作業と、撤退の線を手で数える時間)。費用が小さくなったので ROI は 0.0〜24.0 倍に上がったが、悪い方の端は 0 倍で、得る物は確かめていない。だから「やる」ではなく条件つき。
- [記録] 条件: 撤退の線を「月1回数えられる」にする物がまだ無い。動かす KPI は K-n ではないので `pnpm kpi` は records から読めず、数え方(集計の式)は設計書 0089 の 5 にしか書かれていない。賭け B-0001 の adopted の撤退の線の行か「関わった Issue・PR」に、数え方(式・分母・月末)を1行足し、2026-11-30 に1回目を数えて「## 結果」の実測に書く。見本のアプリには本物の組織が無いので、キット自身では数は架空のままで、使う人のプロダクトで数える。
