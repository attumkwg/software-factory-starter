# 仕様: 組織ごとの機能フラグと、利用の記録(A/B テストの土台)

> 状態: 承認済み(機能フラグの節。承認した人: @attumkwg 2026-10-24。設計書の U-1 を承認)/ 利用の記録の節は下書き(PR ②。依頼: @attumkwg 2026-10-22「A/B テストはあった方がいいかも」。順番は 機能フラグ → 利用の記録 → `/bet` の A/B の型、と決めた)
> 設計: [docs/designs/0012-feature-flags-and-usage.md](../designs/0012-feature-flags-and-usage.md)・ADR: [0025](../adr/0025-feature-flags-and-usage-records.md)
> PR は2つに分ける: ① 機能フラグ(この仕様の「機能フラグ」の節)→ ② 利用の記録(「利用の記録」の節)。

## なぜ作るか

賭け(`docs/product/bets/`)は `psf` → `rollout` で「**一部の組織に出して、使われ続けるか**」を確かめる([guides/bets-and-assets.md](../guides/bets-and-assets.md))。けれどもキットには、

- 一部の組織にだけ機能を出す仕組み(**機能フラグ**)が無い。出すか出さないかを、デプロイでしか変えられない。
- 「どの組織の・誰が・その機能を使ったか」の**記録**が無い。合格と撤退の線(「出した組織の 70% が4週間後も使う」など)を測れない。

PMF の前は組織の数が少なく、A/B テスト(くじで2つの組に分けて差を比べる)をしても差が偶然か分からない。だから先に**段階的な公開(選んだ組織に出して、使われるかを見る)**ができる土台を入れ、A/B の型はその後に足す。

## 受け入れ条件

> 「誰が・何をすると・どうなる」。どのテストかは設計書の「7. 要求との対応」。

### 機能フラグ(PR ①)

定義(開発者):

- [ ] 機能フラグは**コードに定義する**(名前・どの賭けか・説明・状態)。状態は3つ: `rollout`(選んだ組織だけ)/ `on`(全部の組織)/ `off`(全部の組織で止める)
- [ ] 定義に無い名前を、画面・API のコードで使うと型の検査で落ちる
- [ ] フラグは必ず賭け(`B-NNNN`)に結びつく。賭けのファイルが無い・賭けが `idea` / `cpf`(まだ作る段階ではない)・`dropped` / `retired`(やめた・撤去した)なら CI が落ちる(消し忘れを残さない)

切り替え(運営):

- [ ] 運営が、組織の ID と機能の名前を指定して、その組織だけ**入れる・切る**ことができる(コマンド。試し → `--execute`)
- [ ] 試しでは何も変えず、いまの状態と変えた後の状態だけを出す
- [ ] 定義に無い名前・`rollout` ではない機能・無い組織を指定すると、何も変えずに止まる
- [ ] 入れた・切ったことが、**その組織の監査ログ**に「仕組みが」「機能を入れた / 切った」として残る(どの機能かの名前つき)
- [ ] 同じ組織に同じ機能を2回入れても、状態は1つ(2回目は何もしない)

効き方(全員):

- [ ] ログインした人の「自分」(`GET /api/me`)に、**その組織で入っている機能の名前の一覧**が出る。画面はこれでボタン・画面を出し分ける
- [ ] `on` の機能は全部の組織に出る。`off` の機能は、組織で入れてあっても出ない(全部で止める)
- [ ] 入っていない機能の API を呼ぶと 404(無い物と同じ)
- [ ] サポートの代理ログイン中の社員には、見ている組織と同じ一覧が出る(お客さんと同じ画面を見るため)

他社・未ログイン:

- [ ] ある組織で入れた機能は、他社には出ない(組織はセッションからだけ決まる。表は RLS)
- [ ] 未ログインで `GET /api/me` を呼ぶと今までどおり 401

### 利用の記録(PR ②)

記録する(仕組み):

- [ ] 機能の API(や画面を開く API)のハンドラーが「使った」と記録すると、**どの組織の・誰が・どの機能を・どの日に**使ったかが1行残る
- [ ] 同じ人が同じ日に同じ機能を何度使っても、記録は1行(その日の最初だけ)。「日」は組織の時間帯で区切る
- [ ] 記録するのは上の4つだけ。**何をしたか・入れた中身・回数・時刻(秒まで)・画面の URL・IP アドレス・ブラウザの種類は記録しない**
- [ ] サポートの代理ログイン中の社員の操作は記録しない(お客さんが使ったことにならない)。運営の組織の人の操作も記録しない
- [ ] 記録は操作と**同じトランザクションで**足す(操作が失敗して取り消されたら、記録も残らない)

見る(運営):

- [ ] 運営が、機能の名前を指定して、週ごとの「使った組織の数・使った人の数」と「いまその機能が入っている組織の数」を出せる(コマンド)。**組織の ID・名前・人の ID は出さない**(数だけ)
- [ ] 出した数は、賭けの小石に割合で書ける(「出した組織の 6/8 が4週続けて使った」→ 小石には「75%」)

消す:

- [ ] 記録は**決まった日数**を過ぎたら消す(運営のコマンド。試し → `--execute`)。日数は設計書の未確定事項
- [ ] 解約した組織の記録は、組織のほかのデータと一緒に消える(`TENANT_TABLES`)
- [ ] 記録は、お客さんの書き出しには入れない(運営が機能を確かめるための記録で、お客さんの業務のデータではない)

他社:

- [ ] ある組織の人の記録は、他社の人からは読めない・書けない(表は RLS。アプリは足すだけ)

## 権限の表に足す行

**どちらの PR も、新しい API は足さない**(権限の表 `docs/authz/matrix.yaml` に足す行は無い)。

- 機能の一覧は、今ある `GET /api/me` の応答に任意の項目 `features` を足す(足すだけ。CI の「API の互換」が見る)。
- 切り替え・記録の集計・古い記録の削除は、運営のコマンド(`node dist/cli.js …`)。お客さんの画面・API からはできない(設計書の未確定事項 U-1)。
- 利用の記録は、各機能のハンドラーの中で関数を呼ぶ(画面から送る API は作らない。設計書の 3)。

## 悪用のされ方(STRIDE で1行ずつ)

| 観点 | どう悪用されうるか | どう防ぐか(テスト / ルール) |
|---|---|---|
| なりすまし | 別の組織の ID をリクエストに入れて、その組織の機能を使う | 組織はセッションからだけ。機能の判定も記録も `c.var.tx`(組織の文脈つき)で読む。結合テストが2社で確かめる |
| 改ざん | お客さんが自分で機能を入れて、まだ出していない機能を使う / 記録を増やして数を水増しする | 切り替えの API は無い(運営のコマンドだけ)。アプリの接続(`app_rw`)は機能フラグの表を**読むだけ**、記録の表は**読む・足すだけ**(移行の GRANT)。記録は1日1人1行なので、何度呼んでも数は増えない |
| 否認 | 「その機能は入れていない」と言われる | 入れた・切ったは組織の監査ログに残る(足すだけ。ADR 0013) |
| 情報漏えい(他社のデータ) | 他社で何の機能が入っているか・誰が使ったかが見える | どちらの表も `tenant_id`+RLS(ADR 0001)。集計のコマンドは数だけを出し、組織と人の ID を出さない。記録の中身は ID と機能の名前と日付だけで、お客さんの入れた値を持たない |
| 妨害(重い処理・大量の要求) | 機能の判定でリクエストごとに重い問い合わせが走る / 記録の表が際限なく大きくなる | 判定は組織ごとの行を1回で読む(主キーの索引)。記録は1日1人1機能1行で上限があり、決まった日数で消す |
| 権限昇格 | 閲覧者が、入っている機能のフラグを見て書き込みの API を呼ぶ | フラグは「出すか」だけで、権限は今までどおり関所(`policy.ts`)が決める。入っていても権限が無ければ 403 |

## やらないこと

- A/B テスト(くじで組を分ける・組ごとの差を比べる)の仕組み。`/bet` に「A/B の型」を足すのは ①② の後(数が足りない PMF の前は、段階的な公開で足りる)。
- 割合での公開(「組織の 10% に出す」)。PMF の前は組織を選んで出す方が、話を聞きに行ける。
- 人ごとのフラグ(組織の中で一部の人だけに出す)。B2B の機能は組織で使うので、組織ごとにする。
- デプロイなしで全部の組織を一度に止める(すぐに止める)仕組み。止めるのは状態を `off` にしてデプロイ(数分)。
- お客さんの管理者が画面で機能を入れる・切る(未確定事項 U-1)。
- 画面の操作(クリック・画面の移動)をブラウザから送って記録すること・外の分析の製品(Google Analytics など)。
- 集計の画面(ダッシュボード)。コマンドで数を出し、賭けの小石に割合で書く。

## 決めたこと

- 順番は 機能フラグ → 利用の記録 → `/bet` の A/B の型(@attumkwg。依頼の時点で決めてあった)。
- フラグも記録も `tenant_id`+RLS(ADR 0001)。利用の記録はログの許可リスト(ADR 0019)と個人情報の分類(ADR 0018)に合わせ、記録しない物も設計書に書く(依頼)。
