# 仕様: 1〜3人・PMF の前の軽い型

> 1つの仕様 = 1つ以上の Issue。大きければ親 Issue → 子 Issue に割ってから AI に渡す。
> 状態: 下書き

## なぜ作るか

1〜3人で PMF の前の会社は、部品69を「迷ったら残す」で抱え、要らない SSO・SCIM・認証の準備・当番・損益まで残る。外すのは1つずつ PR。題材(TODO)を差し替えた実例も無く、月の費用の下限も「向いていない」に書かれていない(外からの点検 09-adoption の 9-1・9-3・穴 G-48)。

## 受け入れ条件

- [ ] `/tailor` を流した人が「1〜3人・PMF の前」と答えると、カタログの一括の型 `light` の部品(後から足せる物だけ)と、部品ごとの足し直す合図が1画面で出て、1問で「まとめて後で足す / 1つずつ選ぶ / 全部残す」を選べる
- [ ] 「まとめて後で足す」を選ぶと、記録 `docs/product/tailoring.md` にその部品が「消す」・理由「軽い型: 後で足す(合図)」で残る
- [ ] 本番にお客さんのデータがまだ無い間は、軽い型の部品を1つの PR にまとめて消せる(部品ごとにコミットと消す移行を分ける)
- [ ] ほかの答え(認証を取る予定など)の「残す」条件は、軽い型より強い
- [ ] 一括の型に、土台・まだ無い部品・足し直す合図の無い部品・残す部品から頼られている部品を入れると `pnpm kit:catalog` が落ちる
- [ ] README の部品の節(`pnpm kit:readme`)に軽い型の部品が並ぶ
- [ ] 題材を差し替える人が `docs/guides/replace-subject.md` を読むと、TODO → 別の題材の順(足す → 緑 → 消す)・ファイルの量と直し方・AI への頼み方が分かる
- [ ] README の「向いていない」に、本番に出したときの月の費用の下限(約8万円)が書いてある

該当なし(アプリの API は変えない)。

## 悪用のされ方(STRIDE で1行ずつ)

| 観点 | どう悪用されうるか | どう防ぐか(テスト / ルール) |
|---|---|---|
| なりすまし | 該当なし | — |
| 改ざん | 一括の型に土台や守りの部品を紛れ込ませ、まとめて消させる | 土台・残す部品から頼られる部品は `pnpm kit:catalog` が落とす(`kit.test.mjs`)。カタログの変更は PR で人が見る |
| 否認 | 何をなぜ外したか分からない | 記録に部品ごとの理由(足し直す合図)を残す |
| 情報漏えい(他社のデータ) | 該当なし | 外すのは後から足せる部品だけ(テナント分離・認証・秘密・バックアップ・監査ログは土台か軽い型の外) |
| 妨害(重い処理・大量の要求) | 該当なし | — |
| 権限昇格 | 該当なし | — |

## やらないこと

- 個人向け(B2C)の軽い型(別の穴)
- 部品を足し直すコマンド(手引き `docs/kit/upgrade.md` の B の形で持ってくる)
- 題材を差し替えた実際のコード(手順の例だけ)
