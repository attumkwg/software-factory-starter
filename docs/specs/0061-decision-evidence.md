# 仕様: 未確定事項の「承認」は、人が GitHub に書いた答えを指す

> 1つの仕様 = 1つ以上の Issue。大きければ親 Issue → 子 Issue に割ってから AI に渡す。
> 状態: 下書き

## なぜ作るか

設計書の未確定事項を「仮決め」から「承認(@名前 日付)」に書き換えるのは、`pnpm decisions` が書き方を見るだけで、人の答えと突き合わせていない。CI を直そうとした AI が、自分で「承認(@suzuki)」と書いて `pnpm decisions --strict` を緑にできる(台本 [10-ai-incidents.md](../scenarios/10-ai-incidents.md) の 10-5・穴 G-61)。人の承認を関所にした仕組みは、AI が「関所を通る形」を作れると意味が無くなる。

## 受け入れ条件

- [ ] PR で、設計書(`docs/designs/*.md`)の未確定事項の行の状態を `承認`・`変更`・`保留`・`導入時に決める` に変えた(か、その状態で新しく足した)とき、状態の文に GitHub のコメント・レビュー・行のコメントへのリンクが無いと、必須のチェック「未確定事項の答えの出どころ」が落ちる
- [ ] リンク先が、書き込める人(OWNER・MEMBER・COLLABORATOR)でない・ボット・状態の `@名前` と違う人・本文に行の番号(`U-1`)が無い、のどれかなら落ちる
- [ ] リンク先が別の PR・Issue なら、本文に設計書の番号(`0061` など)も要る(同じ `U-1` の答えの使い回しを防ぐ)
- [ ] `仮決め` のまま・`取り下げ`・前から入っていて変えていない行は見ない
- [ ] PR の中でスクリプトを緩めても、その PR には効かない(土台のブランチの物で確かめる)。スクリプトと中身(`decisions-lib.mjs`)は危険度「高」
- [ ] 手元の AI が、人のアカウントの `gh` で「U-1 承認」のような答えを GitHub に書こうとすると、Bash のフックが人に聞く(`KIT_EDIT_GUARD=pr` でも)
- [ ] 書き方と流れは `docs/guides/human-review.md` の 2 にある。`/tailor` の写し方も同じ

## 権限の表に足す行

該当なし(アプリの API は変えない)。

## 要配慮個人情報

- 当たらない(設計書の表と、GitHub のコメント・レビューの書き手と本文だけを読む)

## 悪用のされ方(STRIDE で1行ずつ)

| 観点 | どう悪用されうるか | どう防ぐか(テスト / ルール) |
|---|---|---|
| なりすまし | AI が「承認(@人)」と書く・背景の AI がボットでコメントして指す・外の人がコメントして指す | リンク先の書き手が書き込める人で、ボットでなく、`@名前` と同じ人か(`decisions.test.mjs`)。手元の AI が人のアカウントで書くのはフックが聞く(`guard-bash.test.mjs`) |
| 改ざん | PR の中でスクリプトや一覧を緩める・前の版の答えを指し直す | 土台のブランチの中身で確かめる。スクリプトは「高」。別の PR・Issue の答えは設計書の番号が要る |
| 否認 | 誰がいつ答えたか分からない | 答えは人のアカウントのコメント(GitHub に残る)。チェックの出力に書き手とリンクを出す |
| 情報漏えい(他社のデータ) | 該当なし | 読むのは PR とコメントだけ |
| 妨害(重い処理・大量の要求) | 設計書をたくさん変えて API を連打させる | 変えた設計書の答えの行だけ読む・5分で打ち切り・同じ PR の流れは1つ |
| 権限昇格 | ワークフローの権限で書き込む | 権限は読むだけ・鍵を残さない checkout |

## やらないこと

- 人が答えたコメントを、後から書き換えたかの確かめ(GitHub の編集の記録で人が見る)
- 前から入っている「会話で回答」の行を直す(変えた行だけ見る。古い行は書き換えない)
- 手元の AI が、フックを避けてスクリプトから人のアカウントでコメントする道を塞ぐ(手元は人が見ている前提。わざと残る穴)

## 決めたこと

- 想定の場面「AI の事故」(2026-10-27)で見つかった穴 G-61 を、@attumkwg の依頼「AI の事故の穴を順に PR にして」で作る。足す物は gaps.md に @attumkwg が書いた案(「承認」に変わった行は、その人のコメントかレビューへのリンクを必須にし、CI がリンク先の書き手を確かめる)のとおり

> 設計(どう作るか)は [docs/designs/0061-decision-evidence.md](../designs/0061-decision-evidence.md) に書く(AI 用。網羅的に)。
> AI が仮で決めたこと(人の承認待ち)は、設計書の「未確定事項」に書く。ここには書かない。
