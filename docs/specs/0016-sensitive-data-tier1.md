> 状態: 承認済み(段1を作ることは @attumkwg が 2026-10-25 に選んだ。中身は ADR 0018 の段1の表のとおり)
> 取り組み: セキュリティ(賭けには結びつかない。要配慮を扱う機能が来る前の土台)
> 設計: [docs/designs/0016-sensitive-data-tier1.md](../designs/0016-sensitive-data-tier1.md)・ADR: [0018](../adr/0018-sensitive-data-isolation.md)(段の分け方)・[0029](../adr/0029-sensitive-data-tier1.md)(段1の作り)

## なぜ作るか

キットは、要配慮個人情報(病歴・障害・信条・犯罪の経歴など。個人情報保護法 2条3項)を、分けて置く場所ができるまで1列も足せないようにしてある(ADR 0018 の段0)。医療・介護・人事・採用など、要配慮を扱うプロダクトをこのキットで作り始めると、最初の機能の前に「分けて置く場所」が要る。
その場所(段1)を先に作っておき、要配慮を扱う機能は**決まった1つの入口から、暗号化した値だけを書く**形でしか作れないようにする。要配慮は漏れたら1件でも委員会への報告と本人への通知が要るので、ふつうのデータより守りを一段厚くする。

## 受け入れ条件

### 置き場所と接続

- [ ] DB に、要配慮だけを置くスキーマ `sensitive` がある。アプリのふつうの接続(`app`・ロール `app_rw`)は、そのスキーマに入れない(何を読もうとしても断られる)
- [ ] 要配慮だけの接続(ロール `app_sensitive`)は、ふつうの表(組織・利用者・タスクなど)を読めない。`app_rw`・`app_auth` に入っていない・superuser でも RLS のすり抜けでもない
- [ ] `sensitive` の表も、ほかの表と同じく RLS がかかる(テナントの文脈が無ければ1行も見えない・他社の行は見えない)
- [ ] アプリの接続と要配慮の接続に同じ物を設定すると、API は起動しない

### 暗号化

- [ ] 要配慮の値は、組織ごとのデータ鍵で暗号化してから DB に書く。DB には暗号文だけが入る(元の値の一部も入らない)
- [ ] データ鍵は組織ごとに1本。DB には KMS の鍵で包んだ物だけを置き、中身の鍵は置かない
- [ ] ある組織の暗号文を、別の組織・別の列・別の行に写しても開けない。書き換えた暗号文も開けない
- [ ] 解約のコマンドで組織を消すと、その組織のデータ鍵も消え、残った暗号文(写し)はもう開けない
- [ ] stg・prod では KMS の鍵が無いと起動しない。手元・テスト・プレビューは KMS 無しで動く(コードに書いた包み鍵)

### 入口を1つにする

- [ ] 要配慮のスキーマ・鍵・接続の設定に触れるのは `apps/api/src/sensitive/` の中だけ。外から触ると CI(Semgrep)が落ちる
- [ ] 分類表で `sensitive` にした列は、スキーマ `sensitive` の表にしか置けない。型は文字列(暗号文)だけ(単体テストが落ちる)
- [ ] 社員の代理ログインの最中は、要配慮の値を読み書きできない(403)

### 見張りとインフラ

- [ ] Terraform に、要配慮だけの KMS の鍵と、要配慮だけの接続の秘密がある(使わない間は作らない設定が既定)
- [ ] KMS の鍵を使えるのは API のタスクだけ。移行・運営のコマンドの役割では使えない
- [ ] CloudTrail のロググループがあれば、API のタスク以外が鍵を使った・鍵を消す予約や止める操作があった・開いた数が多すぎる、で知らせが鳴る

### 文書

- [ ] 要配慮のデータはログにも AI にも渡さない、が障害対応の手順書・CLAUDE.md・漏えいの手順書に書いてある
- [ ] `/new-feature`・`/bet` で「要配慮に当たるか」を聞く。`db-migration` に `sensitive` は人の確認が必須と書いてある
- [ ] 段2(別のクラスター)・段3(別の AWS アカウント)の上げ方の手順と「いつ上げるか」の目安が手順書にある

## 権限の表に足す行

なし(API を足さない。要配慮を扱う機能が来たら、その仕様で足す)。

## 悪用のされ方(STRIDE で1行ずつ)

| 観点 | どう悪用されうるか | どう防ぐか(テスト / ルール) |
|---|---|---|
| なりすまし | 別の組織の文脈で要配慮を開く | テナントはセッションからだけ(T-1)。データ鍵と暗号文に組織の ID を結びつける(KMS の文脈・AES-GCM の追加の認証データ)。結合テスト「他社の組織では、写した暗号文を開けない」 |
| 改ざん | DB の暗号文を別の行のものと入れ替える・書き換える | 暗号文に行の ID と列を結びつける。単体テスト「別の組織・別の列・別の行へ写した暗号文は開けない」「書き換えた暗号文は開けない」 |
| 否認 | 誰が要配慮の鍵を開いたか分からない | KMS の呼び出しは CloudTrail に残る(組織の ID の文脈つき)。API のタスク以外の利用で鳴る |
| 情報漏えい(他社のデータ) | ふつうの接続のバグ・SQL の書き間違いで要配慮を読む・ログや Sentry や AI に出る | 接続ユーザーを分ける(結合テスト)・DB には暗号文だけ・入口を1つに(Semgrep)・ログの許可リスト(分類表の名前は伏せる)・バックアップとスナップショットには暗号文だけ |
| 妨害(重い処理・大量の要求) | KMS の上限まで呼ばせる・KMS の障害で全体が止まる | データ鍵を5分メモリに置く。KMS を待つのは2秒まで・トランザクションの外。要配慮を使わない API は KMS に関係なく動く |
| 権限昇格 | 社員の代理ログインで要配慮を見る・運営のコマンドで鍵を使う | 代理ログインの最中は 403(結合テスト)。移行・運営のコマンドの役割は鍵を使えない(鍵のポリシー) |

## やらないこと

- 要配慮の列そのもの(病歴の欄など)を足すこと。キットに要配慮を扱う機能は無い。最初の機能の仕様で、表と API と同意(個人情報保護法 20条2項)を決める
- 段2(別のクラスター)・段3(別の AWS アカウント)の実装。手順書と目安だけ
- 組織ごとの KMS の鍵(T-5。バックアップの中まで暗号で消す)。表の形は備えてある(`kms_key_id`)
- 要配慮の値の検索・並べ替え(要るならハッシュの列を足す。機能の設計書で)
- 要配慮の値を読んだことの監査ログ(書き込みは関所が記録する。読んだ記録が要るかは、機能の仕様で決める)
