# 仕様: 未確定事項の「導入時に決める」(キットの既定値でマージし、使う側の決めることリストに載せる)

> 状態: 下書き
> 設計: [docs/designs/0013-decisions-at-adoption.md](../designs/0013-decisions-at-adoption.md)

## なぜ作るか

設計書の未確定事項は、いま「仮決め」(人がまだ答えていない)と「承認」(人がこのままでよいと答えた)で追っている。仮決めが残る PR は `pnpm decisions --strict`(CI の必須の検査)で落ちる。

ところが、**プロダクトごとに答えが違う問い**がある。たとえば利用規約の設計書(`docs/designs/0009-legal-consent.md`)の U-1〜U-6(同意し直しの基準・周知の日数・誰に同意を求めるか など)は、使う人の事業・契約・法務の確認で答えが変わる。キットの持ち主が「キットの既定はこれでよい」と承認しても、それは**使う人のプロダクトの答えではない**。

いまはこれを「承認」にするしかなく、キットを使い始めた人には「ここはあなたが決める所」と分からない。決めないまま本番に出てしまう。

そこで、キットでは既定値のままマージできて、**使い始めた人の「決めることリスト」に必ず載り、本番に出す前に決まっていなければ止まる**状態を足す。

## 誰が使うか

| 人 | この仕組みでしてほしいこと |
|---|---|
| キットの持ち主 | プロダクトごとに答えが違う問いを「導入時に決める」にして、既定値でマージする |
| キットを使い始めた人 | 「導入時に決める」の一覧を見て、1つずつ「既定のままでよい」か「変える」かを決める |
| AI(Claude Code) | 一覧を出す・`/tailor` で1問ずつ聞く・答えを状態に写す・公開の前に未決を止める |

## 受け入れ条件

### 状態が足される

- [ ] 設計書の未確定事項の状態に `導入時に決める` が使える(`導入時に決める(キットの既定は @名前 YYYY-MM-DD に承認)` の形)
- [ ] `pnpm decisions --strict` は、`導入時に決める` が残っていても落ちない(キットでマージできる)
- [ ] `pnpm decisions`(一覧)に、`導入時に決める` の件数と行が出る
- [ ] `導入時に決める` の行も、種類は4つ(事業判断・利用者の挙動・他チームとの契約や制約・戻せないリスク)のどれかでないと「書き方の問題」になる

### 使う人の決めることリストに載る

- [ ] 使う人が `pnpm decisions --adopt` と打つと、`導入時に決める` の行だけが、設計書ごとに「キットの既定(設計した事実)・問い・どこにあるか」の形で出る。決め方(承認 / 変更)の書き方も出る
- [ ] `/tailor` のチェックシートに「キットが既定で決めた所」が入り、1つずつ(設計書ごとにまとめて)「既定のままでよいか」を聞く
- [ ] README の「使い始めたらやること」に、この一覧を見て決める段がある(カタログから生成)
- [ ] 点検の台帳(`docs/checkup/todo.yaml`)の立ち上げの段に、「公開の前に、導入時に決める が残っていないか」の項目が1件ある

### 使う側で決めたら正式にする

- [ ] 使う人が「既定のままでよい」と答えたら、状態を `承認(@名前 YYYY-MM-DD)` に変える(人の答えなしに変えない)
- [ ] 「変える」と答えたら `変更(@名前 YYYY-MM-DD: どう変えるか)` にして、`/rework` で設計書から作り直す
- [ ] 承認・変更にした行は `--adopt` の一覧から消える

### 本番の公開の前に止める

- [ ] `pnpm decisions --launch` は、`仮決め`・`導入時に決める`・書き方の問題(期限の過ぎた保留を含む)が1件でも残っていれば 1 で終わり、何が残っているかを出す
- [ ] 残っていなければ 0 で終わる
- [ ] `--launch` をどこで流すか(本番のデプロイのワークフロー・公開前の点検)は、人が決める(CI は危険度「高」)

## 悪用のされ方(STRIDE で1行ずつ)

| 観点 | どう悪用されうるか | どう防ぐか(テスト / ルール) |
|---|---|---|
| なりすまし | AI が人の答えなしに `承認` に書き換える | 書き方は今までどおり「人の答えを AI が写す」。`/tailor` は答えをもらってから書く(スキルの決まり) |
| 改ざん | 仮決めを `導入時に決める` に書き換えて、`--strict` をすり抜ける | `導入時に決める` は PR の差分に出る。設計書の決まりで「キットの既定は承認済み」を括弧に書く。`--launch` では止まる |

## やらないこと

- 既存の設計書の状態を、この PR で `導入時に決める` に変えること(候補を出し、持ち主に一つずつ確かめてから別にする)
- `--launch` を本番のデプロイのワークフローに入れること(CI = 危険度「高」。人が決める)
- 使う人の答えを自動で `承認` にすること

## 決めたこと

- 「導入時に決める」状態・`--adopt`・`/tailor` と README への載せ方・使う側で `承認` にする流れ・`--launch` は、キットの持ち主と決めた方針(2026-10-21〜22 の会話。依頼の本文)。
