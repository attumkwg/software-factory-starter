## 第1部 PdM が書く所(業務の要求・業務ルール)

### なぜ作るか

- ペルソナ: キットを使ってプロダクトを作る人(持ち主・PdM・代表)
- 動かす KPI: (キットの物差し: 無人化率・依頼から届くまでの日数。守り: 事故 0件・センサーが正しいかの判定が回っていること)
- 週100〜200本の PR を流すと、必須のチェックが `strict`(最新の main に追いついてから)なので1本ずつ追いつき直しが要り、1日に入る本数に上限がある。マージキューの手順(G-15)は「キューの中で流れないチェックを必須から外す」で、入れる日に守りが弱くなる。
- AI のマージは全部の PR で持ち主の返事を待つ(ADR 0082・0085・0086)。センサー(テスト・型・検査・E2E)が緑で、人が決めることが何も無い PR でも、人を呼ぶ。週200本なら200回。
- 背景の AI が同時に開いてよい PR は5本(G-62)。人が答えなくてよい PR まで数えるので、流量の天井になる。

### 業務の要求

- マージキューを入れるか・どう入れるかが、設定の正(`.github/setup.yml`)に1か所で書けて、`pnpm setup:github --apply` で入る(入れるのは人)
- キューを入れても、必須のチェックを1つも外さずに済む(守りを弱めない)
- 人が決めることが無い PR は、センサーが緑なら人を呼ばずに入れられる(使う人が選ぶ。既定はオフ)
- 背景の AI の PR の上限が、人を待つ本数を数える(人の手に合わせる)。全体の本数にも天井がある(CI と費用)

### 業務ルール

- マージキューの正は `setup.yml` の `ruleset.merge_queue`(既定 `enabled: false`)。入れるなら `strict: false` — キューが最新の main に重ねて確かめるので、追いつき直しが残ると流量が上がらない
- 必須のチェックは全部、キューの中(`merge_group`)でも流れる。キューの中で飛ばされるジョブも許さない — 飛ばされたジョブは「成功」になり、確かめずに入る
- PR の本文・承認・未確定事項の答えを見るチェックは、キューの中ではキューの枝の名前から PR を引いて読み直す — キューに並べた後に本文や承認を書き換えても、入る前にもう一度見る
- センサーだけで入れるのは、守る場所にも「高」の領域にも触らず、印(needs-human・risk:high・tests:weakened)も「🧑‍⚖️」の問いも無く、本文の危険度が「高」でない PR だけ — 人が決めることの一覧([../concepts/human-decisions.md](../concepts/human-decisions.md))の「強制」の行に1つも当たらない PR
- センサーだけで入れるのは、持ち主が環境に `KIT_AI_MERGE=slack` を入れ(ADR 0086)、かつ `setup.yml` の `ai_merge.sensors_only: true` にした所だけ — どちらも AI が自分で入れられない(前者はフック、後者は守る場所なので持ち主の答えが要る)
- 背景の AI の上限は2つ。人を待つ本数(`AI_OPEN_PR_LIMIT`・既定 5)と、全部の本数(`AI_OPEN_PR_TOTAL_LIMIT`・既定 20)
- 数の根拠は【実測】と【推定】を分けて書く

### 受け入れ条件(業務の言葉で)

- [x] `setup.yml` に `ruleset.merge_queue` があり、`pnpm setup:github` が `enabled: true` ならキューの規則を足し、`false` なら外し、書いていなければ画面で足した物を残す。`enabled: true` で `strict: true` なら `pnpm setup:check` が落ちる
- [x] 必須のチェックのワークフローに `merge_group` が無い・キューの中で `if` に飛ばされると、`pnpm setup:check`(CI)が落ちる。今の必須のチェック 16件は全部キューでも流れる
- [x] 「取り組みと作業の種類」「危険度「高」の承認の人数」「未確定事項の答えの出どころ」が、キューの中でキューの枝の名前から PR を引いて確かめ直す。「API の互換」はキューの土台と比べる
- [x] `pnpm pr:merge-when-green <番号> --sensors` が、人を呼ぶ理由が無く必須のチェックが全部緑の PR だけを、記録を残して入れる。理由があれば止めて理由を出す。緑になった後にもう一度見る。main にキューがあれば、マージせずにキューに並べる
- [x] 背景の AI は、人を待つ PR が上限(5)か、全部の PR が上限(20)に達していると動かない。センサーだけで入れる所では、印か問いのある PR だけを人を待つ本数に数える
- [x] AI が GraphQL でキューに並べる・自動マージを付けるコマンドを直接打つと、フックが止める
- [x] 手順書(`docs/runbooks/move-to-org.md` の 3)と手引き(`docs/guides/throughput.md`)に、入れ方・数の根拠(【実測】【推定】)・見る数がある

### 要配慮個人情報

- 当たらない(PR の番号・印・ファイルの道・チェックの名前と結果だけ)。

### やらないこと

- GitHub の設定そのものを変える(`setup.yml` の正と手順まで。`--apply` は人)
- キット自身にマージキューを入れる(個人のリポジトリなので使えない。仕様 0051 のとおりキット自身は移さない)
- キット自身でセンサーだけのマージをオンにする(使う人が選ぶ。既定はオフ)
- 人が増えた後(承認数 1 以上)のセンサーだけのマージ(今のまま AI はマージしない。G-133)
- AI の PR の上限を、リポジトリの変数や `setup.yml` に移す(今の置き場 `claude.yml` の env のまま)

### 決めたこと

- (AI が決めた)入れ方はキットの既定を両方オフ(`merge_queue.enabled: false`・`ai_merge.sensors_only: false`)にして、使う人が選ぶ。ADR 0086(AI のマージは使う人が選ぶ)と同じ考え
- (AI が決めた)キューで流れないチェックを必須から外す手順(仕様 0051)をやめ、全部のチェックをキューでも流す。外すと、キューに並べた後の本文・承認の書き換えを見なくなる
- (AI が決めた)全体の天井は 20 本。根拠は設計書 0091 の 6(【推定】)

## 第2部 AI が網羅して書き、エンジニアが見る所(システムの振る舞い)

### 状態 × 操作

| 状態 \ 操作 | `--reply`(今まで) | `--sensors` |
|---|---|---|
| `KIT_AI_MERGE` が無い | 止める | 止める |
| 承認数 1 以上 | 止める | 止める |
| `sensors_only: false` | 動く | 止める(返事を待つ) |
| 人を呼ぶ理由がある | 理由を記録してマージ | 止めて理由を出す |
| 必須のチェックが落ちた・45分で終わらない | 止める | 止める |
| 緑になった後に印・問いが付いた | 記録に書いてマージ | 止める |
| main にキューがある | キューに並べる | キューに並べる |
| 待つ間に push があった | GitHub が断る | GitHub が断る |

### 境界値

- 人を待つ本数: 上限と同じ数で止める(`>=`)。全体も同じ
- 上限の値: 数でない・0 以下は既定(5・20)
- キューの枝の名前: `gh-readonly-queue/<土台>/pr-<番号>-<版(7〜40 の16進)>` だけを読む。読めなければチェックを落とす(黙って通さない)
- マージキューの数: 同時に確かめる数・まとめる数 1〜100、待つ分 0〜360、チェックの待ち 1〜360。まとめる最小 ≦ 最大

### 権限の組み合わせ

- `pr-work.yml`: `pull-requests: read` を足した(キューの中で本文を読む)。書く権限は無い
- `high-risk-approvals.yml`・`decision-evidence.yml`: 権限は変えない。キューの中では土台(`merge_group.base_sha`)のスクリプトを使う
- `pr-merge-when-green.mjs`: 持ち主の手元かクラウドの `gh`(人のアカウント)。GraphQL の `enqueuePullRequest` を呼ぶのはこのスクリプトだけ

### 悪用のされ方(STRIDE で1行ずつ)

| 観点 | どう悪用されうるか | どう防ぐか(テスト / ルール) |
|---|---|---|
| なりすまし | 人のアカウントで claude に似た名前を付けて、数を減らす | 数えるのはボットで名前が claude で始まる物だけ(`ai-open-prs.test.mjs`。今まで) |
| 改ざん | AI が `sensors_only: true` を書いた PR を自分で入れる | `setup.yml` は守る場所。触る PR は人を呼ぶ理由になり、`--sensors` では入らない(`pr-merge.test.mjs`) |
| 改ざん | キューに並べた後に PR の本文の問いを消す・承認を外す | キューの中で PR を引いて読み直す(`queue-pr.test.mjs`・ワークフロー) |
| 改ざん | 必須のチェックを `if: pull_request` にして、キューで飛ばす | `pnpm setup:check` が落とす(`check.test.mjs`) |
| 否認 | 誰の判断で入ったか分からない | PR に「センサーだけでマージ」の記録(当てた版・数・理由が無かったこと)・コミットの本文 |
| 情報漏えい | 該当なし | — |
| 妨害 | 背景の AI に頼み続けて CI と費用を跳ねさせる | 全体の天井 20 本・モデルの会社の月の上限(今まで) |
| 権限昇格 | AI が GraphQL で直接キューに並べる | フックが止める(`guard-bash.test.mjs`) |
