# 仕様: 使い始める前の一括のセットアップ(pnpm setup:github)とラベルの一覧

> 状態: 下書き
> 設計: [docs/designs/0014-setup-before-use.md](../designs/0014-setup-before-use.md)・ADR: [0027](../adr/0027-setup-before-use-and-kit-role.md)

## なぜ作るか

- キットに部品を足すたびに、PR に「マージの後に人がやる設定」(ラベルを作る・必須のチェックに足す・最初の `/checkup-refresh` を流す)が溜まり、GitHub の画面で手で直していた。ラベルが無くて `gh issue create --label` が落ちたり、ラベルで動くはずのワークフローが動かなかったりした。
- ひな形のリポジトリ(このキット)自身でも、毎週の点検の Issue や定期の脆弱性チェックが回っていた。キットは「作る物」であって「運用する物」ではない。運用は、使う人がキットから自分のリポジトリを作ったときに始めたい。
- 持ち主の言葉(2026-10-24):「ラベルは必要なものを作ってくれませんか?常にそうしたいです」「今これひな形なので、その運用を回すみたいなのはちょっとやりたくあんまないんじゃないですか」「なんか一括で実施前にやるみたいな、こうやって作成していく前にやるみたいな仕組みにできませんかね」

## 受け入れ条件

### 一括のセットアップ

- [ ] 持ち主が `pnpm setup:github` を打つと、GitHub の今の設定と、あるべき設定(`.github/setup.yml`・`.github/labels.yml`)の**差分だけ**が出る。何も書き換えない(試し)
- [ ] 持ち主が `pnpm setup:github --apply` を打つと、差分が反映される。もう一度打つと差分は 0件(何度流しても同じ結果)
- [ ] 反映するのは: ラベル・リポジトリの設定(マージの方法・自動マージ・ブランチの自動削除)・main のルールセット(PR 必須・必須のチェック・最新に追いついてから・直線の履歴・消せない・強制 push できない)・Environments(main だけから使える・prod の承認する人)・Actions の設定(既定は読むだけ・Actions が PR を承認できない・外の人の PR は毎回承認・成果物は7日・SHA で固定した Action だけ)・秘密の見つけ(公開のとき)・Dependabot の通知・非公開の脆弱性の報告・リポジトリの変数 `KIT_ROLE`
- [ ] 秘密(鍵・パスワード)の**値は入れない**。足りない秘密の**名前だけ**を「人がやること」に出す
- [ ] 一覧に無いラベル(GitHub の既定の `bug` など)は**消さない**。「一覧に無い」と出すだけ
- [ ] `gh` が無い・ログインしていない・権限が無い所は、その所だけ「読めなかった」と出し、ほかは続ける。`--apply` で1つ失敗しても、ほかは続け、最後に失敗の件数を出して 1 で終わる
- [ ] 最後に「人がやること」(Renovate の App・秘密の値・`/kickoff`・`/tailor`・`pnpm decisions --adopt`・台帳を自分の物にする・最初の `/checkup-refresh`)を、済んでいない物だけ出す

### ひな形と使う側の見分け

- [ ] `.github/setup.yml` の `template_repository` と同じ名前のリポジトリでは、`--apply` が変数 `KIT_ROLE` を `template` にする。それ以外(キットから作ったリポジトリ)では `product` にする
- [ ] 定期で動くワークフロー(点検の知らせ・定期の脆弱性チェック・ファズ)は、`KIT_ROLE` が `product` のときだけ定期で動く。ひな形では、定期の実行は飛ばされ(落ちない)、手で流すことはできる
- [ ] AWS を使う定期の物(戻す訓練・Cognito の契約テスト・ZAP・プレビューの掃除)は、今までどおり AWS の変数が無ければ飛ぶ(ひな形には AWS の変数を置かない)

### ラベルは「必要な物は必ずある」

- [ ] ラベルの一覧は `.github/labels.yml` の1か所(名前・色・説明・何が使うか)
- [ ] ワークフロー・Issue のテンプレート・`labeler.yml`・`renovate.json`・スクリプト・スキルが使うラベルが一覧に無ければ、CI(`pnpm setup:check`)が落ちる
- [ ] 必須のチェックの名前が、PR で動くジョブの名前に無ければ(ジョブの名前を変えた・消した)、CI が落ちる(必須のチェックが来ないまま、全部の PR が止まるのを防ぐ)
- [ ] ワークフローが使う Environment が `.github/setup.yml` に無ければ、CI が落ちる
- [ ] 定期で動くワークフロー(`schedule:` がある)のジョブに `KIT_ROLE` の見分けが無ければ、CI が落ちる(ひな形で運用が回り出すのを防ぐ)

### ラベルの説明は1か所

- [ ] `.github/labels.yml` に、ラベルごとに **何のラベルか・誰が付けるか(自動 / AI / 人)・いつ付く・付いたら何をするか** がある。GitHub の説明欄(100文字まで)には短い版
- [ ] 人が読む手引き `docs/guides/labels.md` が一覧から作られ(`pnpm setup:labels`)、古ければ CI が落ちる。README・getting-started・playbook・手順書・セットアップの出力からそこへ案内する

### キットの運用と最新化(持ち主の方針。2026-10-24)

- [ ] ひな形では、点検の台帳の運用の項目(見直す日・世の中の変化の取り込みの時期)を確かめても落ちない(注記だけ)
- [ ] 使う人が `pnpm setup:github` を流すと、キットの古くなった所(作った後のキットの更新・取り込みの古さ・見直す日の来た項目・溜まった依存の更新)が「人がやること」に出る

### 台帳を自分の物にする

- [ ] 使う人が `pnpm checkup:adopt --by @自分` を打つと、点検の台帳(`docs/checkup/todo.yaml`)の使い始めた日が今日に、担当者と相談先が自分になり、全部の項目が「まだ」に戻る(引退した項目はそのまま)。キットの持ち主の記録は消さず(記録は足すだけ)、「ここから使い始めた」の1行を足す。コメントと並びは崩さない
- [ ] `pnpm setup:github` は、使う側のリポジトリで台帳の担当者がまだキットの持ち主のときに、これを「人がやること」に出す

## 悪用のされ方(STRIDE で1行ずつ)

| 観点 | どう悪用されうるか | どう防ぐか(テスト / ルール) |
|---|---|---|
| なりすまし | 必須のチェックと同じ名前の状態を、ほかの App が付けて通す | 必須のチェックは GitHub Actions(App の番号 15368)からの物だけにする |
| 改ざん | AI が `.github/setup.yml` の必須のチェックを減らす・承認を外し、`--apply` で守りを弱める | `.github/**`・`scripts/setup/**` は危険度「高」(人の確認・CODEOWNERS)。`--apply` は人が打つ。試しで差分を見せてから |
| 否認 | 誰が設定を変えたか分からない | GitHub の監査ログ(Settings → Logs)に残る。設定の正はリポジトリのファイルで、変えるには PR が要る |
| 情報漏えい | 差分の表示やログに秘密が出る | 秘密は名前だけ読む(値は API でも読めない)。値は入れない |
| 妨害 | 必須のチェックに無い名前を入れて、全部の PR を止める | `pnpm setup:check` がジョブの名前と突き合わせる |
| 権限昇格 | Actions が自分の PR を承認する・PR のブランチから本番の Environment を使う | Actions の承認をオフ・Environments は main だけ(反映し、点検の `gh-envs` が毎週確かめる) |

## やらないこと

- AWS・Slack・Sentry の設定(Terraform と手順書のまま)。秘密の値を入れること
- 一覧に無いラベルを消すこと(Issue から外れてしまう。消すなら人が画面で)
- ひな形の印(GitHub の「Template repository」)を付けること(公開の判断は持ち主。README の注意のとおり)
- 定期で回すこと(セットアップは人が打つ。点検の `w-protection` が毎週、外れていないかを見る)
- 組織(Organization)の設定・チームの作成
