# 仕様: アカウントの安全(二段階認証の設定・メールアドレスとパスワードの変更・組織の二段階認証の必須化)

> 状態: 下書き(AI が書いた。人の承認待ち。仮に決めた所は設計書の「未確定事項」)

## なぜ作るか

ログイン・登録・再設定・二段階認証のコード入力までは自前の画面になった(ADR 0009)が、**利用者が自分で二段階認証を有効にする道が無い**(いまは契約テストの中で API を直接呼ぶしかない)。メールアドレスとパスワードも、ログインした後に自分で変えられない。組織の管理者は「うちの組織は全員に二段階認証を」と決めたいが、決める場所が無い。

同時に、これらの操作は**乗っ取りを固める道**にもなる(盗んだ Cookie でメールアドレスを変える・二段階認証を外す)。だから、変える前にパスワード(と二段階認証のコード)を確かめ直し、変えたことを本人に知らせ、監査ログに残す。

## 受け入れ条件

> 「誰が・何をすると・どうなる」。ここがそのままテストになる(どのテストかは設計書の「7. 要求との対応」)。

二段階認証(TOTP)を自分で有効・無効にする(admin・member・viewer の全員):

- [ ] 画面「アカウント」で「二段階認証を設定する」を押し、パスワードを入れ直すと、**QR コードと、手で入れる鍵**(4文字ずつ区切った英数字)が出る
- [ ] 認証アプリが出す6桁のコードを入れると、二段階認証が**有効**になる。次のログインから、パスワードの後にコードを聞かれる
- [ ] コードが違えば有効にならない(「コードが違います」)。鍵は、やり直すまで同じ物を使える
- [ ] 有効な人は「二段階認証を外す」で、パスワードと**いまのコード**を入れると無効になる。組織が必須にしていれば外せない(ボタンが出ない・API は 403)
- [ ] 有効にした・外したが、本人の組織の監査ログに残る

メールアドレスの変更(全員):

- [ ] 画面「アカウント」で、パスワード(有効ならコードも)を入れ直し、新しいメールアドレスを入れると、**新しいアドレスに確認コード**が届く
- [ ] 確認コードを入れると変わる。次のログインから新しいアドレスで入る。**確認するまでは古いアドレスのまま**(古いアドレスでログインできる)
- [ ] 変わったら、**古いアドレスに「メールアドレスが変わりました」**のお知らせが届く
- [ ] 新しいアドレスがもう使われていても、「使われています」とは言わない(確認コードを入れた後に「このアドレスには変えられません」とだけ言う)
- [ ] 申し込んだ・変えたが監査ログに残る

パスワードの変更(全員):

- [ ] 画面「アカウント」で、いまのパスワード(有効ならコードも)と新しいパスワードを入れると変わる。新しいパスワードの決まりは登録と同じ(`cognito-settings.json`)
- [ ] いまのパスワードが違えば変わらない(「パスワードが正しくありません」)
- [ ] 変わったら、本人のアドレスに「パスワードが変わりました」のお知らせが届く。監査ログに残る

変えた後の他の端末(パスワード・メールアドレス・二段階認証のどれを変えても):

- [ ] 変えた画面はログインしたまま。**ほかの端末・ブラウザのログインは切れる**(次の操作でログイン画面へ)

組織の二段階認証の必須化:

- [ ] 組織の管理者は、画面「設定」の「二段階認証」で「この組織では全員に必須にする」を入れる・切る。入れるときは「まだ設定していない人が N 人います」と確かめてから
- [ ] 必須を入れられるのは、**その管理者自身が二段階認証を有効にしているときだけ**(自分が締め出されないように)
- [ ] 必須の組織で、まだ設定していない人は、ログインした後(すでにログインしている人は次の操作で)**どの画面を開いても「二段階認証の設定」へ回される**。設定するまで、ほかの API は 403(`mfa_setup_required`)
- [ ] 入れた・切ったが監査ログに残る
- [ ] メンバー・閲覧者は必須の設定を見る・変えることができない(403)

サポートの代理ログイン中(docs/specs/0004-support-access.md):

- [ ] 代理の社員は、見ている組織の必須の設定も、**自分のアカウントの設定も**変えられない(403。画面は「代理ログイン中は変えられません」)
- [ ] 必須の組織には、二段階認証を有効にしている社員しか入れない(403)

他社・未ログイン:

- [ ] 他社の人は、別の組織の必須の設定を見る・変えることができない(テナントはセッションからだけ決まるので、自社の物しか触れない)
- [ ] 未ログインは全部 401

開発用ログイン(`AUTH_MODE=dev`)のとき:

- [ ] アカウントの API は無い(404)。画面「アカウント」は「開発用ログインでは使えません」とだけ出す。組織の必須の設定は保存できるが、誰も設定へ回されない

## 権限の表に足す行

| API | admin | member | viewer | 他社 | 未ログイン | 代理の社員 |
|---|---|---|---|---|---|---|
| `GET /api/account` | 200 | 200 | 200 | —(自分の物だけ) | 401 | 403 |
| `POST /api/account/reauth` | 200(違えば 400) | 200(違えば 400) | 200(違えば 400) | — | 401 | 403 |
| `POST /api/account/password` | 204 | 204 | 204 | — | 401 | 403 |
| `POST /api/account/email` | 202 | 202 | 202 | — | 401 | 403 |
| `POST /api/account/email/confirm` | 204 | 204 | 204 | — | 401 | 403 |
| `POST /api/account/mfa/setup` | 200 | 200 | 200 | — | 401 | 403 |
| `POST /api/account/mfa/enable` | 204 | 204 | 204 | — | 401 | 403 |
| `POST /api/account/mfa/disable` | 204 | 204 | 204 | — | 401 | 403 |
| `GET /api/organization/mfa-requirement` | 200 | 403 | 403 | —(自社の物だけ) | 401 | 403 |
| `POST /api/organization/mfa-requirement`(必須にする) | 204(自分が未設定なら 409) | 403 | 403 | —(自社の物だけ) | 401 | 403 |
| `DELETE /api/organization/mfa-requirement`(必須を切る) | 204 | 403 | 403 | —(自社の物だけ) | 401 | 403 |

- `/api/account/*` は Cognito のときだけある(`only_in: cognito`)。流れは結合テストで確かめる。
- 「他社」が「—」なのは、パスに相手の ID が無く、どの組織かはセッションだけで決まるため(他社の物を指す道が無い)。

## 悪用のされ方(STRIDE で1行ずつ)

| 観点 | どう悪用されうるか | どう防ぐか(テスト / ルール) |
|---|---|---|
| なりすまし | **盗んだ Cookie で、メールアドレスを自分の物に変えて乗っ取りを固める**(その後パスワードの再設定で完全に奪う) | 変える前にパスワード(と二段階認証のコード)を確かめ直す。確認コードは新しいアドレスへ・変わったら古いアドレスへ知らせる。確認するまで古いアドレスのまま |
| なりすまし | 盗んだ Cookie で、**二段階認証を外す**(または自分の認証アプリで有効にして本人を締め出す) | 外すにはパスワード+いまのコード。有効にするにもパスワード。どちらも本人に知らせる・監査ログ |
| なりすまし | パスワードの確かめ直しを**総当たり**する | Cognito の続けて間違えたときの一時停止(ログインと同じ)・WAF の流量の上限・失敗はログ(警告)に残す。確かめ直しの札は10分・1回の変更で使い切り |
| なりすまし | 認証アプリを無くした人を装って、**回復を頼む**(サポートをだます) | アプリの中に回復の道を作らない(予備のコードは Cognito に無い)。運営が手順書で、その組織の別の管理者に本人かを確かめてから外す(未確定事項) |
| 改ざん | 別の人のアカウントを変える | 対象は常にセッションの本人だけ(パスに人の ID を取らない)。Cognito はアクセストークンの本人しか変えない |
| 否認 | 「自分は変えていない」と言う | 監査ログ(誰が・いつ・何を)と、本人へのお知らせのメール |
| 情報漏えい | 新しいメールアドレスが**誰かに使われているか**を探る | 申し込みの時点では同じ答え。使われていると分かるのは、そのアドレスの持ち主(確認コードを受け取った人)だけ |
| 情報漏えい | 二段階認証の鍵が漏れる(ログ・外部の QR サービス・画面の覚え) | 鍵はログに出さない(結合テスト)。QR はブラウザの中で描く(外のサービスに送らない)。応答は `no-store` |
| 情報漏えい(他社のデータ) | 他社の組織の必須の設定を見る・変える | 組織はセッションからだけ。他社の物を指すパスが無い |
| 妨害 | 必須を入れて、**全員を締め出す** | 入れられるのは自分が有効にしている管理者だけ。締め出されても、設定の画面とログアウトは使える(設定すれば戻れる) |
| 妨害 | 確認コードのメールを他人のアドレスに大量に送る | 確かめ直しが要る・Cognito の送信の上限・申し込みは監査ログに残る |
| 権限昇格 | 代理の社員が、お客さんの設定や自分の設定を変える | 代理の最中は `/api/account/*` と必須の設定を 403(関所で止める) |
| 権限昇格 | 必須の組織で、設定せずにほかの API を叩く | 関所が毎回「必須の組織か・本人が有効か」を見て 403(画面で隠すだけにしない) |

## やらないこと

- **予備のコード(リカバリーコード)・SMS・メールでの二段階認証・パスキー**(Cognito の Lite では使えない・ADR 0009)
- **管理者が他の人の二段階認証を外す画面**(Cognito の管理の API と IAM の権限が要る。回復は運営の手順書)
- **ロールごとの必須**(「管理者だけ必須」など)。組織の必須は全員に効く1つだけ(未確定事項)
- **ログインしている端末の一覧と、端末ごとのログアウト**(サーバー側のセッション保存が要る。今回は「変えたら他を全部切る」だけ)
- 管理者が他の人のメールアドレスを変える

## 決めたこと

- 仕様の段階で人が決めたことは、まだ無い(本人が席を外していたので、AI が設計書の「未確定事項」に `仮決め` で残した)。
- 範囲は依頼(2026-10-20)のとおり: 自分で TOTP を有効・無効・メールの変更(新しいアドレスに確認コード)・パスワードの変更(いまのパスワードを確かめる)・組織の管理者による必須化と、未設定の人の誘導・監査ログ・代理ログイン中は変えられない。
