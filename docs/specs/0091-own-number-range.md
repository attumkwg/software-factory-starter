## 第1部 PdM が書く所(業務の要求・業務ルール)

### なぜ作るか

キットから作ったリポジトリでは、キットの仕様・設計書・ADR と、自分の仕様・設計書・ADR が同じフォルダに同じ形の番号で並ぶ。キットの新しい版(例: 仕様 0059)を取り込むと、3か月の間に自分で書いた 0059 と重なり、`pnpm adr` が CI で落ちる。どちらを振り直すかの決まりも無く、取り込むたびに番号の付け替えとリンクの直しが要る。

- ペルソナ: キットから作ったリポジトリのテックリード(キットの版を取り込む人)
- 動かす KPI: (キットの物差し: 「使える」の条件 7「外の人に渡せる」の番号の範囲)

### 業務の要求

- キットから使い始める人が、使い始めるときに一度だけ、自分の記録の番号をどこから振るかを決められる
- キットの新しい版を何度取り込んでも、キットの記録と自分の記録の番号が重ならない
- AI と人が新しい仕様・設計書・ADR を書くとき、`pnpm adr` が出す「次の番号」が自分の範囲の中になる

### 業務ルール

- キットは 0001〜4999 だけを使い、使う側は 5000 から振る(既定) — 4桁の番号のまま、両方に数千ずつの余りが残る
- 自分の範囲の始まりは、点検の台帳を自分の物にするとき(`pnpm checkup:adopt`)に決める — 使い始めるときに一度だけ流すコマンドなので、忘れずに決まる
- 範囲が重なる設定・どちらの範囲でもない番号は、CI で落とす — 重なってから気づくのでは、取り込みの PR で振り直しが要る
- キットの中では、キットの範囲を越えた番号を落とす — キットが範囲を守らないと、使う側の番号とぶつかる

### 受け入れ条件(業務の言葉で)

- [ ] 使い始める人が `pnpm checkup:adopt --by @自分` を打つと、自分の記録の番号の始まりが 5000 に決まり、`pnpm adr` の「次の番号」が 5000 になる
- [ ] `--numbers-from 6000` を足すと 6000 から。キットの範囲(〜4999)と重なる数を渡すと、台帳も番号の設定も書かずに止まる
- [ ] 先に `checkup:adopt` を済ませていたリポジトリは、`pnpm adr --own-from 5000` で一度だけ決められる
- [ ] 自分の範囲で 5000・5001 を書いた後にキットの 0059 を取り込んでも、`pnpm adr` は落ちない
- [ ] 範囲の設定が重なっている・キットの範囲と自分の範囲の間の番号がある と、`pnpm adr` が CI で落ちる
- [ ] キットの中で 5000 以上の番号の記録を足すと、`pnpm adr` が CI で落ちる
- [ ] キットの取り込みの手引き(`docs/kit/upgrade.md`)に、番号の範囲と、範囲より前に自分で振った番号の直し方がある

### 要配慮個人情報

- 当たらない(記録の番号の決め方だけ。新しく持つ項目は無い)

### やらないこと

- キットの記録(仕様・設計書・ADR・台本)を `docs/kit/` の下へ移す(@attumkwg 2026-10-29。使う人の声が出てから)
- 範囲より前に自分で振った番号を、自動で振り直す(どれが自分の物かを機械では決められない。手引きの手順で)
- 賭け(`B-NNNN`)・穴(`G-NN`)の番号(キットから取り込む物ではない)

### 決めたこと

- キットの範囲は 0001〜4999・使う側の既定は 5000 から。キットは1か月で約90件ずつ増えたので、0999 で区切ると1年で尽きる。4桁の番号の形(`pnpm adr` のファイル名の決まり)は変えない(2026-10-29。人に聞く4つに当たらないので AI が決めた)
- 範囲の設定は `docs/kit/numbering.yaml` の1つのファイル。キットは `own_from` を変えないので、版をまるごと merge しても使う側の値が残る(2026-10-29。AI が決めた。理由は第2部の「作り」)

## 第2部 AI が網羅して書き、エンジニアが見る所(システムの振る舞い)

### 作り

| 場所 | 何をするか |
|---|---|
| `docs/kit/numbering.yaml` | 範囲の設定: `kit_until: 4999`・`own_from`(キットの中は `null`) |
| `scripts/adr-lib.mjs` | 判定(正規表現を使わない純粋な関数): `checkRange`(設定)・`checkNumbersInRange`(番号)・`nextInRange`(次の番号)・`parseRange`・`withOwnFrom`(コメントを崩さずに `own_from` だけ書く) |
| `scripts/numbering.mjs` | ファイルを読む・書く所: 3つのフォルダを読む・`decideOwnFrom`(範囲が壊れるなら書かずに問題を返す) |
| `scripts/adr.mjs` | `pnpm adr`: 今までの重なりの確かめに範囲の確かめを足し、次の番号を範囲の中で出す。`--own-from N` |
| `scripts/checkup/adopt-cli.mjs` | `pnpm checkup:adopt`: 台帳を確かめた後・書く前に `decideOwnFrom`。`--numbers-from N` |
| `docs/kit/upgrade.md` の 3 | 取り込むときの番号の範囲と、範囲より前に振った番号の直し方 |

- 設定を `upstream.yaml` に入れない — `version` は取り込むたびにキットの値に変わる行なので、隣の行の `own_from` が merge でぶつかりやすい。キットが一度も変えない行だけのファイルにすれば、まるごと merge しても使う側の値が残る(git は片方だけが変えた行をその方で取る)
- キットの中か使う側かは `own_from` が `null` かで分ける — CI でネットを使わずに決まる(`template_repository` と比べる点検の役割の決め方は `gh` が要る)
- `checkup:adopt` は台帳を確かめた後・どちらも書く前に範囲を確かめる — 片方だけ書いて止まると、流し直しで台帳の項目が二重に「使い始めた」になる
- 範囲より前に自分で振った番号(キットの範囲の中)は落とさない — キットの記録か自分の記録かを機械では分けられない。重なれば今までの重なりの確かめが落とす。直し方は手引きに

### 状態 × 操作

| 状態 \ 操作 | `pnpm adr` | `pnpm checkup:adopt` | `pnpm adr --own-from N` |
|---|---|---|---|
| キットの中・まだ使い始めていない(`own_from: null`) | 次の番号は全部の最大の次。4999 を越えた番号は落とす | `own_from` を 5000(か `--numbers-from`)に | `own_from` を N に |
| 使い始めた(`own_from` が数) | 次の番号は自分の範囲の最大の次(無ければ `own_from`)。間の番号は落とす | `own_from` はそのまま(`--numbers-from` があれば変える) | `own_from` を N に |

### 境界値

- `own_from` = `kit_until`(4999): 重なるので落とす。`kit_until + 1`(5000)は通る
- `own_from` が 9999 を越える・整数でない・数でない: 落とす
- `kit_until` が無い・整数でない: 落とす(設定の壊れ)
- `own_from` を 6000 にしたとき、5000〜5999 の番号の記録があれば、書かずに止まる
- 自分の範囲に記録がまだ1件も無い: 次の番号は `own_from` そのもの(4桁に 0 を詰める)
- `_template.md`・4桁の番号で始まらないファイル: 範囲では見ない(形の問題は今までどおり別に落とす)
