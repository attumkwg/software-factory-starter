# 仕様: 週の数字(DORA の4つ・AI が手伝った PR・人の介在率・仕様の在庫)

> 状態: 下書き
> 設計: [docs/designs/0035-delivery-metrics.md](../designs/0035-delivery-metrics.md)・ADR: [0046](../adr/0046-metrics-from-labels-and-repo-records.md)
> 穴 G-12(場面 3-7・3-9・7-2)。

## なぜ作るか

- AI に任せる範囲を広げる(危険度「低」の自動マージ・本番の承認の自動化)には、「速くなったか」と「壊れていないか」を同時に、数字で見る必要がある([concepts/people-and-ai.md](../concepts/people-and-ai.md) の 5・[concepts/line.md](../concepts/line.md) の 8)。いまは毎週の振り返りで「GitHub の Insights を見る」としか書いていない。
- 経営が「AI の席に払って速くなったのか」を決めるための数(決裁用)と、ラインが「何を機械に回すか」を決めるための数(改善用)が混ざると、どちらにも使いにくい。
- 実装が速くなると、次に作る「承認済みの仕様」が足りなくなる。仕様の在庫を数で見たい。
- AI が手伝った PR はコミットから見分けると取りこぼす(署名の無いコミット・人が手で直したコミットが混ざる)。PR に**ラベル**を付けて数えるほうが確か。

## 受け入れ条件

> 「誰が・何をすると・どうなる」。どのテストかは設計書の「7. 要求との対応」。

数える(仕組み):

- [ ] PR を開く・本文を直すと、本文に AI の印(`docs/cost/people.yaml` の `ai_markers`)があるか、AI のボットが作った PR なら、ラベル `ai:assisted` が付く。ラベルは付けるだけで、外さない
- [ ] 人は印の無い AI の PR にラベルを手で付けられ、週の数字も費用のページも、そのラベルで AI の PR と数える
- [ ] 毎週(キットから作ったリポジトリだけ)、週の数字が Actions の要約に出る。手でも流せる(週の数を選べる)

見る(人):

- [ ] 運営・開発の人が `pnpm metrics` を打つと、先週までの N 週(既定 8)の週の数字が出る
- [ ] **決裁用**: 週ごとに、本番のデプロイの数・リードタイム(PR を開いてから本番まで・中央値)・変更の失敗率・復旧の時間(中央値)・マージした PR の数・AI が手伝った PR の割合・AI の PR のうち人の介入なしで終わった割合と、いまの仕様の在庫の数が出る。チームで1つの数
- [ ] **改善用**: 先週マージした PR ごとに、AI が手伝ったか・危険度・人が答えた問いの数・人の手直しの回数・開いてからマージまでの時間が出る。問いの種類ごとの数・先週の障害の振り返り・仕様の在庫(作る待ち・承認待ち)の一覧も出る
- [ ] 人が答えた問いは、PR の本文の「人に判断してほしい所」の表の行で数える。「なし」は0
- [ ] 人の手直しは、AI が手伝った PR のコミットのうち、AI の印が無く、ボットでもマージのコミットでもない物で数える
- [ ] 変更の失敗率と復旧の時間は、本番のデプロイの成否と、障害の振り返り(`docs/incidents/`)の「戻るまで」「変更が原因」の行から数える。行の無い振り返りは件数を「読めなかった物」に出す
- [ ] 仕様の在庫は、承認済みでまだ作っていない仕様(作る待ち)と、下書きの仕様(承認待ち)。日数つき
- [ ] **人の名前・PR の題名と本文は出さない**。人ごとの数も出さない
- [ ] GitHub が読めない(gh が無い・権限が無い)ときも止まらず、読めた物で出して、読めなかった物を書く

## 権限の表に足す行

API は足さない(権限の表 `docs/authz/matrix.yaml` に足す行は無い)。GitHub の権限は、ラベルを付けるジョブだけが `pull-requests: write`(PR のコードを動かさないジョブ)、週の数字は読むだけ(`contents`・`pull-requests`・`deployments` の read)。

## 要配慮個人情報

- 当たらない(プロダクトのデータを読まない)。読むのはリポジトリの PR・デプロイの記録・リポジトリのファイルだけで、お客さんの個人データ・要配慮の表には触らない。障害の振り返りに書くのは「戻るまで」の分と「変更が原因」の はい・いいえ だけ。

## 悪用のされ方(STRIDE で1行ずつ)

| 観点 | どう悪用されうるか | どう防ぐか(テスト / ルール) |
|---|---|---|
| なりすまし | 本文に AI の印を書いて(か消して)、AI の PR の割合を動かす | 本文を書けるのはリポジトリに書ける人だけ。ラベルは付けるだけで、人が見て直せる。数は決める材料の1つ(手引き) |
| 改ざん | PR のコードを書き換えて、ラベルのジョブの書く権限で別の操作をする | 書く権限のジョブは PR のコードを checkout しない(見分けるジョブは読む権限だけ。`vrt.yml` と同じ形)。本文は env で渡す(式を run に書かない) |
| 否認 | 「その数字はどう出したか」と言われる | 数え方を設計書と手引きに書き、`--today` で前の週を出し直せる。JSON も出す |
| 情報漏えい | 要約や成果物から、人ごとの数・PR の中身が広まる | 出すのは数と PR の番号と仕様の番号・題だけ(テストが人の名前と本文の無いことを確かめる)。成果物は非公開のリポジトリのときだけ |
| 妨害(重い処理・大量の要求) | PR が多くて API を使い切る | GraphQL で 50件ずつ読み、1000件で切る(切ったら書く)。毎週1回・手で流すときも1回 |
| 権限昇格 | フォークの PR から書く権限を得る | フォークの PR は見分けるジョブごと飛ばす(`labeler.yml` と同じ) |

## やらないこと

- 人ごとの数・ランキング(人の評価に使わない。費用のページと同じ決まり)。
- 数のダッシュボード(画面)・過去の週の保存(毎回 GitHub から数え直す。`--today` で出し直す)。
- 使い始める前の PR に、さかのぼってラベルを付けること。
- トークンの量・AI の会社の請求からの数(費用のページの SaaS と AI の席)。
- 静的解析の警告・複雑さの推移(`ci.yml` の上限が見張る)。
- 「目標の数」を決めること(自分たちの並びを比べる)。

## 決めたこと

- G-12 の中身(DORA の4つ・AI が手伝った PR を Actions でラベルにして数える・人の介在率・仕様の在庫を週1で・決裁用と改善用を分ける)は、親のセッションの依頼(2026-10-25)と場面 3-7・3-9・7-2 のとおり。
- ラベルは Claude が作って `.github/labels.yml` に足す・定期のワークフローは `KIT_ROLE == 'product'` のときだけ(依頼)。
