# 仕様: キットの新しい版を取り込む道

> 1つの仕様 = 1つ以上の Issue。大きければ親 Issue → 子 Issue に割ってから AI に渡す。
> 状態: 完了(実装済み。@attumkwg が 2026-10-28 に完了とした)

## なぜ作るか

キットから作ったリポジトリは、作った瞬間からキットと離れていく。キットが直した穴・足した守りが届かない。今の手引きは「キットのコミットの一覧を見る」だけで、`/tailor` で消すほど取り込みにくくなる(外からの点検 09-adoption の 9-5・穴 G-42。雛形が捨てられる理由の ②)。

## 受け入れ条件

- [ ] キットから作ったリポジトリは、どの版まで取り込んだかを `docs/kit/upstream.yaml` に持つ(キットの中では、版を切る PR で新しいタグにする)
- [ ] 使う側の担当者が `/checkup` を流すと、キットに新しい版(GitHub のリリース)があれば項目 `kit-upstream` が不合格になり、どの版か・手が要る版をまたぐか・CHANGELOG と手引きの場所を知らせる。同じ版なら合格、キットにまだ版が無ければ合格、読めなければ unknown
- [ ] キットのリポジトリそのもの(ひな形)では `kit-upstream` は比べずに合格
- [ ] `pnpm setup:github` の「人がやること」が、キットに版があれば版と CHANGELOG で、まだ版が無ければ日付で、取り込みの手引きを案内する(コミットの一覧ではなく)
- [ ] `pnpm setup:github` の「人がやること」が、`SECURITY.md` がキットの窓口のままなら書き換えを知らせる
- [ ] 使う人が `docs/kit/upgrade.md` を読むと、版の差分の読み方・取り込み方の選び方(まるごと merge / 差分を要る場所だけ / 直しだけ cherry-pick)・ぶつかりの解き方(消した部品・自分の題材・点検の台帳)・PR の出し方が分かる

## 権限の表に足す行

該当なし(アプリの API は変えない)。

## 要配慮個人情報

- 当たらない(キットの版の番号と GitHub のリリースだけを読む。アプリのデータに触れない)

## 悪用のされ方(STRIDE で1行ずつ)

| 観点 | どう悪用されうるか | どう防ぐか(テスト / ルール) |
|---|---|---|
| なりすまし | 似た名前のリポジトリの「新しい版」を取り込ませる | 比べる相手は `upstream.yaml` の `repository`(既定はキットの元のリポジトリ)と `.github/setup.yml` の `template_repository` だけ。知らせの文の URL もそこから作る |
| 改ざん | 取り込む差分に、守りを弱める変更を混ぜる | 取り込みの PR は守るパスを変えるので危険度「高」になり、人が見る(手引きの 4)。タグは付け替えない(`maintenance.md` の 4) |
| 否認 | どの版を取り込んだか分からない | `upstream.yaml` の `version` と PR の題・本文(手引きの 4)。cherry-pick は `-x` でキットのコミットを残す |
| 情報漏えい(他社のデータ) | 該当なし | 読むのは公開のリリースの名前だけ |
| 妨害(重い処理・大量の要求) | 該当なし | 点検で月1回・`pnpm setup:github` で1回、API を1回読むだけ |
| 権限昇格 | 点検のトークンで書き込む | 点検は読むだけ(`gh api` の GET。`CHECKUP_READ_TOKEN`) |

## やらないこと

- 取り込みを自動でする(PR を自動で出す)。ぶつかりの解き方は使う側の判断が要る
- 「仕組みだけを別に配る(プラグイン)」形に分ける。配る形は持ち主が決める(設計書の 12 に案)
- 古い版への直しの持ち込み(直すのは最新の版だけ。`maintenance.md` の 2)
