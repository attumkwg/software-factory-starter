# 仕様: 問い合わせの受け口の決め方

> 状態: 下書き(想定の場面の穴 G-11 から AI が書いた。2026-10-25。承認は PR で)
> 設計: [docs/designs/0033-support-intake.md](../designs/0033-support-intake.md)・ADR: [0044](../adr/0044-support-intake-outside-and-ids-only-to-ai.md)

## なぜ作るか

- 問い合わせの受け口(メール・フォーム・ヘルプデスクの道具)はキットの外で、どう選び、受けた後に `/report-bug` へどうつなぐかが決まっていない(想定の場面の 2-6・5-4)。
- 問い合わせの本文は個人データ。受け口の道具は委託先になり、AI に何を渡してよいか(AI-6)の当てはめが要る。最近のヘルプデスクの道具は、本文を AI に読ませる機能を持つ。
- 開発の人の兼任で始まるが、いつ2人目を入れるかの目安が無い。2〜3人の体制は1人休むと回らない。

## 受け入れ条件

- [ ] `docs/guides/support-intake.md` に、段階ごとの受け口の形(共有の受信箱 → ヘルプデスクの道具とヘルプの記事 → 検索)がある
- [ ] 道具の選び方(番号と履歴・担当と状態・置き場所の国・AI の機能・アカウント・費用)があり、入れたら委託先の台帳に1件(`委託`・`personal`)と書いてある
- [ ] 道具の AI の機能(要約・自動の返信・分類)は切る、と AI-6 と台帳の決まりを根拠に書いてある
- [ ] 受けた後の仕分け(他社のデータ・個人データの事故・障害・不具合・使い方・契約・中を見てほしい・本人の求め)と、それぞれの行き先の手順書がある
- [ ] 不具合のときの `/report-bug` へのつなぎ(問い合わせ番号・組織の ID・渡す物と渡さない物・受け口と Issue の結び方)がある
- [ ] AI に渡してよい物・渡さない物の表があり、`compliance/ai-data.md` の行から指す
- [ ] 兼任でよい目安と、2人目を入れる目安(件数・最初の返事までの時間・休んだときに止まるか)がある

## 権限の表に足す行

該当なし(API を足さない)。

## 要配慮個人情報

- 当たらない(文書だけ。データを取らない)。要配慮が入った問い合わせは、件数も AI に渡さないと書く。

## 悪用のされ方(STRIDE で1行ずつ)

| 観点 | どう悪用されうるか | どう防ぐか(テスト / ルール) |
|---|---|---|
| なりすまし | お客さんの管理者を名乗って、データの書き出しや削除を頼む | 契約・解約は責任者へ・書面で。中を見るのは管理者が画面で出す期限つきの許可だけ(代理ログイン) |
| 改ざん | 該当なし(文書だけ) | — |
| 否認 | 「問い合わせたのに返事が無い」 | 番号と履歴が残る受け口・担当と状態 |
| 情報漏えい(他社のデータ) | 本文や本番のスクショを AI や Issue に貼る / 道具の AI の機能に本文を読ませる / 共有のアカウントが乗っ取られる | AI に渡すのは ID と集計まで・道具の AI の機能は切る・アカウントは人ごとに二段階認証 |
| 妨害(重い処理・大量の要求) | 大量の問い合わせで受け口を埋める | 受け口の道具の側の制限(この PR の外) |
| 権限昇格 | 該当なし(文書だけ) | — |

## やらないこと

- 受け口の道具を選ぶ・契約する・委託先の台帳に実際の1件を足す(使い始めたとき)
- `/report-bug` のスキルを変える(すでに「個人情報を貼らせない」がある。手引きから指すだけ)
- 本人の開示・削除の求めの手順(穴 G-06)
- 想定の場面(`docs/scenarios/`)の判定と穴の一覧の書き換え(場面の持ち主が直す)
