## 第1部 PdM が書く所(業務の要求・業務ルール)

### なぜ作るか

- ペルソナ: キットを使ってプロダクトを作る人(持ち主・PdM・代表)
- 動かす KPI: (キットの「使える」の条件 1 通しで作れる・5 お金をもらえる)

キットを5人の AI でレビューした(総合 ★2.7)。貯める → 合議 → 決める → 作る は ★4〜4.5 だが、**計測 ★2・戻る ★1.5 でループが閉じていない**。KPI の値を入れる人と周期が無く、結果がペルソナと合議に戻らず、合議の見込みの当たり外れも残らない。ROI は式も累計も無く、今は出せない。持ち主の言葉: 「実際に計測してそのフィードバックをさらに貯めていく流れを繰り返すのが重要」「計画が出た段階でレビュー採点、星何個みたいなのが出るといい」「ROI がどうなったのかが分からない」。

### 業務の要求

- 計測の値を毎週・賭けの結果のたびに貯め、止まったら気づける
- 話を聞いた記録や計測の結果が、ペルソナ・業界の前提・合議に戻る
- 合議の見込みが当たったかを測り、外れが続いたら合議を回し直す
- 計画(合議の結論)に星の採点が出て、後で実測と比べられる
- 賭けごとに ROI の幅と回収の月数を出せる

### 業務ルール

- 推測だけの賛成は価値の星に数えず、拒否があれば価値は ★2 まで。価値と確からしさの星は機械で出し、手で上げない — 作る側の自信は根拠のある星からにする
- 金額はリポジトリに書かず、ROI は倍率と月数の幅だけ — リポジトリは公開されうる
- 合議の記録は書き直さず、回し直すときは新しい記録 — 当たり外れを後から比べられるように

### 受け入れ条件(業務の言葉で)

- [ ] 追う指標の記録が4週より古い・無いと、`pnpm kpi` が知らせる。rollout・adopted の賭けが動かす KPI に記録が無いと知らせる
- [ ] 毎週の手順と `/bet` の結果に、値を1行足す手順がある
- [ ] 話を聞いた記録に「当たるペルソナ・答えた問い・戻すこと」の欄があり、`/persona` の 5 で根拠を推測 → 記録に書き換える
- [ ] 合議の見込みの幅を `kpi.yaml` の `forecasts` に書け、期限の後に `pnpm kpi` が当たり・外れ・測っていないと合議ごとの当たり率を出す。外れが半分を超えたら回し直しをすすめる
- [ ] 合議の記録に星の採点(価値・確からしさ・守り・ROI の見込み・実現性)が要り、価値と確からしさが表から出した値と違うと落ちる
- [ ] ROI の式(得た物・ROI・回収の月数)が手引きにあり、賭けの型に倍率と月数の幅の表がある

### 要配慮個人情報

- 当たらない。

### やらないこと

- 本番から KPI の値を自動で集める(人が打つ運営のコマンドの決まりのまま。ADR が要る)
- 費用のページ(`pl.mjs`)に累計と得た物の列を足す(次の PR)
- CI の範囲の判定を土台の版で流す(#152 の残り)

### 決めたこと

- ループを閉じる案・ROI・計画の星の採点を進める(@attumkwg 2026-10-28。会話で回答)。

## 第2部 AI が網羅して書き、エンジニアが見る所(システムの振る舞い)

### 状態 × 操作

| 状態 \ 操作 | `pnpm kpi` |
|---|---|
| 追う指標の記録が無い・28日より古い | 知らせる |
| rollout・adopted の賭けの KPI に記録が無い | 知らせる |
| forecasts の書き方の誤り(期限・番号・合議・幅) | 落ちる |
| 合議の記録に 8 が無い・軸が欠ける・1〜5 の外 | 落ちる |
| 価値・確からしさの星が表から出した値と違う | 落ちる |

### 境界値

- 古さ: 28日ちょうどは通す・29日から知らせる
- 見込みの比べ: 期限の日までの最後の値。幅の両端は当たり
- 当たり率: 確かめられた見込みが2つ以上で、半分未満なら回し直し

### 権限の組み合わせ

- 該当なし(アプリの API は変えない)
