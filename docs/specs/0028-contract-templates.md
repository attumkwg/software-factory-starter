# 仕様: 申込書・SLA・個人データの取り扱いの取り決めの型

> 状態: 下書き(想定の場面の穴 G-04 から AI が書いた。2026-10-25。承認は PR で)
> 設計: [docs/designs/0028-contract-templates.md](../designs/0028-contract-templates.md)・ADR: [0041](../adr/0041-contract-templates-fixed-and-negotiable.md)

## なぜ作るか

- 営業が申込書・SLA・個人データの取り扱いの取り決めを、お客さんごとに一から作っている。キットの作りからもう決まっている項目(バックアップの期間・戻せる時点・解約後に消えるまで・障害の連絡の型・再委託先)が、営業の使える1枚になっていない(想定の場面の 2-3・2-4)。
- SLA を稼働率の数字だけで出すと、割ったときに「何を測ったか・どの停止を数えるか・補償は・誰が決めるか」で揉める(5-11)。
- 大企業は個別の契約書を求める。変えてよい条件と変えない条件(キットの作りで決まっている物)を先に分けておかないと、守れない約束を書いてしまう(例: prod のバックアップはロックで縮められないのに「30日でバックアップからも消す」と書く)。

## 受け入れ条件

### 共通

- [ ] `docs/legal/README.md` に、キットの作りから決まる項目の一覧(データの置き場所・再委託先・会社どうしの分け方・社員の触り方・操作の記録・暗号化・バックアップ・戻せる時点・解約・書き出し・ログ・見張り・障害の連絡・個人データの事故・止めずに出す・安全管理措置・AI に渡すデータ)が、**キットの既定と根拠のファイル**つきである
- [ ] 同じ所に、条件を「変えない / 仕組みを変えれば変えられる / 契約だけで変えられる」の3つに分けた表と、それぞれの例・頼まれたときの動き方がある
- [ ] どの型も、頭に「文面は書かない。専門家に確かめる」があり、法律の文を含まない
- [ ] どの型も、項目ごとに「キットの既定 / 根拠(どのファイル) / 使う人が決めること」が並ぶ。最後に「専門家に確かめること」がある
- [ ] 型に、お客さんの名前・金額・契約書の写しを書かない決まりがある

### 申込書

- [ ] `docs/legal/order-form.md` に、プラン・人数・始まりの日・支払い・契約の期間・自動更新・解約の申し出の期限・解約したときのデータ・最初の管理者・申し込む権限・規約への同意の欄がある
- [ ] 申し込む権限は、申し込む人と承認した人を分け、組織を作る前に確かめる手順がある
- [ ] キットに無い物(プランの表・人数の上限・請求)は「欄だけ置く・キットは止めない」と書き、穴の番号を指す

### SLA

- [ ] `docs/legal/sla.md` に、何を測るか(外形監視と、外形監視で見えない停止の足し方)・範囲・原因の区分(自社・外のサービス・お客さんの側・計画メンテナンス・緊急の保守)と数えるかどうか・補償の段・法的な義務か努力目標か(項目ごと)・連絡の時間・事実を確定する人と例外を認める人がある
- [ ] 月の稼働率を出す手順(読むだけのコマンド)があり、数字が消えるまでの日数に合わせて、いつ出すかが書いてある
- [ ] 障害の振り返りの型(`docs/runbooks/incident.md` の 6)に、SLA の欄(停止の時間・原因の区分)がある

### 個人データの取り扱いの取り決め

- [ ] `docs/legal/data-processing.md` に、自社の立場(委託先として扱う前提と理由)・預かる物と目的・安全管理措置(根拠を指すだけ)・事故の連絡(期限・中身・誰が報告するか)・再委託先(台帳を指す・足すときの知らせ)・終わったときの返却と削除(バックアップを含む)・監査がある

### つながり

- [ ] `docs/README.md` の地図と `docs/reference.md` のファイルの地図に1行ずつある
- [ ] `docs/guides/data-retention.md`(期間を変えたら直す元の表)から、型を指す
- [ ] キットの部品のカタログ(`docs/kit/catalog.yaml`)に1件ある
- [ ] 答えがプロダクトごとに変わる既定の値(SLA の線・補償・連絡の時間・削除までの日数・契約の期間・申し込む権限の確かめ方・委託先として扱うか)が、設計書の未確定事項にある

## 要配慮個人情報

- 当たらない(文書だけ。データを取らない)。取り扱いの取り決めの型には、要配慮を扱う機能があるときの項目を置く(置き場所は ADR 0029)。

## 悪用のされ方(STRIDE で1行ずつ)

| 観点 | どう悪用されうるか | どう防ぐか(テスト / ルール) |
|---|---|---|
| なりすまし | 権限の無い社員が会社の名前で申し込み、組織を作らせる | 申込書で申し込む人と承認した人を分け、承認した人の会社のメールに確かめてから作る |
| 改ざん | 型の既定の値を、根拠のファイルを直さずに書き換える(仕組みと約束が食い違う) | 値の正は根拠のファイル。仕組みを変えたら型も直す(data-retention.md の頭)。型を変える PR は人が見る |
| 否認 | 「解約を申し出た / 申し出ていない」「その停止は数えるはず」 | 解約は書面だけで受ける。停止の事実は振り返りの記録が正(指揮が書く) |
| 情報漏えい(他社のデータ) | 型の中や営業の資料に、お客さんの名前・金額・事故の中身を書く | 型にお客さんの名前・金額を書かない決まり。会社ごとの条件はリポジトリの外。事故の知らせに他社の名前を書かない |
| 妨害(重い処理・大量の要求) | 該当なし(文書だけ) | — |
| 権限昇格 | 該当なし(文書だけ) | — |

## やらないこと

- 申込書・SLA・取り決めの**文面**(専門家が書く)
- プランの表・人数の上限・請求(穴 G-03)、組織を作る運営のコマンド・招待(穴 G-01・G-02)
- 月の稼働率を自動で出す仕組み(手で出す手順だけ)
- 外形監視に DB まで届く見張りを足すこと(infra の変更。振り返りの S1 で補う)
- 想定の場面(`docs/scenarios/`)の判定と穴の一覧の書き換え(場面の持ち主が直す)
