# 仕様: 危険度「高」の PR だけ、人の承認を決めた人数そろえる

> 1つの仕様 = 1つ以上の Issue。大きければ親 Issue → 子 Issue に割ってから AI に渡す。
> 状態: 下書き

## なぜ作るか

キットは「危険度『高』は人が2人」と約束しているが、GitHub のルールセットの承認数はリポジトリで1つの値で、CODEOWNERS は並べた誰か1人の承認で通る。今の手順(承認 2・CODEOWNERS に2チーム)では、**全部の PR が2人になるか、高でも1人で通るか**のどちらかになる(外からの点検 09-adoption の 9-4・穴 G-43)。

## 受け入れ条件

- [ ] 危険度「高」の場所(`.claude/hooks/protected-paths.json`)を変えた PR か、ラベル `risk:high` の付いた PR は、書き込める人(持ち主・組織の人・共同作業者)の承認が `.github/setup.yml` の `ruleset.high_risk_approvals` の人数に届くまで、必須のチェック「危険度「高」の承認の人数」が落ちる
- [ ] 「高」でない PR は、人数にかかわらずそのチェックが通る
- [ ] 1人の間(`high_risk_approvals: 0`。キットの既定)は、「高」でも数えずに通る
- [ ] PR を出した人・ボット・書き込めない外の人の承認、取り消された承認、後から「変更を求める」にした人の承認は数えない
- [ ] レビューが付いた・取り消されたときに、チェックが流れ直す
- [ ] PR の中で一覧・人数・数えるスクリプトを緩めても、その PR には効かない(土台のブランチの物で数える)
- [ ] `high_risk_approvals` が 0〜6 の整数でない・`required_approvals` より少ないと、`pnpm setup:check` が落ちる

## 権限の表に足す行

該当なし(アプリの API は変えない)。

## 要配慮個人情報

- 当たらない(GitHub の PR のファイル名・ラベル・レビューの状態だけを読む。アプリのデータに触れない)

## 悪用のされ方(STRIDE で1行ずつ)

| 観点 | どう悪用されうるか | どう防ぐか(テスト / ルール) |
|---|---|---|
| なりすまし | 外の人や別のアカウントで「承認」を付けて人数を満たす | 書き込める人(`author_association` が OWNER・MEMBER・COLLABORATOR)だけ数える・出した人とボットは数えない(`review-count.test.mjs`) |
| 改ざん | PR の中で一覧から場所を外す・人数を 0 にする・スクリプトを書き換えて通す | 土台のブランチ(base)の中身で数える(ワークフローの checkout)。一覧とスクリプト自身も「高」 |
| 否認 | 誰が承認したか分からない | チェックの出力に承認した人を並べる |
| 情報漏えい(他社のデータ) | 該当なし | 読むのは PR の情報だけ |
| 妨害(重い処理・大量の要求) | レビューを連打してチェックを何度も流す | 同じ PR の流れは1つに(concurrency で古い方を止める)・5分で打ち切り |
| 権限昇格 | ワークフローの権限で書き込む | 権限は読むだけ(`contents: read`・`pull-requests: read`)・鍵を残さない checkout |

## やらないこと

- CODEOWNERS をチームに書き換える仕組み(人がチームを作ってから手で。`docs/guides/github-setup.md`)
- 「高」の承認者を特定のチームに限る(1人目の持ち主はルールセットの CODEOWNERS の承認が守る)
- マージキューの中で数える(キューを使うなら必須から外す。`取り組みと作業の種類` と同じ)
