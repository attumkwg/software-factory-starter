# 仕様: 個人情報を、置き場所とログで最初から守る

> 状態: 下書き(本人の希望から AI が書いた。承認待ち)
> 設計: [docs/designs/0008-personal-data.md](../designs/0008-personal-data.md)
> 判断の記録: [ADR 0018](../adr/0018-sensitive-data-isolation.md)(要配慮個人情報を分けて置く段階)

## なぜ作るか

このキットは、Sentry に送る中身は「決めた項目だけ」(許可リスト)に絞っている。けれども、**自分の AWS の中のログ(CloudWatch)は「伏せる名前の一覧」**のままで、一覧に無い名前(`name`・`newEmail`・`staffName`・`title`)や深い所の値は素通りする。どの列が個人情報かを決めた表も無いので、AI が列やログを足すたびに、人が目で見て気づくしかない。

要配慮個人情報(病歴・障害・信条など。個人情報保護法 2条3項)を扱うプロダクトでは、漏れたときの害がずっと大きい。**扱い始める前に**、ほかのデータと混ざらない置き場所と、ログに出ない仕組みを持っておく。

2026-10-21 の点検で、ここがいちばん大きい穴と分かった。

## 受け入れ条件

### A. 列の分類表(土台)

- [ ] DB の全部の列に、区分(`public` / `internal` / `personal` / `sensitive`)と利用目的の一言がある(`apps/api/src/db/classification.ts`)
- [ ] AI か人が列を足して、分類を書き忘れると、単体テストが落ちる。もう無い列の分類が残っていても落ちる
- [ ] jsonb の列(監査ログの `details`・送信待ちの `payload`)は、中身のキーも分類する。出来事の中身のキー・API のパスの ID の名前を足して、分類を書き忘れると落ちる
- [ ] 監査ログの `details` と送信待ちの `payload` に、`personal` / `sensitive` のキーは置けない(テストが落ちる)
- [ ] `sensitive` の列は、Postgres のスキーマ `sensitive` の表にしか置けない(ほかの所に置くとテストが落ちる)。いまはこのスキーマが無いので、**分けて置く仕組みを作るまで、要配慮個人情報の列は足せない**
- [ ] 分ける段階(別スキーマ+専用のロール+専用の鍵で列ごとに暗号化 → 別のクラスター → 別の AWS アカウント)が ADR にある
- [ ] 分類から作った「個人情報の台帳」(どの表のどの列に・何の目的で)が `docs/db/` にあり、分類と食い違うとテストが落ちる
- [ ] 列を足す手順(`db-migration`)は区分を必須にし、`sensitive` は人の確認が必須。API を足す手順(`add-api-endpoint`)は、返す値とログに出す項目の区分を確かめる。PR のレビュー(`review-pr`)は分類表を見て確かめる
- [ ] 分類表・ログの部品(API・画面のサーバー・Sentry への送り)は危険度「高」で、AI が変えるときは人の確認が出る

### B. ログを許可リストに

- [ ] API と画面のサーバーのログは、**出してよい項目**(ID・状態・件数・時間など)だけを出し、知らない項目は `[REDACTED]` になる。API と画面のサーバーは同じ部品を使う
- [ ] 分類表の `personal` / `sensitive` の列の名前は、どの深さにあっても伏せる
- [ ] 失敗の文(CloudWatch に出る `err.message` と、送信待ちの `last_error`)は、Sentry に送るときと同じ処理で値を伏せる(メールアドレス・引用符の中・長い数字など)
- [ ] メールの中継(Postfix)のログに、宛先のメールアドレスが出ない
- [ ] 目印つきの値(名前・電話番号・病名に見立てた文)を入れて全部の API を叩き、出たログの全行に目印が1つも無い(結合テスト)
- [ ] 「ログにオブジェクトを丸ごと渡す」を止めるルール(Semgrep)が、`{ title: body.title }`・`{ ...row }`・テンプレート文字列の形も止める
- [ ] データの置き場所の表(`docs/guides/data-retention.md`)に、メールの中継のログ・送り待ち・WAF のログがある

## 権限の表に足す行

なし(API を足さない)。

## 悪用のされ方(STRIDE で1行ずつ)

| 観点 | どう悪用されうるか | どう防ぐか(テスト / ルール) |
|---|---|---|
| なりすまし | 該当なし(ログインの仕組みは変えない) | — |
| 改ざん | AI が分類を `internal` に書き換えて、個人情報をログに出す | 分類表は危険度「高」(人の確認・2人のレビュー)。ログは許可リストなので、分類を変えても名前を許可しない限り出ない |
| 否認 | 該当なし | — |
| 情報漏えい | ログ(CloudWatch)・送信待ちの失敗の文・メールの中継のログに、名前・メールアドレス・入力の値が残り、ログを読める社員や漏れたときに外へ出る | 許可リスト・分類の名前を深さを問わず伏せる・失敗の文を伏せる・全 API を叩いて目印を探す結合テスト |
| 情報漏えい(要配慮) | 要配慮の列がほかの表に混ざり、ふつうの権限・ふつうのバックアップの鍵で読める | `sensitive` はスキーマ `sensitive` にしか置けないテスト。段階は ADR 0018 |
| 妨害 | 該当なし(ログの量は減る方向) | — |
| 権限昇格 | 該当なし | — |

## やらないこと

- スキーマ `sensitive`・専用のロール・専用の鍵を、いま作ること(要配慮の列を足すときに、ADR 0018 の段 1 から作る)
- 利用者を1人だけ消す・匿名化する(`data-retention.md` の次の一歩のまま)
- いまあるログ(CloudWatch に残っている分)を消す・作り直すこと(保存期間で自然に消える)
- 画面(ブラウザ)の中のログ。ブラウザから Sentry に送る分は `packages/error-reporting` がすでに絞っている

## 決めたこと

- 2026-10-21 本人: 「要配慮個人情報と個人情報をログに出さないのを、初めからハーネスとして組み込む」「要配慮を扱う場合は、物理的にデータを隔離して混ざらないようにする」
