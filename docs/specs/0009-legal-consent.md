# 仕様: 利用規約・プライバシーポリシーの版と同意

> 状態: 承認済み(承認した人: @attumkwg 2026-10-22。設計書の未確定事項 U-1〜U-6 を「承認」、U-7 は条文で確かめた。依頼: @attumkwg 2026-10-22「利用規約とか出す必要ありますね。規約が変わったら確認してもらう手順があると思うけど、そういった仕組みを入れないとまずそう」)

## なぜ作るか

このキットで作るサービスは、お客さんの会社と契約して使ってもらう(B2B)。契約の中身は**利用規約**、個人の情報の扱いは**プライバシーポリシー**に書いて見せる必要がある。いまはどちらも置き場所が無く、**誰が・どの版に・いつ同意したか**の記録も無い。

規約は後から変わる。利用者に不利な変更は、変わる日と中身を前もって知らせないと効かない(民法 548条の4。下の「法令」)。大事な変更は、同意し直してもらうのが安全。プライバシーポリシーで利用目的を広げるときは、本人の同意が要る場合がある(個人情報保護法 18条1項)。

このキットで作るサービスは、P マーク・ISMS を求められることが多い。そこでは「同意を取った記録」を見せる必要がある。だから、**版を持ち・同意を足すだけで記録し・同意し直しが要る版に同意していない人は先へ進めない**仕組みを、キットの部品として入れる(規約の文面そのものはキットに入れない。見出しだけのひな形)。

## 受け入れ条件

> 「誰が・何をすると・どうなる」。ここがそのままテストになる(どのテストかは設計書の「7. 要求との対応」)。

文書の版(運営・開発者):

- [ ] 利用規約とプライバシーポリシーは、それぞれ**版**(1, 2, 3 …)を持つ。版ごとに「公開する日時・効力の日時・変更の要約・同意し直しが要るか」が決まっている
- [ ] 本文はリポジトリの Markdown(1つの版 = 1つのファイル)。変えると PR で差分が見える。**公開した版の本文は変えない**(直すなら新しい版)。変えたら CI が落ちる
- [ ] 2つ目からの版は、公開の日から効力の日まで**30日以上**あける(CI が確かめる。日数は未確定事項)
- [ ] キットのひな形は見出しだけ(規約の文面は入れない)

本文を読む(誰でも。ログインしていなくても):

- [ ] 画面「利用規約」「プライバシーポリシー」で、**いま効いている版**の本文・版・効力の日が読める
- [ ] 前の版と、公開済みでまだ効いていない版(次の版)も読める。変更の履歴(版・効力の日・要約)が並ぶ
- [ ] 公開の日時より前の版は、画面にも API にも出ない

登録するとき(Cognito のとき):

- [ ] 画面「登録」に、利用規約とプライバシーポリシーへのリンクと「同意します」のチェックがある。チェックしないと登録に進めない
- [ ] 確認コードを入れて登録を終えたとき、その人がアプリに登録されている(`users` に行がある)なら、**見せた版への同意**が記録される(どの画面から = 登録)
- [ ] 確認コードが違う・アプリにいない人なら、何も記録しない(答えは今までどおり。いるかいないかを言わない)

同意し直し(全員):

- [ ] **同意し直しが要る版が効力の日を迎えた**のに、その版(か後の版)に同意していない人は、ログインした後(すでにログインしている人は次の操作で)**どの画面を開いても「同意の画面」へ回される**
- [ ] それまでの間、同意の画面に要る API(自分・同意する)とログアウトのほかは 403(`terms_acceptance_required`)
- [ ] 同意の画面には、同意が要る文書ごとに版・効力の日・変更の要約・本文へのリンクが出る。「同意する」を押すと記録され、元の画面に戻る
- [ ] 同意しない人は、ログアウトだけできる(同意の画面に「同意しない場合はログアウトしてください。契約については組織の管理者に相談してください」)
- [ ] 組織の管理者が利用規約に同意すると、**組織(契約者)としての同意**として記録される。メンバーと閲覧者は**本人としての同意**
- [ ] プライバシーポリシーへの同意は、誰でも本人としての同意
- [ ] 同意した(誰が・どの文書の・どの版に・いつ・どの画面から・組織としてか本人としてか)は、消せない記録として残る。組織の監査ログにも「同意した」が残る
- [ ] 同じ版に2回同意しても、記録は1つ(2回目は何もしない)

前もって知らせる(軽い変更も同意し直しの変更も):

- [ ] 公開済みでまだ効いていない版があれば、ログインした人の画面の上に**帯**が出る(「利用規約が 11月1日 に変わります」・要約・本文へのリンク)
- [ ] 同意し直しが要る版なら、帯から**前もって同意できる**。同意した人には、効力の日に同意の画面は出ない
- [ ] 運営が**お知らせのメール**を送れる(コマンド。試し → 本当に送る)。組織の全員に1通ずつ。同じ人に同じ版のお知らせを2回送らない。送った記録が残る(周知した証拠)
- [ ] 同意し直しが要らない版は、効力の日を過ぎたら帯が消え、同意の画面も出ない(知らせるだけ)

対象にしない人:

- [ ] サポートの代理ログイン中の社員は、同意の画面に回されない(見るだけなので)。代理の社員は、お客さんの代わりに同意できない(403)
- [ ] 運営の組織(`SUPPORT_TENANT_ID`)の人は、同意の画面に回されない(運営そのものなので)
- [ ] 開発用ログイン(`AUTH_MODE=dev`)でも、同意の画面は同じに動く(Cognito に頼らないので)

他社・未ログイン:

- [ ] 他社の人は、別の組織の同意の記録を見る・作ることができない(組織はセッションからだけ決まる。記録の表は RLS)
- [ ] 未ログインで同意の API を呼ぶと 401。本文の画面は未ログインでも読める

## 権限の表に足す行

| API | admin | member | viewer | 他社 | 未ログイン | 代理の社員 |
|---|---|---|---|---|---|---|
| `POST /api/legal/consents`(同意する) | 204 | 204 | 204 | —(自分の物だけ) | 401 | 403 |

- 「他社」が「—」なのは、パスに相手の ID が無く、どの組織の誰の同意かはセッションだけで決まるため。
- 本文と版の一覧は API にしない(画面のサーバーが、リポジトリの Markdown と版の一覧をそのまま出す。設計書の 1)。
- 同意が要るかは `GET /api/me` に足す(任意の項目。足すだけ)。
- 登録の確認(`POST /api/auth/confirm-sign-up`・公開)の本文に、同意した版を任意の項目として足す(足すだけ)。

## 悪用のされ方(STRIDE で1行ずつ)

| 観点 | どう悪用されうるか | どう防ぐか(テスト / ルール) |
|---|---|---|
| なりすまし | 他人のメールで登録を始め、**その人が同意したことにする** | 記録するのは確認コード(メールの持ち主にしか届かない)が通った後だけ。コードが違えば記録しない |
| なりすまし | 代理ログインの社員が、お客さんの代わりに同意する | 代理の最中は同意の API が 403(`NOT_DURING_SUPPORT`) |
| 改ざん | 同意の記録を書き換える・消す(「同意していない」を「した」に) | アプリの DB の権限は「読む・足す」だけ(直す・消すは無い)。消すのは解約の手順だけ |
| 改ざん | 公開した版の本文を後から書き換える(「その版にはそう書いてあった」にする) | 版の一覧に本文のハッシュを持ち、合わなければ CI が落ちる。書き換えは新しい版として出す |
| 改ざん | 存在しない版・まだ公開していない版・古い版に同意したことにする | API が版の一覧で確かめる(公開済みで、いまの版か次の版だけ。違えば 400) |
| 否認 | 「同意していない」「その版は見ていない」と言う | 同意の記録(版・時刻・画面・組織としてか本人としてか)・監査ログ(requestId でアプリのログとつながる)・お知らせの送った記録 |
| 情報漏えい(他社のデータ) | 他社の同意の記録を見る | 組織はセッションからだけ。表に `tenant_id` と RLS。読む API は作らない |
| 妨害 | 同意の画面で止まって、仕事が止まる(効力の日の朝に全員が止まる) | 前もって帯で知らせ、前もって同意できる。予告は30日以上(CI)。関所が止めるのは「同意し直しが要る版」だけ |
| 妨害 | お知らせのメールを何度も送る | コマンドは運営だけ(API は作らない)。同じ人に同じ版は1回だけ(足すだけの記録の一意) |
| 権限昇格 | 同意せずにほかの API を叩く | 関所が毎回「同意が要るか」を見て 403(画面で隠すだけにしない) |
| 権限昇格 | メンバーが「組織として」同意する | 組織としてか本人としてかは API がロールで決める(本文で選べない) |

## 法令(条文と一次資料で確かめた所)

> キットは既定の仕組みだけを持つ。規約の文面・何を「重要な変更」とするか・予告の日数は、使う人の事業判断と法務の確認が要る(設計書の未確定事項)。
> 条文は e-Gov 法令 API(v2)で 2026-10-22 に読んだ現行の版: 民法 `129AC0000000089_20260624_508AC0000000045`(2026-06-24 施行)・個人情報保護法 `415AC0000000057_20261001_507AC0000000070`(2026-10-01 施行)。法令が変わったら、この節を読み直す。

- **定型約款が契約の中身になる条件**: 「約款を契約の内容とする」合意をするか、定型約款を準備した側が前もってその旨を相手に**表示**しておく(民法 548条の2第1項)。相手の権利を制限し・義務を重くする条項で、信義則に反して相手の利益を一方的に害するものは、合意しなかったものとみなす(同第2項)。合意の前に内容を見せてと言われて断ると、548条の2 が使えない(一時的な通信障害など正当な理由があるときを除く。548条の3第2項)。— 法務省「売買、消費貸借、定型約款などの契約に関する民法のルールが変わります」(パンフレット)https://www.moj.go.jp/content/001289629.pdf ・ 法務省民事局「民法(債権関係)の改正に関する説明資料 －主な改正事項－」https://www.moj.go.jp/content/001259612.pdf
- **定型約款の変更**: 個別の合意なしに変えられるのは、①相手方の一般の利益に合う変更、②契約の目的に反せず、変更の必要性・変更後の内容の相当性・「変更することがある」旨の定めの有無と内容などに照らして合理的な変更、のどちらかだけ(548条の4第1項)。「当社都合で変更することがあります」と書いてあっても、一方的に変えられるわけではない(定めの有無と内容は、②の判断材料の1つ)。
  - **周知は①②どちらの変更にも要る**: 効力発生時期を定め、変更すること・変更後の内容・効力発生時期を、インターネットなどの適切な方法で知らせる(548条の4第2項)。利用者に有利な変更でも、知らせずに済ませてよいわけではない。
  - **②の変更は、効力発生時期までに周知しないと効かない**(同第3項)。
  - 変更の当否は、548条の2第2項(不当な条項)ではなく、第1項の要件で見る(同第4項)。
  - → キットの作りは条文に合う: 版ごとに効力の日(`effectiveAt`)を持ち、同意し直しが要るかどうかにかかわらず、帯とメールで公開から効力の日まで知らせる。
  - — 条文(上の版)・法務省(パンフレット・説明資料)
- **プライバシーポリシー(個人情報保護法)**: 利用目的の変更は、変更前と関連性があると合理的に認められる範囲まで(17条2項)。変えたら本人に通知か公表(21条3項)。その範囲を超えるなら、あらかじめ本人の同意(18条1項)。第三者への提供は、例外を除きあらかじめ本人の同意(27条1項)。「本人の同意」は、本人が判断するのに必要な合理的で適切な方法で得る(確認欄へのチェック・ボタンを押す、が例に挙がる)。— 個人情報保護委員会「個人情報の保護に関する法律についてのガイドライン(通則編)」2-14・2-15・2-16・3-1-2 https://www.ppc.go.jp/personalinfo/legal/guidelines_tsusoku/ 。条番号(17条2項・18条1項・21条3項・27条1項)は、上の版の条文でも同じ。
- **条文で確かめた範囲**: 民法 548条の2〜548条の4・個人情報保護法 17条・18条・21条・27条(設計書 U-7)。それ以外の法令(特定商取引法・消費者契約法・電気通信事業法など)は見ていない。サービスの中身によって効くので、使う人が法務と確かめる。

## やらないこと

- **規約の文面**(見出しだけのひな形。文面は使う人が法務と書く)
- 管理画面から版を足す・本文を直す(版は PR で足す。差分を人が見る)
- 組織の管理者が「誰が同意したか」を一覧で見る画面(記録はある。要るなら次の仕様)
- 組織ごとに違う規約(個別の契約書)・言語ごとの版
- 未成年者の同意(法定代理人)・同意の撤回(B2B で、使うのをやめる = 解約の手順)
- クッキーの同意(Cookie バナー)。いまはログインの Cookie だけで、広告・分析の Cookie を使っていない
- お知らせのメールを決まった日に自動で送る(運営がコマンドで送る。送る日は手順書)

## 決めたこと

- 範囲は依頼(2026-10-22)のとおり: 文書の版(種類・版・効力の日・変更の要約・同意し直しが要るか)・本文はリポジトリの Markdown・同意の記録(誰が・どの版に・いつ・どの画面から・会社としてか個人としてか)・足すだけの表と監査ログ・同意し直しの関所(二段階認証の「設定待ち」と同じ形)・代理の社員は対象外・前もってのメールと帯・登録の画面での同意。
- 何を「重要な変更」とするか・予告の日数・会社と個人の分け方・同意しない人の扱いは、事業判断と法務の確認が要るので、設計書の未確定事項に仮決めで置く(人の答えを待つ)。
