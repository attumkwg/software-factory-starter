# 仕様: 依頼ごとの進み具合の管制(n/m・依存の順番・完成の判定・止まった PR の見張り)

> 状態: 完了(実装済み)
> 道具: `pnpm progress`(`scripts/progress.mjs`)・毎朝と子が閉じたとき `.github/workflows/progress.yml`
> 穴 G-134(`docs/scenarios/gaps.md`)。ロードマップ [../kit/roadmap.md](../kit/roadmap.md) の 6 の「足りない物 4」と、4 の「工場の KPI」の入力「依頼から届くまでの日数」。`/new-feature` の親子の Issue の上に積む。

## 第1部 PdM が書く所(業務の要求・業務ルール)

### なぜ作るか

- ペルソナ: キットを使ってプロダクトを作る人(持ち主・PdM・代表)
- 動かす KPI: (キットの物差し: 依頼から届くまでの日数・無人化率)
- 大きな依頼を子の Issue・PR に割った後、何本中何本が済んだか・どれがどれを待つか・いつ完成と言えるかが見えない。止まった PR に誰も気づかない。北極星の入力「依頼から届くまでの日数」も数えられない。

### 業務の要求

- 依頼(親 Issue)ごとに、子が何本中何本済んだか(n/m)が親 Issue を開けば分かる
- 次に進められる子(待つ相手が全部閉じた子)と、何を待っている子かが分かる
- 完成(出してよい)の判定が、子が閉じたことだけでなく受け入れまでで決まる
- 止まった PR(動いていない)と、進められるのに PR が無い子に気づける
- 依頼から届くまでの日数を数えられる

### 業務ルール

- 子の一覧は親 Issue の本文に1行1つ。先に閉じる子は「(待つ: #番号)」で書く — `/new-feature` が作る形をそのまま読む(別の台帳を作らない)
- 完成 = 子が全部閉じた+受け入れの記録(`docs/acceptance/`)の頭に「親 Issue: #番号」 — 受け入れが「出してよいか」の確かめ(`docs/guides/acceptance.md`)
- 止まった = PR が2日動いていない・進められるようになって2日 PR が無い — 1 PR は半日〜1日の大きさなので、2日は詰まり
- 依頼から届くまでの日数 = 親 Issue を開いた日から、受け入れの最後の回の日まで。8週のうちに完成した物の中央値を見る
- 進み具合は親 Issue の本文の囲い(`<!-- progress:start -->`〜`end`)の中だけを書き直す — 人が書いた要約と子の一覧には触らない

### 受け入れ条件(業務の言葉で)

- [x] `pnpm progress` が、開いている親 Issue ごとに n/m・状態(進行中 / 受け入れ待ち / 完成)・依頼からの日数・次に進められる子・止まった数を出す
- [x] `pnpm progress --write` が、親 Issue の本文に「📍 進み具合」を書く(2回流しても1つ)。`progress.yml` が毎朝と、Issue が閉じた・開き直したときに流す
- [x] 一覧に無い子を待つ・依存が輪になっている親は、進み具合に ⚠️ で出る
- [x] 受け入れの記録の型(`docs/acceptance/_template.md`)と `/accept` に「親 Issue: #」があり、`/new-feature` が子の一覧に「待つ」を書く
- [x] 依頼から届くまでの日数の中央値が出る(完成が無ければ「まだ」)

### 要配慮個人情報

- 当たらない(Issue・PR の番号と題・日数だけ)。

### やらないこと

- 止まった PR を AI に自動で直させる(見張って知らせるまで。直すのは今までどおり AI のセッション)
- GitHub の sub-issues(親子の機能)を使う(REST の形がまだ変わりうる。本文の一覧で足りる)
- 子が閉じたら親を自動で閉じる(閉じるのは受け入れの後に人か AI)

### 決めたこと

- (AI が決めた)子の一覧は親 Issue の本文から読む(`/new-feature` が既に書いている。台帳を増やさない)
- (AI が決めた)止まったと見るのは2日。1 PR は半日〜1日の大きさ(`/new-feature` の 6)
- (AI が決めた)完成の日は受け入れの最後の回の日(本番に出た日ではない。デプロイと Issue をつなぐ物がまだ無い)
- (AI が決めた)書き直すのは開いている親だけ。届くまでの日数には、8週のうちに閉じた親も入れる

## 第2部 AI が網羅して書き、エンジニアが見る所(システムの振る舞い)

### 状態 × 操作

| 状態 \ 操作 | `pnpm progress` | `--write` |
|---|---|---|
| 子の一覧が無い親 | 出さない | 書かない |
| 子が1つでも開いている | 進行中・n/m・次・待つ | 囲いを書く |
| 子が全部閉じた・受け入れの記録が無い | 受け入れ待ち | 「/accept で受け入れ」を書く |
| 子が全部閉じた・受け入れの記録あり | 完成・受け入れの日までの日数 | 受け入れの記録へのリンクを書く |
| 待つ相手が一覧に無い・輪 | ⚠️ を出す | ⚠️ を書く |
| 開いた PR(Closes #子)が2日以上動かない | 止まった +1 | ⏸ を書く |
| 進められる子に PR が無く2日以上 | 止まった +1 | ⏸ を書く |
| 中身が前と同じ | — | 書かない(Issue を無駄に直さない) |

### 境界値

- 止まった: ちょうど2日で止まった(切り捨ての日数 ≧ 2)
- 進められるようになった日: 待つ子のいちばん遅い閉じた日。待たない子は子を作った日
- 中央値: 偶数個なら真ん中の2つの平均
- 子の行: 箇条書き(`- `・`* `・`1. `・`- [ ] `)の頭が `#番号` の行だけ。同じ番号は1回

### 権限の組み合わせ

- `progress.yml`: contents read・issues write(親の本文)・pull-requests read。秘密は使わない
- 定期と Issue の出来事で動くのは KIT_ROLE=product のリポジトリだけ

### 悪用のされ方(STRIDE で1行ずつ)

| 観点 | どう悪用されうるか | どう防ぐか(テスト / ルール) |
|---|---|---|
| 改ざん | 親の本文に偽の囲いを書いて、完成に見せる | 囲いは毎回作り直す(中身は子の Issue の状態と受け入れの記録から。`progress.test.mjs`) |
| 改ざん | 受け入れの記録に別の親の番号を書いて完成にする | 受け入れの記録は PR で入る(レビューと CI を通る) |
| 妨害 | 依存を輪にして、次に進める子を無くす | ⚠️ で出す(`orderProblems`) |
| 情報漏えい | 進み具合に Issue の本文を写す | 番号・題・日数だけ |
| なりすまし・否認・権限昇格 | 該当なし | — |
