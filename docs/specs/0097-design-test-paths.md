## 第1部 PdM が書く所(業務の要求・業務ルール)

### なぜ作るか

- ペルソナ: キットを使ってプロダクトを作る人(持ち主・PdM)と、レビューする人
- 動かす KPI: (キットの物差し: 受け入れで見つかる外れの数・人の介在率。守り: 事故 0件)
- 受け入れで、レビューの観点の台帳にある2つの観点の外れが見つかった。どちらも機械では確かめていなかった。
  - 要求との対応: 設計書の「7. 要求との対応」に「管理者でない人には操作が出ない」を「子3 画面の単体テスト」で確かめると書いたが、そのテストは作られなかった。member・viewer が設定の画面を開くと 500 になった(#186)。
  - 監査ログ: API の名前があるかは確かめていたが、画面の文の一覧に名前が足りず、監査ログの画面に名前がそのまま出た(#187)。
- 人のレビューで毎回拾うのは無理がある。機械で落とせる所は機械で落とす。

### 業務の要求

- 設計書の受け入れ条件ごとに、どのテストのファイルで確かめるかが書いてあり、作り終えた時点でそのファイルがある。テストで確かめない行は、人が確かめる理由が書いてある
- 監査ログの名前を足したら、画面の文も足さないと CI が落ちる

### 業務ルール

- 「要求との対応」のテストの欄には、テストのファイル(名前に `.test.` か `.spec.`)のパスを書く — 通り名(「画面の単体テスト」)やテストでないファイルでは、作り忘れても誰も気づかない
- テストを書かずに人が確かめる行は「(手で確かめる: 理由)」と書く。止めないが、出力に並べて人の目に見せる — 文書の中身など、テストにならない受け入れ条件もある
- 書いたファイルが無くても、作り終える前なら止めない。設計書か、設計書が指す仕様の状態を「完了」にした時点で無ければ止める — 設計書は実装より先に入る(仕様の PR)ので、最初から求めると設計が書けない。作り終えた PR で直すのは仕様の状態のことが多いので、仕様の「完了」でも見る
- 確かめるのは変えた設計書だけ(新しい物・「要求との対応」か状態を変えた物・この PR で「完了」にした仕様を指す物) — 昔の設計書は通り名で書いた物が多い。触ったときに合わせる
- 監査ログの名前は、API の一覧(関所の名前・手で残す名前・代理の社員の読み)の全部に画面の文がある — 画面に名前のまま出ると、お客さんの情シスが読めない

### 受け入れ条件(業務の言葉で)

- [x] 「要求との対応」の行のテストの欄にファイルのパスが無い設計書を足す・直すと、CI が落ち、どの行かを日本語で出す
- [x] 設計書か指す仕様の状態を「完了」にした PR で、書いたパスのファイルが無いと CI が落ちる。それより前は「まだ無い」と出すだけで通る
- [x] 「(手で確かめる: 理由)」と書いた行は落ちずに、出力に並ぶ
- [x] 文の直しだけで昔の設計書に触れても、CI は落ちない
- [x] API の監査ログの名前に画面の文が無いと、画面の単体テストが落ちる。今足りない名前(タスクが完了したメールを止めた・戻したほか)に文を足した
- [x] 設計書のひな形・設計の手順・レビューの観点の台帳に、この2つを書いた

### 要配慮個人情報

- 当たらない(設計書の文とファイルのパス、監査ログの名前だけ)。

### やらないこと

- 昔の設計書(パスを書いていない物)を全部直す(触ったときに合わせる)
- テストの中身が受け入れ条件どおりかを機械で見る(パスがあることまで。中身は人と AI のレビュー)
- #186(設定の画面の 500)を直す(別の PR)

### 決めたこと

- (持ち主が承認 @attumkwg 2026-10-29 会話で回答「仕様が完了なら見る・緩めは承認」)確かめるのは変えた設計書だけ(昔の設計書の全部は見ない)。無いファイルは、設計書か指す仕様が「完了」になってから落とす。どちらも、元の依頼(全部の設計書で・書いたファイルがあること)より緩めた所
- (持ち主が決めた @attumkwg 2026-10-29 会話で回答「テストだけ数え、手も書ける」)パスに数えるのはテストのファイルだけ。テストにならない行は「(手で確かめる: 理由)」と書ける
- (AI が決めた)比べる元は、CI では PR を合わせたコミットの1つ目の親(`HEAD^1`)、手元では `origin/main`。重い検査の要不要(`ci-scope.mjs`)と同じ取り方
- (AI が決めた)パスはリポジトリの根からでも、各パッケージ(`apps/*`・`packages/*`)の中からでもよい。昔の設計書は `apps/api` の中から書いている。「/」で始まる物・「..」を含む物はリポジトリの外を指すので落とす
- (AI が決めた)比べる元が無い(最初のコミット)ときは、見ずに通す(`ci-scope.mjs` と同じ向き)。浅い checkout で元が読めないときは落とす

## 第2部 AI が網羅して書き、エンジニアが見る所(システムの振る舞い)

### 状態 × 操作

| 設計書か仕様の状態 \ 表の行 | テストのパスも「手で確かめる」も無い | 「手で確かめる」だけ | パスはあるがファイルが無い | ファイルがある |
|---|---|---|---|---|
| どちらも完了でない | 落ちる | 出すだけ(通る) | 出すだけ(通る) | 通る |
| どちらかが完了 | 落ちる | 出すだけ(通る) | 落ちる | 通る |

### 境界値

- パスに数える物: 「`」で囲み、「/」を含み、空白が無く、ファイル名に `.test.` か `.spec.` がある物。`mail.int.test.ts`(ファイル名だけ)・`audit-coverage`(通り名)・`pnpm gaps`(コマンド)・`scripts/design-tests.mjs`(テストでない)は数えない。「/」で始まる・「..」を含むパスは落ちる
- 「(手で確かめる: 理由)」: 半角の括弧と「:」。理由が空なら書いていないのと同じ(落ちる)
- 状態: 「> 状態:」の行の頭の言葉(下書き・承認済み・完了)だけを比べ・読む。承認した人の書き換えでは見ない。新しい設計書でこの行が無い・読めない(全角の「：」など)なら落ちる
- 指す仕様: 設計書の「> 仕様:」の行の最初の `../specs/…` のリンク
- 「要求との対応」の節・表・「テスト」の列が無い・行が無い: 落ちる
- 見る設計書: `docs/designs/` の直下の `.md`。`_template.md`・README は見ない。消した物は見ない
- 元と比べられない: 浅い checkout・元が読めない(手元で fetch していない)なら落ちる。最初のコミット(親が無い)なら「比べる元が無い」と出して通す
- 監査ログの名前: `apps/api/src/audit/actions.ts` のコメント以外の行の、「"」で囲んだ点つきの名前(行の終わりの `//` の後ろは見ない)。拾った中に `project.create`・`auth.login`・`support.read` が無ければ拾い方が壊れたとみなして落ちる
