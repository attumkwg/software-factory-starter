## 第1部 PdM が書く所(業務の要求・業務ルール)

### なぜ作るか

利用者1人から「私のデータを消して」と求められたとき(個人情報保護法 35条)、いまは手順書の SQL を2人で手で打つ。表が増えると SQL が古くなり、消し残しに気づけない。試し(どこに何件あるか)はもうあるので、**同じ一覧で消す**コマンドにする。消すときの扱い(匿名化・削除・残す)は設計書 0048 の U-2 で承認済み。

- ペルソナ: お客さんの管理者(本人から求めを受ける)・運営(お客さんの指示で手伝う)
- 動かす KPI: 該当なし(守り。本物の個人データを持つ最初の組織が来る前に要る)

### 業務の要求

- 運営は、お客さんの管理者の書面の指示を受けて、1人分のデータを1つのコマンドで消す・匿名化できる
- お客さんの管理者は、自分の組織の監査ログで「いつ消したか」を見られる

### 業務ルール

- 既定は試し(何も変えない)。本当に消すのは明示の引数があるときだけ — 戻せない操作を打ち間違いで流さない
- 本当に消すときは、試しで出た数を引数で渡し、数が違えば何も変えない — 試しの結果を2人で読み合わせた物と、流す物を同じにする
- 消す・残すの扱いは試しの一覧と同じ(U-2): 本人の行と招待のメールは匿名化、本人だけの記録は削除、監査ログ・規約への同意・作った人や許可した人の ID は残す — ほかの行が本人を指しているので行は残し、値だけを置き換える
- 匿名化した人は止める(ログインできない・契約の人数に数えない) — 名前もメールも無い人が組織に「いる」ことにしない
- 監査ログに、消したこと・件数だけを残す(名前・メールは残さない) — いつ求めに応じたかの証拠
- 運営の組織の人(社員)は、このコマンドでは消さない — 社員の名前は各組織の入室の記録にも写っていて、組織1つの中では消しきれない

### 受け入れ条件(業務の言葉で)

- [ ] 運営が `person-data <組織の ID> <利用者の ID>` を流すと、これまでどおり数えるだけで何も変わらない
- [ ] 運営が `--execute --confirm-rows <試しの anonymize と delete の合計>` を付けると、試しの一覧の扱いのとおりに消す・匿名化する。数が違えば何も変えずに止まる
- [ ] 消した後に試しを流し直すと、`delete` の行が0
- [ ] 消した後、その組織のどの個人情報の列(列の分類の `personal`)にも、本人の名前・メール(変える前のメールも)が残らない
- [ ] お客さんの管理者が監査ログを開くと「本人の求めで、その人のデータを消した」が件数つきで1行ある
- [ ] お客さんの管理者が「組織の人」を開くと、その人は「削除した利用者」で、止めた状態
- [ ] ほかの組織の同じ形の行は変わらない
- [ ] 一覧の表に personal の列が増えたのに、置き換える・残す理由のどちらにも無ければ CI が落ちる
- [ ] 手順書の 5 を、手で打つ SQL からこのコマンドに直す

### 要配慮個人情報

- 当たらない(要配慮の表(スキーマ `sensitive`)には、いまは利用者を指す列が無い。足したときは一覧・消す列・手順書に足す)。

### やらないこと

- Cognito の利用者を消す(いままでどおり手順書の 5 で人が `admin-delete-user`。DB より先に)
- バックアップ・ログの中から1人分を消す(できない。保存期間で消える)
- 運営の社員を消す(社員が辞めたときの手順で別に扱う)
- 本人が画面から直接求める窓口・API

### 決めたこと

- 消すときの扱いは U-2(設計書 0048。@attumkwg が 2026-10-25 に承認)のまま。
- 同じコマンドに `--execute` を足す形にした(ADR 0088)。

## 第2部 AI が網羅して書き、エンジニアが見る所(システムの振る舞い)

### 状態 × 操作

| 状態 \ 操作 | 試し | `--execute --confirm-rows n` |
|---|---|---|
| その組織にいる(n が試しと同じ) | 数える | 消す・匿名化・監査ログ |
| その組織にいる(n が違う) | 数える | 止まる(何も変えない) |
| その組織にいない(他社の人・無い ID) | `found: false` | 止まる(他社にいるかは言わない) |
| もう消した人 | `delete` が0(匿名化の行だけ数える) | もう一度流せる(消す物は無い。監査ログは1行増える) |
| 運営の組織 | 数える | 止まる |

### 境界値

- `--confirm-rows`: 整数でなければ止まる。0 も受け付ける(もう消した人の流し直し)
- 引数の ID: UUID の形でなければ止まる(これまでどおり)

### 権限の組み合わせ

API は作らない(運営のコマンドは表の持ち主の接続で、ECS の1回きりのタスクとして人が流す)。権限の表に足す行はなし。

- [ ] 他社(別の組織)の行は数えず、変えない(組織の文脈と、条件の `tenant_id` の両方で絞る)

### 悪用のされ方(STRIDE で1行ずつ)

| 観点 | どう悪用されうるか | どう防ぐか(テスト / ルール) |
|---|---|---|
| なりすまし | 本人を名乗る他人が消させる | 求めはお客さんが受けて本人を確かめ、運営は書面の指示でだけ流す(手順書の 1) |
| 改ざん | 違う人を消す・試しの後で行が変わる | 引数は ID。試しの数を `--confirm-rows` で渡し、違えば止まる。結合テスト |
| 否認 | 「消した・消していない」 | その組織の監査ログに `person.erase`(件数だけ)。結合テスト |
| 情報漏えい(他社のデータ) | 他社の人の有無が分かる・他社の行を消す | その組織の文脈で。いなければ「いません」だけ。結合テスト |
| 情報漏えい | 出力・ログ・監査ログに名前やメール | 出すのは表と列の名前・件数・扱い・ID だけ。結合テスト「値が入らない」 |
| 妨害 | 重い削除 | 1人分で十数本の SQL。1つのトランザクション。運営が手で流す |
| 権限昇格 | 社員が消すのを口実に中身を見る | コマンドは件数だけを出す |
