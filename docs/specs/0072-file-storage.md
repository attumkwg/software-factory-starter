## なぜ作るか

看板の A 社(工務店向けの現場の写真と日報)の中核は「現場の写真を上げて、事務所と職人で見る」なのに、キットには写真・ファイルを置く部品が無い。DB の行は RLS で組織ごとに分かれるが、**S3 の中身は RLS の外**にあり、キーの付け方・URL の出し方を1つ誤ると、他社の写真がそのまま見える(6-5 の「別の会社の現場の写真が見えた」)。写真には撮った場所(GPS)が入っていて、施主の家の位置が漏れる。各社が自分で作ると、ここで事故が起きる。

## 受け入れ条件

> キットの題材(TODO)に合わせて「タスクに付けるファイル」として作る。題材を差し替えたら、付け先(タスク)を自分の物(現場・日報)に置き換える。

上げる:

- [ ] member・admin がタスクにファイル(写真・PDF)を上げると、API が**その組織の置き場の、新しいキー**への短い期限(5分)の署名つき URL を返し、画面はそこへ直接上げる。URL は認可の関所を通った後でだけ作る
- [ ] 上げられるのは決めた種類(JPEG・PNG・WebP・PDF)と大きさ(1つ 20MB まで)だけ。言った種類・大きさと違う物は、上げても見られる状態にならない(断られる)
- [ ] 上げ終えたと伝えると、API が中身を読み直して、**中身の種類が言った種類と同じか**を確かめ、写真なら**位置情報などの付いた情報(EXIF・XMP・PNG の文字の欄)を消して**から、見られる状態にする。向き(回転)だけは残す
- [ ] viewer は上げられない(403)

見る・消す:

- [ ] viewer・member・admin はタスクのファイルの一覧を見られ、見られる状態のファイルには短い期限(5分)の署名つき URL が付く。期限が切れたら、もう一度 API に聞く
- [ ] 上げた本人(member)は自分のファイルを消せる。admin は組織の誰のファイルでも消せる。member は他人のファイルを消せない(403)
- [ ] タスク・プロジェクトを消すと、付いていたファイルも消える(置き場の中身も、後から自動で消える)
- [ ] 消したファイルの中身は、置き場の「前の版」として **30日**残り、それを過ぎると自動で消える(誤って消したときに運営が戻せる)

他社:

- [ ] 他社の人は、ファイルの ID・タスクの ID を知っていても、一覧・URL・消すのどれも 404(存在を言わない)
- [ ] API が作る署名つき URL は、いつもセッションの組織の置き場の中だけを指す。リクエストの値(URL・本文・ヘッダー)で置き場のキーは決まらない
- [ ] 署名つき URL のキーを書き換えて他社のファイルを指しても、置き場が断る(署名が合わない)。**これを本物と同じ取り決めの置き場(S3 互換の RustFS)に向けた結合テストで確かめる**

解約・書き出し・記録:

- [ ] 解約の削除のコマンド(`delete-tenant`)は、DB を消す前に、その組織の置き場の中身を**前の版も含めて全部**消す。試しでは数えるだけ
- [ ] 組織のデータの書き出しに、ファイルの一覧(名前・種類・大きさ・上げた人の ID・時刻)が入る
- [ ] 上げる・上げ終える・消すは、その組織の監査ログに残る(名前・中身は残さない)
- [ ] ログ・監査ログ・送信待ちの出来事に、ファイルの名前・中身・署名つき URL を出さない

## 権限の表に足す行

| API | admin | member | viewer | 他社 | 未ログイン |
|---|---|---|---|---|---|
| `GET /api/tasks/{taskId}/files` | 200 | 200 | 200 | 404 | 401 |
| `POST /api/tasks/{taskId}/files` | 201 | 201 | 403 | 404 | 401 |
| `GET /api/files/{fileId}` | 200 | 200 | 200 | 404 | 401 |
| `POST /api/files/{fileId}/complete` | 202(自分の物) | 202(自分の物)/ 403(他人の物) | 403 | 404 | 401 |
| `DELETE /api/files/{fileId}` | 204 | 204(自分の物)/ 403(他人の物) | 403 | 404 | 401 |

## 要配慮個人情報

- **使う会社が答える**(設計書の U-6 は「導入時に決める」)。キットの既定は「当たらない」(A 社の現場の写真)で、キットの持ち主が承認した(@attumkwg 2026-10-27)。ただし写真には人・表札・書類が写りうるので、中身は `personal` として扱う(設計書の U-6)。病院の B 社のように診察の写真・紹介状を置くなら、要配慮の置き場(ADR 0029 と同じ、組織ごとのデータ鍵で暗号化)を別に作る(この仕様の範囲外)。

## 悪用のされ方(STRIDE で1行ずつ)

| 観点 | どう悪用されうるか | どう防ぐか(テスト / ルール) |
|---|---|---|
| なりすまし | 他人の署名つき URL を盗んで見る | 期限 5分・URL は API の応答にだけ出し、ログ・監査ログ・出来事に入れない(`files.int.test.ts` でログを確かめる) |
| 改ざん | 上げる URL で、言った物と違う物(HTML・大きな物)を置く | 署名に種類と大きさを含める・上げ終えた後に API が中身を読み直して種類を確かめ、違えば断って消す。見せるのは API が書き直した物だけ(ADR 0080) |
| 否認 | 「消していない」 | 上げる・上げ終える・消すを監査ログに残す |
| 情報漏えい(他社のデータ) | ファイルの ID・キーを推して他社の写真を取る。写真の GPS で施主の家が分かる | キーを作る関数は1つ・組織の ID はセッションから・他社は 404・署名の書き換えは置き場が断る(S3 互換の RustFS の結合テスト)・EXIF を消す |
| 妨害(重い処理・大量の要求) | 大きな物・大量の物を上げて費用を増やす | 1つ 20MB・署名に大きさ・上げ終えない物は置き場が1日で消す・費用のページとアラーム(設計書の U-2) |
| 権限昇格 | member が他人の写真を消す・viewer が上げる | `policy.ts` の権限と「自分の物か」の判断・権限の表のテスト |

## やらないこと

- 画面(タスクの画面のファイルの欄)。題材を差し替えるときに、付け先の画面と一緒に作る。API と OpenAPI が取り決め
- 写真の縮小版(サムネイル)・画像の変換(HEIC → JPEG など)・動画
- PDF の中の付いた情報(作った人など)の削除・ウイルスの検査(設計書の「次の一歩」)
- 組織ごとの合計の上限(容量のプラン)。費用のページで見る(設計書の U-2)
- 要配慮個人情報の写真の置き場
- 中身の一括の書き出し(zip)(設計書の U-4)
