# 仕様: 入社・退職・役割の変更のアカウントの手順

> 状態: 承認済み(承認した人: @attumkwg 2026-10-25。U-1・U-2 はキットの既定として承認し、導入時に決める)
> 設計: [docs/designs/0034-joiner-leaver.md](../designs/0034-joiner-leaver.md)

## なぜ作るか

- 人が入る・辞める日に、GitHub・AWS・Sentry・運営の組織(代理ログイン)・Slack のアカウントを作る・止める手順が無い(想定の場面の 6-9・7-1)。基本方針は「その日のうちに外す」と言うが、何をどの順で外すかが無い。
- 点検の台帳には四半期ごとの棚卸し(`access-review`)しか無く、辞めた人のアカウントが次の棚卸しまで(最長3か月)残りうる。
- 会社のメールを止めても、パスワードと二段階認証でほかの道具には入れてしまう。

## 受け入れ条件

- [ ] `docs/runbooks/joiner-leaver.md` に、人ごとのアカウントがある道具の一覧(AWS・GitHub・運営の組織・Sentry・Slack・Claude・会社のメール)と、役割(エンジニア・CS と営業)ごとに何を渡すかの表がある
- [ ] 入る日の手順(誓約と教育の後・要る物だけ・prod は最初は渡さない・二段階認証)がある
- [ ] 役割が変わる日の手順(減る物はその日に外す)がある
- [ ] 辞める日の手順が、届く範囲の広い順にあり、運営の組織は Cognito を止めてから DB の行を消すコマンドがある。秘密の入れ替え・管理者が2人残るか・点検の担当者の付け替え・端末の返却を含む
- [ ] いつ止めるか(本番に届く物と、ほか)と、止めたアカウントを消すまでの日数がある
- [ ] 1人1回1枚の記録の型があり、名前が入るので公開のリポジトリに置かない、と書いてある。記録の置き場の表(`compliance/records/README.md`)に1行
- [ ] 点検の台帳に、毎月「入った・辞めた人はいたか」を聞く項目が1つあり、`docs/checkup/README.md` と適用宣言書が作り直してある
- [ ] 基本方針の「人の出入り」と、点検の `access-review` から手順書を指す

## 悪用のされ方(STRIDE で1行ずつ)

| 観点 | どう悪用されうるか | どう防ぐか(テスト / ルール) |
|---|---|---|
| なりすまし | 辞めた人が、残ったアカウントで本番やお客さんの画面に入る | 辞める日に全部止める(本番に届く物は辞めると決まった日)。毎月の点検で漏れを聞く |
| 改ざん | 辞めると決まった人が、本番の権限で設定やデータを変える | 本番に届く物は辞めると決まった日に外す(U-1) |
| 否認 | 「その操作は自分ではない」 | 人ごとのアカウント(共有しない)。止めても 90日は消さない(U-2)。監査ログと管理操作の記録は ID で残る |
| 情報漏えい(他社のデータ) | 辞めた人が、知っていた秘密やトークンで入る / 記録に名前が入り、公開のリポジトリに載る | その人が読めた秘密を替える。記録は公開のリポジトリに置かない |
| 妨害(重い処理・大量の要求) | 管理者が1人だけ残り、その人がいないと誰も直せない | 辞めた人が管理者なら、2人残るかを確かめる(`acct-two-admins`) |
| 権限昇格 | 入った人に、最初から prod の権限を渡す | prod は最初は渡さない(当番になるとき・要るときに足す) |

## やらないこと

- 道具の側の自動の連携(人事の仕組みから道具のアカウントを自動で作る・止める。人数が増えたら)
- 入った人が最初に読む順番(`docs/getting-started.md` と README で足りる)
- 想定の場面(`docs/scenarios/`)の判定と穴の一覧の書き換え(場面の持ち主が直す)
