# 仕様: 受け入れを点数にし、外れた理由を分けて書き戻す

> 1つの仕様 = 1つ以上の Issue。大きければ親 Issue → 子 Issue に割ってから AI に渡す。
> 状態: 下書き
> **書く人を「説明の責任」で分ける**([concepts/people-and-ai.md の 1.1](../concepts/people-and-ai.md#11-段を決める問い説明の責任))。第1部は PdM が書く(なぜそうするかをチームに説明できる物)。第2部は AI が網羅して書き、エンジニアが見る(PdM は読まなくてよい)。
> **印**: 何も付けない行 = 確定。`(仮説)` = まだ確かめていない思い込み。`(未確定 U-n)` = 決まっていない(中身は設計書の「未確定事項」の U-n)。

## 第1部 PdM が書く所(業務の要求・業務ルール)

### なぜ作るか

作った機能を「出してよいか」確かめる受け入れが、いまは形も記録も無い。PdM が全部を見ると PdM が詰まり所になり、見た結果も残らないので、同じ種類の外れ(仕様の書き漏らし)が次の仕様でも起きる。

### 業務の要求

- PdM は、受け入れで **PdM にしか判断できない項目を中心に** 見る。網羅が要る確かめは AI と QA に回すのがおすすめ。
- 受け入れの結果が **点数**(合った項目の割合)で残り、回ごとに比べられる。
- 外れた項目ごとに **なぜ外れたか**(要求 / 設計 / AI の仮決め / 実装)が残る。
- 要求のせいで外れた物は、**解決済みの論点**として残り、次の仕様を書くときに AI が読む。

### 業務ルール

- PdM に回す観点のおすすめは4つ: ① 今の操作の流れで仕事が終わるか ② 意図したルールが守られているか ③ 作り込みすぎていないか ④ AI の仮決めのうち製品の判断が要る物 — 網羅が要る確かめ(状態 × 操作・境界値・スマホ・アクセシビリティ・プラン別・ロール別・URL の直打ち)は PdM が説明の責任を持てる物ではないので、AI と QA に回すのがおすすめ。**固定はしない**(どの観点が効くかはチームで違う。外れても CI は落とさず、`pnpm acceptance` が知らせるだけ)。
- 外れた理由は4つに分ける — 直す工程が違うから(要求はナレッジと仕様・設計は設計書・AI の仮決めは未確定事項・実装はコード)。
- 要求のせいの外れは、必ず解決済みの論点に書き戻す — 書き戻さないと、次の仕様で同じ穴を作る。
- 点数は改善のための数で、人や機能の良し悪しを決める数にしない — 人の評価に使うと、項目を甘くする動きが先に起きる。

### 受け入れ条件(業務の言葉で)

- [ ] PdM が `/accept` を始めると、仕様と設計書から受け入れの項目が作られ、おすすめの観点で PdM と AI・QA に振り分けた案が出る。PdM はほかの観点も自分に回せる。PdM の項目は1問ずつ出る
- [ ] AI・QA の項目は、AI が確かめた結果か、QA に渡す一覧として同じ記録に残る
- [ ] 回を終えると、PdM の項目・AI と QA の項目・全体の点数が記録に残る
- [ ] 外れた項目には理由(4つのどれか)と書き戻し先が残る
- [ ] 要求のせいの外れは、解決済みの論点に1行足される(番号つき)
- [ ] 次に `/new-feature` で仕様を書くとき、AI が解決済みの論点を読む
- [ ] 記録の書き方が崩れていたら CI が落ちる(見る人・結果・理由が決まった言葉でない・要求のせいなのに書き戻し先が無い)。観点がおすすめから外れている所は知らせるだけ
- [ ] 記録を取るかは使うときに決められる(キットは型と置き場を用意する。記録が0件でも何も落ちない)

### 要配慮個人情報

- 当たらない(記録は項目と合否と理由だけ。利用者のデータ・画面の中身は書かない)

### やらないこと

- 週の数字(`pnpm metrics`)に点数と理由の内訳を出すこと(仕様 0077 で引き渡しの数字と一緒に)
- 試作(`prototypes/`)の受け入れ。試作は相手(お客さん)に見せて賭けの線で判断する物で、この記録の対象は作った機能
- QA の人の作業の割り振り(誰が・いつ)

### 決めたこと

- 本人の依頼(学びをキットに入れる5本の3本目)で作る。
- PdM の観点は固定せず、おすすめにする(@attumkwg 2026-10-27。会話で回答「おすすめ観点ぐらいに」)。設計書 0075 の U-1
- 記録を取るかは使うときに決める。キットの既定はリポジトリに置き、機密は書かない(@attumkwg 2026-10-27)。設計書 0075 の U-2根拠は `docs/concepts/people-and-ai.md` の 1.1 と、この PR で足す `docs/concepts/line.md` の 2 の受け入れの行

## 第2部 AI が網羅して書き、エンジニアが見る所(システムの振る舞い)

### 状態 × 操作

| 項目の結果 \ 操作 | 回を閉じる(点数を出す) | 理由を書く | 書き戻し先を書く |
|---|---|---|---|
| 合 | 合に数える | 書かない(書いたら書き方の問題) | 書かない |
| 否 | 否に数える | 必須(4つのどれか) | 要求なら必須(`R-n`)。ほかは任意 |
| 未(まだ・見送り) | 点数の分母に入れない | 書かない | 書かない |

### 境界値

- 1回の項目が0件: 書き方の問題(空の回は作らない)
- 合と否が0件(全部が未): 点数は「—」(0% にしない)
- 回の日付: `YYYY-MM-DD`。同じ記録の中で前の回より前の日付は書き方の問題
- 解決済みの論点の番号: `R-1` から。消さない・使い回さない。受け入れの記録が指す `R-n` が論点の一覧に無ければ書き方の問題

### 権限の組み合わせ

該当なし(アプリの API は変えない。記録はリポジトリのファイル)。

### 悪用のされ方(STRIDE で1行ずつ)

| 観点 | どう悪用されうるか | どう防ぐか(テスト / ルール) |
|---|---|---|
| なりすまし | PdM の項目を AI が「合」と書いて PdM が見たことにする | PdM の項目の合否は `/accept` が PdM の答えからだけ書く(スキルの決まり)。PR のレビューで人が見る |
| 改ざん | 外れを「未」にして点数を上げる | 記録は足すだけ(前の回を書き換えない)。git の履歴で見える |
| 否認 | 誰が受け入れたか分からない | 回の頭に「見た人」(GitHub のユーザー名)を書く |
| 情報漏えい(他社のデータ) | 本番の利用者のデータや画面のスクショを記録に貼る | 記録に書くのは項目と合否と理由だけ(CLAUDE.md・docs/security.md の AI-6)。見る所はプレビューか stg |
| 妨害(重い処理・大量の要求) | 該当なし | ファイルを読むだけ |
| 権限昇格 | 該当なし | 該当なし |

> 設計(どう作るか)は [docs/designs/0075-acceptance-record.md](../designs/0075-acceptance-record.md) に書く(AI 用。網羅的に)。
