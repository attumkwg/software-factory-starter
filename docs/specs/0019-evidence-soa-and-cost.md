# 仕様: 証跡の自動収集・適用宣言書(SoA)・規程のひな形・コストのダッシュボード

> 状態: 下書き
> 設計: [docs/designs/0019-evidence-soa-and-cost.md](../designs/0019-evidence-soa-and-cost.md)・ADR: [0032](../adr/0032-evidence-and-cost-outside-the-repo.md)
> PR は2つに分ける: ① 証跡・SoA・規程・`/compliance-check` ② コストのダッシュボード(① の上に積む)

## なぜ作るか

- P マーク・ISMS を取るときは、「決めたとおりに回している」ことを**後から見せられる記録**(証跡)が要る。今のキットは守り(ブランチ保護・Environments・二段階認証・バックアップの訓練)はそろっているが、その時点の設定を残す仕組みが無く、審査の前に画面のスクショを集め直すことになる。
- ISMS の審査では、附属書 A の管理策ごとに「やる・やらない・なぜ・どうやって」を並べた**適用宣言書(SoA)**を出す。キットの部品・点検の台帳は多くの管理策に当たっているのに、その対応が1枚になっていない。
- 規程(基本方針・個人情報保護規程・委託先の管理・教育・内部監査・マネジメントレビュー)は、どの会社でも形がほぼ同じなのに、毎回ゼロから書いている。書いた後の「年1回の見直し」「教育」「内部監査」も忘れられやすい。
- 持ち主の言葉(2026-10-25):「今コストがいくらぐらいかかっているか、今動いているやつがこれでこれぐらいコストが投入されている、みたいなダッシュボード的なものを作れる仕組み」。AWS・GitHub Actions・AI・そのほかの SaaS の費用が、ばらばらの画面に散っていて、「何にいくら」が1枚で見えない。

## 受け入れ条件

### 証跡の自動収集(①)

- [ ] 毎月1日に、ワークフロー `evidence.yml` が、GitHub の設定(main のルールセット・Environments・共同作業者と権限・Actions の設定・守りの機能)・AWS の設定(IAM の要約・人の利用者の二段階認証と鍵の古さ・役割・Security Hub の点数・GuardDuty・バックアップの保管庫のロック)・訓練の結果(戻す訓練・ファズ・点検・脆弱性の検査の最後の実行)・点検の台帳の状態を、1か月ぶんの JSON にまとめる
- [ ] まとめた JSON は、使う側の AWS の**消せない S3**(Object Lock。証跡だけの置き場)に `evidence/<年>/<年-月>/` で置かれる。中身の SHA-256 を並べた目録(`manifest.json`)も一緒に置く
- [ ] 秘密の値(鍵・トークン・パスワード)は集めない。ログ(Actions の画面)には、集めた物の名前と件数だけが出て、中身は出ない
- [ ] ひな形のリポジトリ(`KIT_ROLE=template`)とセットアップの前は、定期の実行が飛ぶ。AWS の変数(役割と置き場)が無いリポジトリでも飛ぶ(落ちない)
- [ ] 1つの集め先が読めなくても(権限が無い・サービスが有効でない)、ほかは集めて置く。読めなかった物は目録に「読めなかった」と理由つきで残る
- [ ] 手元で `pnpm evidence --out <フォルダ>` を打つと、同じ物がフォルダに書かれる(置き場には送らない)
- [ ] 点検の台帳に「毎月の証跡が集まっているか」の項目があり、最後の成功から35日を過ぎると知らせる

### 適用宣言書(SoA。①)

- [ ] 附属書 A(ISO/IEC 27001:2022)の93の管理策を、1か所(`docs/compliance/controls.yaml`)に「適用する・しない・理由・このキットでの実施・根拠のファイル」で持つ
- [ ] 点検の台帳の項目に、当たる管理策の番号(`controls`)と、裏づけになる証跡の名前(`evidence`)の欄がある
- [ ] `docs/compliance/soa.md` は、管理策の一覧・台帳・規程から `pnpm compliance --write` で作られる。古ければ CI(`pnpm compliance`)が落ちる
- [ ] 根拠のファイルが無い・台帳や規程が無い管理策の番号を指している・証跡の名前が収集に無い・`docs/compliance/` の中の相対リンクが切れている、のどれかで CI が落ちる

### 規程と様式のひな形(①)

- [ ] `docs/compliance/policies/` に、基本方針・個人情報保護規程・委託先の管理・教育・内部監査・マネジメントレビューの議事録の型がある。どれも頭に版・責任者・制定日・最後の見直し・次の見直し・当たる管理策を持つ
- [ ] 規程の「次の見直し」の日を過ぎると、点検が知らせる

### `/compliance-check`(①)

- [ ] 担当者が Claude Code で `/compliance-check` と打つと、認証の準備の項目(期限の来た規程の見直し・教育・内部監査・マネジメントレビュー・委託先の見直し)だけを1問ずつ聞き、答えを点検の台帳に書いて PR にする(`/checkup` と同じ書き方)
- [ ] 認証を目指さない間(台帳の `compliance: false`)は、認証の準備の項目は毎週の点検に出ない。`/compliance-check` からは見られる

### コストのダッシュボード(②)

- [ ] 毎日、ワークフロー `cost.yml` が、AWS(Cost Explorer。環境ごと・AWS のサービスごと・賭けのタグ・PR ごとの環境)・GitHub Actions(ワークフローごとの分数)・そのほかの SaaS と AI の席など(台帳に手で書いた月額。AI の使用量を API で自動で取ることはしない — 持ち主の答え 2026-10-25)を、1つの JSON に集める
- [ ] 集めた JSON から、静的な HTML のページ(1枚)を作る。今月の合計・月末の見込み・見積もり(段階の表)と実績・何にいくら(動いている物ごと)・過去の月の並び、が見える
- [ ] ページと JSON は、使う側の**非公開の置き場**(AWS の S3)にだけ置く。公開のリポジトリ・公開の成果物・GitHub Pages には出さない。Actions の成果物にも、リポジトリが非公開のときだけ置く
- [ ] Terraform: 全部のリソースに既定のタグ(`Project`・`Environment`・`ManagedBy`・`Repository`・`Bet`)が付く。動いている物(api・web・mail・DB など)には `Component` が付く。コスト配分タグの有効化・費用の急な変化の見張り(Cost Anomaly Detection)を足す。予算(AWS Budgets)は今のまま
- [ ] 手元で `pnpm cost --out <フォルダ>` を打つと、同じ JSON と HTML がフォルダに書かれる

## 悪用のされ方(STRIDE で1行ずつ)

| 観点 | どう悪用されうるか | どう防ぐか(テスト / ルール) |
|---|---|---|
| なりすまし | PR のブランチのワークフローが、証跡の役割を引いて偽の証跡を置く | 役割は main からだけ引ける(OIDC の条件 `ref:refs/heads/main`)。PR の版は書き換えられるので信じない |
| 改ざん | 審査の前に、都合の悪い月の証跡を消す・書き換える | Object Lock(保存の期間の間は消せない・上書きしても前の版が残る)。目録の SHA-256 で中身の一致も見られる |
| 否認 | 「その時は設定していた」と言い張る・言い張られる | 毎月の設定の写しが、日付つきで消せない場所にある |
| 情報漏えい | 証跡や請求の詳細(使っているサービス・金額・人の名前)が公開のリポジトリやログに出る | 置き場は使う側の非公開の S3 だけ。ログは名前と件数だけ(テストで確かめる)。成果物は非公開のリポジトリのときだけ |
| 妨害 | Cost Explorer の呼び出し(1回 $0.01)を大量に流して費用を増やす | 呼ぶ回数は1日に決まった数だけ(10回まで)。手で流すのも main だけの役割 |
| 権限昇格 | 証跡を集める役割で、データ(DB・S3 の中身)を読む・書き換える | 役割は設定を読むだけ+証跡の置き場への書き込みだけ。データを読む操作は持たない |

## やらないこと

- 審査そのもの・審査機関とのやりとり・P マーク・ISMS の取得の判断(人と専門家)
- 規程の中身を自社に合わせること(ひな形まで。会社名・責任者・例外は人が埋める)
- 本番の DB の中身・利用者のデータを証跡にすること(設定と記録だけ)
- 請求書の PDF・支払いの詳細を集めること(金額の集計だけ)
- SaaS の費用を、その SaaS の API から自動で取ること(台帳に手で書いた月額)
- CloudWatch のダッシュボード(ADR 0032 で比べて、静的な HTML にした)
