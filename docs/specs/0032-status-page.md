# 仕様: 稼働状況のページの選び方と、障害の知らせとのつなぎ

> 状態: 承認済み(承認した人: @attumkwg 2026-10-25。U-1〜U-3 はキットの既定として承認し、導入時に決める)
> 設計: [docs/designs/0032-status-page.md](../designs/0032-status-page.md)・ADR: [0043](../adr/0043-status-page-outside-our-aws.md)

## なぜ作るか

- 障害のとき、お客さんが「いま落ちているのか」を自分で見られる所が無く、問い合わせが CS に集まる(想定の場面の 5-6)。障害は「直す」より「伝える」で信頼を失う。
- SLA の型([legal/sla.md](../legal/sla.md))は計画メンテナンスを7日前に知らせる決まりで、知らせる所が要る。

## 受け入れ条件

- [ ] `docs/guides/status-page.md` に、いつ要るか・選び方(自分の基盤と別か・独自のドメイン・載せる部品・更新のしかた・購読・公開か・稼働率の数字・費用・日本語)がある
- [ ] 入れる手順があり、委託先の台帳に書く1件の例(購読を使わないとき・使うときの違い)がある
- [ ] 障害の重さ(S1〜S3)と計画メンテナンスを、ページの状態といつ載せるかに対応させた表がある
- [ ] ページに載せる文は、`runbooks/incident.md` の 4 の型と同じ文にする決まりがある。他社のデータ・個人データの事故はページに書かない決まりがある
- [ ] `runbooks/incident.md` の 4(お客さんへの知らせ)と 5(終わり方)から、ページを指す

## 権限の表に足す行

該当なし(API を足さない)。

## 要配慮個人情報

- 当たらない(文書だけ。データを取らない)。

## 悪用のされ方(STRIDE で1行ずつ)

| 観点 | どう悪用されうるか | どう防ぐか(テスト / ルール) |
|---|---|---|
| なりすまし | ページのアカウントを乗っ取り、偽の障害やメンテナンスを載せる | 知らせる役だけに個人のアカウント(共有しない)。二段階認証は外のサービスの設定で |
| 改ざん | 稼働率の数字を見栄えよく出し、SLA の数字と食い違わせる | ページに稼働率を出さない(U-3)。SLA の正は sla.md の測り方 |
| 否認 | 「知らせが無かった」 | ページの履歴と、メールの第1報が同じ文で残る |
| 情報漏えい(他社のデータ) | 障害の文に他社の名前・内部の仕組み・漏えいの中身を書く / 購読のメールアドレスが外の会社から漏れる | incident.md の 4 の決まり(事実だけ・他社の名前を書かない)。漏えいはページに書かない。購読は最初は使わない(U-1) |
| 妨害(重い処理・大量の要求) | 障害のときに、ページが本番と一緒に落ちる | 自分の AWS と別の所に置く(ADR 0043) |
| 権限昇格 | 該当なし(文書だけ) | — |

## やらないこと

- 外のサービスを選ぶ・契約する(使う人が決める)。委託先の台帳に実際の1件を足す(使い始めたとき)
- 外形監視からページを自動で更新する仕組み
- 想定の場面(`docs/scenarios/`)の判定と穴の一覧の書き換え(場面の持ち主が直す)
