# 仕様: 組織の開通(運営のコマンド `create-tenant`)

> 状態: 完了(実装済み。未確定事項は設計書で答え済み。@attumkwg が 2026-10-27 に完了とした)
> 設計: [docs/designs/0026-tenant-provisioning.md](../designs/0026-tenant-provisioning.md)・ADR: [0039](../adr/0039-tenant-provisioning-command.md)
> 手順書: [docs/runbooks/tenant-provisioning.md](../runbooks/tenant-provisioning.md)。穴 G-01(`docs/scenarios/gaps.md`)。

## なぜ作るか

申し込みを受けた会社を本物の組織にする道が、本番の DB に SQL で `organizations.tenants` と `organizations.users` に行を足すことしか無かった(運営の組織の作り方と同じ)。CS が本番の DB を触り、打ち間違い(名前・メールの大文字・時間帯)が起き、監査ログにも残らない。解約には `delete-tenant`(試し → 名前の確認 → 実行)があるのに、始めの側に同じ形の物が無い。営業 → CS の受け渡し(申込書・事前登録の項目)をそのまま入力にできる形が要る。

## 受け入れ条件

- [ ] 運営(本番の AWS に入れる開発)は、申し込みの JSON を**非公開の S3 の決まった場所(申し込みの置き場)**に置き、コマンド `create-tenant <置き場のキー>` で、まず**試し**を流せる。**コマンドの引数に名前・メールを渡さない**(ECS のタスクの引数は CloudTrail に残るため。キーは申込番号などで、会社や人の名前を入れない)。試しは本番と同じ処理を流してから取り消すので、何も残らない
- [ ] 本番で落ちる理由(最初の管理者のメールアドレスが、もうどこかの組織で使われている など)は、試しでも同じに落ちる
- [ ] 本当に作るのは、同じキーに `--execute --confirm-name <組織の名前>` を付けたときだけ。名前が申し込みと違えば何も作らない
- [ ] 置き場の中身は、読み終えたら人が消す(手順書)。消し忘れても7日で消える。上書き・消した古い版も1日で消える
- [ ] 手元(local / test / preview)では、置き場の代わりに手元のファイルを読める
- [ ] 申し込みの JSON は `name`(組織の名前)・`timeZone`(既定 `Asia/Tokyo`)・`mfaRequired`(二段階認証を全員に必須にするか。既定 false)・`admin.email`・`admin.name`(最初の管理者)。**知らない項目(プラン・人数・始まりの日・申込番号など)は読み飛ばし、読み飛ばした項目の名前を出す**(申込書・事前登録の書き出しをそのまま渡せる)
- [ ] 項目が正しくなければ、どの項目かだけを言って止める(値は出さない)
- [ ] 1つのトランザクションで、組織と最初の管理者(ロール admin・メールは小文字・Cognito とはまだ結びつかない)を作る。途中で失敗したら何も残らない
- [ ] 同じ申し込みを2回流しても、2つ目は作らない(最初の管理者のメールが重なるので止まる)
- [ ] 作ったことを、**作った組織の監査ログ**と**運営の組織の監査ログ**の両方に「仕組みが・組織を作った」として残す(名前・メールは残さない。最初の管理者の ID だけ)
- [ ] 出力は JSON 1行(試しは時間帯・必須・読み飛ばした項目、本番はそれに組織の ID と最初の管理者の ID)。組織の名前とメールアドレスはログに出さない
- [ ] 最初の管理者は、Cognito で登録(確認コード)→ ログインすると、その組織の管理者として入れる。ほかの組織の物は見えない
- [ ] 最初の管理者への案内(登録の仕方)は、手順書の文の型で CS が送る(招待の画面 G-02 ができたら、仕組みで送る)

## 権限の表に足す行

なし(API は作らない。コマンドは表の持ち主の接続で、ECS の1回きりのタスクとして人が流す)。

## 要配慮個人情報

- 当たらない(組織の名前・管理者の名前とメールアドレス。要配慮の項目は申し込みに入れない。入っていても読み飛ばして DB に書かない)。

## 悪用のされ方(STRIDE で1行ずつ)

| 観点 | どう悪用されうるか | どう防ぐか(テスト / ルール) |
|---|---|---|
| なりすまし | 申し込みに他人のメールを書いて、その人の組織の管理者を作る | 作るのは users の行だけ。ログインできるのは、そのメールを Cognito で確かめた本人だけ(初めてのログインで、確認済みのメールが一致したときだけ結びつく。ADR 0007) |
| 改ざん | 違う申し込み(別の会社)で作る | 試しの出力と申込書を2人で見て、組織の名前を打って確かめる(`--confirm-name`) |
| 否認 | 「頼んでいない組織ができた」「誰が作った」 | 作った組織と運営の組織の両方の監査ログに残る。ECS のタスクを流した人は CloudTrail に残る |
| 情報漏えい(他社のデータ) | 作った組織から、ほかの組織の物が見える | RLS(新しい組織の文脈で書く)。結合テスト「ほかの組織の物は 404」 |
| 情報漏えい | ログに名前・メールが出る | 出力は ID・時間帯・必須・項目の名前だけ。項目の誤りも項目の名前だけ |
| 情報漏えい | 申し込み(管理者の名前・メール)が、消せない記録(CloudTrail の RunTask)や置き場に残り続ける | 引数は置き場のキーだけ(形を決めて、名前を入れられない)。置き場は非公開・自前の鍵・TLS だけ。読み終えたら消す・7日で消える。読めるのはコマンドの役割だけ(その置き場の中だけ) |
| 妨害 | 同じ申し込みを何度も流して組織が増える | 最初の管理者のメールの重なりで2つ目は止まる。コマンドは人が流す |
| 権限昇格 | 既にある組織の人を、別の組織の管理者にする | 1人 = 1組織(メールは全体で一意)。使われているメールでは作れない |

## やらないこと

- 画面・API からの申し込み(セルフサーブの登録)。契約を確かめてから運営が作る
- プラン・人数の上限・請求(G-03)。申し込みに書いてあっても読み飛ばす
- 申込書・事前登録の置き場そのもの(LP・外の道具)。この仕様は「その項目を JSON にして渡す」まで
- 組織の名前・時間帯を後から変えるコマンド(いまは画面にも無い。要れば別の仕様)
- 招待のリンクで最初の管理者を招く(G-02 の仕様 0027 で、案内のメールを仕組みで送る)

## 決めたこと

- 削除と同じく、API ではなくコマンド(ECS の1回きりのタスク・表の持ち主)。既定は試し、`--execute --confirm-name` で本当に作る(`delete-tenant` と同じ形。ADR 0039)。
- 試しは「流してから取り消す」。数えるだけの試しでは、メールの重なり(ほかの組織の行は RLS で見えない)を前もって見られないため。
- 申し込みは非公開の S3 に置き、コマンドはキーだけを受けて読む(管理者の名前・メールを CloudTrail に残さない。@attumkwg 2026-10-25 の回答。設計書 0026 の U-1)。流すのは本番の AWS に入れる開発で、CS は申込書を渡して出力を一緒に確かめる(2人。同 U-2)。
