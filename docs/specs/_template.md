# 仕様: <機能の名前>

> 1つの仕様 = 1つ以上の Issue。大きければ親 Issue → 子 Issue に割ってから AI に渡す。
> 状態: 下書き / 承認済み(承認した人: @ )/ 完了待ち(作り終えた。「完了」にするのは人)/ 完了
> **書く人を「説明の責任」で分ける**([concepts/people-and-ai.md の 1.1](../concepts/people-and-ai.md#11-段を決める問い説明の責任))。第1部は PdM が書く(なぜそうするかをチームに説明できる物)。第2部は AI が網羅して書き、エンジニアが見る(PdM は読まなくてよい)。
> **印**: 何も付けない行 = 確定。`(仮説)` = まだ確かめていない思い込み(賭けの仮説・話を聞いた数が少ない)。`(未確定 U-n)` = 決まっていない(中身は設計書の「未確定事項」の U-n。ここは印と番号だけ)。

## 第1部 PdM が書く所(業務の要求・業務ルール)

> **書かない3つ**
> 1. 基本の流れ(一覧・登録・更新・削除の当たり前の動き。AI が型どおりに作る)
> 2. システムの状態が軸に入る判定表(「状態 × 操作でボタンがどうなるか」は第2部へ)
> 3. 理由が「整合性のため」「エラーを防ぐため」としか書けない行(第2部か設計書へ)

### 業務の要求

> 利用者が何をできるようになるか。画面やボタンではなく、業務の言葉で。

- <誰が・何をできるようになる>

### 業務ルール

> 決まりと、なぜそうするか(1行)。**理由をチームに説明できない行はここに置かない**(第2部へ)。

- <決まり> — <なぜ(業務の理由)>

### 受け入れ条件(業務の言葉で)

> 「誰が・何をすると・どうなる」で書く。ここがそのままテストになる。拒否のされ方・他社からの見え方は第2部に書く。

- [ ] <ロール> が <操作> すると <結果>

### 要配慮個人情報

> 病歴・障害・信条・犯罪の経歴など(個人情報保護法 2条3項)が入りうるか。**人が答える**(AI が「当たらない」と決めない)。

- <当たらない / 当たる: どの項目か・取る前の同意をどの画面で取るか(法 20条2項)。当たるなら置き場所は ADR 0029(`apps/api/src/sensitive/`)>

### 決めたこと

- <人が決めたこと(対話で答えたこと)。大きければ docs/adr に書く>
