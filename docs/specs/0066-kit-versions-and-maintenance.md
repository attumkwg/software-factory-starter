# 仕様: キットの版と保守の約束

> 1つの仕様 = 1つ以上の Issue。大きければ親 Issue → 子 Issue に割ってから AI に渡す。
> 状態: 完了待ち(作り終えて main に入っている・穴 G-41 は済み。「完了」にするのは持ち主。2026-10-28 の整合の直しで「下書き」のままと分かった)

## なぜ作るか

外の会社がキットを審査に出すと、「誰が・どこまで・いつまで直すか」「穴をどこに知らせるか」「どの版を使っているか」を必ず聞かれる。今は版のタグも変更の記録も穴の報告先も無く、外部のコードの審査・契約に載せられない(外からの点検 09-adoption の 9-5・穴 G-41)。

## 受け入れ条件

- [ ] 穴を見つけた外の人が、ルートの `SECURITY.md` を読むと、公開の Issue に書かずに GitHub の非公開の報告(Security → Report a vulnerability)で知らせる道・書いてほしいこと・対象の版が分かる(日数は約束しない)
- [ ] キットを使う人が、ルートの `CHANGELOG.md` を読むと、版ごとに「取り込むときにすること・足した・変えた・直した・セキュリティ・消した」が分かる
- [ ] 審査をする人が、`docs/kit/maintenance.md` を1ページ読むと、誰が・どこまで直すか・**保守の日数も期限も約束しないこと**・版の付け方(タグの名前・いつ切るか)・保証の無さ(MIT)と、保守が契約で要るときの持ち方が分かる
- [ ] キットから自分のリポジトリを作った人が、getting-started の ② を読むと、`SECURITY.md` を自分の連絡先に置き換えること・キットの変更の記録は `kit` の側で読めることが分かる
- [ ] タグを打つ・GitHub のリリースを作るのは持ち主(人)。AI はしない

## 悪用のされ方(STRIDE で1行ずつ)

| 観点 | どう悪用されうるか | どう防ぐか(テスト / ルール) |
|---|---|---|
| なりすまし | 持ち主を名乗る人が「直した版」と偽のタグ・リリースを配る | タグとリリースは持ち主のリポジトリの物だけが正(`maintenance.md` の 4)。取り込むのは `kit` の remote(元のリポジトリ)からだけ |
| 改ざん | 版を切った後にタグを付け替える | タグは付け替えない・消さない(`maintenance.md` の 4)。直しは次の版で |
| 否認 | 穴の知らせを受けたか分からない | GitHub の非公開の報告で受け、やり取りがリポジトリの勧告に残る |
| 情報漏えい(他社のデータ) | 穴の中身を公開の Issue・PR に書かれ、直す前に広まる | `SECURITY.md` で公開の Issue に書かないよう頼む。届く・まだ直していない穴の中身は Issue にも PR にも書かない(`docs/guides/vulnerabilities.md` と同じ) |
| 妨害(重い処理・大量の要求) | 該当なし | 文書だけ |
| 権限昇格 | 該当なし | 文書だけ |

## やらないこと

- タグを打つ・GitHub のリリースを作る・リポジトリの設定を変える(持ち主がする。非公開の報告は `.github/setup.yml` の `private_vulnerability_reporting: true` で既に有効)
- 古い版に戻って直す(直すのは最新の版だけ)
- 上流の更新を取り込む手順(穴 G-42 で別に)
- 有償の保守の契約の型
- 返事や直すまでの日数・手入れの期限の約束(キットは作成中。@attumkwg 2026-10-27「保守はこのキットで約束する必要がない」)
