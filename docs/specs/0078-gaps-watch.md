> **書く人を「説明の責任」で分ける**([concepts/people-and-ai.md の 1.1](../concepts/people-and-ai.md#11-段を決める問い説明の責任))。第1部は PdM が書く。第2部は AI が網羅して書き、エンジニアが見る。

## 第1部 PdM が書く所(業務の要求・業務ルール)

### なぜ作るか

穴の一覧(`docs/scenarios/gaps.md`)と台本・手引きは、並行の作業で一気に増えた。済んだ穴を「穴」「無い」と書いた文が残り、質問票のスキルや外から来た人がそれを読んで「できない」と答える。数(全部で何件・何件済み・何件残り)も文書ごとに違った。持ち主は「個別に直しすぎて全体の整合が崩れるのが怖い」「一番大事なのは、このキットで実際に SaaS が作れるか」と言っている。

### 業務の要求

- キットを育てる人が、穴の一覧の今の数(全部・済み・作業中・残り・段ごと)を1つのコマンドで見られる。
- 済んだ穴を「まだ無い」と書いた文書が残っていたら、PR の CI で分かる。
- 残っている穴が、どの段(今すぐ・使える前に・使えた後で)にも入っていなければ分かる。

### 業務ルール

- 足す順番の正は、穴の一覧の「🎯」の節の段 — 古い節の印(🔴🟡🟢)は節ごとに意味が違い、並べる根拠にならない。
- 済んだ穴の行は消さずに「✅ 済み」にし、指す仕様は「下書き」のままにしない(作り終えた PR で「完了」にし、マージする人が見る)— 「済み」と「下書き」が並ぶと、どちらが今か分からない。
- 仕様・設計書・ADR の経緯の文と、台本の「足す前の判定」は直さない — 当時の記録だから。
- 今の数は手で書かず、コマンドが作る — 手で書いた数は、次の PR で古くなる。

### 受け入れ条件(業務の言葉で)

- [ ] `pnpm gaps` で、全部と段ごとの「全体・済み・ほぼ済み・作業中・残り」が出る
- [ ] 済んだ穴を ❌・「穴 G-xx」・「G-xx が埋まるまでは」・「G-xx を入れるときは」で指す文書があると、CI が落ちて場所を出す
- [ ] 穴の番号が重なる・行の頭の印の形が崩れる・済みの行の仕様が「下書き」・残る穴が段に無い、のどれかで CI が落ちる
- [ ] `pnpm gaps --write` で、穴の一覧の頭の「今の数」の表が作り直される。古いままだと CI が落ちる

### 要配慮個人情報

- 当たらない(リポジトリの文書だけを読む)

### やらないこと

- 「無い」「未」と書いた文を全部拾うこと(言葉が広すぎて、今も無い物と区別できない。拾うのは決まった書き方だけ)
- 仕様・設計書・ADR の中を見ること(記録なので直さない)
- 開いている PR を GitHub に聞いて 🔧 を確かめること(CI は外を見ない。番号があるかだけ)

### 決めたこと

- 2026-10-27 に @attumkwg が、全体の整合の直しを「全部おすすめどおりで」と決めた(会話)。G-109 の芯として、この見張りを作る。
- 2026-10-29 に @attumkwg が、残りの穴を意義の判断役で棚卸しし、やらないと決めた穴を「⛔ やらない」にすると決めた(会話「判定どおりに gaps.md を並べ直して」)。行は消さず、段に入れず、数は別の列で出す — 「残り」に混ぜると公開までの残りが大きく見え、消すと決めた理由が残らない。

## 第2部 AI が網羅して書き、エンジニアが見る所(システムの振る舞い)

### 状態 × 操作

| 穴の行の状態 \ 見ること | 段に入っているか | 指す仕様 | 文書で「穴」と書かれたら |
|---|---|---|---|
| ✅ 済み | 入っていてよい(数に出る) | 「下書き」なら落ちる・無い番号なら落ちる | 落ちる |
| ✅ ほぼ済み | 要る | 見ない | 落ちない(残りがある) |
| 🔧 作業中 | 要る。PR の番号(#数字)も要る | 見ない | 落ちない |
| 🔴🟡🟢 残り | 要る | 見ない | 落ちない |
| → G-xx に束ねた | 親の段に入る(段の表に子を書くと落ちる)。親が ⛔ やらない なら段に入れない | 見ない | 落ちない |
| ⛔ やらない | 入れない(段の表に書くと落ちる。数は「やらない」の列) | 見ない | 落ちない |

### 境界値

- 番号は `G-` と2〜3桁。「G-80〜G-84」は間も数える。
- 段の表の「穴」の列は「(」より前の番号だけを数える(「G-116(G-72 を束ねた)」は G-116)。
- 「済」「足す前」を書いたかたまり(表のセルか、表でない行)は見ない(分かって書いている)。
- 台本(`docs/scenarios/`)の「- 足す前の判定」の行と、その下の字下げした行は見ない。

### 権限の組み合わせ

該当なし(アプリの API は変えない。手元と CI で文書を読むだけ)。

### 悪用のされ方(STRIDE で1行ずつ)

| 観点 | どう悪用されうるか | どう防ぐか(テスト / ルール) |
|---|---|---|
| なりすまし | 該当なし(読むだけ) | — |
| 改ざん | AI が「済」の字を足して古い文を検査から逃がす | 逃がすのは「済」「足す前」を書いたかたまりだけ。PR の差分で人が見る(文書の PR は危険度「低」) |
| 否認 | 該当なし | — |
| 情報漏えい(他社のデータ) | 該当なし(リポジトリの文書だけ) | — |
| 妨害(重い処理・大量の要求) | 該当なし(文書は数百件) | — |
| 権限昇格 | 該当なし | — |
