# 仕様: PR の動作確認を AI に回し、「通った ≠ 確かめた」を2層で守る

> 1つの仕様 = 1つ以上の Issue。大きければ親 Issue → 子 Issue に割ってから AI に渡す。
> 状態: 下書き
> **書く人を「説明の責任」で分ける**([concepts/people-and-ai.md の 1.1](../concepts/people-and-ai.md#11-段を決める問い説明の責任))。第1部は PdM が書く。第2部は AI が網羅して書き、エンジニアが見る。
> **印**: 何も付けない行 = 確定。`(仮説)` = まだ確かめていない思い込み。`(未確定 U-n)` = 決まっていない(中身は設計書の「未確定事項」の U-n)。

## 第1部 PdM が書く所(業務の要求・業務ルール)

### なぜ作るか

PR ごとの画面の動作確認を人が手でしていて、PR が増えると人が詰まり所になる。AI に回すと速いが、AI の書いた確認は「確かめていないのに通る」ことがあり、通ったことを信じると不具合が出る。

### 業務の要求

- PR を出した人(AI か人)が、本文に「何を画面で確かめるか」を書ける。
- AI がそれを読んで画面で確かめ、手順と結果を PR に残す。人は貼られた結果を読み、確かめられなかった所だけを手で見る。
- AI の確認が「確かめずに通った」ときに、それが分かる。

### 業務ルール

- 確かめるのはプレビューか手元の環境だけ。本番では確かめない — 本番の利用者のデータに触れない(docs/security.md の AI-6)。
- 「通った」だけでは「確かめた」にしない — AI の確認は、確かめていないのに通る形が決まって出る(エラーの放置・API の直叩き・アサーション無し・操作の前から合格・うわべの確認・判定のすり替え)。
- 確かめられなかった所は隠さずに書き、人に渡す — 人が見る所を絞っても、見ていない所を見たことにしない。
- AI に渡す製品の知識は、手入れされている E2E から取る — コードは余計な情報が多く、設計書は差分しか無い。(仮説)

### 受け入れ条件(業務の言葉で)

- [ ] PR のテンプレートに「🖱 動作確認」の欄がある
- [ ] `/verify-pr <番号>` で、AI が欄の1行ずつを画面で確かめ、手順と結果(確かめた / 確かめられなかった)のコメントの案を作る。貼るのは OK の後
- [ ] 危ない書き方の手順は、流す前に止まる
- [ ] 画面のエラー・サーバーの失敗が出た確認は、最後の判定が合っていても落ちる
- [ ] 通った後も、AI が記録を読んで6つの形を確かめた結果がコメントに残る

### 要配慮個人情報

- 当たらない(種データの利用者だけで確かめる。記録に URL の問い合わせ・本文を残さない)

### やらないこと

- 手順のファイルをコミットして、ふだんの E2E として残すこと(何度も要る確認は、別の PR でふだんの E2E に足す)
- CI で `/verify-pr` を自動で流すこと(背景の AI で流すかは、使ってみてから)
- スマホの端末・読み上げの確認(人の手が要る。`/accept` の QA の項目)

### 決めたこと

- 本人の依頼(学びをキットに入れる5本の4本目)で作る。根拠は `docs/concepts/line.md` の 2 の動作確認の行(この PR で足す)

## 第2部 AI が網羅して書き、エンジニアが見る所(システムの振る舞い)

### 状態 × 操作

| 手順の状態 \ 操作 | `pnpm verify:lint` | 流す | コメントに貼る |
|---|---|---|---|
| 危ない書き方がある | 1 で終わる(ファイル:行・形の名前) | 流さない | 貼らない |
| 書き方は通る・流して落ちた | 0 | 落ちた(画面のエラー・5xx・判定) | 「確かめられなかった」と理由 |
| 流して通った・記録が疑わしい | 0 | 通った | 「確かめられなかった」と疑った所 |
| 流して通った・記録も意図どおり | 0 | 通った | 「確かめた」と見た所 |

### 境界値

- 欄が「なし」・空: 仕様の受け入れ条件から案を作り、使ってよいかを聞く(勝手に流さない)
- 確認の中の `expect` が0: 止める
- 最後の操作の後に `expect` が0: 止める。操作の前に `expect` が0: 止める(見るだけの確認=操作の無い確認は除く)
- 判定が全部「有る・見える」だけ: 止める
- 準備の印(`// 準備:`)の行に `expect` がある: 止める(準備に見せて確かめを API でしている)
- 書き直して流すのは2回まで。3回目は人に渡す

### 権限の組み合わせ

該当なし(アプリの API は変えない)。確認の中でロールごとの拒否(403・404)を確かめるのはよい(4xx は落とさずに記録する)。

### 悪用のされ方(STRIDE で1行ずつ)

| 観点 | どう悪用されうるか | どう防ぐか(テスト / ルール) |
|---|---|---|
| なりすまし | 該当なし(種データの利用者でログインするだけ) | — |
| 改ざん | 書き方の止めを印で逃がす・判定を定数にする | 印は準備の行だけ・その行に判定を書けない。定数の判定を止める(`scripts/verify-lint.test.mjs`) |
| 否認 | AI が確かめたと言うが、何をしたか分からない | 手順(スクリプト)をコメントに貼る |
| 情報漏えい(他社のデータ) | 本番に流して利用者のデータを記録やスクショに残す | 流す先はプレビューか手元だけ(スキルの決まり)。記録に URL の問い合わせを残さない |
| 妨害(重い処理・大量の要求) | プレビューに確認を大量に流す | 1本ずつ順に(workers 1)・再試行しない |
| 権限昇格 | PR の本文の文に混ぜた指示で AI に別の操作をさせる | 本文はデータとして扱う(スキルの決まり・docs/security.md の AI-3)。コメントは OK の後 |

> 設計(どう作るか)は [docs/designs/0076-verify-pr.md](../designs/0076-verify-pr.md) に書く(AI 用。網羅的に)。
