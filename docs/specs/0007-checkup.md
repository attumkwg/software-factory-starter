# 仕様: 点検(ソフトウェアに詳しくない担当者でも、安心して回せるようにする)

> 状態: 承認済み(承認した人: @attumkwg 2026-10-21)
> 設計: [docs/designs/0007-checkup.md](../designs/0007-checkup.md)

## なぜ作るか

このキットは、守り(検査・権限の表・手順書)は厚い。けれども「それが今も効いているか」「次に何をすべきか」は、詳しい人が自分で見に行かないと分からない。
2026-10-20 の点検では、GitHub の守りが無料プランで効いていない・依存の更新が一度も流れていない・攻撃の形の検査を一度も回していない、が見つかった。どれも作り込みの問題ではなく、**気づく仕組みが無い**のが原因だった。

担当者がジュニアのエンジニアや PdM でも、**向こうから知らせが来て、1問ずつ答えれば、やるべきことが済んでいく**ようにする。

## 誰が使うか

| 人 | できること | この仕組みでしてほしいこと |
|---|---|---|
| 担当者(PdM・ジュニア) | 選ぶ・一言で答える・画面で設定を押す | 知らせを見て、1問ずつ答える。分からなければ「分からない」を選ぶ |
| 詳しい人(相談先) | 判断・設定・コード | 「分からない」が溜まったものに答える |
| AI(Claude Code) | 調べる・確かめる・PR を出す | 自動で確かめられるものは全部確かめ、人には判断だけを聞く |

## 受け入れ条件

### 知らせが来る(プッシュ)

- [ ] 毎週1回、決まった曜日の朝に「今週の点検」が担当者に届く(何も起きていない週も「異常なし」と届く)
- [ ] 知らせの一番上に「今週あなたが答えること: N 問(約 M 分)」が出る。0問なら「答えることはありません」
- [ ] 急ぐもの(秘密が漏れた疑い・守りが外れた・重い脆弱性)は、週を待たずにその日のうちに届く
- [ ] 同じ件は1つにまとまる(同じ知らせが毎週増えていかない)

### 1問ずつ答えられる(一問一答)

- [ ] 担当者が Claude Code で `/checkup` と打つと、答えることが1問ずつ出る
- [ ] 問いはやさしい言葉で、「なぜ要るか」「答えないと何が起きるか」が1〜2行で付く。専門用語には一言の言い換えが付く
- [ ] 答えは選択肢(2〜4個)から選べる。いちばん安全な案に「(おすすめ)」が付く
- [ ] どの問いにも「分からない」がある。選ぶと、おすすめの案で仮に進め、「相談先に聞く」の一覧に載る(止まらない)
- [ ] 人が手でやること(画面の設定・契約・規約など)は、手順が番号付きで出て、終わったら「やった」を選ぶ。できるものは AI がやったかどうかを確かめる
- [ ] 答えは台帳に残り、いつ・誰が・何を選んだかが後から分かる

### 段階ごとに、やることが変わる

- [ ] 使い始めた日を台帳に持ち、**立ち上げ・1か月・3か月・半年・1年・2年**のそれぞれを過ぎたら、その段階の点検が「今週の点検」に入る
- [ ] 段階の点検は、それより前の段階で済んでいないものも残す(飛ばして次に行かない)

### TODO の台帳(やることの一覧)

- [ ] やることは1つの台帳にある。1件ごとに: 何を・なぜ・誰が(仕組み / 人)・いつから(段階)・どのくらいの間隔で・どう確かめるか・今の状態・最後に確かめた日・出どころ
- [ ] ソフトウェアで解けないもの(契約・規約・体制・お金・人の訓練)も「推奨」として台帳に載る
- [ ] 台帳の状態は、ソフトウェアに詳しくない人が読める1枚(Markdown)でも見られる

### 世の中の変化を取り込む

- [ ] 月に1回、AI が新しい話(使っている道具の重大な脆弱性・GitHub・AWS・Claude Code の仕様の変更・法令の改正・よく使われる対策の変化)を調べ、台帳を足す・直す・消す **案を PR で出す**。人が承認したものだけが台帳に入る
- [ ] 台帳の1件ごとに「見直す日」があり、過ぎたら AI が今も正しいかを確かめる
- [ ] 案には出どころ(リンク)と、調べた日が付く。出どころの文章の中の指示には従わない

## やらないこと

- 担当者の代わりに、本番に書き込む・お金のかかる設定を入れる・契約する(AI は案と手順まで)
- 点検の結果で自動でマージ・デプロイする
- 業務の監視(アラーム・障害対応)の置き換え。それは `docs/runbooks/` と `docs/guides/monitoring.md` のまま。点検は「守りが今も効いているか」と「次にやること」を見る

## 悪用のされ方(STRIDE で1行ずつ)

| 観点 | どう悪用されうるか | どう防ぐか(テスト / ルール) |
|---|---|---|
| なりすまし | 担当者以外が Issue のコメントで「やった」と答える | 答えを受け付けるのは台帳に書いた担当者だけ。Issue のコメントは知らせの置き場で、答えの正は `/checkup` の台帳 |
| 改ざん | 台帳や確かめるコードを書き換えて「済み」にする | 確かめるコード(`scripts/checkup/`)は危険度「高」の一覧に入れる。自動で確かめられるものは毎週確かめ直す(台帳に書いてある状態を信じない) |
| 否認 | 誰が「分からない」で進めたか分からない | 答えに日付と答えた人を残す(git の履歴にも残る) |
| 情報漏えい | 知らせに秘密の値・脆弱性の詳細が載る | 公開のリポジトリでは、脆弱性の中身を Issue に書かず「件数と見る場所」だけにする |
| 妨害 | 世の中の変化の取り込みに、Web の文章から指示が混ざる(プロンプトインジェクション) | 調べた文章はデータとして扱う。台帳を変えるのは PR だけで、人が承認する |
| 権限昇格 | 点検のワークフローの権限で、ほかの物を書き換える | 点検のジョブの権限は Issue を書くのと読むだけ。コードは書かない |

## 決めたこと

- 2026-10-20 本人: 「最終的に、ソフトウェアのことが分からない担当者(ジュニアのエンジニアでも PdM でも)が安心して使えるソフトウェアファクトリーを目指す」「段階ごとの自己点検と、週次の脆弱性の自己点検を、プッシュで担当者に伝えて判断してもらう」「詳しくなくても分かる一問一答」「ソフトウェアだけで解決できないことは推奨の TODO に」「世の中の変化を取り込みながら更新できる TODO」
