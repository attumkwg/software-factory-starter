# 仕様: お知らせ・プレスリリースの型と、導入事例の許可

> 状態: 下書き(想定の場面の穴 G-38 から AI が書いた。2026-10-25。承認は PR で)
> 設計: [docs/designs/0040-announcements.md](../designs/0040-announcements.md)

## なぜ作るか

- 正式に出す日に業界紙・地域の新聞・業界の会に知らせたいが、リリースノート(`/release-notes`)はあっても、広報の文の型が無い(想定の場面の 8-4)。
- お客さんの会社の名前やロゴを出すには許可が要る。許可をどこで取り、どこに記録するかが決まっていない。記録が無いまま出すと、取り消しのときに何をどこから外すかも分からない。

## 受け入れ条件

- [ ] `docs/guides/announcements.md` に、出す物の種類(リリースノート・お知らせ・プレスリリース・導入事例)と、元・相手・出す人がある
- [ ] 下書きの材料(リリースノートの利用者向け・positioning.md・brand.md)と、書かない物(言わないこと・根拠の無い数字・比べる言い方・許可の無い名前・まだ出していない物の約束・中の言葉)がある
- [ ] プレスリリースの型(見出し・リード・背景・できること・お客さまの声・開始日と料金・会社の情報・問い合わせ先)がある。文面は書かない
- [ ] 名前・ロゴ・事例を出す許可の段(出さない・名前・名前とロゴ・事例と声)と、誰の許可か(声と写真は本人の同意も)がある。既定は「出さない」
- [ ] 許可の取り方(申込書の欄か書面・メール)と、記録の置き場(リポジトリの外)・記録の欄・出す前の確かめ・取り消されたとき・解約したときがある
- [ ] 申込書の型(`docs/legal/order-form.md`)に「導入事例・名前とロゴ」の欄がある
- [ ] `/release-notes` のスキルが、お知らせ・プレスリリースが要るかを聞き、手引きの型で下書きする。許可の無い名前を書かない決まりがある

## 権限の表に足す行

該当なし(API を足さない)。

## 要配慮個人情報

- 当たらない(文書だけ)。事例の記事で社員の名前・写真を出すときは本人の同意(個人データ)と書く。

## 悪用のされ方(STRIDE で1行ずつ)

| 観点 | どう悪用されうるか | どう防ぐか(テスト / ルール) |
|---|---|---|
| なりすまし | 許可した人に権限が無い(担当者が勝手に許可した) | 記録に許可した人の役職。申込書と同じ所で取る |
| 改ざん | 根拠の無い数字・比べる言い方で売る | 書かない物の決まり。下書きに確かめた項目を1行ずつ添える |
| 否認 | 「名前を出してよいとは言っていない」 | 口頭だけで出さない。記録(取り方と写しの場所)を残す |
| 情報漏えい(他社のデータ) | 許可の無いお客さんの名前を出す / 許可の記録(会社の名前)をリポジトリに書く | 既定は出さない。記録はリポジトリの外 |
| 妨害(重い処理・大量の要求) | 該当なし | — |
| 権限昇格 | 該当なし | — |

## やらないこと

- 文面を書く・配信する(人がする)
- 配信の道具を選ぶ(使うなら委託先の台帳に1件)
- `docs/product/` の型(positioning・brand)を変える(読むだけ)
- 想定の場面(`docs/scenarios/`)の判定と穴の一覧の書き換え(場面の持ち主が直す)
