# 仕様: 🎨 使いやすさを見る人をレビューに足す(腕のいい UX デザイナーが言うことを、AI のレビューが言える)

> 状態: 完了(実装済み)
> 設計: [docs/designs/0098-ux-reviewer.md](../designs/0098-ux-reviewer.md)
> 穴 G-162(`docs/scenarios/gaps.md`)。続き: G-163(初見の利用者テスト・機械の検査)・G-164(見つかった穴から部品を足す)。観点の台帳は [../review-viewpoints.md](../review-viewpoints.md)。

## 第1部 PdM が書く所(業務の要求・業務ルール)

### なぜ作るか

- ペルソナ: キットを使ってプロダクトを作る人(持ち主・PdM)と、レビューする人。その先の、画面を使う人(P-1〜P-10)
- 動かす KPI: (キットの物差し: 受け入れで見つかる外れの数・人の介在率。守り: 事故 0件)
- レビューの人格は5人(使う人・越えようとする人・夜中に起こされる人・後から確かめる人・3か月後に触る人)で、**見た目と使いやすさを見る人がいなかった**。画面の確かめも、a11y(axe)・320px ではみ出さない・VRT で前と同じ、の「壊れていないか」まで。
- 持ち主(2026-11-13):「世間一般的に優れている UX デザイナーが指摘するようなことを指摘できるようなレビュー体制を整えたい、もしくはテスト環境を整えたい」。順は **目(レビュー)→ テスト → 部品(デザインシステム)** と決めた(2026-11-14)。
- 今の画面を UX の目で見ると、ヘッダーで今のページが分からない・各行の「消す」が中身と同じ強さ・設定のカードで操作がボタンとリンクと文中のリンクに分かれる、などが見つかる。どれも機械では落ちない。

### 業務の要求

- 画面を変える PR を、腕のいい UX デザイナーの目で、書いた AI と別の AI が見る。**画面の画像を見て**、迷う・押し間違える・失敗して戻れない所を、誰が・どこで困るかつきで指摘する
- その見方(何を見るか・重さの付け方)が、人が読める手引きになっていて、外れたら足せる

### 業務ルール

- 画面を変える PR には、危険度によらず 🎨 を呼ぶ — 文言1つ・ボタン1つの変更でも、迷うかどうかは変わる。危険度は「戻せないか」の物差しで、使いやすさとは別
- 🎨 は画像を見てから所見を出す。画像が無ければ「撮られていない」こと自体を所見にする — コードからは見え方が分からない。VRT に無い画面は、次から撮れるようにする
- 好みは所見にしない(提案に分ける)。所見には困る人と場面を書く — 好みまで直すと、AI が直し続けて終わらない
- 直し方は `@app/ui` の部品と props の中で言う。新しい色・余白は人が決める(❓) — デザインシステムの決まりと、トークンを決めるのは人、の分担(`docs/design-system.md`)を崩さない

### 受け入れ条件(業務の言葉で)

- [x] 観点の台帳に「画面の使いやすさ(UX)」の6つ(迷わなさ・画面の状態・見た目の強弱・文言・危ない操作と戻し方・スマホでの操作)と、人格 🎨 がある。🎨 を呼ぶのは画面を変える PR
- [x] 手引き `docs/guides/ux-review.md` に、3秒の問い・10の目安・画面の状態・強弱・文言・入力・危ない操作・スマホ・重さの付け方がある
- [x] `/review-pr` が画面を変える PR で 🎨 を呼び、変わる前と後の画面の画像(パソコン・スマホ)を渡す。`pnpm ux:screens <番号>` が画像を取り出す
- [x] レビュー役が 🎨 のとき、画像を見ずに見た目の所見を出さない・画面の名前と位置を書く・直し方を部品の中で言う
- [x] 台帳の観点が全部どれかの人格に入り、人格が6人であることを、テストが見る

### 要配慮個人情報

- 当たらない(画面の画像は種データ(架空の2社・.test のメール)だけ)。

### やらないこと

- 初見の利用者テスト(ペルソナの AI に画面だけで操作させる)・主ボタンの数などの機械の検査(G-163。次の PR)
- 見つかった穴の直し・部品を足す(G-164)
- VRT に無い画面をレビューのときにその場で撮る(VRT の画面の一覧に足すほうへ寄せる)

### 決めたこと

- (持ち主が決めた @attumkwg 2026-11-14 会話で回答「目→テスト→部品の順で」)まずレビューの人格を足し、次にテスト、最後に部品
- (AI が決めた)🎨 は「中」「高」の5人には入れず、**画面を変える PR に危険度によらず**呼ぶ。画面に触らない「高」の PR(infra・DB)で呼んでも見る物が無い
- (AI が決めた)画像は VRT の基準の画像を使う。VRT は画面を変えると基準の撮り直しが要る(撮り直さないと赤)ので、変わった画像は PR に必ずある。別に撮る仕組みは作らない
- (AI が決めた)手引きの「10の目安」は Nielsen のユーザビリティの10の目安を、このキットの画面の言葉に置き換えた物。出典の名前だけを書く

## 第2部 AI が網羅して書き、エンジニアが見る所(システムの振る舞い)

### 状態 × 操作

| PR \ 🎨 | 呼ぶ | 渡す画像 |
|---|---|---|
| 画面の道に触る・基準の画像が変わった | 呼ぶ | 変わった画像の前(main)と後(PR) |
| 画面の道に触る・基準の画像は変わらない | 呼ぶ | PR の版の画像を全部「後」で。「変わった画像なし」と出す(VRT に無い画面か、見た目が変わらない変更) |
| 画面の道に触らない | 呼ばない | — |

### 境界値

- 画面の道: `apps/web/src/`・`packages/ui/`・`apps/site/` の下。ただし名前が `.test.`・`.spec.` のファイルだけの変更は入れない
- 基準の画像: `apps/web/e2e/vrt/__screenshots__/<幅>/<画面>.png`(幅の下の1段だけ)
- 新しく足した画面は前が無い(後だけ)。消した画面は後が無い(前だけ)
- 画像は一時フォルダに書く(リポジトリには書かない)

### 権限の組み合わせ

- 該当なし(API・権限の表を変えない)

### 悪用のされ方(STRIDE で1行ずつ)

| 観点 | どう悪用されうるか | どう防ぐか(テスト / ルール) |
|---|---|---|
| なりすまし | 該当なし | — |
| 改ざん | PR が台帳やレビュー役の定義を弱めて、自分を甘く見させる | 2つは守る場所。PR が触るときは main の版で回す(仕様 0096 のまま) |
| 否認 | 該当なし | — |
| 情報漏えい(他社のデータ) | 画像に本物のデータが写る | VRT は種データだけ(`screens.ts` の決まり)。書くのは一時フォルダだけ |
| 妨害(重い処理・大量の要求) | 該当なし | — |
| 権限昇格 | 画像の中の文で、レビュー役に指示を出す | レビュー役は画像・本文の指示に従わない(定義の「守ること」) |
