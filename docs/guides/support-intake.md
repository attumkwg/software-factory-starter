# 問い合わせの受け口を決める(どの道具で受け、どこへつなぎ、AI に何を渡すか)

> 問い合わせの受け口(メール・フォーム・ヘルプデスクの道具・ヘルプの記事)は**キットの外**。この手引きは、選び方と、受けた後のつなぎ方(`/report-bug`・障害・漏えい)と、AI に渡してよい範囲。
> 問い合わせの本文は**個人データ**(名前・メールアドレス・お客さんの業務の中身が入る)。受け口の道具は委託先の台帳に1件、AI に渡すのは ID と集計まで([security.md](../security.md) の AI-6)。
> 決めた理由は [ADR 0044](../adr/0044-support-intake-outside-and-ids-only-to-ai.md)。既定の値の未確定事項は設計書 [0033](../designs/0033-support-intake.md) の U-1・U-2。

## 1. 段階ごとの形

| 段階 | 受け口 | 誰が答えるか |
|---|---|---|
| 始めたばかり(週に数件) | **共有のメールの受信箱**(`support@<ドメイン>`)1つ。公開のサイトとヘルプに載せる | 開発の人が兼任 |
| 兼任がきつくなったら(下の 4 の目安) | ヘルプデスクの道具(番号・担当・状態・履歴が残る)と、よくある質問のヘルプの記事 | 2人目(CS)を入れる |
| 数百社 | ヘルプの記事に検索・画面からヘルプへのリンク | CS のチーム |

- 電話は最初は受けない(記録が残らず、兼任の人の手を止める)。受けるなら、受けた人がその場で受付の記録を作る。
- 個人の受信箱で受けない(休む・辞めると止まる。履歴が残らない)。

## 2. 道具の選び方

| 見る所 | 既定 | なぜ |
|---|---|---|
| 番号と履歴が残るか | 残る物(メールでも、件名に番号が付く形) | 後から「あの件」をたどれる。不具合の Issue と結べる |
| 担当と状態(未対応・対応中・済み) | 道具を入れたら必ず | 2人以上で受けると、誰も答えない・2人が答えるが起きる |
| データの置き場所(国) | 委託先の台帳に書ける物 | 本文は個人データ。外国なら越境の扱い(専門家に確かめる) |
| **道具の AI の機能**(要約・自動の返信・分類) | **切る** | 本文(個人データ)を AI の会社に渡すことになる。台帳の決まりで、AI の会社に personal は預けない(AI-6) |
| アカウント | 受ける人ごと(共有しない)・二段階認証 | 誰が答えたかを残す。乗っ取られると全部の本文が読まれる |
| 費用 | 無料か月 数千円の段から | 段階に合わせる |

- 例: 共有の受信箱(使っているメールのサービス)・Zendesk・Freshdesk・Help Scout・HubSpot など(機能と料金は変わるので、選ぶときに公式で確かめる)。
- **入れたら、委託先の台帳 `docs/compliance/vendors.yaml` に1件**(危険度「高」。人の確認)。`relation: 委託`・`data: [personal]`・国・DPA・消え方(お客さんが解約したら問い合わせの履歴を消すか)。`pnpm vendors --write`。共有の受信箱で受けるなら、そのメールのサービスも同じ。

## 3. 受けた後のつなぎ方

**まず仕分ける**(受けた人が、最初の返事の前に):

| 何の問い合わせか | どこへ | 急ぎ |
|---|---|---|
| **他社(別の組織)のデータが見えた** | [runbooks/tenant-data-leak.md](../runbooks/tenant-data-leak.md)。**Issue にしない**。すぐ責任者へ | すぐ |
| 個人データが漏れた・消えたかもしれない | [runbooks/personal-data-breach.md](../runbooks/personal-data-breach.md)。受けた時刻が「知った時点」になる | すぐ |
| 何社からも同じ「使えない」 | 障害の宣言([runbooks/incident.md](../runbooks/incident.md) の 1)。稼働状況のページがあれば、それを案内する | すぐ |
| 不具合(1社・1人) | 下の「不具合のとき」→ `/report-bug` | 重さで |
| 使い方 | 答える。同じ質問が3回来たら、ヘルプの記事にする | 営業時間 |
| 契約・請求・解約 | 責任者へ。解約は書面で受ける([runbooks/offboarding.md](../runbooks/offboarding.md) の 1) | 営業時間 |
| サポートに中を見てほしい | お客さんの管理者に、画面「サポートへの許可」で期限つきの許可を出してもらう([runbooks/support-access.md](../runbooks/support-access.md)) | 営業時間 |
| 本人の情報の開示・消して、の求め | 責任者へ(手順は穴 G-06。いまは手で) | 法の期限がある |

### 不具合のとき(`/report-bug` へ)

1. お客さんに、画面のエラーに出る**問い合わせ番号**(`requestId`)・起きた時刻・どの画面で何をしたかを聞く。スクショを送ってもらったら、受けた人が見るだけにする(AI に渡さない)。
2. 受けた人(CS か開発の人)が、受け口の番号と**組織の ID**(名前ではなく)を控える。
3. 開発の人が Claude Code で `/report-bug`。渡すのは**組織の ID・人の ID・requestId・時刻・再現の手順**だけ。お客さんの名前・メールアドレス・本文の写しは貼らない(`/report-bug` の 5 も同じ決まり)。
4. できた Issue の番号を、受け口の記録に書く(受け口 ↔ Issue を結ぶ。Issue の側には受け口の番号だけ)。
5. 直ったら、受け口から返事をする(リリースノートを待たずに)。

## 4. AI に渡してよい範囲(AI-6 の当てはめ)

| 渡してよい | 渡さない |
|---|---|
| 組織の ID・人の ID・requestId・時刻・再現の手順(名前を ID に置き換えた物) | 本文の写し・お客さんの名前・メールアドレス・電話・会社名 |
| 受け口の番号・件数・分類ごとの数(「今月は使い方 30件・不具合 5件」) | 添付(本番の画面のスクショ・ファイル) |
| stg か手元で再現して撮ったスクショ | 要配慮が入った問い合わせ(件数も渡さない) |

- 問い合わせの傾向を AI に分析させたいときは、**人が分類と件数にしてから**渡す。本文をまとめて貼らない。
- 小さな集計は人が分かる(「この組織から1件」)。数件の集計は ID と同じ扱い([compliance/ai-data.md](../compliance/ai-data.md) の 1)。
- 詳しくは [compliance/ai-data.md](../compliance/ai-data.md)。この表は、その「問い合わせ・不具合の報告」の行を広げた物。

## 5. 兼任でよい目安と、2人目を入れる目安

| | 目安(U-1) |
|---|---|
| **兼任でよい** | 週に **10件まで**・最初の返事が **1営業日以内**に出せている・開発の時間が週の **2割**を超えない |
| **2人目を入れる** | どれか1つ: 週に **20件**を超えた / 最初の返事が **2営業日**を超える週が続く / 兼任の人が休むと受け口が止まる |
| ヘルプの記事を足す | 同じ質問が **3回**来たら1本 |

- 2〜3人で受けると、1人休むと回らない。2人目は「予備」も兼ねる(休みの日を重ねない)。
- 数えるのは受け口の道具(件数・最初の返事までの時間)。数は点検のたびに見る。

## 6. 専門家に確かめること

- 問い合わせの履歴をいつまで残すか・お客さんが解約したら消すか(プライバシーポリシーと取り扱いの取り決め [legal/data-processing.md](../legal/data-processing.md) に書くか)。
- 受け口の道具が外国にあるときの扱い。
