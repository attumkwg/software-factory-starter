# 手引き: 週100〜200本の PR を流す(流量の受け皿)

> 仕様 [0095](../specs/0095-throughput.md)・設計書 [0091](../designs/0091-throughput.md)・ADR [0094](../adr/0094-sensor-only-merge.md)。G-135。
> 3つのつまみは全部 `.github/setup.yml` と `claude.yml` に1行ずつ。**既定は全部、今までどおり**(キュー無し・全部の PR で返事を待つ・人を待つ PR は5本)。入れるのは人。

## 1. どこで詰まるか

| 詰まる所 | 何が起きるか | つまみ |
|---|---|---|
| main に入る所 | 必須のチェックが `strict`(最新の main に追いついてから)なので、1本ずつ「追いつく → CI を流し直す → マージ」の直列になる | ① マージキュー |
| 人の返事 | AI のマージは全部の PR で持ち主の返事を待つ。週200本なら200回 | ② センサーだけで入れる範囲 |
| 背景の AI の数 | 開いた PR が5本で止まる。人が答えなくてよい PR も数える | ③ AI の PR の上限 |

## 2. 数(【実測】と【推定】を分ける)

- 【実測】キット自身(2026-10-27〜29): CI(`ci.yml`)の1回は中央値 3.0分・90% 3.5分。PR を開いてからマージまで中央値 32分。1日に入った最大は35本。直近60本のうち、人を呼ぶ理由が無かった PR は11本(18%。キット自身は守りを作るので低い)。
- 【推定】製品で1本 30分(E2E・結合が伸びる)なら、strict の直列では1日 48本(24時間止まらず)・20本(10時間)。マージキューで同時に5本確かめると 10時間で 約100本(キューで2割落ちれば 約80本)。週200本(平日で1日40本)にはキューが要る。
- 詳しい式は設計書 0091 の 6。

## 3. ① マージキュー

使えるのは組織の公開のリポジトリと、Enterprise Cloud の組織の非公開のリポジトリ(個人のリポジトリでは使えない)。組織に移す手順は [../runbooks/move-to-org.md](../runbooks/move-to-org.md)。入れる手順は同じ手順書の 3。

- `setup.yml` の `ruleset.merge_queue.enabled: true` と `ruleset.strict: false` にする PR → マージの後に人が `pnpm setup:github --apply`。
- 必須のチェックは1つも外さない。全部のワークフローがキューの中(`merge_group`)でも流れ、PR の本文・承認・未確定事項の答えを見るチェックは、キューの枝の名前から PR を引いて読み直す。`pnpm setup:check`(CI)が、`merge_group` の無い・キューで飛ばされる必須のチェックを落とす。
- AI のマージ(`pnpm pr:merge-when-green`)は、キューがあればマージせずにキューに並べる。

## 4. ② センサーだけで入れる範囲(人を呼ばない)

人が決めること([../concepts/human-decisions.md](../concepts/human-decisions.md))が何も無い PR は、センサーが緑なら持ち主の返事を待たずに入れる。**使う人が選ぶ。既定はオフ**(ADR 0094)。

- 入れる条件: 持ち主が環境に `KIT_AI_MERGE=slack`(ADR 0086)+ `setup.yml` の `ai_merge.sensors_only: true`(この PR は人を呼ぶ)+ 1人の間。
- 入れる PR: 守る場所・高の領域に触らない / 印 needs-human・risk:high・tests:weakened が無い / 本文の「🧑‍⚖️」に問いが無い / 本文の危険度が「高」でない / 必須のチェックが全部緑。
- 打つのは `pnpm pr:merge-when-green <番号> --sensors`。理由が1つでもあれば止めて理由を出す(その PR は今までどおり返事を待ち、積み場に載る)。入れたら PR に「センサーだけでマージ」の記録が残る。
- おかしな PR が入ったら revert し、どのセンサーが足りなかったかを書く(センサーを足す PR は人を呼ぶ)。
- **オンにする PR で一緒に直す物**: ルートの `CLAUDE.md` の「してはいけない」のマージの例外の文と、`/slack-request`(`.claude/skills/slack-request/SKILL.md`)の「仮決めが無いときも聞く」に、`--sensors` の例外を1行ずつ。AI の振る舞いの決まりなので、AI が先に書き換えず、持ち主が答えた PR で入れる(このキットでは既定がオフなので、まだ書いていない)。

## 5. ③ 背景の AI の PR の上限

`claude.yml` の env:

| 変数 | 既定 | 数える物 |
|---|---|---|
| `AI_OPEN_PR_LIMIT` | 5 | 人を待つ PR。②がオンなら印か問いのある PR だけ、オフなら全部(全部が返事を待つ) |
| `AI_OPEN_PR_TOTAL_LIMIT` | 20 | 背景の AI が開いた PR の全部(CI の同時の数と費用の天井) |

- どちらかに達すると、前の段が止めて新しく動かない。人を待つ PR に答えるか、キューで入るのを待ってから頼む。

## 6. 入れた後に見る数(1週間)

- キューの待ち時間と、キューで落ちた数(落ちる PR が多ければ「1回にまとめる数」`max_entries_to_merge` を下げる)
- `pnpm metrics` の人の介在率と、積み場(`pnpm queue`)の件数・いちばん古い待ち
- センサーだけで入れた PR のうち、revert した数(1本でもあれば、足りなかったセンサーを足す)
- Actions の分数(非公開のリポジトリなら費用。`docs/guides/cost-dashboard.md`)
