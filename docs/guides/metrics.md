# 週の数字(DORA・AI が手伝った PR・人の介在率・無人化率・仕様の在庫・引き渡し)

> 仕様: [specs/0035](../specs/0035-delivery-metrics.md)・設計: [designs/0035](../designs/0035-delivery-metrics.md)・ADR: [0046](../adr/0046-metrics-from-labels-and-repo-records.md)・引き渡しは [specs/0077](../specs/0077-handoff-metrics.md)・[designs/0077](../designs/0077-handoff-metrics.md)・無人化率は [specs/0098](../specs/0098-weekly-unmanned-rate.md)・[designs/0094](../designs/0094-weekly-unmanned-rate.md)
> 何を測るかの考え方は [concepts/line.md](../concepts/line.md) の 8。毎週の振り返りは [playbook.md](../playbook.md) の「毎週やること」。

## 1. 出し方

- **毎週**: `metrics.yml` が月曜 8:30(日本時間)に流し、Actions の要約(Actions → Metrics → いちばん新しい実行)に出す。キットから作ったリポジトリ(`KIT_ROLE=product`)でだけ動く。手で流すのはどこでも(Run workflow・週の数を選べる)。
- **手元**: `pnpm metrics`(先週までの8週)・`pnpm metrics --weeks 12`・`pnpm metrics --today 2026-10-26`(前の週を出し直す)・`pnpm metrics --out <フォルダ>`(`metrics.json` と `metrics.md`)。`gh` のログインで読むだけ。
- 読む物: マージした PR(本文の「人に判断してほしい所」・ラベル・コミット・コメントの数・レビュー)・本番(Environment `prod`)のデプロイ・障害の振り返り(`docs/incidents/`)・仕様(`docs/specs/`)。**人の名前・PR の題名と本文は出さない**(数と PR の番号と仕様の番号・題だけ)。

## 2. 決裁用と改善用

| | 決裁用 | 改善用 |
|---|---|---|
| 何を決める | 任せる範囲を広げるか(危険度「低」の自動マージ・本番の承認の自動化)・AI に払う額は見合うか | 何をルール・テスト・lint・スキルに変えるか(毎週30分の振り返り) |
| 形 | 週ごとの並び。チームで1つの数 | 先週の PR ごとの明細・問いの種類・障害・仕様の在庫の一覧 |
| 見る人 | 経営・CTO・EM | ラインの振り返りに出る人 |

- **人ごとの数は出さない**。人の評価に使うと、数字を良く見せる動きが先に起きる(費用のページの人の時間と同じ決まり)。役割が変わった人の数は下がるので、平均で決めない。
- 決裁用の数は「決める材料の1つ」。2か月ぶんの並びを見て、上がり下がりの理由を改善用の明細で確かめてから決める([concepts/people-and-ai.md](../concepts/people-and-ai.md) の 5)。

## 3. 数の意味

| 数 | 数え方 |
|---|---|
| 本番のデプロイ | その週に成功した本番のデプロイの数(GitHub の Environment `prod`。`deploy.yml` の「prod に出す」) |
| リードタイム | PR を開いてから、マージの後の最初の成功した本番のデプロイまで(時間・中央値)。マージした週で数える。まだ出ていない PR は入れない |
| 変更の失敗率 | (失敗した本番のデプロイ+「変更が原因: はい」の振り返り)÷ 試した本番のデプロイ。デプロイの無い週は — |
| 復旧の時間 | 振り返りの「戻るまで: 何分」の中央値(振り返りの日付の週) |
| マージした PR | その週にマージした PR(ボットの PR は入れない) |
| AI が手伝った | マージした PR のうち、ラベル `ai:assisted` が付いた物の割合 |
| AI の PR で人の介入なし | AI が手伝った PR のうち、人が答えた問いが0で、人の手直しも0の割合。**変更の失敗率と並べて見る**(介入を減らして失敗が増えたら戻す) |
| 人が答えた問い | PR の本文の「人に判断してほしい所」の表の行の数(「なし」は0)。種類は表の2つ目の列 |
| 人の手直し | AI が手伝った PR のコミットのうち、AI の印(`docs/cost/people.yaml` の `ai_markers`)が無く、ボットでもマージのコミットでもない物の数 |
| 無人化率【推定】 | 1 − 人が使った工数 ÷ 全部を人が書いたらの工数(幅)。式は [kit/roi.md](../kit/roi.md) の 2 と同じ: 人の工数 = AI の PR × 15分 + 人の PR × 120分 + ボットの PR × 5分 + コメント × 3分 + ほかの人のレビュー × 20分(分は `docs/cost/people.yaml`)。人の工数の上の端(= 無人化率の低い方)に、問い1つ × 5分を足す。全部を人が書いたら = AI の PR も 120分。ボットを含むその週にマージした PR で数え、決裁用の下に内訳(工数【推定】・PR・問い・コメント・レビュー・手直し【実測】)と N 週の合計を出す。コメントはボットを除く(`pnpm kpi --roi` と同じ。費用のページだけボットを含む)。人と AI の PR が無い週は — |
| 仕様の在庫: 作る待ち | 状態が「承認済み」で、仕様・設計書・ADR・場面・賭けの外(コード・手引き・手順書・スキル)から番号が指されていない仕様。日数は状態の行の最初の日付から |
| 仕様の在庫: 承認待ち | 状態が「下書き」の仕様 |
| 引き渡し: 実装の完了から受け入れまで | 受け入れの記録(`docs/acceptance/`)の第1回の日付 − 記録の頭の「実装の PR」のうち最後にマージした日(日本時間・日)。週の中央値。第2回からは数えない。PR が読めなければ数えず「読めなかった物」へ |
| 引き渡し: 受け入れの点数 | その週の回を合わせた 合 ÷(合+否)。外れた理由(要求・設計・AI の仮決め・実装)の内訳も([acceptance.md](acceptance.md)) |
| 引き渡し: 設計が原因の作り直し | 設計書の「作り直しの記録」の行のうち、入った工程が「設計」の割合(行の日付の週) |

## 4. 数を正しく保つために

- **AI が手伝った PR**: `ai-label.yml` が、本文に AI の印(Claude Code の署名)がある PR と AI のボットが作った PR にラベル `ai:assisted` を付ける(付けるだけ)。印の無い AI の PR(ほかの道具で書いた・署名を消した)は**人が手で付ける**。間違って付いたら外し、本文の印も消す。費用のページの人の時間も同じラベルで見分ける。
- **障害**: 振り返り(S1・S2)に「戻るまで」「変更が原因」の行を書く([runbooks/incident.md](../runbooks/incident.md) の 6)。書いていないと、読めなかった物に件数が出る。S3(振り返りを書かない障害)は数に入らない。
- **仕様**: 作り終えたら状態を「完了」にする。作る待ちに作った仕様が残っていたら、状態を直すか、作った物(コード・手引き)から仕様か設計書の番号を指す。
- **使い始める前の PR** にはラベルが無い(さかのぼって付けない)。並びはラベルを入れた週から読む。
- **無人化率**は分が決まった目安(【推定】)。測った時間ではないので、実感とずれたら `people.yaml` の分を直す(費用のページの人の時間も一緒に変わる)。AI の PR はラベルか本文の印で見分ける(費用のページと同じ)ので、ラベルだけの「AI が手伝った」とずれることがある。人の手直しと、Claude Code への指示・会話の時間は式に入らない。ボットの PR は人の工数にも全部を人が書いたらにも同じ分で入るので、ボットの PR が多い週は少し下がる。コメントが 100件・レビューが 50件を超えた PR は、超えた分を数えず「読めなかった物」に件数が出る。

## 5. 見る順(毎週30分の振り返りで)

1. 決裁用の並びで、変更の失敗率と復旧の時間が悪くなっていないか(「壊れていないか」)。無人化率は毎週いちばん目に見る入力の数だが、北極星ではない([kit/roadmap.md](../kit/roadmap.md) の 4)。壊れていない週だけ、上がったかを見る。
2. デプロイの数とリードタイム(「速くなったか」)。
3. AI の PR で人の介入なしの割合。上がっていて失敗率が横ばいなら、任せる範囲を広げる候補([concepts/people-and-ai.md](../concepts/people-and-ai.md) の 5)。
4. 改善用の「人が答えた問いの種類」で、同じ種類が続いていれば、観点・ルール・テストにする([guides/human-review.md](human-review.md) の 5)。
5. 引き渡しで、待ちが長い・設計が原因の作り直しが多い継ぎ目を**1つだけ**選び、入力・出力・人が判断する所を決めて1回回す(例: 実装が終わった日に受け入れを始める・設計に進む基準を見直す)。次の週の数で効いたかを見て、効いたら決まり(スキル・手引き)にする([concepts/line.md](../concepts/line.md) の 2)。
6. 仕様の在庫が0に近い・保守の PR ばかりなら、企画が詰まっている。`/new-feature`・`/bet` で次の仕様を作る([concepts/line.md](../concepts/line.md) の「企画が詰まりになる」)。
