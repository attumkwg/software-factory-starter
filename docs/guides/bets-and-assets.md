# 機能ごとの賭け(CPF → PMF を小石を残しながら)と、資産・費用の案

> 機能1つぶんの「確かめながら作る」を、**賭け(bet)**として記録する。対話で進めるときは `/bet`。
> プロダクト全体の始め方は [before-pmf.md](before-pmf.md)(`/kickoff`)。この手引きはその**1段下**。
> 後半の「資産か費用か」は**一般的な考え方の整理**で、会計や税の助言ではない。**確定は税理士・監査法人と**決める。

## 言葉

| 言葉 | 意味 | 確かめる物 |
|---|---|---|
| CPF(困りごとが合う) | その困りごとは本当にあり、困っている人が十分いる | 話を聞く・行動のデータ・問い合わせ |
| PSF(解決策が合う) | その解決策で困りごとが消える | 画面だけ・裏を手作業で・試作 |
| PMF(市場に合う) | お金を払って使い続け、勧めなくても広がる | 継続率・「無くなったらとても困る」40%・紹介 |
| 賭け(bet) | 機能1つぶんの仮説と、その CPF → PMF の記録 | `docs/product/bets/B-NNNN-*.md` |
| 小石 | 足すだけの判断の記録(日付・何をした・結果・判断・証拠) | 賭けのファイルの「小石」の表 |

## 2段の入れ子

```
プロダクト全体  docs/product/plan.md            ① 困りごと → ② 解決策 → ③ お金 → ④ 続けて使うか → PMF   (/kickoff)
 └ 機能(賭け)  docs/product/bets/B-NNNN-*.md  idea → cpf → psf → rollout → adopted(定着)/ retired(撤去)  (/bet)
     └ 仕様・設計・PR  docs/specs/ docs/designs/                                                         (/new-feature)
```

- **プロダクト全体が PMF の前**: 賭けは「全体の計画(plan.md)の仮説を確かめるため」だけに開く。機能を増やして PMF を探さない(いちばん危ない思い込みが先)。賭けの「親」には plan.md のどの仮説かを書く。
- **プロダクト全体が PMF の後**: 賭けが主役になる。賭けの「親」には、動かしたい指標(継続・解約・問い合わせ・単価など)を書く。新しい客層・新しい用途を狙うときは、全体を「新しい版」として `/kickoff` からもう一度回す(PMF は繰り返せる)。
- **PMF の後も賭けを回す。** 「作れば使われる」は PMF の後でも思い込み。機能ごとに線を決めて確かめ、外れたら撤去する。使われない機能は、保守の費用だけがかかり続ける。

## 段階

| 段階 | 確かめること | おもな手 | 次へ進む目安 |
|---|---|---|---|
| `idea` | なぜ今これか・親の仮説(か指標)につながるか | 下調べ・既存の問い合わせや数字を見る | 確かめる線と期限を決めた |
| `cpf` | その困りごとは、使っている組織に本当にあるか | 話を聞く・問い合わせ・行動のデータ | 合格の線を通った |
| `psf` | この解決策で、その困りごとが消えるか | 画面だけ・裏を手作業で・機能フラグの裏の試作 | 合格の線を通った |
| `rollout` | 一部の組織に出して、使われ続けるか | 機能フラグで一部に出す・使う割合と継続を見る | 合格の線を通った |
| `adopted` | (定着)全部に出して、効いているかを見続ける | 指標を見る・保守 | 使われなくなったら撤去を決める |
| `retired` | (撤去)コード・フラグ・表を消す | 撤去の PR | — |
| `dropped` | (やめた)途中でやめた。**立派な成果**として何が分かったかを残す | — | — |

- **段階は飛ばさない。** 困りごとが既に確かめられている(全体の計画で確かめた・問い合わせが山ほどある)なら、その段階で `飛ばす` の小石を理由つきで1行書いてから次へ。黙って飛ばすと `pnpm bets` が落ちる。
- **機能の PMF**(`rollout` の合格の線)は、その機能を使う組織の割合・使い続ける割合・解約や問い合わせへの効き目で書く。「良さそう」では書かない。

## rollout の確かめ方(段階的な公開と A/B)

`rollout` は「一部の組織に出して、使われ続けるか」。出し方と数え方は機能フラグと利用の記録([feature-flags.md](feature-flags.md))。

| 型 | すること | 合格の線の形 | 向いている時 |
|---|---|---|---|
| **段階的な公開**(ふつう) | 運営が選んだ組織に入れ、`usage-report` の継続率(初めて使った週ごとの組の、N 週後に使った割合・N 週続けた割合)を見る | 「入れた組織の 70% 以上が4週続けて使う」(「続けて」なら `continuedPct`・「4週後も」なら `activePct` と線に書く) | PMF の前。組織が少なく、使わない組織に話を聞きに行ける |
| **A/B** | 組織(か人)をくじで2組に分け、B の組にだけ入れて、同じ指標を A の組と比べる | 「B の継続が A より5ポイント以上高い(組ごとに 400 以上で)」 | 比べる指標が1つに決まっていて、組ごとに十分な数がある |

- ⚠️ **PMF の前は、ほとんどの場合 A/B の数が足りない。** 50% が 60% になる(10ポイント)くらいの差を見分けるには、組ごとに 400 前後が目安で、差が小さいほどもっと要る。数が足りないまま比べると、偶然の差を「効いた」と読んでしまう。足りなければ段階的な公開で確かめ、話を聞いて理由を集める。
- A/B でも、線と期限は確かめる前に書く。**途中で数を見て止めない**(良さそうに見えた所で止めると、偶然を拾いやすい)。
- どの組織がどちらの組かは、賭けのファイルに書かない(運営の記録へ。個社の名前と数字を書かない決まりと同じ)。
- キットには、くじで組を分ける仕組みと組ごとの差の集計はまだ無い(数が足りる段階になったら足す。ADR 0025 の見直す合図)。

## 線を先に決める・小石を足す

- **合格の線・撤退の線・期限を、確かめる前に書く。** 後から決めると、都合よく読んでしまう([before-pmf.md](before-pmf.md) と同じ)。
- 小石の判断は次のどれか。

| 判断 | 意味 | 段階 |
|---|---|---|
| `開く` | 賭けを始めた(最初の1行) | `idea` のまま |
| `続ける` | 途中の結果。まだ決めない | そのまま |
| `進む` | 合格の線を通った | 次の段階へ |
| `飛ばす` | この段階は確かめなくてよい(理由を「結果」に) | 次の段階へ |
| `変える` | 解決策・相手・確かめ方を変えて、もう一度 | そのまま(線を引き直すなら `線を動かす` も) |
| `戻る` | 前の段階の前提が崩れた | 1つ前へ |
| `線を動かす(@名前)` | 線か期限を変えた。**本人の判断として**名前を残す | そのまま(「線と期限」に新しい行) |
| `やめる` | 撤退の線に当たった・やめると決めた | `dropped` |
| `撤去する` | 定着した機能を消すと決めた | `retired` |

- **期限を過ぎたら決める。** 進む・変える(線を引き直す)・やめるのどれか。期限を過ぎて決めていない賭けは `pnpm bets` の一覧に ⏰ で出る(毎週の振り返りで見る)。
- 証拠はリンクで残す(インタビューの記録・PR・ダッシュボード)。**個社の名前と数字は書かない**(「使う組織の 32%」のように割合まで)。

## 線に届かなくても進む(意思で進む)

- 線は**目安**。届かなくても、本人が「それでもやる」と決めれば進んでよい。キットは止めない([ADR 0035](../adr/0035-fit-journey-is-a-guide.md))。
- 進むときに残す物は3つ: **引き受けた危なさ**(何が外れたら全部むだになるか)・**止める線と期限**(どうなったらやめるか)・**決めた人**。小石の判断は `意思で進む(@名前)`、表は「意思で進んだ判断」。
- `pnpm bets` は ⚑ で一覧に出し、止める線の期限を過ぎたら ⏰ で知らせる。続けるか・やめるかを決めて、小石を足す。
- 線を甘くして通す(`線を動かす`)より、意思で進んだと残すほうが、後から「なぜ出したのか」「いつやめるのか」が分かる。

## ロードマップの1枚

- `pnpm bets --roadmap` が、賭けを「いま確かめている・次にやる・定着した・やめた」に分けた**社内の版**を出す(段階・何を・親・次に決める日。⚑ 意思で進んだ・⏰ 決める日を過ぎた)。
- `pnpm bets --roadmap --public` は**社外の版**(営業の商談・展示会・LP 用)。時期を約束しない書き方で、題名と段階の言い換えだけ。親・日付・賭けの ID・やめた物は出さない。
- `--write` で `docs/product/roadmap.md`・`roadmap-public.md` に書く。正は賭けのファイルなので、手で直さない。週の振り返りで作り直す。

## PR の色分け(取り組み・作業の種類)

全部の PR の本文に、2つを書く(PR テンプレートの「🎯 取り組み」。空なら CI が落ちる)。これが、後で資産と費用を分けるときの元になる。

| 欄 | 書く物 |
|---|---|
| 取り組み | `bet:B-NNNN`(どの賭けか)/ `保守` / `不具合` / `基盤` / `セキュリティ` |
| 作業の種類 | `探索`(確かめるための試作・捨てる前提)/ `作り込み`(本番の機能を作る・足す・良くする)/ `保守`(今の価値を保つ。依存の更新・軽い直し・不具合)/ `撤去` |

- 1つの PR に1つずつ。混ざるなら PR を分ける(1 Issue = 1 PR)。
- Renovate などのボットの PR は、空なら `保守` / `保守` とみなす。

## 資産か費用か(案の出し方)

### 一般的な整理(日本の「自社利用のソフトウェア」)

- SaaS の機能は、日本の基準では多くの場合「**自社利用のソフトウェア**」として扱われる。
- **将来の収益の獲得(か費用の削減)が確実と認められるとき**に資産に載せ、決めた年数(5年以内がよくある)で償却する。確実と言えない探索(研究開発にあたる部分)は費用。
- だから、**「合格の線を通った」という記録が、資産に載せる根拠の資料になる。** 小石を残すことは、会計の面でも効く。

### 案の表(賭けの段階 × 作業の種類)

| 段階 | 作業の種類 | 区分の案 | 理由 |
|---|---|---|---|
| `idea` / `cpf` / `psf` | 何でも | **費用** | 収益が確実とは言えない(探索) |
| `rollout` | `探索`(捨てる前提の実験) | **費用** | 同上 |
| `rollout` | `作り込み`(psf の合格の後の、本番の作り込み) | **資産の候補** | 合格の記録がある |
| `adopted` | `作り込み`(機能の追加・性能の向上) | **資産の候補** | 価値を高める改良 |
| どこでも | `保守`(不具合・依存の更新・軽い直し) | **費用** | 今の価値を保つだけ |
| `retired` / `rollout` からの `dropped` | `撤去` | 資産に載せた物があれば**除却の候補** | 使わなくなった |

- 賭けのファイルの「会計区分の判定」には、**段階が変わるたびに**、その段階の案を1行足す(`/bet` が書く)。「確定した人」は人が答えるまで `未確定`。
- ⚠️ 会社の方針(小さい会社は全部費用にする、など)・税務の扱い・金額の重要性で変わる。**キットは案と根拠をそろえるだけで、決めない。**
- ⚠️ 海外の基準で決算するなら別の整理が要る(たとえば米国の基準は、段階での判定をやめる方向に変わった)。

## リポジトリに置く物・置かない物

**このリポジトリは公開されるかもしれない前提で書く。** 金額は置かない。

| 置く(リポジトリ) | 置かない(会計ソフト・非公開の表) |
|---|---|
| 賭けの ID・仮説・線・判断の記録・証拠のリンク | 人件費・時間単価・給与 |
| PR ごとの取り組みと作業の種類 | 売上の金額・顧客ごとの単価 |
| 区分の案と理由・確定した日と人 | 確定した金額・仕訳 |
| 指標は割合まで(「使う組織の 32%」) | 個社の名前と数字 |

- **コスト**: 人の時間は会計の側で、賭けごとの PR の数を目安に割り振る(PR の一覧は「取り組み」で探せる)。
- **利益**: 賭けの合格の線に書いた指標と、会計の側の売上を突き合わせる。機能ごとの売上はきれいに出ないので、「その機能を使う組織とそうでない組織の継続・単価の差」で見る。
- 月1回の集計は `/ledger`(費用のページの `ledger.csv`。賭けごとの人の時間を PR の作業の種類と段階で分けた案と根拠の PR)。AWS の費用はタグ `Bet` で賭けに割り振る。賭けごとの PL(売上 − 原価の幅)は費用のページ([cost-dashboard.md](cost-dashboard.md) の 6.)。時給と売上は非公開の置き場にだけ置く。

## 機械の守り

| 守り | していること | どこで |
|---|---|---|
| 線を先に決める | 結果の小石より前に、その段階の線と期限があるか(決めた日 ≦ 小石の日付) | `pnpm bets`(CI) |
| 段階を飛ばさない | 小石の判断をたどった段階が、「いまの状態」の段階と合うか・飛ばしていないか | `pnpm bets`(CI) |
| 線を黙って動かさない | 同じ段階の線が2行以上なら、`線を動かす(@名前)` の小石があるか | `pnpm bets`(CI) |
| 区分の案を残す | 入った段階ごとに、会計区分の判定の行があるか | `pnpm bets`(CI) |
| 期限切れの見張り | 期限を過ぎて決めていない賭けを ⏰ で一覧に出す(落とさない) | `pnpm bets`・毎週の振り返り |
| PR の色分け | PR の本文の「取り組み」と「作業の種類」が空でないか・`bet:` なら賭けのファイルがあるか | CI(PR の本文。`.github/workflows/pr-work.yml`) |
