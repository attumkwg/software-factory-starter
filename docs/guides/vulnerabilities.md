# 脆弱性(CVE)の精査と対応方針: `/cve` の手引き

> 見つける道具(Trivy・Dependabot の通知・Renovate)はもうある。足りなかったのは「**うちに関係あるか**」と「**いつまでに・どう直すか**」を決める所。
> それを `/cve` が調べて案にし、人は**2つだけ**決める。記録は [docs/security/vulns.md](../security/vulns.md)、漏れは `pnpm vulns` が見る。

## 1. いまあるもの・`/cve` が足すもの

| 仕組み | していること | 足りない所(`/cve` が埋める) |
|---|---|---|
| Trivy(`ci.yml`) | PR ごとに依存とイメージの既知の CVE。HIGH・CRITICAL で止める | 中以下は見ない・コードが動いていない間に出た CVE は拾えない |
| `vuln-scan.yml` | Trivy と zizmor を最新の DB で(毎週月曜 5:00 に自動・手動でも)。落ちたら Issue | 「関係あるか」は人が読む |
| Dependabot の通知 | GitHub の勧告と lockfile を突き合わせる([manual-setup.md](manual-setup.md) の 1 の 7 で有効に) | 開発用か本番か・届くかは見ない(pnpm の間接の開発用の依存も runtime と出る) |
| Renovate(`renovate.json`) | 上げる PR を出す(脆弱性は待たずに) | どれを急ぐかは決めない |

## 2. 呼び方

| 呼び方 | いつ | すること |
|---|---|---|
| `/cve CVE-2026-XXXXX`・`/cve GHSA-xxxx-xxxx-xxxx`・`/cve <勧告の URL>` | ニュースで見た・誰かに聞かれた | その1件を精査する |
| `/cve`(引数なし) | 毎週・`vuln-scan.yml` の Issue が立ったとき | **見回り**: 通知・定期の結果・主な依存と基盤の発表の直近2週間ぶんを集めて、全部を精査する |
| `/checkup` から | 点検で「重い脆弱性が開いていないか」が赤のとき(点検の台帳ができてから) | 見回りと同じ |

## 3. 精査の6段(1件ずつ、この順に)

| # | 確かめること | 確かめ方 | 違えば |
|---|---|---|---|
| 1 | **入っているか** | `pnpm-lock.yaml`・Dockerfile のベース(`node:24-trixie-slim`・distroless・`debian:trixie-slim`)・Terraform のプロバイダー・ワークフローの Action | 該当なし |
| 2 | **版が当たるか** | 勧告の範囲と、入っている版を**全部**(同じ依存が複数の版で入ることがある) | 該当なし |
| 3 | **どこで動くか** | 本番の依存 / 開発用 / CI だけ / 手元だけ。`pnpm why <名前> -r` で入ってくる道を出し、本番のイメージ(`Dockerfile` の実行用の段)に入るかを見る | 開発用・手元だけなら重さを1段下げる |
| 4 | **穴のある使い方をしているか** | 勧告の「条件」(使う関数・設定・機能)を、コードと設定で検索する | 届かない |
| 5 | **外から届くか** | 公開の API・画面・メール・管理の画面・中だけ(VPC の中・運営だけ) | 届く道が無ければ重さを1段下げる |
| 6 | **悪用が出回っているか** | CISA の KEV(悪用が確認された一覧)・EPSS(悪用される見込みの点数)・公開の PoC | 出回っていれば重さを1段上げる |

- 結果は3つ: **該当なし** / **入っているが届かない** / **届く(要対応)**。
- **分からない所は推測で埋めない。** 4 や 5 が確かめきれないなら「届く」とみなして方針を出し、分からない所をそのまま書く。

## 4. 期限(届くものだけ)

重さは CVSS の点数ではなく、**上の精査で上げ下げした後の重さ**。

| 重さ | 期限 | 例 |
|---|---|---|
| 緊急(届く+悪用が出回っている、または認証・テナント分離・秘密に触る) | **当日〜72時間** | 本番の依存の認証の抜け |
| 高 | 7日 | 外から届く DoS |
| 中 | 30日 | 条件が限られる情報の漏れ |
| 低・届かない | 次の定期の更新(Renovate)で | 開発用の依存の中の穴 |

## 5. 直し方(上から順に検討する)

1. **上げる**: 直った版に上げる。Renovate の PR があればそれを使い、無ければ PR を出す。下の 8 の自己点検も。間接の依存でも、直った版が親の範囲の中にあるなら(古いのは lockfile だけ)、`pnpm update -r <名前>` で lockfile だけを上げる(2 の overrides は使わない。毎月の lockfile の見直しを待たない)。
2. **間接の依存だけ上げる**: 親が古い版を固定しているときは、`pnpm.overrides`(ルートの `package.json`。または `pnpm-workspace.yaml` の `overrides`)。親が壊れないかテストを全部回し、親が直したら外す(外す日をコメントに)。
3. **置き換える・外す**: 親の更新が止まっている・使っていない機能のための依存なら外す。
4. **設定で塞ぐ**: 直った版がまだ無いとき。WAF のルール・機能を止める・設定を変える(手で塞いだことを手順書 `docs/runbooks/` に)。
5. **基盤の穴は、作り直して出し直すまで**: Node.js・PostgreSQL・土台のイメージ(distroless など)の穴は、上げただけでは本番に届かない。手順書 [../runbooks/platform-vuln.md](../runbooks/platform-vuln.md)(作り直し → stg → 本番・手元の処理系も上げる)。
6. **届かないので外す**: Trivy の指摘なら `.trivyignore.yaml` に**理由と見直す日**を書く(危険度「高」のファイル)。Dependabot の通知は「コードを使っていない(vulnerable code is not actually used)」で閉じる。**閉じるのは人**(AI は閉じ方を渡すだけ)。

## 6. 人が決めるのは2つだけ

| 問い | 種類 | いつ聞くか |
|---|---|---|
| 期限までに直せない・直すと壊れるとき、**受け入れて期限を延ばすか** | 戻せないリスク | 1〜4 のどれも期限に間に合わないとき |
| 緊急のとき、**本番をすぐ出し直すか** | 事業判断(営業時間・お客さんへの連絡) | 重さが緊急のとき |

それ以外(関係あるか・重さ・直し方・期限)は `/cve` が決めて、理由を残す。お客さんに知らせる必要があるか(直した後)も人が決める。

## 7. 記録の置き場(**公開のリポジトリなので**)

| 結果 | 置き場所 |
|---|---|
| 該当なし・入っているが届かない | [docs/security/vulns.md](../security/vulns.md) に1行(日付・ID・パッケージ・結果・理由・見直す日) |
| **届く・まだ直していない** | **リポジトリにも Issue にも PR の本文にも書かない。** GitHub の非公開の Security Advisory の**下書き**に、精査と方針と期限を書く(下)。直す PR の題名と本文は「依存を上げる」程度にとどめる |
| 届く・直した | 直した PR がマージされてから `vulns.md` に「届く・直した」の1行 |

- 公開のリポジトリでは、Issue・PR・コミットの文は誰でも読める。**直す前に「どこが・どう届くか」を書くと、攻め方の案内になる。**
- 非公開の下書きの作り方: リポジトリの Security → Advisories → New draft security advisory(または `gh api -X POST repos/{owner}/{repo}/security-advisories`。下書きは管理者と招いた人だけが見える)。**本文に元の勧告の ID(GHSA-… / CVE-…)を書く**(`pnpm vulns` がそれで「精査済み(非公開)」と数える)。下書きは公開しない(公開するかは人が決める)。
- 下書きを読めない人は `pnpm vulns` で「確かめられなかった」と出る(落ちない)。

### `pnpm vulns`

- Dependabot の開いている通知と `vulns.md` を突き合わせ、🔴 まだ精査していない通知・🔒 非公開の下書きで扱っている通知・📝 記録はあるが開いたままの通知・⏰ 見直す日が来た記録・⚠️ 書き方の問題を出す。
- `pnpm vulns --strict` は 🔴・⏰・⚠️ が1件でもあれば 1 で終わる(点検で使う)。
- 通知は `gh` で読む。`gh` が無い・ログインしていない・権限が無いときは落とさずに「確かめられなかった」と出し、記録の側だけを見る。
- CI では回さない(ワークフローの `GITHUB_TOKEN` は Dependabot の通知を読めない。見直す日が来ただけで、関係ない PR を落とさないため)。

## 8. 依存の更新の自己点検

Renovate の PR・`/cve` が出す「上げる」PR で、マージの前に確かめる。

| 依存 | 触る所 | 危険度 |
|---|---|---|
| `hono` | API と画面のサーバーの入口・Cookie・ヘッダー | **高**(小さい版でも) |
| `jose` | ID トークンと Cookie の署名の確かめ | **高** |
| `pg` | DB の接続・TLS | **高** |
| `drizzle-orm`・`drizzle-kit` | DB の読み書き・移行の生成 | **高** |
| `@tanstack/react-start` | 画面の SSR・サーバー関数 | **高** |
| ほかの本番の依存 | — | 中(`renovate.json` のとおり) |
| 開発用の依存の小さい更新 | — | 低(`renovate.json` のとおり) |

- `renovate.json` は大きい版だけを `risk:high` にする。**上の5つは小さい版でも「高」として見る**(PR の危険度の欄を「高」にし、人が2人で見る)。
- 確かめること:
  - 変更履歴(リリースノート)に、セキュリティ・既定の値の変更・壊れる変更が無いか。
  - `pnpm test` と `pnpm test:integration`(認証・Cookie・RLS・2社のテストが通るか)。画面の依存なら `pnpm test:e2e` も。
  - `pnpm why <名前> -r` で、同じ依存の古い版が残っていないか(残っていれば 5 の 2)。
  - 公開から日が浅い版を入れていないか(`pnpm-workspace.yaml` の `minimumReleaseAge`。緊急で外すなら理由を PR に)。
