# 人が見る所を絞る(未確定事項・人向けのまとめ・上流からの作り直し)

> 元にした考え方: freee の横路隆さん(CAIO)の講演「freeeにおける大規模ソフトウェアファクトリーの実践」(AI×開発組織 Summit 2026・2026-10-16)。
> [スライド](https://speakerdeck.com/freee/freee-niokeru-kibo-no-jissen-aix-kaihatsu-soshiki-summit-2026)

## 考え方

- **人が全文を読むのではなく、判断が要る所だけを見る。** 完全に無人(誰も分からない物が溜まる)でも、人が全部読む(人が詰まり所になる)でもない。止められる物は機械・判断が要る物は AI・**残りだけ人へ**。
- **AI 用の資料と、人向けのまとめを分ける。** 設計書は AI のために省略せず網羅的に書く(**正はこちら**)。人はそれを開かず、別に作る「全体像・事実・理由・問い」だけを見る。
- **観点を溜めるほど、人が見なくていい範囲が広がる。** 人がレビューで気づいた観点を [review-viewpoints.md](../review-viewpoints.md) に戻すと、次から AI のレビューとテストが判定できる。見る量を減らすのは、読み飛ばしではなく「確認済み」を増やすこと。
- **誤りは、入った工程から作り直す。** コードだけ継ぎ当てない。

## 1. 人に聞くのは4つだけ

| 種類 | 例 | なぜ人か |
|---|---|---|
| **事業判断** | 作る・作らない・優先度・料金・受け入れ基準の線引き・出す/出さない | 顧客価値の責任を持つのは人 |
| **利用者の挙動** | 利用者がどう使うか・どう受け取るか(画面の流れ・既定値・文言の誤解) | 実際の利用者を知っているのは人 |
| **他チームとの契約や制約** | 外部サービス・他チームの API・契約書・法律・SLA | コードやドキュメントの外にある |
| **戻せないリスク** | データを消す・移す・外へ送る(メール)・お金・権限を広げる・公開した API の形・秘密 | 間違えたら取り返せない |

- **それ以外は AI と機械に任せる。** 調べれば分かること(既存のコード・用語集・ADR・権限の表)・型どおりの作り(ふつうの一覧・登録・更新)・テストで確かめられることは、人に聞かない。AI が決めて、設計書の「決めたこと」に理由と一緒に書く。
- 🔁 「聞きたくなった」ときは、まず4つのどれに当たるかを書く。**どれにも当たらなければ聞かない。**
- このキットの危険度「高」(認証・認可・権限の表・移行・infra・CI)は、ほぼ「戻せないリスク」に当たる。

## 2. 未確定事項(AI の仮決めと、人の承認を分けて残す)

AI は4つの問いにぶつかっても**止まらない**。いちばんありそうな案で**仮に決めて先へ進み**、それを「未確定事項」に1行書く。人は後でまとめて答える(夜に AI が回り、朝に人が判断する形)。

### 置き場所

- **正は機能ごとの設計書** `docs/designs/NNNN-<名前>.md` の「未確定事項」の表(テンプレートは [designs/_template.md](../designs/_template.md))。要求・設計・実装のどの工程で出た仮決めも、同じ表に書く。
- **PR の本文**の「🧑‍⚖️ 人に判断してほしい所」に、まだ「仮決め」の行を写す(人はここで答える)。
- **一覧**: `pnpm decisions` で、全部の設計書から「仮決め」「導入時に決める」「保留」の行を集めて出す。

### 書式

| 番号 | 工程 | 種類 | 仮決め(設計した事実) | なぜそうしたか | 人が判断する問い | 状態 |
|---|---|---|---|---|---|---|
| U-1 | 設計 | 戻せないリスク | 解約の削除は API を作らずコマンドだけにした | 鍵1本で全データを消せないようにするため | 運営が手でコマンドを打つ運用でよいか | 仮決め |

- **番号**は設計書の中で U-1, U-2 …(消さない。取り下げても番号は使い回さない)。
- **工程**: ナレッジ / 要求 / 設計 / 実装 / テスト。
- **種類**: 上の4つのどれか。**4つに当たらない物は、ここに書かない**(「決めたこと」へ)。
- **状態**(この書き方でそろえる。`pnpm decisions` が読む):

| 状態 | 意味 | 書く人 |
|---|---|---|
| `仮決め` | AI が決めた。人はまだ見ていない | AI |
| `承認(@名前 YYYY-MM-DD)` | 人がこのままでよいと答えた | 人の答えを AI が写す |
| `変更(@名前 YYYY-MM-DD: どう変えるか)` | 人が違うと答えた → `/rework` でその工程から作り直す | 人の答えを AI が写す |
| `保留(@名前: YYYY-MM-DD までに決める)` | 人が「後で決める」と決めた | 人の答えを AI が写す |
| `取り下げ(理由)` | 作り直しで問い自体が無くなった | AI |
| `導入時に決める(キットの既定は @名前 YYYY-MM-DD に承認)` | キットの既定としては人が承認した。けれども答えがプロダクトごとに違うので、使い始めた人が決める | キットの持ち主の答えを AI が写す |

### 承認の流れ

1. AI が仮決めして、設計書の表に `仮決め` で1行足す。作業は止めない。
2. PR の本文に、`仮決め` の行を「事実 / 理由 / 問い」で写す。
3. 人が PR のコメント(か会話)で、番号ごとに **承認 / 変更 / 保留** を答える。
4. AI が表の状態を書き換える(**人の答えが無いのに `承認` にしない**)。どのコメントで答えたかのリンクも添える。
5. `変更` があれば `/rework` で、その工程から下流を作り直す。
6. **`仮決め` が1件でも残る PR はマージしない**(`pnpm decisions --strict` が 1 で終わる。CI の「Biome・型・単体」でも流すので、残っていれば CI が落ちる)。`保留` は期限つきなので残してよい。ただし期限が過ぎると、どの PR の CI も落ちる(答えるか期限を延ばす)。

### 導入時に決める(キットの既定でマージし、使う人が決める)

キットには、使う人の事業・利用者・契約や法務の確認で**答えが変わる問い**がある(例: 利用規約の同意し直しの基準・点検の担当者・検索に載せるか)。キットの持ち主がキットの既定として承認しても、使う人のプロダクトの答えではない。そういう行は `導入時に決める` にする(ADR 0026・[designs/0013-decisions-at-adoption.md](../designs/0013-decisions-at-adoption.md))。

- **どの行をそうするかは、キットの持ち主が決める**(AI が仮決めや承認を勝手に書き換えない)。括弧に既定を承認した人(`@名前`)が無いと書き方の問題になる。
- `pnpm decisions --strict`(CI)は落ちない。キットの既定のままマージしてよい。
- 使い始めた人は `pnpm decisions --adopt` で一覧を見る(`/tailor` が設計書ごとに1問ずつ聞く)。既定のままでよければ `承認(@名前 YYYY-MM-DD)`、変えるなら `変更(…)` にして `/rework`。書き換えるのは状態の列だけ。
- **本番に出す前は `pnpm decisions --launch`**。`仮決め`・`導入時に決める`・書き方の問題が1件でも残っていれば 1 で終わる(期限内の `保留` は止めない)。

## 3. 人向けのまとめ(PR の本文)

設計書(AI 用)は全部の観点を省略せずに書く。人には PR の本文に、次の4つだけを出す。`/design` と `/review-pr` が作る。

```markdown
## 🧭 全体像
<3行まで。何を・誰のために・どこを変えるか。図が要るなら mermaid を1つ>

## 🧑‍⚖️ 人に判断してほしい所
| 番号 | 種類 | 設計した事実 | なぜそうしたか | 人が判断する問い |
|---|---|---|---|---|
| U-1 | 戻せないリスク | 削除は API でなくコマンドだけ | 鍵1本で消せないように | 運営が手で打つ運用でよいか |

## 🔎 観点ごとの扱い
| 観点 | 扱い | 理由 |
|---|---|---|
| データモデル | 最重要 | 新しい表。解約で消す一覧に入れる |
| API | 機械で検証 | 権限の表のテストが全ロールを叩く |
| 状態遷移 | 低優先 | 状態を変えない |

## 🤖 AI が決めたこと(聞かなかった)
<件数と、設計書の「決めたこと」へのリンクだけ>
```

- 問いは必ず **「設計した事実 / なぜそうしたか / 人が判断する問い」の3つを並べる**。「全文を読み解いて」ではなく「この設計でよいか」を答えられる形にする。
- 問いは **「はい / いいえ」か選択肢で答えられる**ように書く。
- 標準の作り(ふつうの CRUD)や、調べれば分かることは出さない。

### 観点ごとの扱い(5つ)

観点の一覧は [review-viewpoints.md](../review-viewpoints.md)(共通の8つ+このプロダクト特有)。変更ごとに、観点のそれぞれへ次のどれかを**理由つき**で付ける。

| 扱い | いつ | 人は |
|---|---|---|
| **最重要** | 4つの問いに当たる・戻せない | 必ず読んで答える |
| **採用** | この変更で中身が変わる | 「事実」を読む |
| **軽く確認** | 変わるが、既存の型どおり | 1行だけ見る |
| **機械で検証** | テスト・型・lint・CI が判定する | 見ない(どのテストかを理由に書く) |
| **低優先** | この変更ではほぼ関係しない | 見ない(理由を1行) |

## 4. 上流から作り直す

レビューの指摘・`変更` の答え・不具合が出たら、**誤りが入った工程**を先に決める。そこを直し、下流は一式を差分で作り直す。手順は `/rework` スキル。

```
ナレッジ(用語集・領域の説明・ADR)→ 要求(仕様)→ 設計(設計書)→ 実装(コード)→ テスト
```

| こうだったら | 入った工程 |
|---|---|
| 用語集・領域の説明が古い・無い ので AI が取り違えた | ナレッジ |
| 仕様どおりに作ったのに、欲しかった物と違う | 要求 |
| 仕様は正しいが、設計書の判断が違う | 設計 |
| 設計書どおりに作れていない | 実装 |
| 作りは正しいが、テストが受け入れ条件を確かめていない | テスト |

- 上流を直したら、**下流を自分で順に作り直す**(設計書 → コード → テスト → PR の本文)。コードだけ継ぎ当てない。
- 誤りの原因が「見る観点が無かった」なら、[review-viewpoints.md](../review-viewpoints.md) に観点を足す(次から AI が見る)。
- 仕様・設計書は、**完了するまでは直してよい**。完了(マージして出した)後は記録なので直さず、新しい仕様を足す([docs/README.md](../README.md))。

## 5. 人の介在率を測る

- **人の介在率** = 人が答えた問いの数・人が手で直した回数を、PR ごとに数える。毎週の振り返りで見る([playbook.md](../playbook.md))。数えるのは `pnpm metrics`(毎週 `metrics.yml`)。問いは本文の「人に判断してほしい所」の表の行、手直しは AI の印の無いコミット([metrics.md](metrics.md) の 3)。
- 目標は「人が見る量を減らす」こと。同じ種類の問いが何度も出たら、観点・ルール・テストにして機械に回す。

## 6. 仕様の承認: 設計に進む基準(ブロッカーがゼロ)

仕様の承認(人が必ず止まる3か所の1つ。[concepts/line.md](../concepts/line.md) の 2)の基準は **「ブロッカーがゼロ」**。欠陥ゼロではない。中・小の指摘(言い回し・例の足りなさ・後で決めてよい細部)が残っていても設計へ流す。仕様は完了するまで直してよい(4)。

### ブロッカーの5つ(どれか1つでも当たれば、設計に進まない)

| # | 満たすこと | 当たる例(ブロッカー) | 確かめ方 |
|---|---|---|---|
| 1 | **全体の設計に響く事柄が、確定か仮説かの印つきで書かれている** | 「月ごとに締める」か「いつでも直せる」かが書いていない(表とデータの持ち方が変わる) | AI が第1部の業務の要求と業務ルールを読み、設計の向きが変わる事柄を挙げて、印の有無を並べる |
| 2 | **要求どうし・今の仕様と矛盾していない** | 「誰でも消せる」と、今の仕様の「記録は消さない」がぶつかる | AI が今の仕様(`docs/specs/`)・用語集・ADR と突き合わせ、ぶつかる行を並べる |
| 3 | **捨てた仮説・確かめている途中の仮説が、確定した要求に混ざっていない** | 賭けの小石で「効かなかった」とした案が、印の無い行で残っている | AI が賭けのファイル(`docs/product/bets/`)の小石と照らす。確かめ中の物は `(仮説)` |
| 4 | **未確定の事柄に印がある** | 「承認者は上長(たぶん)」のように、決まっていないのに確定の顔をしている | `(未確定 U-n)` が設計書の未確定事項の U-n とそろっているか。AI が埋めた所に印が無いか |
| 5 | **やり方や技術の判断を書きすぎていない** | 第1部に「キューで非同期に送る」「この表に列を足す」がある | 第1部に、どう作るか(画面の部品・表・API・技術)が入っていないか。入っていれば第2部か設計書へ移す |

- **AI は PR を出す前に5つを自分で確かめ、PR の本文に「設計に進む基準」として5行(満たす / 直した所)で書く**(`/new-feature`)。人はその5行と第1部だけを読んで承認する。
- 5つのどれかに当たったら、その場で仕様を直してから出し直す(設計で継ぎ当てない。4)。直せない(人の答えが要る)物は、設計書の未確定事項に `仮決め` で書いて印を付ければ、4 は満たす。
- **ブロッカーでない指摘は止めない**。PR のコメントに残すか、仕様を直してそのまま設計へ進む。「全部直ってから」にすると、仕様が人の詰まり所になる([concepts/line.md](../concepts/line.md) の 6)。
- 設計(`/design`)は、仕様がこの基準を満たしてから始める。設計の途中で5つのどれかが崩れていると分かったら、仕様に戻って直す(工程は「要求」。4)。
