# ペルソナ → KPI → 計測 → 資産(機能を作る理由を、数で言う)

> 仕様 [0081](../specs/0081-persona-kpi.md)・[0082](../specs/0082-persona-council.md)。型は `docs/product/_template-industry.md`・`_template-personas.md`・`councils/_template.md`・`_template-kpi.yaml`、見本は `industry.md`・`personas.md`・`councils/2026-10-28-kpi.md`・`kpi.yaml`(TODO アプリ・架空)。スキルは `/persona`・`/council`。確かめは `pnpm kpi`・`pnpm bets`。

## なぜ

このキットでやりたいのは、**安全に、KPI を達成したかを見て、資産価値を高める**こと。そのためには、作る機能が「誰の・何を・どれだけ良くしたか」を数で言えないといけない。言えないと、計測も KPI も決まらず、資産に載せる根拠(「将来の収益か費用の削減が確実」)も出せない。守り(CI・関所)は、この線で価値を生む物を安全に出し続けるためにある。

```
業界の前提(industry.md)… /persona
  → ペルソナ(personas.md の P-n。7つの立場の地図)
    → 合議(councils/)… /council: 1人ずつ別の AI → 反論役 → 議論の回 → 議長
      → 人が1回で極端に絞る: KPI の木(kpi.yaml)北極星 1 ← 入力 1〜2 / 守り 1〜2(残りは見るだけ)と、出す前の合否の一覧
        → これを満たすために作る → 何周もレビュー(アイデア・仕様・試作・PR)→ 受け入れのレビュー → 人がマージ
      → 賭け(bets/)が入力の指標を動かす。psf から必須
        → 計測(usage-report・「無くなったら困るか」・手で数える)→ records に値
          → 線に届いたか → 会計区分の判定の根拠(資産の候補か)
```

## 1. 業界の前提とペルソナ(`/persona`)

- **ペルソナが分からないときは探す**: 業界団体・官公庁の資料・求人の職務内容・導入事例や口コミ・法令から、7つの立場ごとの役割の候補を出典つきで出し、人が選ぶ(`/persona` の 0。人が見ている手元でだけ調べる)。
- **業界の前提を先に書く**(`docs/product/industry.md`。客層が2つ以上なら `industries/<名前>.md`)。仕事の流れと道具・決め方とお金・決まり・7つの立場に誰が当たるか・断る理由。業界が違えば、使う人も止める人も断る理由も違う。行ごとに根拠(記録・事例・推測)。
- ペルソナは **7つの立場の地図**を埋める: 使う人・買う人・決める人・止める人・周りの人・失う人・運営。それぞれ1人以上(会社向けなら 10〜20人が目安)。足りない立場があると `pnpm kpi` が落ちる。客層が2つ以上なら、`- 客層:` を付け、客層ごとにそろえる。
- 1人ずつ `## P-n <一言>`。「立場」「決める力(拒否権・予算・影響・なし)」「根拠」と、「成功の物差し(数で)」「制約」「断る理由」「何があれば変わるか」を具体的に。**薄いペルソナは、合議で薄い意見しか出さない**。
- **欲しい成果は数で言える形**にする(「整理が 30分 → 0分」「催促の電話が週5回 → 1回」)。北極星と入力の指標はここから作る。
- 確かめていない物は `(仮説)`。話を聞いたら記録(`interviews/`)へのリンクを足す。
- 番号は変えない。やめたペルソナも消さない(賭けが指しているため)。

## 2. 合議(`/council`)

AI でペルソナの合議を超高速に回す。**合議は判断の参考で、必須の関所にしない**(仕様 0084)。既定は反論役1人の軽い形。下の表の全部(全員の形)を回すのは、KPI を最初に決めるときと人が頼んだときだけ。やる・やらないを言い切るのは、11 の意義の判断役と人。

| 段 | 中身 |
|---|---|
| 1人ずつ | ペルソナごとに別の AI。ほかの答えを見せない(つられないように)。賛否・成功の数・北極星の案・守り・断る理由・考えが変わる条件・確かめたい問い。主張ごとに根拠(記録・事例・推測) |
| 反論役 | 多数の意見の弱い所・見落とした立場・水増しできる数・満場一致の疑い |
| 議論の回 | ほかの人の要約と反論を見て、見直すか |
| 議長 | 北極星(多くの立場の成功が同じ向きに動く数)・入力・守り(止める人・失う人・運営の「悪くしてはいけない数」から)・**出す前の合否の一覧**(数にできない拒否の条件)・次に本物の人に確かめる問い |

- 種類は KPI のほか、**レビュー**(アイデア・仕様・試作・PR)と**受け入れ**。レビューは、議長が案を直しては次の周に出す、を何周も回す(新しい拒否が出なくなるか、3周まで)。**人の前に出てくるのは、レビューを大量に回した後の案だけ**。
- **推測だけの賛成は数えない**。**拒否権の反対は多数決で消さない**(出す前の合否の一覧にし、満たすまで出さない)。
- 記録は `docs/product/councils/YYYY-MM-DD-<名前>.md`(形は `pnpm kpi` が見る。軽い形は `- 形: 軽い` と 2・5・6・7 だけ。7つの立場のそろいは知らせるだけで、落とさない)。
- **決めるのは人、決める場は1回**。題材が何をする物かを先に見せ、KPI は1問ずつ迫る(北極星1つ → 入力は最大2つ → 守りは最大2つ)。外した候補は `watch:`(見るだけの数)へ。拒否権の条件は KPI から外れても「出す前の合否の一覧」で守る。レビューなら、満たすべき条件の候補から作る前に満たす物を選び、受け入れ条件にする(これを満たすために作る)。
- `kpi.yaml` の各指標に `council:`(どの合議か、意義の判断の記録から来たか)。`status: 確か` の指標は、合議(`councils/`)か意義の判断(`verdicts/`)の記録からでないと落ちる。
- 賭けは psf に入る前に、種類「賭け」の軽い合議を回してよい(拒否の条件と、動かす KPI の見込み)。
- 見本の合議([councils/2026-10-28-kpi.md](../product/councils/2026-10-28-kpi.md))では、10人全員が「条件つき」で素直な賛成は0人、北極星の案は10通りに割れた。反論役が仮の北極星の水増しを突き、議論の回で5人が「予告の当たり率」を選び、職人は「人の評価に使われる」と反対した → 「個人ごとの集計を出さない」を出す前の条件にした。

## 3. KPI の木(`docs/product/kpi.yaml`)

| 種類 | 数 | 中身 | 例(見本) |
|---|---|---|---|
| 北極星 `K-0` | 1つ | ペルソナが価値を得た瞬間を数える。売上ではなく、その手前の「価値が届いた」数 | 期限の前に完了したタスクがあった組織の数(週) |
| 入力 `K-1`〜 | 1〜2 | 北極星を動かす物。**賭けはこれを動かす** | 期限の前日の夕方までに、現場が更新済みだった割合 |
| 守り `K-G1`〜 | 1〜2 | 「安全に」の部分。北極星が伸びても、これが悪くなったら止める | 完了を押し終わるまでの秒数 |
| 見るだけ `watch` | いくつでも | 合議の候補のうち、人が外した物。目標も線も持たず、様子だけ見る | 4週後も使っている組織の割合 |

- **多いと運用できない**ので、追う数は北極星を入れて最大5つ。見本では合議の13の候補から、人が4つに絞った([councils/2026-10-28-kpi.md](../product/councils/2026-10-28-kpi.md) の 7)。

- 目標は `target: { value, by }`(少ないほど良い指標は `direction: below`)。PMF の前で決まらなければ書かない(`pnpm kpi` が「目標が無い」と出すだけ)。
- 守りは `limit: { value, direction }`(below = 下回っていること)。
- `status` は 仮説 / 確か / やめた。やめた指標も消さない。

## 4. 計測(どこで数えるか)

| `measure.how` | 何で数えるか | 書く物 |
|---|---|---|
| `usage` | 機能の利用の記録(`platform.feature_usage`)。運営のコマンド `usage-report <機能>` の、使った組織・人の数と継続率(仕様 0012・0022) | `feature`(機能フラグの名前)・`metric` |
| `survey` | 「無くなったら困るか」の問い(仕様 0046) | `source` |
| `manual` | 運営の集計・費用のページ・手で数える | `source`(何で数えるか) |

- 値は `records` に足す(古い行は消さない): `{ date, kpi, value, source }`。
- **割合と件数はリポジトリに書いてよい**(組織名・個人は書かない)。**金額の指標(`money: true`)は、目標・線・値の金額をリポジトリに書かない**。金額は費用のページと同じ非公開の置き場に置き、リポジトリには `reached: true / false`(線に届いたか)だけ。
- 毎週の点検か、賭けの小石を足すときに測って1行足す。`pnpm kpi` が最新の値と線を並べる(届いた・まだ・期限を過ぎた・守れている・超えた)。

## 5. 賭け・仕様・PR とのつなぎ

- 賭けの「いまの状態」に `- ペルソナ: P-n` と `- 動かす KPI: K-n`(守りの K-Gn も)。**psf から必須**(無い・木に無い番号なら `pnpm bets` が落ちる)。idea・cpf は任意。
- 仕様の「なぜ作るか」と、PR の「🎯 取り組み」の「動かす KPI」に、賭けから写す。
- 賭けの線(合格・撤退)は、なるべく動かす KPI の言葉で書く(「入れた組織の K-1 が 70% 以上」)。

## 6. 資産の根拠

- 会計区分の判定(`bets-and-assets.md`)の「理由」に、合格の線と並べて **動かす KPI が線に届いたか** を書く(`K-1: 届いた(2026-11-30 の記録)`)。
- 届いていなくても、自動で費用にはしない。案と根拠をそろえるだけで、確定は人(会計)。

## 7. 既存のリポジトリに入れるとき

キットを丸ごと入れなくても、**`industry.md`・`personas.md`・`councils/`・`kpi.yaml` と `pnpm kpi`・`/persona`・`/council` だけ**入れれば、この線は引ける。業界が違えば `/persona` で前提から作り直す。次に賭けのファイル(`bets/`)を足すと、機能ごとに「どの KPI を動かしたか」が残り始める。CI・関所はその後でよい(穴 G-51 の入口)。

## 8. ループを閉じる(計測 → 戻す)

```
計測(毎週・/bet の結果)→ kpi.yaml の records に1行
話を聞く → interviews/ に「当たるペルソナ」「答えた問い」「戻すこと」
  → /persona の 5: ペルソナ・業界の前提の根拠を 推測 → 記録 に書き換える
  → /council の 7: 回し直す合図(見込みの外れ・守りの超え・賭けをやめた・記録が溜まった)
```

- `pnpm kpi` が知らせる: 追う指標の記録が4週より古い・無い / rollout・adopted の賭けが動かす KPI に記録が無い。
- 毎週の手順(`docs/playbook.md`)と `/bet` の B の 4 に、値を1行足す手順がある。

## 9. 合議の当たり外れと、計画の星

- 合議の結論の KPI には**見込みの幅**を付け、人が決めた後 `kpi.yaml` の `forecasts` に写す。期限の後、`pnpm kpi` が実測と比べて **当たり / 外れ / 測っていない** を出し、合議ごとの当たり率を出す。外れが半分を超えたら回し直しをすすめる。
- 合議の記録の 8 に**星**を付ける(価値・確からしさ・守り・ROI の見込み・実現性)。価値と確からしさは表から機械で出し(推測だけの賛成は数えない・拒否があれば価値は ★2 まで)、手で上げると `pnpm kpi` が落とす。
- 星は**後で実測と比べる**: 星が高かった計画が本当に KPI を動かしたか。合議と採点の当たり外れが、次の合議の確からしさと ROI の説明になる。低い星は「何をすれば上がるか」の合図(例: 確からしさ ★1 → 話を聞く)。

## 10. ROI(やった結果、どれだけ得たか)

金額はリポジトリに書かない(費用のページと同じ非公開の置き場)。リポジトリには**倍率の幅と月数と、届いたか**だけ。

- 得た物(月)= 売上の差 + 削減した時間 × 時給 + 解約の減りの額
- **ROI =(得た物の累計 − 原価の累計)÷ 原価の累計**(原価は人の時間・AI・インフラ。費用のページの賭けごとの分の累計)
- **回収の月数 = 原価の累計 ÷ 得た物(月)**
- 幅で出す: 悪い方は「得た物が少なく、原価が多い」組み合わせ(`scripts/loop-lib.mjs` の `roiRange`)。
- 賭けのファイルの「ROI」の表に、rollout・adopted で1行ずつ足す(日付・ROI の幅・回収の月数の幅・動かす KPI が届いたか)。
- キット自身の ROI は、実地の通しで測った「1件の依頼の時間・人が呼ばれた回数・費用」を最初の基準にする(`pnpm metrics` の週の数字を残す)。

## 11. 意義の判断役(やる / やらない を言い切る)

工場の使命は「**意義のあることを、意味の分からない速さで実現する**」。合議は材料にとどめ、「意義があるからやる / やらない」は意義の判断役(`.claude/agents/purpose-judge.md`)が短く言い切り、人が問い(多くて1つ)に答える。仕様 0084。

| 場面 | 呼ぶスキル | 何を判断するか |
|---|---|---|
| アイデア | `/bet`(開くとき・idea → cpf) | 困りごとを確かめに行く意義があるか |
| 分解の前 | `/new-feature`(子 Issue・PR が2本以上に分かれる依頼) | PR を何本も流す意義があるか。条件つきなら、どこまでで止めるか |
| 受け入れ | `/accept` | できた物が、判断のときの意義(数)に届く見込みか |
| キット | 人が頼んだとき | キット自身が3つの問い(何者か・何ができるか・意義はあるか)に答えられているか |

PR 1本ずつには使わない(重くなる)。記録は `docs/product/verdicts/`(キット自身は `docs/kit/verdicts/`。型は `docs/product/verdicts/_template.md`)。

**3つの歯止め**(`pnpm kpi` が見る。`scripts/verdict-lib.mjs`):

1. **やらない線**: やる・条件つきは、意義の行に数が要る(誰の・どんな困りごとが・どれだけ減るか)。数で言えなければ「やらない」。熱意で何にでも意義を見つける賛成係にしない。
2. **ROI の根拠**: やる・条件つきは、動かす KPI・見込み(幅と期限)・費用の見込み・得る物の見込み(月)・測る月数・止める線が要る。ROI の見込みの行は 10 の式(`roiRange`)で出した値と同じでないと落ちる(手で上げない)。金額は書かない(人日の幅)。
3. **当たり外れ**: 期限の後、`pnpm kpi` が実測(記録の「- 実測:」か、`kpi.yaml` の `records`)と見込みを比べ、当たり(幅の中か良い向きの外)/ 外れ / 測っていない を出し、判断役の当たり率を出す。外れが半分を超えたら(2件以上)、物差しを見直す合図。**判断役もセンサー**なので、期限を過ぎた記録は、正しかったかを人が「- 人の判定:」で判定する(`pnpm kpi` が待っている記録を出す)。
