# PR の動作確認(/verify-pr)と「通った ≠ 確かめた」

> 仕様: [specs/0076](../specs/0076-verify-pr.md)・設計: [designs/0076](../designs/0076-verify-pr.md)・ADR: [0081](../adr/0081-verify-scripts-not-tests.md)
> 考え方は [concepts/line.md](../concepts/line.md) の 2(⑤ 検証)。手順は `/verify-pr`。

## 考え方

- **画面の動作確認も AI に回す**。PR の「🖱 動作確認」の欄を AI が読み、E2E の部品で確かめ、手順をスクリプトにして PR に貼る。人は貼られた手順と記録を読んで、足りない所だけを手で見る。
- **AI に製品の知識を渡す源は、手入れされている E2E**(`apps/web/e2e/` の流れと `helpers.ts`)。コードは余計な情報が多く、設計書は差分しか無く、ヘルプは人向け。E2E は「この画面はこう操作する」をそのまま持っている。
- **「スクリプトが通った」≠「確かめた」**。AI の書いた確認は、確かめていないのに通ることがある。2層のゲートを置く。
- 簡単な確認は手のほうが速い。AI に回すのは、組み合わせが多い・何度も見る・手順を残したい物から。

## 1. 2層のゲート

| 層 | 何で | 止める物 |
|---|---|---|
| 1層目 | `pnpm verify:lint`(書き方で止める) | 下の表の「1層目」の欄 |
| 2層目 | AI が記録(`verify-log`)・トレース・スクショを疑って読む | 書き方では止まらない物。通っても読む |

| すり抜けの形 | 例 | 1層目(書き方) | 2層目(読んで確かめる) |
|---|---|---|---|
| エラーの放置 | 画面にエラーが出ている・500 が返っているのに、最後の文言だけ見て合格 | `.catch(() => {})`・空の `catch`・`try` を止める。画面のエラーと 5xx は `verify-fixture.ts` が落とす | 記録の console のエラーと 4xx が、確認の意図どおりか(403 を確かめる確認の 403 はよい) |
| API の直叩き | 画面で作るはずの物を API で作り、画面を通っていない | `page.request`・`request.post`・`fetch` などを止める(準備だけなら `// 準備: 理由`) | 準備の印の行が、確かめたい操作そのものになっていないか |
| アサーション無し | 操作しただけで合格 | 確認ごとに `expect` が1つ以上・最後の操作の後にも1つ以上 | 最後の `expect` が、動作確認の欄の「どうなる」を見ているか |
| 操作の前から合格 | 消す前から一覧に無い・保存する前から「保存しました」が出ている | 最後の操作の前にも `expect` が要る | 前の `expect` が「後」と逆の状態を見ているか(前後で同じ物を見ていないか) |
| うわべの確認 | 見えるか・有るかだけ見て、中身(文言・値・件数・URL)を見ない | 確認の中の判定が全部「有る・見える」だけなら止める | 中身の判定が、動作確認の欄の値と同じか |
| 判定のすり替え | 応答を差し替える・画面の中を直に書き換える・`expect(true)`・`expect.soft` | `route`・`evaluate`・定数の `expect`・`expect.soft`・`force: true`・`waitForTimeout`・`test.only` などを止める | 動作確認の欄の「どうなる」と、`expect` の中身が同じことを言っているか(別の物にすり替えていないか) |

- 1層目で止まったら、書き方を直す(印や回り道で逃がさない)。
- 2層目で疑わしければ、その項目は「確かめた」にしない。PR のコメントに「確かめられなかった」と理由を書き、人に渡す。

## 2. 置き場と流し方

- 手順は `apps/web/e2e/verify/pr-<番号>.spec.ts`(コミットしない。`.gitignore`)。`test` と `expect` は `../verify-fixture` から。部品は `../helpers.ts` とふだんの E2E。
- 流す先は PR のプレビュー環境(`E2E_BASE_URL=https://pr-<番号>.preview.<domain>`)か、手元の docker compose(http://localhost:8080)。**本番には流さない**。
- `pnpm verify:lint apps/web/e2e/verify/pr-<番号>.spec.ts` → `E2E_BASE_URL=… pnpm --filter @app/web verify e2e/verify/pr-<番号>.spec.ts`。
- PR のコメントに貼る物: 動作確認の欄の1行ずつに「確かめた / 確かめられなかった(理由)」・手順(スクリプト)・記録の要点(console のエラー・4xx の数)。**画面のスクショに種データ以外を写さない**。
- 同じ確認を何度もするようになったら、ふだんの E2E(`apps/web/e2e/*.spec.ts`)に足す(コミットする。大事な流れ5本程度までの決まりは `apps/web/CLAUDE.md`)。

## 3. 始め方

1. 人が1回、手で操作して、動作確認の欄の書き方をそろえる(誰が・どこで・何をすると・どうなる)。
2. 雑な指示で `/verify-pr` を流し、手順と記録を読んで直す(2層目で何が見つかったかを、この手引きの表に足す)。
3. 意図どおりに確かめられるようになったら、PR ごとに回す。
