# 使いやすさの見方(🎨 使いやすさを見る人の手引き)

> 画面を変える PR を、**腕のいい UX デザイナーが横で見ていたら言うこと**を、AI のレビュー役が言えるようにするための手引き。
> 呼び方と記録は `/review-pr`(観点の台帳 [../review-viewpoints.md](../review-viewpoints.md) の「👥 レビューの人格」の 🎨)。仕様 [0099](../specs/0099-ux-reviewer.md)・設計 [0098](../designs/0098-ux-reviewer.md)。
> 機械で確かめている所(axe・320px・VRT・Semgrep。[../design-system.md](../design-system.md) の「確かめる仕組み」)は**壊れていないか**まで。ここで見るのは **迷わないか・間違えないか・失敗しても戻れるか**。

## 0. 見る物

- **画面そのもの**(いちばん大事)。`/review-pr` が渡す画像を、パソコンの幅とスマホの幅(320px)の両方で見る。変わる前の画像があれば並べて見る。**コードだけで判断しない**(コードからは「どう見えるか」が分からない)。
- 差分(`apps/web/src/pages/`・`apps/web/src/routes/`・`packages/ui/`・文言)。
- 仕様の受け入れ条件と、そのペルソナ([../product/personas.md](../product/personas.md))。**その人が、その画面を、どんな場面で開くか**を思い浮かべてから見る(忙しい合間に・スマホで・初めて・月に1回だけ)。
- 画像が無い・撮られていない画面を変えているなら、それ自体が所見(⚠️「VRT の画面の一覧(`apps/web/e2e/vrt/screens.ts`)に足す」)。

## 1. 3秒の問い(最初に、画面を開いた人になって答える)

1. **ここは何の画面か**(見出しと中身から、3秒で言えるか)
2. **いまどこにいるか**(ナビで今のページが分かるか・どこから来てどこへ戻れるか)
3. **次に何をすればいいか**(いちばん押してほしいボタンが、いちばん目立っているか)
4. **押したら何が起きるか**(ボタンの言葉で結果が分かるか。戻せない操作が、それと分かるか)
5. **うまくいったか・失敗したら戻れるか**(結果が見えるか。失敗の文に直し方があるか)

1つでも答えられなければ、それが最初の所見になる。

## 2. 10の目安(世間で定番の「ヒューリスティック」を、このキットの画面に当てた形)

出典: Jakob Nielsen の「ユーザビリティの10の目安」(1994・2024 改訂)。名前は短くした。

| # | 目安 | この画面で見ること(例) |
|---|---|---|
| H1 | 今の状態が見える | 保存した・送った・読み込み中が分かる(トーストか画面に残すか)。件数・進み具合(何件中何件済み)。選んだ物が選ばれて見える |
| H2 | 利用者の言葉で | 中の言葉(テナント・ロールの ID・API の名前・英語の状態名)が画面に出ていない。並びは利用者の仕事の順 |
| H3 | 戻れる・やめられる | 戻せない操作には確認。確認より「取り消し」のほうが良い所はないか。入力の途中でやめても失わない。戻る道(一覧へ・前の画面へ)がある |
| H4 | 同じ物は同じに | 同じ操作は同じ言葉・同じ部品・同じ位置(あるカードはボタン、隣のカードはリンク、はズレ)。`@app/ui` の決まりどおり |
| H5 | 間違えにくく | 押し間違えやすい所に危ない操作が無い(主な操作の隣に「消す」)。入力の形を先に示す(例・単位・桁)。選べるものは選ばせる |
| H6 | 覚えなくてよい | 前の画面で見た値を覚えていないと進めない作りになっていない。選択肢や今の値が見えている |
| H7 | 慣れた人に近道 | よく使う操作が奥に埋まっていない(毎日使う人の手数)。キーボードで進める(Enter で送れる) |
| H8 | 引き算 | 1画面に主ボタンは1つ。同じ強さの物が並びすぎていない。説明の文が長すぎない(読まれない)。飾りの線・枠が多すぎない |
| H9 | 失敗の文で直せる | エラーは「何が起きたか+どうすればいいか」を、その欄の近くに。赤い色だけで伝えない。中の言葉(500・forbidden)を出さない |
| H10 | 迷ったら助けがある | 初めての人がつまずく所(空の画面・初めての設定)に、短い説明か次の一歩 |

## 3. 画面の状態(見落としの多い所。仕様に無くても見る)

1つの画面には、少なくとも次の状態がある。**差分で触った画面について、どれが作られていて、どれが抜けているか**を見る。

| 状態 | 良い形 |
|---|---|
| 空(0件・初めて) | 「まだ○○はありません」+何をすれば増えるか+その操作。ただの空白や、見出しだけの表にしない |
| 読み込み中 | 何かが来ると分かる(場所を取った形・短い文)。画面ががたつかない |
| 失敗 | 何ができなかったか+もう一度・戻る道。画面ごと真っ白にしない |
| 一部だけ | 一部が読めない・権限が無い部分は、その部分だけ断る |
| 多い | 100件・1,000件で探せるか(絞り込み・ページ)。表がスマホで読めるか |
| 長い | 長い名前・長い文で、崩れない・切れて意味が変わらない(省略するなら全文を見る道) |
| 権限が無い | 押せない物は、隠すか、押せない理由が分かる形に。押してから断らない |
| 終わった後 | 作った・消した・送った後に、どこに何が出るか(作った物が見える・一覧に戻る) |

## 4. 見た目の強弱(デザインの基本の4つ)

- **強弱(ヒエラルキー)**: 見出し → 主な操作 → 中身 → 補足、の順に目が動くか。見出しの段(`Heading` の `level`)と大きさが合っているか。全部が同じ太さ・同じ色だと、どれも目に入らない。
- **近さ**: 関係のある物は近く、関係の無い物は離す(ラベルと入力欄は近く、別の組は間を空ける)。間はトークンの `gap` で。
- **そろえ**: 左の端・ボタンの位置・数字の右寄せがそろっているか。
- **くり返し**: 同じ種類の物(カード・行)は同じ形。1つだけ違う形の物は「特別」に見える。

## 5. 文言

- ボタンは**動詞で、結果が分かる言葉**(「OK」「はい」ではなく「消す」「招待を送る」)。確認のダイアログのボタンは、問いの答えになっている。
- 同じ物は同じ言葉(「消す」と「削除」、「組織」と「会社」が混ざらない)。用語は [../domain/](../domain/) の言葉に合わせる。
- 札(`Badge`)の言葉だけで意味が分かるか(「送る」「任意」だけだと、何が送るのか・何が任意か分からない)。
- 説明の文は短く、最初の1文で要点。注意書きは本当に要る所だけ(全部に付けると全部読まれない)。
- 中の言葉・英語の状態名・エラーの番号を出さない。日付・時刻・数は利用者の慣れた形(日本時間・桁の区切り)。

## 6. 入力(フォーム)

- ラベルは常に見える(入力例 `placeholder` をラベルの代わりにしない。打つと消える)。
- 何を入れればよいかが先に分かる(例・形・必須か)。
- エラーは、その欄のすぐ近くに、直し方つきで。打ち直したら消える。
- 押した後に二度押せない・何が起きているか分かる(`useAction`)。
- 欄の順が仕事の順。長いフォームは段に分ける。

## 7. 危ない操作

- 戻せない操作(消す・止める・送る・権限を変える)は、**主な操作より目立たせない・隣に置かない**。行ごとに大きく並べるより、行の「…」や詳しい画面の奥へ。
- 確認のダイアログは、**何が・どこまで・戻せるか**を書く(「このプロジェクトと中のタスク12件を消します。元に戻せません」)。
- 戻せる作りにできるなら、確認より取り消し(トーストの「元に戻す」)。

## 8. スマホ

- 押す所は 24px 以上(機械が見る)に加えて、**親指で届くか・隣と押し間違えないか**。
- 横に並べた物が折り返したとき、意味の順が崩れないか(ナビ・ボタンの並び)。
- 表は横に動く枠の中で、いちばん大事な列が最初に見えるか。
- 長い説明がスマホで何画面ぶんになるか(読まれない)。

## 9. 重さの付け方(`.claude/agents/reviewer.md` の3つに当てる)

| 重さ | 🎨 で当てる物 | 例 |
|---|---|---|
| ❌ 直すべき | デザインシステムの決まり([../design-system.md](../design-system.md))に反する・受け入れ条件の操作を、そのペルソナが画面だけで終えられない・戻せない操作を確認なしにできる・状態が抜けて画面が壊れて見える | 主ボタンが2つ・0件で見出しだけの表・エラーが中の言葉 |
| ⚠️ 気になる | 上の目安に当たり、**誰が・どこで困るかが言える**もの | 「消す」が各行で中身と同じくらい目立つ(押し間違え)・ボタンとリンクが混ざる |
| ❓ 人の判断 | 利用者の挙動の思い込みに頼る所(この人はスマホで使うか・毎日使うか)・ブランドや言葉の線引き | 「この画面は月1回しか開かない前提でよいか」 |
| 提案(所見に入れない) | 好み・別の案のほうが良さそう、くらいの物 | 色味・余白をもう少し |

- **「好み」と「困る」を分ける**。困る人と場面が言えない物は提案へ。
- **直し方は `@app/ui` の中で言う**(画面で `style` を書く案は出さない)。部品や props が足りないなら「`packages/ui` に足す」とし、新しい色・余白なら ❓(トークンを決めるのは人)。
- 場所は `ファイル:行` に加えて、**画面の名前・幅・画面の中の位置**(「タスク(スマホ)の上から2つ目の行の右」)。

## 10. 機械で確かめられるようになったら

同じ所見が2回出たら、テストか Semgrep にできないかを考え、台帳の「機械で確かめている所」に書く(例: 1画面の主ボタンの数・確認なしの危ない操作・空の状態の有無)。**目で見る物を減らすほど、🎨 は難しい所(流れ・言葉・強弱)に集中できる。**
