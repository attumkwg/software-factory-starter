# 受け入れ(点数と、外れた理由の書き戻し)

> 仕様: [specs/0075](../specs/0075-acceptance-record.md)・設計: [designs/0075](../designs/0075-acceptance-record.md)
> 考え方は [concepts/people-and-ai.md](../concepts/people-and-ai.md) の 1.1(説明の責任)と [concepts/line.md](../concepts/line.md) の 2(⑤ 検証の受け入れ)。手順は `/accept`。

## 考え方

- **受け入れ = 作った機能を「出してよいか」確かめること**。仕様の承認(作ってよいか)と、PR のレビュー(このコードでよいか)の後、機能フラグを開ける・本番に出す前に1回。
- **PdM が見るのは、PdM にしか判断できない項目だけ**。網羅が要る確かめは AI と QA に回す。全部を PdM が見ると、PdM が詰まり所になる(項目の4分の1ほどに絞れる例が多い)。
- **点数にして、外れた理由を分ける**。理由で直す工程が違う。要求のせいの外れは、解決済みの論点に書き戻して次の仕様で同じ穴を作らない。
- **点数は改善の数**。人や機能の良し悪しを決める数にしない(人の評価に使うと項目を甘くする動きが先に起きる。[metrics.md](metrics.md) の 2 と同じ決まり)。

## 1. 誰が何を見るか

| 見る人 | 観点(記録に書く言葉) | 中身 |
|---|---|---|
| **PdM** | `流れ` | 今の操作の流れで、仕事が最後まで終わるか |
| | `ルール` | 仕様の第1部の業務ルールが守られているか |
| | `作り込み` | 作り込みすぎていないか(頼んでいない機能・凝りすぎた画面) |
| | `仮決め` | AI の仮決め(設計書の未確定事項)のうち、製品の判断が要る物 |
| **AI** か **QA** | `状態` | 状態 × 操作の全部の組み合わせ(仕様の第2部) |
| | `境界値` | 上限・空・重複・時刻の境目・お金の端数 |
| | `権限` | ロール別・他社 404・未ログイン |
| | `URL` | URL の直打ち・戻る・再読み込み |
| | `スマホ` | 狭い幅(320px)・触って押せるか |
| | `a11y` | キーボード・読み上げ・コントラスト(自動の検査で見えない所) |
| | `プラン` | プラン別の表示と上限 |
| | `その他` | 上のどれでもない網羅の確かめ |

- PdM の4つの観点を AI や QA に回さない。網羅の観点を PdM に回さない(どちらも CI が落ちる)。
- AI が確かめる項目は、E2E の部品で手順を書いて流す(`/verify-pr` がある版ではそれを使う)。人の手が要る物(本物の端末・読み上げ)は `QA` にして一覧で渡す。
- 見る所はプレビューか stg。本番の利用者のデータは見ない・書かない(CLAUDE.md・[security.md](../security.md) の AI-6)。

## 2. 記録の書き方

置き場は `docs/acceptance/NNNN-<名前>.md`(仕様と同じ番号と名前)。型は [_template.md](../acceptance/_template.md)。`/accept` が書く。

- 回ごとに `## 第N回 YYYY-MM-DD` の見出しを足す(日付は受け入れを始めた日)。**前の回は書き換えない**。直してからもう一度見るなら、次の回を足す。
- 頭に「実装の PR」(#番号)を書く(実装が終わってから受け入れが始まるまでの日数を数えるため)。
- 表の列: `# | 観点 | 見る人 | 項目 | 結果 | 外れた理由 | 書き戻し先`。
  - 結果: `合` / `否` / `未`(まだ・この回は見送り。点数の分母に入れない)
  - 外れた理由(`否` のときだけ): 下の 3 の4つのどれか
  - 書き戻し先: `要求` なら `R-n`(必須)。ほかは設計書の節や未確定事項の番号・Issue

## 3. 外れた理由と、どこを直すか

| 理由 | 例 | 直す所(上流から。[human-review.md](human-review.md) の 4) |
|---|---|---|
| `要求` | 仕様に書いていなかった・書き方があいまいで別の意味に取れた | 解決済みの論点に1行(`R-n`)+仕様を直す(完了した仕様なら新しい仕様)。用語や決まりの抜けなら用語集・領域の説明・ADR も |
| `設計` | 仕様は正しいが、設計書の判断が違った | 設計書を直し「作り直しの記録」に1行 → `/rework` |
| `AI の仮決め` | AI が仮に決めた所(未確定事項・印の無い穴埋め)が副作用を生んだ | 未確定事項の行を `変更` にする(人の答えで)→ `/rework` |
| `実装` | 設計どおりに作れていない | 不具合として直す(`/report-bug`)。同じ種類が2回出たらテストか lint に |

- 1つの外れに理由は1つ。迷ったら上流の方(要求 > 設計 > AI の仮決め > 実装)。
- `AI の仮決め` が多い → 仕様の印(`(仮説)`・`(未確定 U-n)`)が足りていない合図。仕様を書く手順を見直す。

## 4. 解決済みの論点

`docs/domain/resolved-questions.md`。要求のせいの外れから、**次の仕様を書く人(AI)が読む形**で残す。

- 1行 = 1つの論点: 何が書かれていなかったか・どう決めたか・分かった所(受け入れの記録へのリンク)・書き戻したナレッジ・日付。
- `/new-feature` と `/design` は仕様と設計の前にここを読み、当たる論点を第1部に書く(書き漏らさない)。
- 同じ論点が3回出たら、仕様の型(`docs/specs/_template.md`)か `/new-feature` の聞くことに足す(ラインを直す)。

## 5. 点数の読み方

- `pnpm acceptance` が記録ごと・回ごとに出す: PdM の点数・AI と QA の点数・全体・項目の数(うち PdM)・外れた理由の内訳。
- 見るのは**並びと理由の偏り**。1回の点数で機能の良し悪しを決めない。
  - PdM の項目が全体の4分の1を大きく超える → PdM に網羅を回していないか。
  - `要求` が多い → 仕様の第1部か、ナレッジ(用語集・解決済みの論点)が足りない。
  - `設計` が多い → 設計に進む基準([human-review.md](human-review.md) の 6)か設計の手順を見直す。
