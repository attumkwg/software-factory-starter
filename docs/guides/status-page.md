# 稼働状況のページ(ステータスページ)を選んで、障害の知らせとつなぐ

> **お客さんが「いま落ちているのか」を自分で見られる所**。無いと、障害のたびに問い合わせが CS に集まり、CS が1件ずつ同じことを答える。
> キットの中には作らない(外のサービスか、別の置き場に置く)。この手引きは選び方と、[runbooks/incident.md](../runbooks/incident.md) の「お客さんへの知らせ」とのつなぎ方。
> 決めた理由は [ADR 0043](../adr/0043-status-page-outside-our-aws.md)。既定の値の未確定事項は設計書 [0032](../designs/0032-status-page.md) の U-1〜U-3。

## 1. いつ要るか

- お客さんが数社のうちは、障害の知らせ(管理者へのメール。[runbooks/incident.md](../runbooks/incident.md) の 4)で足りる。
- **要るのは**: 障害のときに同じ問い合わせが何件も来るようになったら・SLA を出したら(計画メンテナンスの予告を載せる所が要る。[legal/sla.md](../legal/sla.md) の 3)・お客さんの情シスに「障害情報はどこで見られますか」と聞かれたら。

## 2. 選び方

**いちばん大事なのは、自分の AWS と別の所で動くこと**(本番が落ちたときに、ページも一緒に落ちると意味が無い)。

| 見る所 | 既定 | なぜ |
|---|---|---|
| **自分の基盤と別か** | 外のサービスにする(自分の AWS の上に作らない) | 本番・DNS・CloudFront が落ちても見えるように |
| 独自のドメイン | `status.<ドメイン>`(CNAME で外のサービスへ) | お客さんが覚えやすい。DNS を自分の Route 53 に置くなら、DNS の障害では見えなくなることを知っておく |
| 載せる部品 | 画面・API(ログインと操作)・メール(お知らせ)の3つ | 外形監視が見ている物([guides/monitoring.md](monitoring.md))とそろえる。内部の仕組みの名前(DB・AWS のサービス名)は出さない |
| 更新のしかた | **人が手で**(知らせる役)。外形監視から自動で「調べています」を出すのは、慣れてから | 自動だと、誤報も外に出る。文面は事実だけにする決まり(incident.md の 4)を人が守る |
| 購読(お客さんがメールで受け取る) | **最初は使わない**(U-1) | 購読のメールアドレスは個人データ。外の会社(多くは米国)に預けることになる |
| 公開か、お客さんだけか | **公開**(ログイン無しで見られる)(U-2) | 落ちているときはログインできない。お客さんの社内で転送もしやすい |
| 稼働率の数字を出すか | **出さない**(U-3) | SLA の稼働率の正は [legal/sla.md](../legal/sla.md) の 7 の測り方。ページの数字と2つになると、割ったときに揉める |
| 費用 | 無料か月 数千円の段から | 段階に合わせる([concepts/](../concepts/README.md) の段階と費用) |
| 日本語 | ページと購読のメールが日本語で出せる | お客さんが読む |

- 外のサービスの例: Atlassian Statuspage・Instatus・Better Stack など(機能と料金は変わるので、選ぶときに公式で確かめる)。
- 自分で作るなら、本番と別のアカウントか別のサービスの静かなページ(手で書き換える1枚)。本番の AWS の上に置かない。

## 3. 入れるとき

1. 委託先の台帳 `docs/compliance/vendors.yaml` に1件足し、`pnpm vendors --write`(危険度「高」。人の確認)。購読を使わないなら、渡すのは公開の文だけ:

   ```yaml
   - id: status-page
     name: <サービスの名前>
     status: active
     relation: 渡さない # 購読(メールアドレス)を使うなら 委託・data に personal
     what: 稼働状況のページ(障害と計画メンテナンスの知らせ。docs/guides/status-page.md)
     country: <国>
     data: [public]
     contract:
       dpa: 不要 # 購読を使うなら、相手の DPA を確かめて書く
       link: <約款の URL>
     certifications: []
     checked_on: <確かめた日>
     deletion:
       when_we_leave: <アカウントを消すと、過去の知らせが消えるか>
       when_tenant_leaves: お客さんの物を預けていないので関係しない
     match: {}
   ```

   - コードやワークフローから呼ぶ(SDK・Actions)なら、`match` に書く。手で更新するだけなら空でよい。
2. 部品を3つ(画面・API・メール)作り、状態の言葉を下の 4 の対応にそろえる。
3. `status.<ドメイン>` を CNAME で向ける。
4. 知らせる役の人(2人以上)だけにアカウントを作る。共有のアカウントにしない(誰が書いたかを残す)。
5. 画面のヘルプ・申込書の連絡先・SLA の「知らせる先」に、ページの URL を書く。

## 4. 障害の重さと、ページの状態の対応

| 重さ([runbooks/incident.md](../runbooks/incident.md) の 1) | ページの状態 | いつ載せるか |
|---|---|---|
| S1(全員が使えない・データが消えた) | 大きな障害 | 宣言したら**第1報と同時に**(30分以内) |
| S2(一部の機能・一部の会社が使えない・とても遅い) | 一部に影響 | 宣言したら第1報と同時に(1時間以内) |
| S3(回り道がある・見た目) | 載せない | 直したらリリースノート |
| 計画メンテナンス | メンテナンスの予定 | **7日前まで**([legal/sla.md](../legal/sla.md) の 3) |

- **ページに載せる文は、メールの第1報・続報・復旧と同じ文**(incident.md の 4 の型)。2つの所で違うことを書かない。
- 他社のデータが見えた・個人データが漏れたかもしれない、は**ページに書かない**(個別の連絡と法の手順。[runbooks/tenant-data-leak.md](../runbooks/tenant-data-leak.md)・[runbooks/personal-data-breach.md](../runbooks/personal-data-breach.md))。ページには「一部の機能を止めています」のように、止めた事実だけ。
- 1社だけの障害(その会社の設定・データ)は載せず、その会社に個別に知らせる。

## 5. 専門家に確かめること

- 購読を使うとき、メールアドレスを外国の会社に預けることの扱い(プライバシーポリシーに書くか・同意が要るか)。
