# CI の待ち(どこで待っているか・どう縮めたか・次に効く手) 

> 目当ては「PR を出してからマージできるまでの待ち」を短くすること。検査を減らして速くはしない(落とすべき物が通るようにしない)。
> 決めた理由: [ADR 0028](../adr/0028-ci-wait.md)

## 待ちの形

マージできるのは、必須のチェック(`.github/setup.yml` の `required_checks`)が全部緑で、**最新の main に追いついている**とき(`strict: true`)。
個人のリポジトリではマージキューが使えないので、1本マージするたびに、ほかの PR を main に追いつかせて CI を全部流し直す。待ちは「1回の CI の長さ × 並んだ本数」で積み上がる。

1回の長さを決めるのは、いちばん長いジョブ(いまは E2E)。もう1つ、**同時に動けるジョブの数の上限**(無料のプランは 20)がある。1回の push で約17のジョブ(CI 13・VRT 2・PR の取り組み・Labeler)が動くので、2本を同時に流すと、あふれたジョブは空くまで待つ。

## 縮めた所

| 何を | どうした | どこ |
|---|---|---|
| 起動の待ち(ヘルスチェック) | イメージの HEALTHCHECK は 10秒ごと。postfix → api → web → alb の順に「次の確かめ」を待ち、起動のたびに約30秒を捨てていた。起動の間(60秒)だけ1秒ごとに確かめる(`start_interval`)。確かめ方と、動いた後の 10秒は変えない | `docker-compose.yml` の `x-fast-start`・`docker-compose.cognito.yml` |
| E2E のブラウザを入れる(約20秒) | アプリの起動を待つ間に、裏で入れる | `ci.yml` の E2E |
| E2E のテスト | 全体の長さを決めていたのは、ログインの期限のテスト(`session.spec.ts`)1本。API が Cookie を出し直すのは1分に1回なので、1分待つ。これが最後の方に始まり、ほかが 40秒で終わった後も1分待っていた。組(`chromium-wait`)を分けて**先頭で流し**、CI は3並列(1つはこの待ち・2つでほか) | `apps/web/playwright.config.ts` |
| Cognito でのログイン | API のイメージはもう作ってあるので、作り直さない(`--build` を外す。無い偽物の Cognito だけ作る) | `ci.yml` の E2E |
| VRT のブラウザのイメージ(約1.5GB・約35秒) | 取ってくる間に、アプリを作って起動する(前は取り終わるまで待ってから) | `vrt.yml` |
| 文書だけの PR | 重いジョブ(結合・E2E・イメージ・移行・API の互換・VRT)は中身を省き、**成功を返す**(必須のチェックは止まらない)。速い検査(Biome・型・単体・秘密・Semgrep・Trivy fs・ワークフロー)はいつも流す。main への push とマージキューでは全部流す | `.github/scripts/ci-scope.mjs`(下) |

### 「文書だけ」の見分け(`ci-scope.mjs`)

PR の合わせたコミット(GitHub が作る、PR を main に重ねたコミット)と、その1つ目の親(= いまの main)の差分を見る。追いついた後も「この PR が足す差分」だけを見る。

- 文書とみなす: `docs/` の下(`docs/authz/` を除く)・`apps/`・`packages/` の外の `.md`
- 文書とみなさない: `docs/authz/matrix.yaml`(結合テストが全行を叩く)・画面に入る規約の本文(`apps/web/src/legal/**/*.md`)・ほか全部
- 迷ったら「流す」に倒す: 差分が取れない・空・PR 以外・名前を変えたファイル(元の名前も数える)

省くジョブも1つずつ動き、最初の手順で見分けてから後ろの手順を飛ばす。ジョブごと飛ばす(`if`)と、組を並べたジョブ(イメージの `matrix`)は名前の `${{ matrix.app }}` が展開されず、必須のチェックが「待ち」のまま止まるため。VRT はジョブごと飛ばす(組を並べていないので、飛ばされたジョブは成功を返す)。

ここを広げると検査が飛ぶので、`.github/**`(危険度「高」)に置いている。見分けを変えたら `ci-scope.test.mjs` も直す。

## やらなかった手と理由

| 手 | やらなかった理由 |
|---|---|
| 必須のチェックを減らす・「最新に追いついてから」を外す | 守りが弱くなる(並べた PR が合わさって main を赤くする)。やるなら持ち主が決める |
| 追いついただけの差分なら重いジョブを省く | 追いつくと「この PR+新しい main」の組み合わせは初めてになる。それを確かめるのが `strict` の意味なので省けない |
| Docker の層のキャッシュを E2E・VRT とイメージの検査で共有する | **試して外した**。`docker/bake-action` でイメージの検査のジョブのキャッシュ(`type=gha`)を読むと、層は全部当たるが、取ってきて広げて Docker に読み込むのに約30秒かかり、作り直すのとほぼ同じ(E2E で約7秒・VRT は縮まず)。仕組みと Action が1つ増えるわりに効かない |
| E2E を4並列にする | **試して外した**。4 コアの機械にアプリも同居するので、1本ずつが倍遅くなり、全体は同じだった |
| E2E を機械ごとに分ける(シャード) | 分けるたびに起動(約30秒)が増え、同時に動くジョブも増える(上限 20 に当たる)。4並列で足りるうちは分けない |
| ジョブをまとめて数を減らす | チェックの名前が変わり、必須のチェックの付け替え(`pnpm setup:github --apply`)が要る。待ち行列が本当に詰まるのは「同時に何本も追いつかせる」とき(下) |

## 並んだ PR を入れるときのこつ(人・AI の進め方)

**追いつかせるのは、次に入れる1本だけ**にする。開いている PR を全部いっぺんに main に追いつかせると、その本数 × 約17 のジョブが同時に並び、上限 20 にあふれて、どの PR も遅くなる(そのうえ、次にマージすると、また全部やり直しになる)。

## 見直す合図

- E2E の「作る」が 60秒を超えた → 層のキャッシュの共有(`docker buildx bake` に `cache-from: type=gha`)
- E2E のテストが 2分を超えた → 2つに分ける(シャード。必須のチェックの名前は、まとめのジョブに残す)
- ジョブの開始までの待ち(並び)の p90 が 60秒を超えた → 小さいジョブ(gitleaks・actionlint・squawk)を1つにまとめる
