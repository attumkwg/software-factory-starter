# 題材を差し替える(TODO → 自分のプロダクト)の手順の例

> TODO アプリ(組織 → プロジェクト → タスク)は、ラインを見せるための題材。**ラインは残し、題材を差し替える**。何を残し何を差し替えるかの表は [getting-started.md](../getting-started.md) の ②。ここは、それを**実際にどの順で・どのファイルを**やるかの例。
> 例の題材: 工務店向けの「**現場**(`sites`)と**日報**(`reports`)」(想定の場面の A 社。写真は保存の部品 G-45 ができてから)。

## 0. どれくらいの量か(2026-10-27 に数えた)

`tasks`・`projects`・`projectId`・`taskId` が出てくるファイルは `apps`・`packages` に **約130**。ただし大半は機械的に直る:

| 場所 | ファイルの数 | 中身 | 直し方 |
|---|---|---|---|
| `apps/api/src/domains/projects`・`tasks` | 10 | 表・読み書き・API・領域の `CLAUDE.md` | **新しい領域を足してから、古い領域を消す**(下の 2・5) |
| `apps/api/drizzle/meta` | 約23 | 移行の記録(自動で作られる) | 触らない(消す移行を足すと増えるだけ) |
| `apps/api/test/integration`・`unit` | 約38 | 2社の分離・権限の表・RLS のテストの**題材** | 新しい領域の名前で同じ形を書く(テストの形は残す) |
| `apps/web`(画面・E2E・VRT) | 約25 | 画面・E2E の流れ・見た目の基準 | 画面を作り直し、E2E は「大事な流れ5本」を新しい題材で。VRT は `pnpm vrt:update` |
| `packages/shared`・`logging`・`error-reporting` | 約9 | 契約のスキーマ・ログの許可リストの `projectId`・`taskId` | 足すだけの決まり(`shared` は項目を消さない。ログの名前は `ALLOWED_KEYS` に足す) |
| `apps/api/src`(監査・送信待ち・認可・個人データ) | 約9 | 監査ログの名前・出来事の名前・権限の名前・1人分の書き出し | 新しい名前を足す。古い名前は古い領域と一緒に消す |
| `docs/authz/matrix.yaml` | 1 | 権限の表の行 | 新しい API の行を足し、古い行は古い API と一緒に消す |

- 🧭 **考え方**: 古い題材を先に消すと、2社の分離・権限の表のテストが一度に赤くなり、何が壊れたか分からない。**足す → 緑を確かめる → 消す**の順。

## 1. 仕様にする(半日)

Claude Code に:

> 「`/new-feature` で、現場(名前・住所・工期)を組織ごとに持ち、現場ごとに日報(日付・天気・作業の内容・人数)を書けるようにしたい。管理者は現場を消せる。メンバーは日報を書ける。閲覧者は見るだけ」

- 仕様 `docs/specs/NNNN-sites-and-reports.md` と設計書ができる。**権限の表の答え**(管理者・メンバー・閲覧者・他社・未ログイン)は自分で確かめる。
- 「人に聞く4つ」に当たる所(例: 日報を書いた本人以外も直せるか)は、設計書の未確定事項に `仮決め` で出てくる。答える。

## 2. 新しい領域を足す(1〜2日。AI が作り、人が見る)

> 「`.claude/skills/add-domain` で領域 `sites` を足して。次に `reports`(`sites` に頼る)」

- 領域ごとに: `src/domains/<領域>/{schema,repository,routes,index}.ts`・全部の表を集める所(`src/db/schema.ts`)とルートの登録(`app.ts`)・スキーマと RLS の移行・`dependencies.ts` の向き・列の分類(`classification.ts`)・解約で消す一覧(`TENANT_TABLES`)・領域の資料と `CLAUDE.md`(型から)が1つの PR でそろう。
- API は `.claude/skills/add-api-endpoint` で1本ずつ(権限の表に1行・2社のテスト)。書き込みの API は監査ログの名前(`audit/actions.ts`)に1行。
- ✅ ここで `pnpm test:all` が緑。**古い TODO はまだ残っている**(2つの題材が並ぶ)。

## 3. 画面を作り直す(1〜3日)

> 「`apps/web` に現場の一覧・現場の詳細(日報の一覧)・日報を書く画面を作って。部品は `@app/ui` だけ」

- 画面の決まりは `apps/web/CLAUDE.md`。ログインの後の最初の画面を、プロジェクトの一覧から現場の一覧に替える。
- E2E は新しい題材で「大事な流れ」を書く(ログイン → 現場を作る → 日報を書く → 他社から見えない)。
- 見た目の基準は `pnpm vrt:update` で撮り直し、撮った画像を見てからコミット。

## 4. 種データと言葉(半日)

- 種データ(`pnpm db:seed`)を **2社のまま** 現場と日報に替える(Acme・Globex)。
- 用語集 `docs/domain/glossary.md` に「現場」「日報」を足し、「プロジェクト」「タスク」は消す領域と一緒に外す。
- ルートの `CLAUDE.md` の最初の1行(何のプロダクトか)を直す(危険度「高」)。

## 5. 古い題材を消す(1日。1つずつ PR)

> 「`tasks` の領域を消して。消す移行を足し(昔の移行は書き換えない)、権限の表の行・監査ログの名前・ログの許可リストの名前・E2E・テストも外して。`pnpm test:all` が緑になるまで」 → 終わったら `projects` も同じに。

- 消す順は**頼られている側を後に**(`tasks` は `projects` に頼るので、`tasks` が先)。
- まだ本番が無いなら、移行を `0000` から作り直してもよい(getting-started の ② の 2)。本番があるなら、必ず消す移行を足す。
- 消し漏れは、権限の表の網羅のテスト・領域の向きのテスト・CI の検査が落としてくれる。`grep -rn "taskId\|projectId" apps packages` で残りを確かめる。

## 6. 終わったら

- 仕様と設計書は**消さない**(記録)。題材を差し替えたことは、プロダクトの記録(`docs/product/`)に1行。
- `/tailor` をもう一度流す(題材が変わると、要る部品が変わることがある)。
- かかった時間の目安(この例): **4〜7日**(仕様と確認は人、書くのは AI)【仮定】。測った数があれば、この手引きに足す。
