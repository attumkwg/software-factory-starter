# お客さんのデータはどこに・いつまで残るか

> 解約の手順([runbooks/offboarding.md](../runbooks/offboarding.md))と、**契約書・利用規約・プライバシーポリシーの「データの保存と削除」**の元になる表。仕組みや期間を変えたら、この表と契約の文面を一緒に直す。
> 期間は Terraform の既定の値。環境ごとに変えていたら、その値に読み替える。
> **どの列が個人情報か**(DB の中の、何を・何のために)は [個人情報の台帳](../db/personal-data.md)(列の分類表から作る)。この表は「どこに・いつまで」。

## 1. 置き場所と、消した後に残る期間

| 置き場所 | 中身 | 解約で消す(削除のコマンド) | 消した後も残る期間 | なぜ |
|---|---|---|---|---|
| DB(Aurora) | 組織・利用者・プロジェクト・タスク・監査ログ・サポートの許可と入室・送信待ち・規約への同意とお知らせの記録・機能フラグ・利用の記録(誰がどの日にどの機能を使ったか。**解約しなくても400日で消す**。docs/runbooks/usage-records.md) | **すぐ消える** | — | 規約への同意の記録は、解約の前の書き出しに入る(争いに備えて運営が別に残すかは docs/designs/0009-legal-consent.md の U-5) |
| Aurora の自動バックアップ | DB の写し(時点復元) | 消せない | **14日**(prod の `backup_retention_days`) | 期限で自動で消える |
| AWS Backup の保管庫(毎日) | DB の写し | 消せない | **35日** | 保管庫のロック(誰にも消せない) |
| AWS Backup の保管庫(毎月) | DB の写し | 消せない | **365日** | 同上。「先月末に戻したい」に答えるため |
| Cognito | ログインのメール・パスワード(のハッシュ)・二段階認証 | 手順書の 3 で消す | — | |
| CloudWatch Logs(DB のログ) | 遅い SQL の形・ロック待ち・失敗の種類。**渡した値・失敗の詳細(値が入る)は出さない設定** | 消さない | **30日**(`modules/aurora` の `log_retention_days`) | 期限で自動で消える |
| CloudWatch Logs(API のログ) | ID(組織・利用者・リクエスト)・失敗の種類。**出してよい項目だけを出す(許可リスト)**。題名・本文・メールアドレスは伏せ、失敗の文の値も伏せる(`packages/logging`・結合テスト `personal-data-logs.int.test.ts`) | 消さない | **90日**(prod の `log_retention_days`) | 期限で自動で消える |
| Sentry | 失敗の種類・スタック・ID(値は伏せる) | 消さない | Sentry のプランの保存期間(既定 90日) | 同上 |
| CloudWatch Logs(画面のサーバーのログ) | API と同じ部品・同じ決まり(許可リスト。`packages/logging`) | 消さない | **90日**(prod の `log_retention_days`) | 期限で自動で消える |
| CloudWatch Logs(メールの中継のログ) | 送った・送れなかった・やり直しの記録(キューの ID・Message-ID・相手のサーバーの答え)。**宛先・送り元のメールアドレスは伏せてから出す**(`docker/postfix/entrypoint.sh`) | 消さない | **30日**(`modules/mail-relay` の `log_retention_days`) | 期限で自動で消える |
| 送り待ち(メールの中継の EFS) | まだ渡せていないメール(**宛先・件名・本文が入る**) | 消さない | 渡せたらすぐ消える。渡せなければ**最長5日**でやり直しをやめて消す(`maximal_queue_lifetime`)。バックアップは取らない | Postfix が自動で消す |
| CloudWatch Logs(WAF のログ) | 来たリクエストの IP・URL(**検索の値が入る**)・ヘッダー(Cookie と Authorization は伏せる)・止めたかどうか | 消さない | **30日**(`modules/waf` の `log_retention_days`) | 期限で自動で消える |
| 送ったメール | 相手の受信箱にある物 | 消せない | — | こちらの手を離れている |
| 書き出したファイル | お客さんの手元 | 消せない | — | お客さんの物 |

- **バックアップの中から1社だけを消すことはできない**(写しは全社まとめて)。上の期間が過ぎれば、自動で消える。期間の内にバックアップから戻すことがあっても、**消した組織は戻さない**(戻したら、その組織だけ削除のコマンドをもう一度流す)。
- いちばん長く残るのは、**毎月のバックアップの最長 365日**。契約には「解約から最長1年(と数日)で、バックアップからも消える」と書く。

## 2. 契約・規約に書くこと(下書き)

> 解約日から○日以内に、お客様のデータを当社のシステムから削除します。削除の前に、管理者の画面からデータを書き出せます。バックアップに含まれるデータは、バックアップの保存期間(最長1年)が過ぎると自動で削除されます。その間、バックアップからお客様のデータを戻すことはありません。

- ○日は、運営が手順書を回せる日数で決める(例: 30日)。
- 個人情報の扱い(利用者の削除の依頼)も同じ表で答えられる。1人だけを消すのは、いまはコマンドが無い(利用者の削除・匿名化は次の一歩)。

## 3. 次の一歩

- テナントごとの KMS の鍵(大きなお客さん向け): 鍵を消せば、バックアップの中のその組織のデータも読めなくなる(暗号による消去。docs/security.md の T-5)
- 利用者を1人だけ消す・匿名化する(監査ログの「誰が」は ID のまま残る)
- 監査ログの保存期間を決めて、過ぎた分を消す(`app.audit_purge` の仕組みは入っている)

## 4. 漏えいのときの分担(契約に書く)

お客さんの業務のデータでは、多くの場合お客さんが「委託元」・自社が「委託先」になる。漏えい等が起きたら自社はお客さんに**知ってから3〜5日のうちに**知らせ、委員会への報告と本人への通知はお客さんと一緒に進める([runbooks/personal-data-breach.md](../runbooks/personal-data-breach.md) の 4)。契約には、**自社が個人データを取り扱う立場か・漏えい等のときに何日以内に何を知らせるか・報告と本人への通知をどちらが出すか**を書く(自社が委託先に当たるかは専門家に確認する)。
