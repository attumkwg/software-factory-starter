# CI の上限(画面の大きさ・コードの複雑さ・テストのカバレッジ)と画面の圧縮

CI(`ci.yml` の「Biome・型・単体」。API のカバレッジだけは「結合」のジョブ)は、次の3つが上限を超えると落ちる。どれも「いまより悪くしない」ための見張りで、目標の値ではない。

| 見張るもの | 上限 | どこで決めている | 手元で |
|---|---|---|---|
| 画面の JS・CSS の大きさ | JS の合計 640KB・一番大きい JS 146KB・CSS の合計 4KB(どれも gzip) | `apps/web/scripts/check-bundle-size.mjs` | `pnpm --filter @app/web build && pnpm --filter @app/web size` |
| 関数の複雑さ・長さ、ファイルの長さ | 複雑さ 15・関数 80行・ファイル 300行(空行は数えない) | `biome.json` | `pnpm lint` |
| テストのカバレッジ(単体。API は単体+結合) | パッケージごと(下の表) | 各パッケージの `vitest.config.ts`(画面は `vite.config.ts`) | `pnpm test:coverage` |

## 1. 画面の JS・CSS の大きさ

**根拠**: 2026-10-20 の大きさ(JS の合計 263.6KB・一番大きい JS 132.6KB・CSS 1.8KB)に約10%を足した。画面を1つ足すのは 1〜3KB なので、ふつうの機能追加では超えない。日付・グラフ・UI の部品集のような重いライブラリ(gzip で 20KB〜)を足すと超える。CSS はもともと小さいので、10%ではなく KB で幅を取った。

- **2026-10-26 に JS の合計だけ 290KB → 640KB に上げた**(@attumkwg の判断)。SSO の画面を足して 290.9KB になり、重いライブラリではなく画面が増えたことで上限に届いたため。合計には開くまで読まれない画面の分も入るので、画面が増えるほど自然に増える。利用者が待つ量に近い「一番大きい JS」(最初に必ず読むまとまり)の上限 146KB は変えていない。

gzip の大きさで比べるのは、ブラウザに届く量に近いから(実際は brotli で届くので、もう少し小さい)。一番大きい JS は、React・ルーターなど最初に必ず読むまとまりで、初めて開いたときの速さに一番効く。

**超えたら**: まず小さくできないかを考える(その画面でだけ使うものは画面ごとに読み込む・軽いライブラリにする・使う関数だけ読み込む)。それでも要るなら、`check-bundle-size.mjs` の数字を上げ、**上げる理由を PR の「人に判断してほしい所」に書く**(利用者の待ち時間が増えるので、人が判断する)。

## 2. 関数の複雑さ・長さ、ファイルの長さ

| 規則(Biome) | 上限 | 根拠 |
|---|---|---|
| `complexity/noExcessiveCognitiveComplexity` | 15 | Biome と SonarQube の既定。if や入れ子が重なって、読む人(AI も)が追えなくなる手前 |
| `complexity/noExcessiveLinesPerFunction` | 80行 | 画面1つに収まる長さ |
| `style/noExcessiveLinesPerFile` | 300行 | AI はファイルを丸ごと読むので、大きいファイルは関係の無い所まで読み、間違いの元になる。CSS(部品の見た目をまとめた `packages/ui`)は対象外 |

**超えたら**: 関数を分ける・ファイルを領域ごとに分ける。上限は上げない。どうしても分けられない理由があれば、`biome.json` の例外に足し、PR に理由を書く。

### 例外(いまは無い)

上限を入れた日(2026-10-20)に、すでに超えていた8か所は `biome.json` の `overrides` で例外にしていたが、同じ日に全部リファクタして例外を消した(振る舞いは変えず、関数とファイルを分けた)。新しく例外を足すときは、上の「超えたら」のとおり理由を PR に書く。

## 3. テストのカバレッジ(単体。API は単体+結合)

`pnpm test:coverage` が単体テストを流し、行(lines)と分岐(branches)の割合が下限を下回ると落ちる。`apps/api` だけは単体と結合(Testcontainers)を一緒に流した値で見るので、手元で流すには Docker が要る。

| パッケージ | 2026-10-20 の値(行 / 分岐) | 下限(行 / 分岐) |
|---|---|---|
| `apps/api`(単体+結合) | 87.0% / 79.7%(2026-10-22) | 85 / 77 |
| `apps/web` | 25.7% / 25.4% | 23 / 23 |
| `packages/shared` | 81.9% / 63.2% | 79 / 61 |
| `packages/error-reporting` | 95.6% / 75.3% | 93 / 73 |
| `packages/logging` | 96.8% / 78.7%(2026-10-22) | 94 / 76 |
| `packages/fake-cognito` | 71.0% / 56.4% | 68 / 54 |

**根拠**: いまの値の約2ポイント下。テストの無い小さなファイルを1つ足しただけでは落ちず、テストを消す・テストの無い大きな塊を足すと落ちる幅。

- `apps/api` は単体と結合を合わせた値。DB を使う所(リポジトリ・認可の関所・RLS)は結合テストで確かめるので、単体だけだと行 33% / 分岐 31% にしかならず、見張りとして効かない(2026-10-22 に単体だけの下限 33 / 30 から切り替えた)。CI では「結合」のジョブが `pnpm --filter @app/api test:coverage` を流す。単体は数秒なので、「Biome・型・単体」と二度流しても時間はほぼ増えない(手元で単体 3 秒・結合 12 秒・合わせて 15 秒)。
- `apps/web` の画面(`.tsx`)は E2E で確かめるので、単体の値は低い。
- `packages/ui` は単体テストが無いので測っていない。

**上げ方**: テストを足して値が上がったら、下限も「新しい値の約2ポイント下」に上げてよい(下げるのは、理由を PR に書いて人が判断する)。

**下限の設定(`vitest.config.ts`)・`biome.json`・`apps/api/.squawk.toml`・`apps/web/playwright*.config.ts` は危険度「高」**(G-60)。下限を下げた・外した、テストを消した・`skip` や `only` を足した・`expect` や `assert` が減った・`biome-ignore` などの注釈を足した PR には、ラベル `tests:weakened` が付く(`.github/workflows/test-weakening.yml`。止めずに印を付け、危険度「高」とみなす)。付いたら、理由を PR の本文に書く。設定のファイルを足したら、守る一覧(`.claude/hooks/protected-paths.json`)にも足す。

## 4. 画面の圧縮(ALB は圧縮しない)

AWS の ALB は応答を圧縮しない。そのままだと、画面の JS(約850KB)や HTML が生のまま届く。そこで画面のサーバー(`apps/web/server`)が自分で圧縮する。

| 何を | どうやって | なぜ |
|---|---|---|
| 配る JS・CSS(`/assets/*`) | **ビルドのときに** brotli(一番強く)と gzip で圧縮しておき(`scripts/precompress.mjs`)、ブラウザが受け取れる方を返す | 中身が変わらないので、一番強い圧縮を1回だけかければよい。リクエストごとの CPU を使わない。JS は 434KB → 117KB(brotli) |
| SSR の HTML | **その場で** brotli(強さ 4)か gzip で圧縮し、**描けた塊ごとに流し出す**(`server/compress.ts`) | HTML は毎回違う。ストリーミング SSR は、データを待つ間に先に描けた部分(画面の枠)を送るので、圧縮が「ためてから出す」と、その効き目が無くなる。塊ごとに流すと少しだけ縮みが悪いが、最初の表示を遅らせない |

CloudFront を前に置く形にしたときは、CloudFront の圧縮に任せてもよい(そのときもこのままで害は無い。もう縮んでいるものは CloudFront が縮め直さない)。API の JSON は、このとき対象にしていない(API は別のサービス)。
