# 設計とレビューの観点(溜めていく台帳)

> 設計書(`docs/designs/`)はこの観点の順に書き、レビュー(`/review-pr`)はこの観点ごとに「扱い」を付ける。扱いの5つと使い方は [guides/human-review.md](guides/human-review.md)。
> **人がレビューで「これも見るべきだった」と気づいたら、ここに1行足す。** 足した観点は次から AI が見る。機械で確かめられるようになったら「機械で確かめている所」に書き足す。

## 共通の8つ

| # | 観点 | 何を見るか | 機械で確かめている所 | 人に聞く(4つ)に当たりやすい所 |
|---|---|---|---|---|
| 1 | 設計方針 | 既存の ADR・領域の境目に沿っているか。新しい部品や依存を足していないか | `domain-boundaries.test.ts`(領域の向き・輪) | 新しい外部サービス(契約)・ADR を覆す判断 |
| 2 | データモデル | 表・列・参照・索引。お金と時刻の型。消す・移す | squawk(移行)・`rls.int.test.ts`・`offboarding.int.test.ts`・Semgrep(`no-float-money`・`no-local-time`) | 列を消す・型を変える(戻せない)・持つ個人データ |
| 3 | API | 入力と出力の形・失敗の応答・互換 | `api-compat`(oasdiff)・`input-validation.int.test.ts` | 公開した形を変える(戻せない)・他チームが呼ぶ API |
| 4 | 状態遷移 | 状態の種類と、移ってよい向き・戻せるか | (領域ごとのテスト) | 利用者に見える状態の意味(利用者の挙動) |
| 5 | システム間連携 | アウトボックス・メール・Cognito・Sentry など外との出入り | `outbox.int.test.ts`・`mail.int.test.ts`・偽物の Cognito の契約テスト | 外へ送る物(戻せない)・外部の制約(契約) |
| 6 | 業務ルール | 受け入れ条件の決まり・境界値・誰が何をできるか | 権限の表のテスト・領域のテスト | 決まりの線引き(事業判断) |
| 7 | 要求との対応 | 受け入れ条件の1つずつに、設計とテストがあるか。仕様に無い振る舞いを足していないか | (設計書の「要求との対応」の表で突き合わせる) | 仕様に無い判断(事業判断) |
| 8 | 非機能 | 性能(N+1・件数が増えたとき)・セキュリティ(STRIDE)・運用(ログ・アラーム・手順書)・費用 | Semgrep・Trivy・gitleaks・ZAP・`logger.test.ts` | 費用が増える(事業判断)・秘密や個人データ(戻せない) |

## 👥 レビューの人格(誰の気持ちで見るか)

> 同じ差分でも、**誰の気持ちで見るかで見つかる物が変わる**。`/review-pr` は、書いた AI と別の AI(`.claude/agents/reviewer.md`)を**人格ごとに1つずつ**呼び、その人格が持つ観点を上の表の「何を見るか」で全部見させる。ほかの人格の答えと、書いた AI の会話は渡さない(渡すのは PR の番号と人格だけ)。CI(「機械で確かめている所」)は参考で、直すか・このままかは人が1問ずつ決める([guides/human-review.md](guides/human-review.md) の 7・仕様 0096)。
> 人格は製品のペルソナ([product/personas.md](product/personas.md))と、携わる人の立場([scenarios/18-roles-review.md](scenarios/18-roles-review.md))から選んだ。**「この人の気持ちで見ていれば気づけた」と分かったら、観点と同じく1行足す。**

| 人格 | どういう気持ちで見るか | 持つ観点 | 呼ぶ PR |
|---|---|---|---|
| 🧑‍💼 使う人(仕様のペルソナ。管理者でない役割も) | 自分の仕事がこの変更で止まらないか・迷わないか。自分の役割で開いたら何が起きるか | 業務ルール・状態遷移・要求との対応・画面の部品 | 中・高。低でも画面か API の動きを変えるとき |
| 🦹 越えようとする人(悪意のある利用者・他社の人) | どこから他社のデータを取れるか。権限を越えられるか。入力で壊せるか | テナント分離・権限の表・API・非機能(STRIDE) | 中・高 |
| 🌙 夜中に起こされる人(SRE・基盤) | 壊れたら気づけるか。すぐ戻せるか。件数が増えても遅くならないか | データモデル・システム間連携・非機能(運用・性能)・一覧のページングと索引・解約で消す一覧 | 中・高 |
| 🔍 後から確かめる人(監査・CISO・審査員) | 誰がいつ何をしたかを後から言えるか。個人情報がログや記録に漏れていないか | 監査ログ・ログの個人情報・列の分類・サポートの代理ログイン | 中・高 |
| 🧑‍🔧 3か月後に触る人(入社したエンジニア・初見の AI) | 読んで分かるか。テストが要求を本当に指しているか。決まり(ADR・設計書)と食い違っていないか | 設計方針・要求との対応 | 全部(低も) |

- 危険度「低」の PR は 🧑‍🔧 だけ(画面か API の動きを変えるなら 🧑‍💼 も)。「中」「高」は5人全員。
- 2026-10-29 の受け入れで見つかった2つは、🧑‍💼 の気持ち(member で設定を開いたら?)と 🔍 の気持ち(監査ログで後から読めるか?)で見ていれば、レビューで気づけた(仕様 0093 の受け入れの第1回)。

## 隠す物(人に出さない)

- 標準の作り(一覧・登録・更新・削除が既存の型どおり)
- 調べれば分かること(既存のコード・用語集・ADR に書いてあること)
- 上の「機械で確かめている所」で落ちる物(テストが緑なら人は見ない)
