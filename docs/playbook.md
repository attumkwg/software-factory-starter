# 開発の進め方(プレイブック)

> このキットで「1つの機能を作って出す」までの流れと、毎週やること。
> 人が止まって判断するのは **② 仕様と設計の承認** と **⑦ 危険度「中・高」のレビュー** と **⑨ 本番の承認** の3か所だけ。ほかは仕組みと AI に流す。
> 人が見るのは全文ではなく、**判断が要る所だけ**(人に聞く4つ: 事業判断・利用者の挙動・他チームとの契約や制約・戻せないリスク)。考え方は [guides/human-review.md](guides/human-review.md)。

> 何を作るかがまだ決まっていない・作る前に確かめたいときは、この流れの手前で `/kickoff`([guides/before-pmf.md](guides/before-pmf.md))。機能1つぶんは `/bet` で賭けを開いてから(合格と撤退の線を先に決める。[guides/bets-and-assets.md](guides/bets-and-assets.md))。

## 1つの機能の流れ

| # | やること | 誰が | 使うもの |
|---|---|---|---|
| ① | 「これ作りたい」を形にする | 人+AI(対話) | `/new-feature` スキル(不具合は `/report-bug`) |
| ② | 仕様と設計を承認する | **人** | 仕様と設計の PR(`docs/specs/`・`docs/designs/`)。人は PR の本文(全体像・事実・理由・問い)だけを見て、未確定事項に答えてマージ |
| ③ | 1つの PR で終わる大きさに割る | AI が案 → 人が OK | `/new-feature` が親 Issue と子 Issue を作る |
| ④ | 実装する | AI(人も可) | 手元の Claude Code か、`claude.yml`(いまは手動) |
| ⑤ | PR を出す | AI | PR テンプレート・危険度のラベル(自動) |
| ⑥ | 確かめる | 仕組み | `ci.yml`(自動)・プレビュー(`preview.yml`、いまは手動) |
| ⑦ | レビューする | 危険度で変わる(下の表) | CODEOWNERS・「人に判断してほしい所」 |
| ⑧ | stg に出す | 仕組み | `deploy.yml`(いまは手動) |
| ⑨ | 本番に出す | **人が承認** | GitHub の environment「prod」 |
| ⑩ | 見守る | 仕組み+当番 | ログ(requestId・tenantId)・アラーム・`docs/runbooks/` |

### ① と ③: 対話で決めて Issue にする

- Claude Code で `/new-feature` と打ち、「タスクに期限を付けたい」のように一言で書く。
- Claude が1問ずつ聞く(誰の困りごとか → 受け入れ条件 → 各ロールと他社の扱い → 悪用のされ方 → 大きさ)。選択肢から選ぶだけで進む。
- 最後に要約を見せるので、OK なら Claude が次をする。
  - 仕様を `docs/specs/NNNN-名前.md` に、設計書を `docs/designs/NNNN-名前.md` に書いて、1つの PR にする(②で人が承認。設計書は `/design` が書く)
  - 親 Issue と子 Issue を作る(**あなたが OK と言ったときだけ**)
- 不具合は `/report-bug`。再現の手順・期待と実際・影響の範囲を聞いて Issue にする。

### ②: 仕様と設計の PR で、人が見る所

- **設計書は AI 用**(省略せず網羅的に。正はこちら)。人は開かなくてよい。
- 人は **PR の本文**だけを見る: 全体像 / 人に判断してほしい所(設計した事実・なぜそうしたか・人が判断する問い)/ 観点ごとの扱い / AI が決めたこと。
- AI は4つの問いにぶつかっても止まらず、**仮に決めて「未確定事項」に残す**。人は番号ごとに「承認 / 変更 / 保留」を PR のコメントで答える。
- `仮決め` が残っている間はマージしない(`pnpm decisions --strict`)。全部の設計書の仮決めと保留の一覧は `pnpm decisions`。

### 直すとき: 上流から作り直す

- レビューの指摘・未確定事項の「変更」・不具合が出たら、`/rework`。誤りが入った工程(ナレッジ・要求・設計・実装・テスト)を先に決め、そこを直してから下流を一式作り直す。**コードだけ継ぎ当てない。**
- 原因が「見る観点が無かった」なら、[review-viewpoints.md](review-viewpoints.md) に1行足す(次から AI が見る)。

### ④ 実装のときに AI が使うもの

| こんなとき | 使うもの |
|---|---|
| ルール全般 | `CLAUDE.md`(全体)・`apps/api/CLAUDE.md`・`apps/web/CLAUDE.md` |
| API を足す | `.claude/skills/add-api-endpoint`(権限の表に1行足す) |
| DB を変える | `.claude/skills/db-migration`(段階に分ける・RLS・squawk) |
| 書いたら | フックが自動で整形(`.claude/hooks/format.mjs`) |
| 終える前 | フックが型と影響範囲のテストを回す(2回落ちたら人へ) |
| 設計する | `/design`(設計書と、人向けのまとめ。仮決めは未確定事項に) |
| 直す | `/rework`(誤りが入った工程から、下流を一式作り直す) |
| PR を見る | `/review-pr <番号>`(判断の単位・判断してほしい所・観点ごとの扱い・チェック) |

### ⑦ レビュー: 危険度で人の出番を変える

ラベルは変えたファイルで自動で付く(`.github/labeler.yml`)。複数付いたら一番高いもの。

| 危険度 | 例 | 人のレビュー | 見る所 |
|---|---|---|---|
| 低 | 文言・ドキュメント・テストの追加 | 0人(CI が緑なら可) | 最初の1〜2か月は人も見て、AI の見逃しを数える |
| 中 | ふつうの機能・不具合の修正 | 1人 | 「人に判断してほしい所」と、受け入れ条件どおりか |
| 高 | 認証・認可・権限の表・移行・infra・CI | 2人 | 権限の表の差分・移行の段階・Terraform の plan |

レビューの進め方(PMF 前は手で):

1. レビューする人が Claude Code で **`/review-pr <PR番号>`**。差分を「判断の単位」に分け、影響の大きい順に並べ、**人に判断してほしい所**(権限の表・移行・Terraform・認証認可・テナント分離・未確定事項の仮決め)を「事実・理由・問い」で冒頭に出し、[観点](review-viewpoints.md)ごとの扱い(最重要〜低優先)と、危険度ごとのチェック(テスト・権限の表・N+1・ログの個人情報・テナント)の結果をコメント案にする。
2. 人は冒頭の「判断してほしい所」から見る。コメント案を直して、OK なら Claude が `gh` で PR に書く。
3. 危険度「高」では、手で `/security-review` も回す(手順は [security.md](security.md))。細かい不具合探しは `/code-review <PR番号>`。
4. 承認するのは人(AI は承認しない)。

PR が増えて手で回すのが追いつかなくなったら、自動のレビュー(`@claude` か Anthropic 公式の Code Review)を検討する。選択肢の比較は [guides/code-review.md](guides/code-review.md)。

## 毎週やること(30分)

> 守りが今も効いているか・段階(立ち上げ〜2年)でやることは、点検の台帳([checkup/todo.yaml](checkup/todo.yaml)。1枚は [checkup/README.md](checkup/README.md))に移していく。`pnpm checkup` が自動で確かめられる物を確かめ、人に聞くこと・人がやることを出す。担当者は Claude Code で `/checkup` と打ち、1問ずつ答える。

| やること | 何を見るか | 使うもの |
|---|---|---|
| ラインの振り返り | AI が同じ失敗をした所 → ルール・テスト・lint・スキルのどれに変えるか。人がレビューで気づいた観点を台帳に足す | `CLAUDE.md`・`.claude/skills/`・`.semgrep/`・[review-viewpoints.md](review-viewpoints.md) |
| 未確定事項 | 保留の期限が過ぎていないか・仮決めのまま止まった PR は無いか | `pnpm decisions` |
| 賭け | 期限を過ぎて決めていない賭け(⏰)・線がまだ無い賭け(⏳)→ 進む・変える・やめるを決める | `pnpm bets`・`/bet` |
| 依存の更新 | Renovate の PR をまとめて見る(低はまとめてマージ)。認証・Cookie・暗号・DB に触る依存は小さい版でも高として見る。大きい版は Dependency Dashboard の承認待ちに並ぶので、上げる物にチェックを入れる | `renovate.json`・[guides/vulnerabilities.md](guides/vulnerabilities.md) の 8 |
| 脆弱性 | 精査していない通知・見直す日が来た記録 → 関係あるか・期限と直し方を決める | `pnpm vulns`・`/cve` |
| リリースノート | 先週マージした PR をまとめる(公開は人) | `/release-notes` スキル |
| 数字 | デプロイ回数・PR が出てからマージまで・失敗して戻した回数・**人の介在率**(PR ごとの、人が答えた問いの数と、人が手で直した回数。減っていくのが良い) | GitHub の Insights・PR の「人に判断してほしい所」 |
| 仕様の在庫 | 次の週に AI に渡せる「承認済みの仕様」があるか | `docs/specs/`・Issue |

> 💡 実装が速くなると「次に何を作るか」が足りなくなる。毎週、仕様の在庫を見る。

## 毎月・四半期にやること

| いつ | やること | 使うもの |
|---|---|---|
| 毎月 | stg の戻す訓練を流して結果を見る(自動にするまでは手で Run workflow。落ちたら Issue が立つ) | Actions → Restore drill の Summary |
| 毎月 | 障害の振り返りの再発防止の Issue が閉じたか | `docs/incidents/` |
| 四半期 | **prod の戻す訓練**(2人・手で。結果は Issue に `restore-drill` のラベル) | [runbooks/db-restore.md](runbooks/db-restore.md) の 5 |
| 四半期 | 手順書を1つ選んで、stg で通しでやってみる(古くなっていないか) | [runbooks/](runbooks/) |

## 人と AI の分担

| 仕事 | 人 | AI |
|---|---|---|
| 何を作るか・なぜ | 決める | 質問して形にする(`/new-feature`) |
| 受け入れ条件・権限 | 承認する | 案を書く |
| 設計 | 問い(4つだけ)に答える | 設計書を網羅的に書く・仮決めを未確定事項に残す(`/design`) |
| 実装・テスト | 詰まった所を手伝う | 書く |
| レビュー | 中は1人・高は2人 | 一次レビュー |
| 本番に出す | 承認する | (触らない) |
| ラインの改善 | 毎週決める | ルールやスキルの案を書く |

**人に聞くのは4つだけ**: 事業判断・利用者の挙動・他チームとの契約や制約・戻せないリスク。それ以外(型どおりの作り・調べれば分かること・テストで確かめられること)は AI と機械に任せる([guides/human-review.md](guides/human-review.md) の 1)。

AI にさせないこと: 本番の鍵に触る・`.github/` や CODEOWNERS を勝手に変える・自分で頼んだ PR を自分で承認する・人の答えなしに未確定事項を「承認」にする。
