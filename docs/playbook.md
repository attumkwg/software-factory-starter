# 開発の進め方(プレイブック)

> このキットで「1つの機能を作って出す」までの流れと、毎週やること。
> 人が止まって判断するのは **② 仕様の承認** と **⑦ 危険度「中・高」のレビュー** と **⑨ 本番の承認** の3か所だけ。ほかは仕組みと AI に流す。

## 1つの機能の流れ

| # | やること | 誰が | 使うもの |
|---|---|---|---|
| ① | 「これ作りたい」を形にする | 人+AI(対話) | `/new-feature` スキル(不具合は `/report-bug`) |
| ② | 仕様を承認する | **人** | 仕様の PR(`docs/specs/`)をレビューしてマージ |
| ③ | 1つの PR で終わる大きさに割る | AI が案 → 人が OK | `/new-feature` が親 Issue と子 Issue を作る |
| ④ | 実装する | AI(人も可) | 手元の Claude Code か、`claude.yml`(いまは手動) |
| ⑤ | PR を出す | AI | PR テンプレート・危険度のラベル(自動) |
| ⑥ | 確かめる | 仕組み | `ci.yml`(自動)・プレビュー(`preview.yml`、いまは手動) |
| ⑦ | レビューする | 危険度で変わる(下の表) | CODEOWNERS・「人に判断してほしい所」 |
| ⑧ | stg に出す | 仕組み | `deploy.yml`(いまは手動) |
| ⑨ | 本番に出す | **人が承認** | GitHub の environment「prod」 |
| ⑩ | 見守る | 仕組み+当番 | ログ(requestId・tenantId)・アラーム・`docs/runbooks/` |

### ① と ③: 対話で決めて Issue にする

- Claude Code で `/new-feature` と打ち、「タスクに期限を付けたい」のように一言で書く。
- Claude が1問ずつ聞く(誰の困りごとか → 受け入れ条件 → 各ロールと他社の扱い → 悪用のされ方 → 大きさ)。選択肢から選ぶだけで進む。
- 最後に要約を見せるので、OK なら Claude が次をする。
  - 仕様を `docs/specs/NNNN-名前.md` に書いて PR にする(②で人が承認)
  - 親 Issue と子 Issue を作る(**あなたが OK と言ったときだけ**)
- 不具合は `/report-bug`。再現の手順・期待と実際・影響の範囲を聞いて Issue にする。

### ④ 実装のときに AI が使うもの

| こんなとき | 使うもの |
|---|---|
| ルール全般 | `CLAUDE.md`(全体)・`apps/api/CLAUDE.md`・`apps/web/CLAUDE.md` |
| API を足す | `.claude/skills/add-api-endpoint`(権限の表に1行足す) |
| DB を変える | `.claude/skills/db-migration`(段階に分ける・RLS・squawk) |
| 書いたら | フックが自動で整形(`.claude/hooks/format.mjs`) |
| 終える前 | フックが型と影響範囲のテストを回す(2回落ちたら人へ) |

### ⑦ レビュー: 危険度で人の出番を変える

ラベルは変えたファイルで自動で付く(`.github/labeler.yml`)。複数付いたら一番高いもの。

| 危険度 | 例 | 人のレビュー | 見る所 |
|---|---|---|---|
| 低 | 文言・ドキュメント・テストの追加 | 0人(CI が緑なら可) | 最初の1〜2か月は人も見て、AI の見逃しを数える |
| 中 | ふつうの機能・不具合の修正 | 1人 | 「人に判断してほしい所」と、受け入れ条件どおりか |
| 高 | 認証・認可・権限の表・移行・infra・CI | 2人 | 権限の表の差分・移行の段階・Terraform の plan |

危険度「高」では、手で `/security-review` も回す(`docs/security.md` は後の PR で足す)。

## 毎週やること(30分)

| やること | 何を見るか | 使うもの |
|---|---|---|
| ラインの振り返り | AI が同じ失敗をした所 → ルール・テスト・lint・スキルのどれに変えるか | `CLAUDE.md`・`.claude/skills/`・`.semgrep/` |
| 依存の更新 | Renovate の PR をまとめて見る(低はまとめてマージ) | `renovate.json` |
| リリースノート | 先週マージした PR をまとめる(公開は人) | `/release-notes` スキル |
| 数字 | デプロイ回数・PR が出てからマージまで・失敗して戻した回数 | GitHub の Insights |
| 仕様の在庫 | 次の週に AI に渡せる「承認済みの仕様」があるか | `docs/specs/`・Issue |

> 💡 実装が速くなると「次に何を作るか」が足りなくなる。毎週、仕様の在庫を見る。

## 人と AI の分担

| 仕事 | 人 | AI |
|---|---|---|
| 何を作るか・なぜ | 決める | 質問して形にする(`/new-feature`) |
| 受け入れ条件・権限 | 承認する | 案を書く |
| 実装・テスト | 詰まった所を手伝う | 書く |
| レビュー | 中は1人・高は2人 | 一次レビュー |
| 本番に出す | 承認する | (触らない) |
| ラインの改善 | 毎週決める | ルールやスキルの案を書く |

AI にさせないこと: 本番の鍵に触る・`.github/` や CODEOWNERS を勝手に変える・自分で頼んだ PR を自分で承認する。
