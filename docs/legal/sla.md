# 型: SLA(稼働の約束)

> ⚠️ **文面は書かない。専門家に確かめる。** ここにあるのは「SLA に何を決めて書くか」と、キットの既定・根拠・使う人が決めること。補償を「唯一の救済」にできるか・損害賠償の上限との関係・不可抗力の範囲は、専門家と決める。
> 共通の項目と「変えてよい / 変えない」の分けは [README.md](README.md)。既定の値の未確定事項は [designs/0028](../designs/0028-contract-templates.md) の U-2〜U-4。

**稼働率の数字だけを書かない。** 割ったときに揉めるのは、数字ではなく「何を測ったか・どの停止を数えるか・誰が決めるか」が書いていないから。下の 1〜7 を全部決めてから出す。

## 1. 何を測るか

| 項目 | キットの既定 | 根拠 | 使う人が決めること |
|---|---|---|---|
| 測る物 | **外から開けるか**: prod の画面(`/readyz`)と API(`/api/auth/options`)の外形監視。東京・シンガポール・オレゴンから30秒ごと | [guides/monitoring.md](../guides/monitoring.md)・`infra/terraform/modules/uptime` | ログインの後の画面の流れまで測るか(本物のブラウザの見張り。PMF の後・月 1,500〜3,000円) |
| 外形監視で見えない停止 | **外形監視は DB に触らない**(DB が止まっても緑のことがある)。そこで、障害の振り返りで「全員が使えない」(S1)とした時間帯も停止に足す | `modules/uptime` の頭の説明・[runbooks/incident.md](../runbooks/incident.md) の 1・6 | — |
| 停止の分 | 1か月(日本時間の1日 0:00 〜 月末 24:00)のうち、上の2つの**どちらかで止まっていた分**(重なりは1回だけ数える) | 下の 7 の測り方 | — |
| 一部だけの停止 | **数えない**(一部の機能・一部の会社だけ = S2 は、稼働率に入れない) | [runbooks/incident.md](../runbooks/incident.md) の 1 | 1社だけが全く使えないときを、その会社の分として数えるか |
| 稼働率の式 | (月の分 − 停止の分 − 対象外の分)÷(月の分 − 対象外の分) | — | — |

## 2. どの範囲か

| 項目 | キットの既定 | 使う人が決めること |
|---|---|---|
| 環境 | prod だけ(stg・プレビュー・試作は入れない) | — |
| 機能 | 画面と API が開けること。試している途中の機能(機能フラグで一部の組織だけに出している物)は入れない([guides/feature-flags.md](../guides/feature-flags.md)) | 中心の機能を名指しするか |
| メール | 入れない(送り待ちは最長5日やり直す。相手のサーバー次第。[guides/mail.md](../guides/mail.md)) | — |
| データの書き出し・サポートの代理ログイン | 入れない | — |

## 3. 原因の区分(どの停止を数えるか)

障害の指揮が、振り返り([runbooks/incident.md](../runbooks/incident.md) の 6)の「SLA」の行に区分を書く。

| 区分 | 例 | 既定 | 根拠 |
|---|---|---|---|
| **自社** | アプリの不具合・出し直し・設定の誤り・DB の入れ替え・自社の AWS の設定 | **数える** | — |
| **外のサービス(再委託先)** | AWS の1つのサービスの障害・外形監視の地点の障害 | **数える**(自社が選んだ再委託先の障害は、お客さんから見て自社の障害) | [compliance/vendors.md](../compliance/vendors.md) |
| 外のサービスの大規模な障害 | AWS が公表した、東京のリージョン全体にまたがる障害 | **数えない**(不可抗力の範囲。専門家と決める) | 別のリージョンへの備えは「仕組みを変えれば変えられる」([README.md](README.md) の 3) |
| **お客さんの側** | お客さんのネットワーク・端末・お客さん自身の操作(消した・設定を変えた)・お客さんからの大量のアクセスを WAF が止めた・規約の違反で止めた | **数えない** | [runbooks/attack.md](../runbooks/attack.md) |
| 計画メンテナンス | **7日前まで**に知らせた止める作業。月に**4時間まで** | **数えない**(4時間を超えた分は数える) | 出し直しは止まらない(blue/green)。止まるのは DB の入れ替え・大きな版上げなど([runbooks/deploy-rollback.md](../runbooks/deploy-rollback.md)) |
| 緊急の保守 | 穴を塞ぐために、知らせずに止めた | **数える** | [guides/vulnerabilities.md](../guides/vulnerabilities.md) |

## 4. 補償の段

| 項目 | キットの既定(仮。設計書 0028 の U-2) | 使う人が決めること |
|---|---|---|
| 約束の線 | 月の稼働率 **99.5%**(30日の月で、止まってよいのは約3時間36分) | 線の高さ。99.9%(約43分)にするなら、DB の入れ替え1回で割る([README.md](README.md) の「戻す早さ」) |
| 段 | 99.5% 未満 → その月の利用料の **10%** / 99.0% 未満 → **25%** / 95.0% 未満 → **50%** | 段の数と割合 |
| 形 | 次の請求から引く(**返金ではない**)。解約した後は残らない | 返金にするか |
| 上限 | その月の利用料の **50%** | — |
| 唯一の救済か | **はい**(稼働率を割ったことへの救済は、この補償だけ) | 専門家と、損害賠償の条との関係を決める |

## 5. 法的な義務か、努力義務か

**項目ごとに、どちらかを必ず書く**(曖昧にすると、割ったときに両方の読み方で揉める)。

| 項目 | 既定 | 割ったとき |
|---|---|---|
| 月の稼働率の線 | **約束(義務)** | 4 の補償だけ |
| 障害の連絡の時間(下の 6) | **努力目標** | 補償なし。振り返りで遅れた理由を書く |
| 戻せる時点(5分ほど前まで)・戻す早さ | **努力目標** | 補償なし |
| 解約後にバックアップから消える日(最長 365日) | **約束(義務)**。ロックで勝手に延びも縮みもしない | — |

## 6. 連絡の時間

| 項目 | キットの既定 | 根拠 | 使う人が決めること |
|---|---|---|---|
| 最初の知らせ | S1 は **30分以内**・以後1時間ごと / S2 は **1時間以内** | [runbooks/incident.md](../runbooks/incident.md) の 1・4 | 時間の長さ |
| 時間の数え方 | **営業時間の中で数える**。営業時間の外は努力(夜間の当番がいない段階) | 当番を置くまでは営業時間だけ。置いたときの決まりと SLA との対応は [guides/on-call.md](../guides/on-call.md) の 7 | 営業時間(例: 平日 9:00〜18:00)。夜中も約束するなら、当番を置くのが先(「仕組みを変える」) |
| 知らせる先 | お客さんの管理者と、申込書の連絡先 | [order-form.md](order-form.md) | 状況のページ(公開の障害情報)を持つか |
| 文面 | 事実だけ・推測と原因の決めつけを書かない | [runbooks/incident.md](../runbooks/incident.md) の 4 | — |
| 振り返りを渡すか | S1・S2 の振り返り(5営業日以内)の要旨を、求められたら渡す。他社の名前と内部の仕組みの名前は消す | [runbooks/incident.md](../runbooks/incident.md) の 6 | 求められなくても渡すか |
| 個人データの事故 | [data-processing.md](data-processing.md) の 3 | — | — |

## 7. 誰が事実を確定し、誰が例外を認めるか

| 役 | キットの既定 | 根拠 |
|---|---|---|
| **事実を確定する人** | 障害の**指揮**。振り返り(5営業日以内)に、停止の時刻・停止の分・原因の区分を書く。これが SLA の正 | [runbooks/incident.md](../runbooks/incident.md) の 2・6 |
| **例外を認める人** | **責任者**(基本方針の最高責任者か、その人が決めた人)。区分の争い・申し出の期限を過ぎた物・段の外の扱いを決める | [compliance/policies/basic-policy.md](../compliance/policies/basic-policy.md) |
| 補償の始まり | **お客さんの申し出**で始める。期限は**翌月の末日**まで(請求が手作業の間。プランの表は G-03 で入ったが、請求は外の会計ソフトで手で。自動で当てるのは、請求の仕組みが入ってから) | 設計書 0028 の U-3 |
| 月の稼働率を出す | 運営が、月が明けて**最初の週**に下の測り方で出す(5分ごとの数字は 63日で消える) | 下の「測り方」 |

### 測り方(人が打つ。読むだけ)

1. ヘルスチェックの ID を出す(Route 53 の数字はバージニアにしか無い):

   ```bash
   aws route53 list-health-checks --query "HealthChecks[].{id:Id,path:HealthCheckConfig.ResourcePath}" --output table
   ```

2. 画面と API の2つについて、月の「開けなかった分」を出す。`HealthCheckStatus` の5分ごとの平均(1 = 開けた・0 = 開けない)から、`(1 − 平均) × 5` を足す:

   ```bash
   aws cloudwatch get-metric-data --region us-east-1 --start-time 2026-09-30T15:00:00Z --end-time 2026-10-31T15:00:00Z --metric-data-queries '[{"Id":"h","MetricStat":{"Metric":{"Namespace":"AWS/Route53","MetricName":"HealthCheckStatus","Dimensions":[{"Name":"HealthCheckId","Value":"<ヘルスチェックの ID>"}]},"Period":300,"Stat":"Average"}}]' --query "MetricDataResults[0].Values" --output text | tr '\t' '\n' | awk '{ s += (1 - $1) * 5 } END { printf "%.0f 分\n", s }'
   ```

   - 時刻は UTC で渡す(上は日本時間の10月1日 0:00 〜 11月1日 0:00)。
   - 数字が欠けた区間は、止まったとは数えない。振り返りの記録で指揮が決める。
3. 画面と API の大きい方に、その月の S1 の振り返りの時間帯のうち重ならない分を足し、3 の区分で数えない分を引く。
4. 結果を、その月の振り返り(か運営の記録)に残す。**お客さんの名前は書かない**。

> 月の稼働率を自動で出す仕組みは、まだ無い(手で出す)。

## 8. 専門家に確かめること(出す前に)

- 補償を「唯一の救済」とし、損害賠償の上限の条とどう並べるか。
- 「外のサービスの大規模な障害」を不可抗力として外せるか。外すときの書き方。
- 計画メンテナンスの知らせ方(メールで足りるか)と、7日・4時間の線。
