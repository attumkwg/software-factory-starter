# 設計書と、人向けのまとめを作る

目的: 設計書は **AI のために省略せず網羅的に**書く(正はこちら)。人はそれを開かず、PR の本文の **「全体像・事実・理由・問い」だけ**を見て判断する。考え方は `docs/guides/human-review.md`。

## 1. 作業の前に読む(ガイド)

読んだ物は設計書の「作業の前に読んだ物」に書く。

- 仕様: `docs/specs/NNNN-<名前>.md`(受け入れ条件・権限の表の行・悪用のされ方・やらないこと)
- 観点: `docs/review-viewpoints.md`(共通の8つ+このプロダクト特有)
- ナレッジ: `docs/domain/glossary.md`・`docs/domain/<領域>/README.md`・関係する `docs/adr/`・`docs/authz/matrix.yaml`
- 既存のコード: その領域の `apps/api/src/domains/<領域>/`・`packages/shared/src/schemas.ts`・画面なら `apps/web/src/`

ナレッジが古い・無いせいで判断できない所は、推測で埋めずに「未確定事項」(工程: ナレッジ)にする。

## 2. 設計書を書く

`docs/designs/_template.md` を写して `docs/designs/NNNN-<名前>.md`(仕様と同じ番号と名前)。

- **全部の節を書く。当てはまらない節も消さずに「該当なし(理由)」**。人が読む前提で削らない。
- 「7. 要求との対応」で、受け入れ条件の1つずつに「設計のどこ」と「テスト」を書く。**空の欄があれば、そこを埋めるまで先へ進まない**(センサー)。
- 「9. このプロダクト特有」は、`review-viewpoints.md` の特有の観点を全部並べる。

## 3. 判断を2つに分ける

書いている間に出た判断のそれぞれに、`docs/guides/human-review.md` の **人に聞く4つ**(事業判断・利用者の挙動・他チームとの契約や制約・戻せないリスク)のどれに当たるかを考える。

| 当たるか | どうするか |
|---|---|
| 当たらない | AI が決める。「11. 決めたこと」に理由と一緒に書く。人には聞かない |
| 当たる | **止まらずに**いちばんありそうな案で仮に決め、「12. 未確定事項」に `仮決め` で1行(事実・理由・問い) |

- 問いは「はい / いいえ」か選択肢で答えられる形にする。
- 仕様の段階で人が決めたこと(仕様の「決めたこと」)は、もう一度聞かない。

## 4. 観点ごとの扱いを付ける

「10. 観点ごとの扱い」に、観点のそれぞれへ **最重要 / 採用 / 軽く確認 / 機械で検証 / 低優先** のどれかを理由つきで。

- 未確定事項がある観点は「最重要」。
- 「機械で検証」には、どのテスト・検査が判定するかを書く(`review-viewpoints.md` の「機械で確かめている所」)。テストがまだ無いなら「機械で検証」にしない。

## 5. 人向けのまとめを作る

`docs/guides/human-review.md` の 3 の形で、**PR の本文**に書く(全体像 / 人に判断してほしい所 / 観点ごとの扱い / AI が決めたこと)。

- 「人に判断してほしい所」には、未確定事項の `仮決め` の行だけを「番号 / 種類 / 設計した事実 / なぜそうしたか / 人が判断する問い」で写す。
- 設計書の中身を写し直さない(長くしない)。詳しくは設計書へのリンクで。
- `pnpm decisions` で、仮決めの一覧と書き方の問題が無いかを確かめる。

## 6. PR を出す

- `/new-feature` から来たときは、**仕様と同じ PR** に設計書を入れる(ブランチ `spec/NNNN-<名前>`)。単独で頼まれたときは `design/NNNN-<名前>`。
- PR の本文 = 5 の人向けのまとめ。危険度は資料だけなら「低」。
- 子 Issue があれば、本文に「設計: docs/designs/NNNN-…」を足す(`gh issue edit`。直す前に「Issue を直してよいか」を聞く)。

## 7. 人が答えたら

1. 番号ごとの答え(承認 / 変更 / 保留)を、設計書の表の「状態」に写す。書き方は `docs/guides/human-review.md` の 2。答えたコメントへのリンクも。
2. `変更` があれば `/rework` で、その工程から作り直す。
3. `pnpm decisions --strict` が 0 で終わったら、マージしてよいと伝える(マージは人がする)。

## してはいけない

- 人の答えが無いのに、状態を `承認` にする。
- 4つに当たらない判断を、未確定事項にして人に聞く(人が見る量が増える)。
- 4つに当たる判断を「決めたこと」に入れて、人に見せずに進める。
- 設計書を「人が読みやすいように」削る(削るのは人向けのまとめの方)。
- 権限の表(`docs/authz/matrix.yaml`)を直接変える(実装の PR で `/add-api-endpoint` が足す)。
