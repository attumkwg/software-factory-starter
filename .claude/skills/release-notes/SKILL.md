# リリースノート

## 手順

1. 前回のリリースを調べる: `gh release list --limit 1`(無ければ最初のコミットから)。
2. その後に main に入った PR を集める:
   `gh pr list --state merged --base main --search "merged:>=<前回の日付>" --json number,title,labels,body --limit 200`
3. PR を分ける(PR のラベルと本文から。分からなければ「その他」):
   - ✨ 新しい機能 / 🐛 直したこと / 🔐 セキュリティ / 🧹 中の改善(利用者には見えない)
   - `risk:high` の PR と DB の移行は、社内向けに必ず載せる
4. 2つ書く:
   - **利用者向け**: 何ができるようになったか。中の言葉(テーブル名・関数名)を使わない。「中の改善」は載せない。
   - **社内向け**: PR 番号つきの全部。移行・権限の表の変更・設定の変更・戻すときの注意。
5. 下書きとして作る(公開は人がする):
   `gh release create <版> --draft --title "<版>" --notes-file <ファイル>`
6. お知らせ・プレスリリースも要るか聞く。要るなら、利用者向けを元に `docs/guides/announcements.md` の 3 の型で下書きを作る。`docs/product/positioning.md` の「言わないこと」・数字の根拠・お客さんの名前の許可の記録(同じ手引きの 4)を確かめたかを1行ずつ添える。配信は人がする。

## してはいけない

- 公開(`--draft` を外す)を自分でしない。
- 社内の PR 本文にある顧客名・個人の情報を利用者向けに書かない。
- 許可の記録が無いお客さんの名前・ロゴ・声を、お知らせ・プレスリリースに書かない。
