# 不具合を、対話で Issue にする

## まず確かめること(最初の1問)

「**他社(別の組織)のデータが見えた**疑いはありますか?」を、はい / いいえ / 分からない で聞く。
**はい・分からない**なら、Issue は作らずに `docs/runbooks/tenant-data-leak.md` を開いて見せ、すぐ責任者に連絡するよう伝えて終える(公開の Issue に書くと広がるため)。

## 聞くこと(1回に1つ。AskUserQuestion で選択肢を出す)

1. **どこで**: 画面か API か(画面ならどのページ)。環境は local / preview / stg / prod のどれか。
2. **誰で**: admin / member / viewer のどれでログインしていたか。
3. **再現の手順**: 「1. … 2. … 3. …」。Claude が案を書き、合っているか聞く。毎回起きるか・たまにか。
4. **期待と実際**: 「本当はどうなるはずか」と「実際どうなったか」。エラーの文言があれば。
5. **requestId**: 画面のエラーか、応答の `x-request-id` にある。分からなければ飛ばしてよい(ログを引くのに使う)。**個人情報・パスワード・トークンは貼らせない**。
6. **影響の範囲**: 1人だけか・その組織の全員か・全社か。回避の方法はあるか。

聞いている間に、コードとログ(手元なら `docker compose logs api`)で原因の見当がつけば、それも書き添える(推測と分かる書き方で)。

## 危険度を決める

| 当てはまるもの | 危険度 |
|---|---|
| 認証・権限・お金・個人データ・全社に影響 | 高 |
| ふつうの機能が使えない・1つの組織の全員に影響 | 中 |
| 見た目・文言・回避できる小さな不具合 | 低 |

## まとめて確認 → OK のときだけ Issue を作る

1. `.github/ISSUE_TEMPLATE/bug.yml` の項目の順で、本文をまとめて見せる。最後に「直ったと言える条件」(受け入れ条件)を2つ以上。うち1つは「再現するテストが足されている」。
2. 「この内容で Issue を作ってよいか」を聞く。
3. OK なら `gh issue create --title "<短い要約>" --label kind:bug --label risk:<high|medium|low> --body "<本文>"`。
   ラベルは `.github/labels.yml` にある物だけを使う(無いと失敗する。そのときは本人に `pnpm setup:github --apply` を頼む。`gh label create` で一覧に無いラベルを作らない)。
4. 作った Issue の URL を伝える。直すかどうかは聞くだけ(勝手に直し始めない)。
